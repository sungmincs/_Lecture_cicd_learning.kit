# 10.8 GitLab CI → EKS — 예상 결과

## 상태 확인

### 파이프라인 성공 (Part A / Part B)

```
GitLab Pipelines:
  test  ✓   build  ✓   (update-manifest ✓)   deploy/sync  ✓
```

deploy job 로그:
```
$ aws eks update-kubeconfig --region $AWS_REGION --name $EKS_CLUSTER_NAME
Added new context ...
$ kubectl apply -f deploy_manifest/worklog-backend.yaml
deployment.apps/worklog-backend configured
```

sync-argocd job:
```
$ argocd app sync worklog-backend
$ argocd app wait worklog-backend --health
Health Status: Healthy
```

### EKS에서 배포 확인

```
$ kubectl get pods
NAME                               READY   STATUS    RESTARTS   AGE
worklog-backend-xxxx               1/1     Running   0          1m
```

## 체크리스트

- [ ] CI/CD Variables: `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`(Masked), `AWS_REGION`, `EKS_CLUSTER_NAME`, `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN`, (Part B) `ARGOCD_SERVER`/`ARGOCD_PASSWORD`, `GITHUB_TOKEN`
- [ ] ⛔ **CI IAM 유저에 `eks:DescribeCluster` 정책 + EKS access entry 둘 다** (10.6 공통)
- [ ] ⛔ **deploy_manifest HTTPRoute → ALB Ingress** (10.6 공통)
- [ ] ⛔ **`.gitlab-ci.yml` script에서 콜론(`:`) 포함 항목은 작은따옴표로 감쌀 것**. `echo "build successful: ..."`, `sed ... image: ...`, `git commit -m "deploy: ..."` 처럼 콜론+공백이 든 항목을 안 감싸면 GitLab YAML이 매핑으로 오인해 **0 job 실패**(`mapping values are not allowed`). CI lint로 사전 확인
- [ ] Part A: build → `update-kubeconfig` → `kubectl apply` 성공
- [ ] Part B: 이미지태그 push → `argocd app sync`/`wait --health` → Synced/Healthy
- [ ] `kubectl get pods`에 worklog-backend `Running`

## 검증 메모

- 2026-07-03 기준 **authored YAML 콜론버그 수정 + CI lint valid까지 확인**. **실제 파이프라인 트리거는 생략 확정.** 동일 CI→EKS 메커니즘(aws 인증→`kubectl apply`→`argocd sync`)이 10.6(GitHub)·10.7(Jenkins) 실배포로 입증됐고 GitLab은 CI 문법만 다르며 그 문법은 lint로 검증됨. EKS 재기동 비용 대비 실익이 낮아 실트리거는 생략한다.
- ⚠️ 파이프라인 즉시 실패가 항상 quota 소진은 아니다. 먼저 CI lint로 config(콜론버그 등)를 확인할 것.
