# 3.3 Docker 이미지 빌드 + Docker Hub Push — 왜 이 흐름?

## 상황

ch3.2에서 학습자는 mock 앱을 npm으로 띄워봤다. 화면은 잘 보였지만:

- Node.js를 직접 설치해야 했다
- 다른 학습자와 공유하려면 같은 환경 세팅이 필요하다
- "내 환경에서는 되는데" 문제가 잠재되어 있다

ch3.3에서는 이 한계를 컨테이너로 해결한다. **앱과 실행 환경(Node.js·Python·의존성)을 하나의 이미지로 묶어 Docker Hub에 push**하여 어디서든 같은 환경으로 동작하게 만든다.

## 학습자가 물어볼 수 있는 질문

- "npm으로 띄우는 거랑 뭐가 달라?"
- "Dockerfile은 누가 만드는 거야? 내가 만들어야 해?"
- "내 이미지를 Docker Hub에 올리면 누가 받을 수 있어?"
- "왜 build랑 push가 분리되어 있어?"

## 추천: 명령 직접 입력 + Hub push (mock + backend 둘 다)

본 강의는 다음 조합으로 진행한다:

- **빌드 대상**: `worklog-frontend-mock` + `worklog-backend` 두 개
- **빌드 위치**: control plane 노드(`cp-k8s`)에서 직접 build
- **레지스트리**: Docker Hub (`<dockerhub_username>/worklog-*:buildtest1`)
- **진입 방식**: 학습자가 명령을 직접 입력 (AI에 자연어로 물어볼 수도 있음)

이 챕터에 적합한 이유:

- **mock + backend 모두 컨테이너화**: ch3.4에서 K8s에 배포할 때 두 이미지가 모두 필요
- **cp에서 build**: 학습자가 K8s 클러스터 위에서 모든 작업을 하는 흐름이 자연스러움. 호스트 머신을 별도로 셋업하지 않음
- **Docker Hub (private 레지스트리 아님)**: 공개 레지스트리라 ch3.4 K8s pull이 별도 인증 없이 동작. 학습 진입장벽 낮음
- **의도적 push 실패 학습 포인트**: 첫 push에서 의도적으로 `denied` 에러를 거치게 함 — `docker login`의 필요성을 학습자가 직접 체험. 강사가 의도적으로 설계한 학습 흐름

## 비교 (참고용 — 본 강의는 선택지 없음)

| 옵션 | 장점 | 단점 | Notiflex 적합도 |
|------|------|------|----------------|
| **Docker Hub (현재)** | 무료 public, 별도 인증 없이 K8s pull, 가장 일반적 | 무료 plan은 pull rate limit 있음 | ★★★ |
| GitHub Container Registry (ghcr.io) | GitHub과 통합, private도 쉬움 | K8s pull 시 ImagePullSecrets 설정 필요 | ★★ |
| AWS ECR / GCP Artifact Registry | 클라우드 통합, 운영급 보안 | 설정 복잡, 비용 발생 | ★ (ch10 Terraform에서 다룸) |
| Self-hosted Registry | 외부 의존 0, 사내망 OK | 운영 부담 | ★ |

→ 본 강의는 학습 진입장벽을 최소화하기 위해 Docker Hub 사용. ch10에서 AWS ECR로 발전.

## 핵심 개념

- **이미지 vs 컨테이너**: 이미지는 정적인 빌드 산출물(클래스), 컨테이너는 실행 중인 인스턴스(객체)
- **Dockerfile 멀티스테이지**: backend Dockerfile은 두 단계로 구성 — 첫 단계에서 poetry로 requirements.txt 추출, 두 번째 단계에서 그것만 가져와 가벼운 이미지 생성. 빌드 도구를 최종 이미지에 포함시키지 않는 패턴
- **이미지 태그**: `<image-name>:<tag>` 형식. 같은 이미지에 여러 태그 부여 가능. `buildtest1`은 학습용 명명. 운영에서는 `v0.1.0` 등 의미 있는 버전을 쓰며 ch5에서 git tag 기반 자동화로 발전
- **Layer 캐시**: Docker는 Dockerfile 각 RUN/COPY 명령을 layer로 캐시. 같은 빌드를 두 번째 실행하면 변경된 layer만 재빌드되어 빠름
- **docker login의 의미**: Docker Hub는 push 시 인증 필요. `docker login`은 ~/.docker/config.json에 인증 토큰을 저장하여 이후 push 명령이 인증되도록 함
- **public 이미지**: Docker Hub 기본은 public. 누구나 `docker pull <username>/...` 가능. ch3.4에서 K8s가 이 이미지를 pull해 배포

## 진행 미리보기

ch3.3가 끝나면 다음 그림이 완성된다:

```
[학습자 GitHub]
  ├── worklog-frontend-mock (fork)
  └── worklog-backend (fork)

[control plane (cp-k8s)]
  └── docker build → 이미지 2개 생성
       │
       ↓ docker push
[Docker Hub]
  ├── <dockerhub_username>/worklog-frontend-mock:buildtest1
  └── <dockerhub_username>/worklog-backend:buildtest1
```

ch3.4에서는 이 두 이미지를 K8s가 pull하여 Pod로 띄운다 (+ MongoDB 공식 이미지).
