# 3.4 Worklog 앱 K8s 배포 — 왜 이 구성?

## 상황

ch3.3에서 mock과 backend 두 이미지를 Docker Hub에 push했다. 한 머신에서 `docker run`으로 띄울 수도 있지만:

- 컨테이너 하나 죽으면 자동 복구 안 됨
- 여러 노드에 분산 배치 못 함
- 외부 노출, 영구 저장, 헬스체크가 분리되어 있음

ch3.4에서는 이를 K8s가 어떻게 운영급으로 해결하는지 본다.

## 학습자가 물어볼 수 있는 질문

- "Pod이 뭐야? Deployment랑은 어떻게 달라?"
- "ClusterIP, NodePort, LoadBalancer, Gateway 다 뭐고 언제 뭘 써?"
- "MongoDB 데이터는 Pod이 죽으면 어떻게 돼?"
- "코드 바꾸면 어떻게 배포해? 매번 매니페스트 다시 쓰는 거야?"

## 추천: 3-tier 구성 + Gateway API + NFS PV

본 강의의 ch3.4는 다음 조합으로 진행:

- **frontend Pod** (mock) — Deployment 1 replica
- **backend Pod** (FastAPI) — Deployment 1 replica + readiness/liveness probe
- **mongodb Pod** — Deployment 1 replica + NFS PVC (영구 저장)
- **외부 노출** — Gateway API (`Gateway` + `HTTPRoute`), `worklog-frontend.myk8s.local`, `worklog-backend.myk8s.local`. NGINX Gateway Fabric controller + MetalLB
- **이미지 출처** — ch3.3에서 push한 학습자 Docker Hub

이 챕터에 적합한 이유:

- **운영 환경의 최소 단위** — 무상태(frontend, backend) + 상태(mongodb) 구분, 외부/내부 노출 분리, 헬스체크. K8s 객체의 핵심 모두 등장
- **mock → 진짜 backend로 전환** — ch3.2의 MSW는 빠지고, ch3.3에서 만든 backend Pod이 그 자리. mock 학습 흐름의 자연스러운 다음 단계
- **NFS PV로 영구 저장** — Pod이 죽어도 데이터 유지. ch2에서 셋업된 `managed-nfs-storage`(default) 활용
- **Gateway API로 도메인 기반 라우팅** — 한 LB IP에 여러 host. Ingress보다 모던하고 확장성 좋은 표준 (Kubernetes 1.32 GA). 인프라(Gateway)와 앱(HTTPRoute) 책임 분리

## 비교 (참고용 — 본 강의는 Gateway API 고정)

### 외부 노출 방식

| 방식 | 장점 | 단점 | 본 강의 적합도 |
|------|------|------|:--:|
| **Gateway API + MetalLB LB** (현재) | 인프라/앱 분리, 호스트·path 라우팅, K8s 표준 진화 방향 | Ingress보다 객체 수 많음(Gateway+HTTPRoute) | ★★★ |
| Ingress + MetalLB LB | 단순, 오래된 표준 | maintenance 모드 (신규 기능 없음), L4/L7 분리 어려움 | ★★ |
| NodePort | 셋업 단순, 추가 controller 불필요 | 포트 30000~32767 한정, 도메인 라우팅 X | ★★ |
| LoadBalancer 단독 | service별 독립 IP | 한 IP 한 서비스, 비용 ↑ | ★ |

→ ch2에서 NGINX Gateway Fabric + MetalLB 이미 셋업됨. 운영급 모던 패턴을 처음부터 학습.

### MongoDB 상태 저장 방식

| 방식 | 장점 | 단점 | 본 강의 적합도 |
|------|------|------|:--:|
| **NFS PVC** (현재, `managed-nfs-storage` default, csi-driver-nfs) | Vagrant 환경에 셋업 완비, ReadWriteMany | NFS export 의존, 운영급 클러스터엔 부적합 | ★★★ (학습용) |
| local volume | 빠름 | 노드 묶임, Pod 재스케줄 시 데이터 잃음 | ★ |
| hostPath | 단순 | 노드 묶임 + 보안 우려 | ★ |
| 클라우드 native (EBS/PD) | 운영급 신뢰성 | 클라우드 의존, ch10 EKS에서 다룸 | ★★ (ch10) |

## 핵심 개념

- **Pod** — K8s의 가장 작은 배포 단위. 보통 컨테이너 하나 (사이드카 패턴이면 여러 개)
- **Deployment** — Pod의 spec(replica 수, rollout 전략 등)을 관리하는 객체. Pod 직접 만들지 않고 Deployment를 만들어 Pod을 관리하는 게 표준
- **Service** — Pod 그룹에 안정적 endpoint 제공. Pod IP는 재시작 시 바뀌니까 Service의 ClusterIP / DNS 이름으로 통신
- **Gateway API** — Kubernetes Ingress의 모던 후속. Gateway(인프라 측: 어떤 listener·port·TLS)와 HTTPRoute(앱 측: 어떤 host·path → 어떤 service)를 분리하여 책임/RBAC 분리 가능
- **Gateway** — 외부 진입 자원. `gatewayClassName`이 GatewayClass(controller 구현체)와 연결. listener에서 port/protocol 정의
- **HTTPRoute** — 라우팅 규칙. `parentRefs`로 Gateway에 연결, `hostnames` + path matches로 트래픽을 backend service에 전달
- **MetalLB** — bare-metal K8s에서 LoadBalancer 타입 Service에 외부 IP 할당. 클라우드 환경엔 클라우드 LB가 그 역할
- **PersistentVolumeClaim (PVC)** — Pod이 영구 저장 공간을 요청하는 방법. PV(실제 저장)와 분리되어 어플리케이션이 인프라 세부를 몰라도 됨
- **Probe** — Pod의 건강 검사. liveness(죽었으면 재시작), readiness(준비됐을 때만 트래픽 받음)
- **RollingUpdate** — Deployment의 기본 rollout 전략. 새 Pod이 Ready되면 옛 Pod을 한 개씩 제거 → 무중단 배포. ch7에서 Blue-Green, Canary 등 더 정교한 전략 다룸

## 진행 미리보기

ch3.4가 끝나면 다음 그림이 완성된다:

```
[학습자 호스트]
  └── 브라우저
       │  http://worklog-frontend.myk8s.local
       │  http://worklog-backend.myk8s.local
       │  (호스트 hosts 파일에 192.168.1.XX 등록)
       ↓
[Vagrant K8s cluster (cp + w1~w3)]
  └── MetalLB → nginx-gateway controller (EXTERNAL-IP 192.168.1.XX)
       └── Gateway: nginx-gateway (controller 설치 시 자동 생성, default ns)
            ├── HTTPRoute: worklog-frontend.myk8s.local → svc worklog-frontend
            │   └── Pod: worklog-frontend (mock, <user>/worklog-frontend-mock:buildtest1)
            └── HTTPRoute: worklog-backend.myk8s.local → svc worklog-backend
                └── Pod: worklog-backend (<user>/worklog-backend:buildtest1)
                     └── env MONGO_HOST=worklog-mongodb.default.svc.cluster.local
                          └── svc worklog-mongodb (ClusterIP, 27017)
                               └── Pod: worklog-mongodb (mongo:4.4.29-focal)
                                    └── PVC pvc-worklog-mongodb (NFS, managed-nfs-storage)
```

ch3.4의 변경 워크플로우(`buildtest1` → `buildtest2`)는 학습자에게 "코드 한 줄 바꾸고 배포까지" 흐름의 첫 체험. 운영에서 이걸 자동화하는 게 ch4 이후의 CI/CD.
