# 3.2 Worklog 앱 받아 실행 — 왜 mock + Docker 없이?

## 상황

학습자가 ch2에서 Vagrant + VirtualBox로 K8s 클러스터를 구축했다. 다음 단계로 "이 클러스터에서 어떤 앱을 운영할 것인가"를 정해야 한다. 그러나 K8s 배포에 바로 들어가기 전에:

- 앱이 어떻게 생겼는지 시각적으로 확인
- 컨테이너·K8s 없이도 동작하는 가장 가벼운 형태로 시작

이 두 가지를 짧게 거치는 것이 ch3.2의 목적이다.

## 학습자가 물어볼 수 있는 질문

- "이 클러스터에서 뭘 돌릴 거야?"
- "그냥 앱 화면부터 한번 보고 싶은데, 어떻게 받지?"
- "컨테이너부터 시작 안 하고 npm으로 그냥 띄울 수도 있어?"

## 추천: `worklog-frontend-mock` 단독 + npm dev server

본 강의는 Worklog 앱의 frontend(mock 버전)을 다음과 같이 받는다:

- 저장소: https://github.com/sungmincs/worklog-frontend-mock
- 실행 방식: control plane 노드 위에서 `yarn install` + `yarn dev` (Docker 없음)

이 챕터에 적합한 이유:

- **백엔드 의존 없음**: MSW(Mock Service Worker)가 API 요청을 가로채 가짜 응답을 반환 — 이 단계에서 backend·MongoDB를 신경 쓸 필요가 없다
- **Docker 없는 가장 가벼운 시작**: 의존성 설치 → 실행 → 화면 확인. 컨테이너 개념을 아직 몰라도 진입 가능
- **다음 차시의 동기 부여**: "내 환경에서만 동작하는 한계"를 체감하게 하여 ch3.3 Docker화의 필요성을 자연스럽게 끌어냄

## 핵심 개념

- **MSW (Mock Service Worker)**: 브라우저의 service worker가 fetch/XHR을 가로채 미리 정의된 mock 응답을 반환. 백엔드 없이 frontend만으로 화면 시연 가능
- **Vite dev server**: 개발용 빌드 도구. `yarn dev`로 5173 포트에서 hot reload 지원하는 서버 실행. 운영용 빌드(`yarn build`)와는 다름
- **`--host 0.0.0.0`의 의미**: 기본값(`127.0.0.1`)은 같은 머신에서만 접속 가능. control plane VM 안에서 실행한 dev server를 호스트 브라우저에서 접속하려면 `0.0.0.0`으로 외부 인터페이스에 바인딩 필요

## 진행 미리보기

ch3.2가 끝나면 학습자의 머릿속에 다음 그림이 자리잡는다:

```
[학습자 호스트 브라우저]
       │ http://192.168.1.10:5173
       ↓
[Vagrant control plane VM]
  └── Vite dev server (yarn dev)
       └── React + MSW (mock 응답)
```

ch3.3에서는 이 흐름을 Docker 컨테이너로 바꾸고, ch3.4에서는 K8s에 배포한다.
