### 단계 1: Docker Pipeline 플러그인 확인 `[학습자 직접 · 웹]`

Jenkins → Jenkins 관리 → Plugins → Installed plugins에서 "Docker Pipeline"을 찾는다. ch4.5 설치 스크립트가 이미 넣었으므로 보통 할 일은 없다. 없으면 Available plugins에서 설치한다.

### 단계 2: Plugin 방식 Jenkinsfile 작성 `[AI 프롬프트]`

`[채우기: ...]` 한 줄은 학습자가 작성한다. 프롬프트 전체를 복사해 붙여 넣고 그 자리를 작성한 뒤 보낸다. 이 절에서 배울 내용이 그 자리에 있다.

```text
Jenkinsfile의 Build Image stage가 Docker Pipeline 플러그인으로 실제 빌드와 push를 하게 바꿔줘. echo로 두었던 빌드를 진짜 이미지 빌드로 바꾸려는 거야.
파일: /root/workspace/worklog-backend/Jenkinsfile
조건:
- docker.build()와 docker.withRegistry('https://index.docker.io/v1/', ...)를 사용해줘.
- [채우기: withRegistry에 넘길 Credentials ID. 5.5에서 Jenkins에 등록한 것]
- 이미지는 <dockerhub_username>/worklog-backend, 태그는 9자 short SHA와 full SHA 2개
끝나면: 바꾼 부분을 보여줘. 커밋 전에 멈춰줘.
```

### 단계 5: 스캔과 결과 확인 `[학습자 직접 · 웹]`

'Scan Multibranch Pipeline Now'로 빌드를 시작한다. Console Output에서 `+ docker build -t <dockerhub_username>/worklog-backend:<short_sha> .`와 push 결과를 보고, Docker Hub에서 9자 short SHA와 full SHA 태그를 확인한다. Jenkins가 올린 이미지는 아키텍처가 하나다(빌드한 노드의 것. Apple Silicon 맥이면 arm64, x86 PC면 amd64). 5.3과 5.4의 GitHub Actions는 amd64와 arm64를 함께 올렸다. 이 차이는 10.7에서 EKS(amd64 노드)로 갈 때 다시 나온다. 실패를 고친 뒤 같은 커밋으로 다시 돌릴 때는 스캔이 아니라 main 브랜치 job의 '지금 빌드' 메뉴를 누른다. Console Output에 `WARNING! Using --password via the CLI is insecure`가 찍히는데, withRegistry가 내부에서 비밀번호 옵션으로 로그인해서 나오는 경고다. 빌드 결과에는 영향이 없고, 5.3에서 배운 `--password-stdin`과 비교해 설명할 거리다.

## 주의사항

- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ✅ AI가 해도 됨: Plugin 방식 Jenkinsfile 작성, 간소화 포인트 설명
- ⛔ Docker Pipeline 플러그인이 설치되지 않은 상태에서는 `docker.build()`, `docker.withRegistry()` 메서드를 사용할 수 없다.
- ⛔ `docker.withRegistry()`의 첫 번째 인자는 레지스트리 URL이며, Docker Hub의 경우 `https://index.docker.io/v1/`을 사용한다.
- ⛔ Credentials ID(`dockerhub-credentials`)가 5.5에서 등록한 것과 정확히 일치해야 한다.

## 트러블슈팅

### `permission denied while trying to connect to the Docker daemon socket`

```
ERROR: permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock
```

- 원인: 에이전트 Pod는 노드의 `/var/run/docker.sock`(root:docker, 660)을 쓴다. 에이전트 이미지의 docker 그룹 GID는 998인데, 이 강의 노드(Ubuntu 24.04)의 docker 그룹 GID는 988이다. 그래서 컨테이너 안 jenkins 사용자가 소켓에 접근하지 못한다.
- 지금 JCasC(`ch4/4.5/jenkins-config.yaml`)는 에이전트 Pod 템플릿에 `supplementalGroups: "988"`을 넣어 이 문제를 막는다(2026-10-08 수정, run-38 판단17). 이 오류가 나면 옛 JCasC로 설치됐거나 노드의 docker GID가 988이 아닌 것이다.
- 확인: `getent group docker`(노드에서). 988이 아니면 JCasC의 `supplementalGroups` 값을 그 GID로 바꾼다.
- 다시 빌드: 같은 커밋은 스캔해도 새 빌드가 생기지 않는다. main 브랜치 job에서 '지금 빌드' 메뉴를 누른다.
- 소켓을 `chmod 666`으로 여는 방법도 있지만 쓰지 않는다. Docker 재시작이나 VM 재부팅 뒤에 660으로 돌아가고, 실무에서도 쓰지 않는다.
