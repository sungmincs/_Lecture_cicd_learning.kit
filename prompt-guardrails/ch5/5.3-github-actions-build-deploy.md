# 5.3 [GitHub] CI 파이프라인 실제로 구현하기

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 워크플로 확인, git push
> - `[학습자 직접 · 웹]`: Docker Hub 토큰 발급, GitHub Secrets 등록, 실행 결과 확인
> - `[AI 프롬프트]`: 파이프라인 yaml 작성, 배포 매니페스트(`deploy_manifest/`) 준비
>
> 작업 위치는 컨트롤 플레인 노드의 `/root/workspace/worklog-backend`다.

## 사전 조건

- ch4 완료 (worklog-backend fork가 노드의 `/root/workspace/worklog-backend`에 있고 ch4 워크플로 3개와 Jenkinsfile이 push된 상태)
- ch3.5 완료 (Docker Hub에 `<dockerhub_username>/worklog-backend:buildtest1` 존재)

## 실행 지침

### 단계 1: 앞 절 파이프라인이 꺼져 있는지 확인 `[학습자 직접]`

ch4에서 만든 워크플로 3개(4.3 hello 2개, 4.4 빌드 파이프라인)는 4.5 단계 1에서 껐다. 꺼져 있는지 본다. 하나라도 `active`면 끈다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow list --all -R <github_username>/worklog-backend      # 셋 다 disabled_manually
```

### 단계 2: Docker Hub Access Token 발급 `[학습자 직접 · 웹]`

Docker Hub → Account Settings → Personal access tokens → Generate new token. 권한은 Read & Write.
ch3.5에서 `docker login`에 쓴 토큰을 다시 써도 된다. 값은 발급 화면에서만 보이므로 저장한 값이 없으면 새로 만든다.

### 단계 3: GitHub Secrets 등록 `[학습자 직접 · 웹]`

저장소 → Settings → Secrets and variables → Actions → New repository secret

| Secret 이름 | 값 |
|---|---|
| `DOCKERHUB_TOKEN` | Docker Hub Access Token |

### 단계 4: 파이프라인 yaml 작성 `[AI 프롬프트]`

`[채우기: ...]` 한 줄은 학습자가 작성한다. 프롬프트 전체를 복사해 붙여 넣고 그 자리를 작성한 뒤 보낸다. 이 절에서 배울 내용이 그 자리에 있다.

```text
worklog-backend 이미지를 빌드해 Docker Hub에 올리는 GitHub Actions 파이프라인을 만들어줘. push할 때마다 테스트를 통과한 코드로 이미지를 만들려는 거야.
파일: /root/workspace/worklog-backend/.github/workflows/build-pipeline.yaml
조건:
- Docker Hub username은 <dockerhub_username>, 토큰은 secrets.DOCKERHUB_TOKEN
- job 순서: init-and-test(uv로 테스트) → build → 성공 알림과 실패 알림
- 이미지는 amd64와 arm64를 함께 빌드
- [채우기: 이미지 태그를 무엇으로 붙일지. 어느 커밋에서 만든 이미지인지 알 수 있게]
- 알림은 아직 echo로
끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.
```

<details>
<summary>예시 보기</summary>

| 빈칸 | 예시 | 이 줄이 필요한 이유 |
|---|---|---|
| 이미지 태그 | 커밋 full SHA와 앞 8자 2개를 붙여줘 | 태그만 보고 어느 커밋에서 만든 이미지인지 알 수 있다. 8자는 사람이 읽기 쉽다 |

</details>

✅ 정답 파일 (완성 후 비교): `ch5/5.3/1.build-pipeline.yaml`

정답의 테스트 step은 `export TESTING=true` 뒤에 pytest를 돈다. 이 값이 있으면 앱이 실제 MongoDB 대신 mongomock(메모리 안의 가짜 DB)을 써서 러너에 MongoDB가 없어도 테스트가 된다(worklog-backend `src/worklog/db.py`). AI가 이 줄을 빼면 테스트가 MongoDB 연결에서 멈출 수 있다. arm64 이미지는 러너가 amd64라 BuildKit에 들어 있는 QEMU로 에뮬레이션해 빌드하므로 amd64보다 느리다.

### 단계 5: 배포 매니페스트 준비 `[AI 프롬프트]`

```text
ch6에서 Argo CD가 배포할 매니페스트를 만들어줘. 배포할 상태를 저장소에 파일로 두려는 거야.
파일: /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml
조건:
- 구성은 ch3.6의 worklog-backend.yaml과 같게(Secret, Deployment, Service, HTTPRoute)
- Docker Hub username은 <dockerhub_username>, 이미지는 ch3.5의 buildtest1 태그
끝나면: dry-run으로 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.
```

✅ 정답 파일 (완성 후 비교): `ch5/5.3/deploy_manifest/worklog-backend.yaml`

이 폴더는 ch5 파이프라인이 쓰지 않는다. ch6.5에서 Argo CD가 이 폴더를 보고, ch6.7부터 파이프라인이
여기 적힌 이미지 태그를 바꾼다. `buildtest1`은 ch3.5에서 이미 Docker Hub에 올렸으므로 ch6.5에서 바로 배포된다.

> 💡 MongoDB Secret(`worklog-mongodb-creds`)이 매니페스트 안에 들어 있다. 실습용 데모 비밀번호라 예외로 Git에 둔다(AGENTS.md 핵심 안전 규칙).
> 실무에서는 Secret을 Git에 두지 않는다.

### 단계 6: git push `[학습자 직접]`

파이프라인 파일과 매니페스트를 한 커밋으로 push한다. 따로 push하면 빌드가 한 번 더 돈다(루프 방지 `paths-ignore`는 ch6.7에서 넣는다).

```bash
cd /root/workspace/worklog-backend
git add .github/workflows/ deploy_manifest/
git commit -m "add: build and push pipeline, deploy manifest"
git push
```

### 단계 7: Actions 실행 결과 확인 `[학습자 직접 · 웹]`

- GitHub → Actions 탭 → `worklog backend pipeline`의 각 job 성공 여부 확인
- Docker Hub의 `worklog-backend` 저장소에 8자 short SHA와 full SHA 태그가 amd64, arm64로 올라왔는지 확인

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username | ❌ 반드시 확인 |
| `<github_username>` | 학습자의 GitHub username (단계 1의 `gh workflow` 명령) | ❌ 반드시 확인 |

## 주의사항

- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ⛔ AI가 하지 말 것: GitHub Secrets를 직접 등록하거나 Docker Hub 토큰 값을 묻지 말 것
- ✅ AI가 해도 됨: 파이프라인 yaml 작성
- ✅ AI가 해도 됨: Secrets 등록 경로 안내
- ✅ AI가 해도 됨: 빌드/push 실패 원인 분석
- ⛔ 정답 파일의 `<dockerhub_username>`은 3곳이다. 파이프라인 yaml의 `DOCKER_REPOSITORY`, `DOCKERHUB_USERNAME`과 매니페스트의 `image:`. 모두 본인 계정으로 바꾼다.
