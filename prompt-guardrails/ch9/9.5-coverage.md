# 9.5 CI 강화 - Test Coverage 임계값

> **학습자 진입 방식**:
> - `[학습자 직접]`: git push, 파이프라인 결과 확인
> - `[AI 프롬프트]`: 테스트 커버리지 80% 미만이면 파이프라인 실패하도록 설정

## 사전 조건

- ch9/9.4 완료 (security-scan 단계 포함된 파이프라인 동작 확인)

## 실행 지침

### 단계 1: 기존 파이프라인에 Coverage 임계값 추가 `[AI 프롬프트]`

사용하는 CI 플랫폼에 맞게 아래 프롬프트를 사용한다.

**GitHub Actions:**

> "`ci.yaml`의 test job에서 커버리지 임계값 80%를 적용해줘.
> - `uv run coverage run --source ./src/worklog -m pytest --disable-warnings -v`
> - `uv run coverage report --fail-under=80` 추가
> - TESTING=true 환경변수 설정 필요"

✅ 정답 파일 (완성 후 비교): `ch9/9.5/1.coverage-github.yaml`

**Jenkins:**

> "기존 Jenkinsfile의 Test stage에서 커버리지 임계값 80%를 적용해줘.
> - `TESTING=true uv run coverage run --source ./src/worklog -m pytest --disable-warnings -v`
> - `uv run coverage report --fail-under=80` 추가"

✅ 정답 파일: `ch9/9.5/2.coverage-jenkins.groovy`

### 단계 2: git push + 파이프라인 결과 확인 `[학습자 직접]`

```bash
git add .github/workflows/  # 또는 Jenkinsfile
git commit -m "ci: add coverage threshold gate (80%)"
git push
```

파이프라인 UI에서 test 단계 커버리지 출력 확인.

### 단계 3: 게이트가 막는 것 확인 `[학습자 직접]`

현재 커버리지는 약 95%라 80%로는 통과한다. `--fail-under=99`로 잠시 올려 push하면 test 단계가 실패하는 것을 본다.
확인한 뒤 80으로 되돌려 다시 push한다. 실제로 80% 미만이면 AI에게 테스트 추가를 요청한다(아래 프롬프트).

> "현재 테스트 커버리지가 80% 미만이야. 커버되지 않는 부분을 확인하고, 커버리지를 높이기 위한 테스트 케이스를 추가해줘."

AI가 미커버 영역을 분석하고 테스트 코드 추가 제안 → 적용 후 재push.

### 단계 4: 임계값의 의미 이해 `[AI 프롬프트]`

> "테스트 커버리지 80% 임계값이 실무에서 어떤 의미인지, 그리고 100%가 항상 좋은 건 아닌 이유를 설명해줘."

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username (Jenkins 정답만. GitHub 정답은 빌드 단계가 없다) | ❌ 반드시 확인 |

Jenkins 정답은 8.6 Jenkinsfile에 앞 절까지의 게이트 stage를 쌓은 전체 파이프라인이라 이미지 빌드, push, 매니페스트 갱신까지 한다(9.3 Lint → 9.4 Security Scan → 9.5 커버리지 기준 → 9.6 Scan). 이미지 태그 규칙도 8.6과 같다(dev-, staging-, 태그 이름).

## 검증 중 발견된 이슈 (강의자 참고)

- **GitHub Actions BRANCH 버그 (Full CI/CD)**: `ch8/8.4/1.full-cicd-workflow.yaml`의 update-manifest job에서 `${GITHUB_REF#refs/heads/}` 방식은 v* 태그 빌드 시 `refs/tags/v1.0.0`을 그대로 반환하여 push 실패. if/elif 분기 방식으로 수정.

## 주의사항

- ⛔ AI가 하지 말 것: `coverage report` 만 실행하고 `--fail-under` 없이 마무리하지 말 것
- ⛔ AI가 하지 말 것: `TESTING=true` 환경변수 누락 (worklog-backend는 TESTING=true 필요)
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: 커버리지 미달 영역 분석 및 테스트 추가 제안
- ✅ AI가 해도 됨: 80% 임계값 조정 (학습 목적으로 70% 등으로 낮추기 가능)
- ⚠️ 기존 테스트가 80% 미만이면 파이프라인이 실패한다 — 이것은 정상 동작. AI에게 테스트 추가 요청.
- ⚠️ `--source ./src/worklog` 경로 확인 필요 — worklog-backend 저장소 구조 기준
