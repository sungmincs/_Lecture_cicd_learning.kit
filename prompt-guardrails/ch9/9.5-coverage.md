# 9.5 CI 강화 - Test Coverage 임계값

> **학습자 진입 방식**:
> - `[학습자 직접]`: git push, 임계값을 올려 실패시키기와 되돌리기
> - `[학습자 직접 · 웹]`: GitHub Actions와 Jenkins의 실행 결과 확인
> - `[AI 프롬프트]`: 두 파이프라인에 커버리지 80% 기준 추가

## 사전 조건

- ch9/9.4 완료 (security-scan 단계가 든 파이프라인이 통과하는 상태)

## 실행 지침

### 단계 1: GitHub 워크플로에 test job `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/.github/workflows/ci.yaml`에 test job을 추가해 커버리지 기준 80%를 적용해줘. push는 내가 할게.
> - security-scan job 완료 후 실행 (`needs: [security-scan]`)
> - `uv run coverage run --source ./src/worklog -m pytest --disable-warnings -v`
> - `uv run coverage report --fail-under=80`
> - TESTING=true 환경변수 설정 필요"

✅ 정답 파일 (완성 후 비교): `ch9/9.5/1.coverage-github.yaml`

### 단계 2: Jenkinsfile의 Test stage에 기준 추가 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Jenkinsfile`의 Test stage에서 커버리지 기준 80%를 적용해줘. push는 내가 할게.
> - `TESTING=true uv run coverage run --source ./src/worklog -m pytest --disable-warnings -v`
> - `uv run coverage report --fail-under=80`"

✅ 정답 파일 (완성 후 비교): `ch9/9.5/2.coverage-jenkins.groovy`

### 단계 3: git push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add .github/workflows/ci.yaml Jenkinsfile
git commit -m "ci: add coverage threshold gate (80%)"
git pull --rebase
git push
```

### 단계 3-1: 커버리지 출력 확인 `[학습자 직접 · 웹]`

Actions 탭의 test job 로그와, Jenkins를 스캔한 뒤 main 빌드의 Test stage에서 `TOTAL` 줄을 본다. 지금 커버리지는 약 95%라 80% 기준을 통과한다.

### 단계 4: 기준을 올려 게이트가 막는 것 보기 `[학습자 직접]`

통과만 봐서는 게이트가 동작하는지 알 수 없다. GitHub 쪽 기준을 잠시 99로 올린다.

```bash
cd /root/workspace/worklog-backend
grep -n "fail-under" .github/workflows/ci.yaml
sed -i 's/--fail-under=80/--fail-under=99/' .github/workflows/ci.yaml
grep -n "fail-under" .github/workflows/ci.yaml           # 99로 바뀌었는지 확인
git commit -am "test: raise coverage threshold to 99"
git pull --rebase
git push
```

### 단계 4-1: 실패 확인 `[학습자 직접 · 웹]`

Actions 탭에서 test job이 실패하는지 본다. 로그 끝에 `Coverage failure: total of 95 is less than fail-under=99` 같은 줄이 나온다.

### 단계 5: 되돌리기 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git revert --no-edit HEAD
git pull --rebase
git push
```

Actions 탭에서 test job이 다시 성공하는지 본다.

### 단계 6: 임계값의 의미 이해 `[AI 프롬프트]`

> "테스트 커버리지 80% 임계값이 실무에서 어떤 의미인지, 그리고 100%가 항상 좋은 건 아닌 이유를 설명해줘."

## 트러블슈팅

### 처음부터 80% 미만이라 실패한다

게이트가 맞게 동작한 것이다. AI에게 "현재 테스트 커버리지가 80% 미만이야. 커버되지 않는 부분을 확인하고 테스트 케이스를 추가해줘"라고 요청하고, 추가된 테스트를 커밋해 다시 push한다.

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username (Jenkins 정답만. GitHub 정답은 빌드 단계가 없다) | ❌ 반드시 확인 |

Jenkins 정답은 8.6 Jenkinsfile에 앞 절까지의 게이트 stage를 쌓은 전체 파이프라인이라 이미지 빌드, push, 매니페스트 갱신까지 한다(9.3 Lint → 9.4 Security Scan → 9.5 커버리지 기준 → 9.6 Scan). 이미지 태그 규칙도 8.6과 같다(dev-, staging-, 태그 이름).

## 주의사항

- ⛔ AI가 하지 말 것: git push와 Jenkins 스캔을 대신 하지 말 것
- ⛔ AI가 하지 말 것: `coverage report` 만 실행하고 `--fail-under` 없이 마무리하지 말 것
- ⛔ AI가 하지 말 것: `TESTING=true` 환경변수 누락 (worklog-backend는 TESTING=true 필요)
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: 커버리지 미달 영역 분석 및 테스트 추가 제안
- ✅ AI가 해도 됨: 80% 임계값 조정 (학습 목적으로 70% 등으로 낮추기 가능)
- ⚠️ 기존 테스트가 80% 미만이면 파이프라인이 실패한다 — 이것은 정상 동작. AI에게 테스트 추가 요청.
- ⚠️ `--source ./src/worklog` 경로 확인 필요 — worklog-backend 저장소 구조 기준
