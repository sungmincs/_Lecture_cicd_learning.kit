# 9.5 CI 강화 - Test Coverage 임계값

> **학습자 진입 방식**:
> - `[학습자 직접 · 웹]`: GitHub Actions와 Jenkins의 실행 결과 확인
> - `[AI 프롬프트]`: 파이프라인 2개에 커버리지 80% 기준 추가, push, 기준을 올려 실패시키기와 되돌리기(프롬프트는 학습자가 처음부터 작성)

요청과 계획 검토 방식은 8.3의 "8장부터 짧게 요청하고 계획을 검토한다"와 같다.

## 사전 조건

- ch9/9.4 완료 (security-scan 단계가 든 파이프라인이 통과하는 상태)

## 실행 지침

### 단계 1: GitHub 워크플로에 test job `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
ci.yaml에 test job을 추가해 커버리지 기준을 80%로 정해줘. 테스트 없는 코드가 늘면 막으려는 거야. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/.github/workflows/ci.yaml
- security-scan job이 끝난 뒤 실행(needs: [security-scan])
- TESTING=true로 uv run coverage run --source ./src/worklog -m pytest --disable-warnings -v
- uv run coverage report --fail-under=80
- 참고: 테스트 명령은 같은 폴더의 multi-env.yaml(8.4)의 init-and-test job과 같게 해줘.
- 끝나면: yaml 문법을 검사하고 바뀐 부분을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| security-scan 뒤에 실행 | 앞 게이트가 실패해도 테스트까지 진행 |
| TESTING=true로 테스트 | MongoDB가 없어 테스트 실패 |
| coverage report --fail-under=80 | 커버리지가 낮아도 통과 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch9/9.5/1.coverage-github.yaml`

### 단계 2: Jenkinsfile의 Test stage에 기준 추가 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
Jenkinsfile의 Test stage에 커버리지 기준 80%를 넣어줘. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/Jenkinsfile
- 지금 Test stage의 uv run coverage report에 --fail-under=80을 붙여
- 다른 stage는 그대로 둬.
- 끝나면: 바뀐 부분을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| report 줄에만 --fail-under=80 | 다른 줄이 바뀌어 테스트가 달라짐 |
| 다른 stage 변경 없음 | 앞 절에서 만든 단계가 바뀜 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch9/9.5/2.coverage-jenkins.groovy`

### 단계 3: push `[AI 프롬프트]`

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
ci.yaml과 Jenkinsfile을 커밋하고 push해줘. 커밋 메시지는 ci: add coverage threshold gate (80%), push 전에 git pull --rebase 해줘.
```

**AI가 따를 조건**

- 커밋 메시지는 ci: add coverage threshold gate (80%)
- push 전에 git pull --rebase
- 끝나면: push 결과를 보여줘.

### 단계 4: 커버리지 출력 확인 `[학습자 직접 · 웹]`

Actions 탭의 test job 로그와, Jenkins를 스캔한 뒤 main 빌드의 Test stage에서 `TOTAL` 줄을 본다. 지금 커버리지는 약 95%라 80% 기준을 통과한다.

### 단계 5: 기준을 올려 push `[AI 프롬프트]`

통과만 봐서는 게이트가 동작하는지 알 수 없다. GitHub 쪽 기준을 잠시 99%로 올린다.

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
ci.yaml의 커버리지 기준만 99%로 올려 push해줘. 게이트가 막는지 보려는 거야. 커밋 메시지는 test: raise coverage threshold to 99.
```

**AI가 따를 조건**

- ci.yaml의 --fail-under 값만 바꾸고 Jenkinsfile은 그대로 둬.
- 커밋 메시지는 test: raise coverage threshold to 99, push 전에 git pull --rebase
- 끝나면: 바뀐 줄과 push 결과를 보여줘.

### 단계 6: 실패 확인 `[학습자 직접 · 웹]`

Actions 탭에서 test job이 실패하는지 본다. 로그 끝에 `Coverage failure: total of 95 is less than fail-under=99` 같은 줄이 나온다.

### 단계 7: 되돌리기 `[AI 프롬프트]`

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
방금 올린 커밋을 git revert로 되돌려 push해줘. 커버리지 기준을 80%로 되돌리려는 거야.
```

**AI가 따를 조건**

- git revert --no-edit HEAD
- push 전에 git pull --rebase
- 끝나면: push 결과를 보여줘.

Actions 탭에서 test job이 다시 성공하는지 본다.

### 단계 8: 임계값의 의미 이해 `[AI 프롬프트]`

짧은 질문이라 직접 친다.

```text
테스트 커버리지 80% 임계값이 실무에서 어떤 의미인지, 그리고 100%가 항상 좋은 건 아닌 이유를 설명해줘.
```

## 트러블슈팅

### 처음부터 80% 미만이라 실패한다

게이트가 맞게 동작한 것이다. AI에게 "현재 테스트 커버리지가 80% 미만이야. 커버되지 않는 부분을 확인하고 테스트 케이스를 추가해줘"라고 요청하고, 추가된 테스트를 커밋해 다시 push한다.

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username (Jenkins 정답만. GitHub 정답은 빌드 단계가 없다) | ❌ 반드시 확인 |

Jenkins 정답은 8.6 Jenkinsfile에 앞 절까지의 게이트 stage를 쌓은 전체 파이프라인이라 이미지 빌드, push, 매니페스트 갱신까지 한다(9.3 Lint → 9.4 Security Scan → 9.5 커버리지 기준 → 9.6 Scan). 이미지 태그 규칙도 8.6과 같다(dev-, staging-, 태그 이름).

## 주의사항

- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: Jenkins 스캔을 대신 하지 말 것. 단계 3, 5, 7의 요청이 없을 때 커밋과 push를 하지 말 것
- ⛔ AI가 하지 말 것: `coverage report` 만 실행하고 `--fail-under` 없이 마무리하지 말 것
- ⛔ AI가 하지 말 것: `TESTING=true` 환경변수 누락 (worklog-backend는 TESTING=true 필요)
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: 커버리지 미달 영역 분석 및 테스트 추가 제안
- ✅ AI가 해도 됨: 80% 임계값 조정 (학습 목적으로 70% 등으로 낮추기 가능)
- ⚠️ 기존 테스트가 80% 미만이면 파이프라인이 실패한다 — 이것은 정상 동작. AI에게 테스트 추가 요청.
- ⚠️ `--source ./src/worklog` 경로 확인 필요 — worklog-backend 저장소 구조 기준
- ⚠️ Jenkinsfile의 비밀값(`*_PSW`, `ARGOCD_ADMIN_PASSWORD`)은 `sh """` 안에서 `\$변수`로 넘긴다. `${...}`로 쓰면 Groovy가 값을 먼저 풀어 Console Output에 `Groovy String interpolation` 경고가 남는다(6.8 "검증 중 발견된 이슈")
