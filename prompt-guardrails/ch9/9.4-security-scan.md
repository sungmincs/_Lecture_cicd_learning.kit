### 단계 5: 취약점 고치기 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend`에서 `uv run pip-audit`이 취약점을 찾았어. 직접 의존성인지 간접 의존성인지 보고 `uv lock --upgrade-package`로 락파일을 올려줘. 고친 뒤 `TESTING=true uv run pytest`로 테스트가 통과하는지와 pip-audit이 깨끗한지 확인해줘. 커밋과 push는 내가 할게."

간접 의존성(fastapi, motor가 끌어오는 것)은 `pyproject.toml`이 아니라 락파일만 올린다. 직접 의존성도 같은 명령으로 올릴 수 있고, 취약한 버전을 다시 받지 않게 하려면 `pyproject.toml`의 하한을 올린다.

### 단계 6: 시크릿 탐지 확인 `[학습자 직접]`

가짜 토큰이 든 파일을 만들어 gitleaks가 잡는지 본다. 커밋하지 않고 작업 트리에서만 한다.

```bash

printf 'TOKEN = "ghp_%s"\n' "$(tr -dc 'A-Za-z0-9' </dev/urandom | head -c 36)" > src/worklog/leak_demo.py
```

## 트러블슈팅

### `error: Failed to spawn: pip-audit`

fork의 `pyproject.toml`에 pip-audit이 없는 경우다. `[project.optional-dependencies]`의 dev에 `"pip-audit>=2.7.0"`을 넣고(이 저장소는 `[dependency-groups]`가 아니다) `uv lock`으로 락파일을 갱신해 함께 커밋한다.

### `uvx pip-audit`으로 바꾸면 통과하는데

통과하는 것이 아니라 아무것도 검사하지 않는 것이다. `uvx`는 도구를 격리된 임시 환경에 설치해 실행하고, pip-audit은 자기가 있는 환경의 패키지를 검사한다. 그 환경에는 프로젝트 의존성이 없다.
실측(2026-08-30): `starlette==1.0.0`(취약점 6건)을 둔 프로젝트에서 `uv run pip-audit`은 탐지했고 `uvx pip-audit`은 `No known vulnerabilities found`였다.

### gitleaks 설치가 404

`$(uname -s)`는 `Linux`(대문자)를 주는데 릴리스 자산은 소문자 `linux`이고 파일 이름에 버전이 들어간다. 올바른 형식은 `gitleaks_8.30.1_linux_x64.tar.gz`이고 arm64 노드에서는 `arm64`다.

## 주의사항

- ⛔ AI가 하지 말 것: git push와 Jenkins 스캔을 대신 하지 말 것
- ⛔ AI가 하지 말 것: `uvx pip-audit`으로 바꾸지 말 것(트러블슈팅)
- ⛔ AI가 하지 말 것: 가짜 토큰을 커밋하지 말 것
- ⛔ AI가 하지 말 것: `.gitleaks.toml`에서 `[[rules.allowlist]]` slice 형태 사용 (gitleaks v8 비호환)
- ⛔ AI가 하지 말 것: `gitleaks/gitleaks-action@v2` 없이 GitHub Actions에서 gitleaks 직접 설치 시도
- ✅ AI가 해도 됨: .gitleaks.toml 작성, 파이프라인 작성
- ✅ AI가 해도 됨: pip-audit 취약점 발견 시 락파일 갱신(`uv lock --upgrade-package`) 또는 버전 업그레이드 제안
- ✅ AI가 해도 됨: gitleaks 탐지 오탐(false positive) 원인 분석 및 allowlist 조정
- ⚠️ GitHub gitleaks-action은 push 이벤트에서 그 push에 들어온 커밋만 검사한다(실측 1 commit). `fetch-depth: 0`은 그 범위의 커밋을 받아 두기 위해 필요하다. 이력 전체를 보는 것은 Jenkins의 `gitleaks detect --source .`다(실측 107 commits).
- ⚠️ Jenkins gitleaks 자산은 `uname -m`으로 x64와 arm64를 나눈다(정답 파일). `uname -s`를 쓰면 404.
- ⚠️ Jenkins gitleaks는 job이 받아 둔 모든 ref의 이력을 본다. 태그 job은 태그까지 받고 브랜치 job은 받지 않는다. 그래서 가짜 키를 커밋한 브랜치나 태그가 하나라도 남아 있으면
  main 빌드는 통과하는데 태그 빌드만 Security Scan에서 막힐 수 있다(run-38 후속: 검증 fork의 옛 백업 태그로 `leaks found: 21`). 시연한 가짜 키는 어느 ref에도 커밋하지 않는다.
- ⚠️ **(run-16, #95) gitleaks 탐지 시연/테스트 조건 2가지**:
  - **엔트로피 필요**: `ghp_aaaa...`처럼 반복 문자는 엔트로피 부족으로 미탐지 → **랜덤 영숫자** 가짜 키여야 탐지됨(예: `ghp_` + 무작위 36자, `sk_live_` + 무작위 24자).
  - **작업트리 스캔은 `--no-git`**: 기본 `gitleaks detect`는 git 커밋 이력만 스캔. 미커밋/작업트리 파일을 잡으려면 `detect --no-git`.
  - AWS 예제키 `AKIAIOSFODNN7EXAMPLE`는 gitleaks 기본 allowlist(문서 예제)라 영원히 미탐지 → 테스트 패턴으로 쓰지 말 것.
