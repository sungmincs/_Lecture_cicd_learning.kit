# 9.7 CD 강화 - prod 수동 승인 게이트

> **학습자 진입 방식**:
> - `[학습자 직접]`: 워크플로 켜기, `kubectl apply`, 태그 push, OutOfSync 확인, 수동 sync
> - `[학습자 직접 · 웹]`: Actions 실행 확인, Argo CD UI에서 차이 보기
> - `[AI 프롬프트]`: prod Argo CD Application에서 자동 sync 비활성화

## 사전 조건

- ch8 완료 (dev/staging/prod Argo CD Application 3개가 자동 sync 중)
- ch9/9.6 완료 (Dockerfile을 고쳐 Trivy를 통과한 상태, GitHub `ci.yaml`은 꺼져 있음)

## 실행 지침

### 단계 0: 이 절은 GitHub 워크플로로 한다 `[학습자 직접]`

태그를 push하면 바로 도는 쪽이 보기 쉬워 GitHub `ci.yaml`을 다시 켠다. 이 절에서는 Jenkins를 스캔하지 않는다.

```bash
gh workflow enable ci.yaml -R <github_username>/worklog-backend
mkdir -p /root/ch9
```

### 단계 1: prod Application의 지금 상태 확인 `[학습자 직접]`

```bash
argocd app get worklog-backend-prod | grep -E "Sync Policy|Sync Status"      # Sync Policy: Automated (Prune)
```

### 단계 2: prod Application yaml 수정 `[AI 프롬프트]`

> "prod 환경 Argo CD Application의 자동 sync를 꺼서 수동 승인이 필요하게 만든 yaml을 컨트롤 플레인 노드의 `/root/ch9/1.argocd-prod-manual.yaml`로 저장해줘. `/root/ch8/2.argocd-apps-multi-env.yaml`의 prod 부분을 바탕으로 하고, 적용은 내가 할게.
> - Application 이름: `worklog-backend-prod`, destination namespace: prod, targetRevision: main
> - 저장소: `https://github.com/<github_username>/worklog-backend.git`
> - 자동 sync 제거: `syncPolicy`에서 `automated`를 뺀다
> - dev, staging Application은 넣지 마"

✅ 정답 파일 (완성 후 비교): `ch9/9.7/1.argocd-prod-manual.yaml`

핵심 차이:
```yaml
# 자동 sync (ch8 방식)
syncPolicy:
  automated:
    prune: true
    selfHeal: true

# 수동 승인 (ch9 방식)
syncPolicy: {}  # 자동 sync 비활성화
```

### 단계 3: yaml 적용 `[학습자 직접]`

```bash
cd /root/ch9
kubectl apply -f 1.argocd-prod-manual.yaml
argocd app get worklog-backend-prod | grep "Sync Policy"      # Manual
```

### 단계 4: 새 버전 태그 push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git checkout main && git pull --rebase
git tag v1.4.0
git push origin v1.4.0
```

### 단계 4-1: 태그 실행 확인 `[학습자 직접 · 웹]`

Actions 탭에서 v1.4.0 실행이 scan을 통과하고 deploy까지 성공하는지 본다. deploy가 main의 매니페스트를 `v1.4.0`으로 고친다.

### 단계 5: prod가 기다리는지 확인 `[학습자 직접]`

```bash
argocd app get worklog-backend-prod --refresh | grep -E "Sync Policy|Sync Status"      # OutOfSync
kubectl get deploy worklog-backend -n prod -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # 아직 이전 태그
argocd app diff worklog-backend-prod      # Git과 클러스터의 차이. image와 IMAGE_TAG 두 줄
```

매니페스트는 바뀌었는데 prod는 그대로다. 사람이 승인할 때까지 기다린다. Argo CD UI의 `worklog-backend-prod` 화면에서도 같은 차이를 APP DIFF로 볼 수 있다.

같은 main을 보는 6.5의 `worklog-backend`(default)는 자동 sync라 기다리지 않고 `v1.4.0`으로 바뀐다(Argo CD가 Git을 확인하는 주기 때문에 몇 분 걸릴 수 있다). `kubectl get deploy worklog-backend -n default -o jsonpath='{.spec.template.spec.containers[0].image}'`로 본다. 자동과 수동의 차이를 나란히 볼 수 있다.

### 단계 6: 수동 sync(승인) `[학습자 직접]`

```bash
argocd app sync worklog-backend-prod
kubectl get deploy worklog-backend -n prod -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # v1.4.0
```

Argo CD UI에서는 `worklog-backend-prod`의 SYNC 버튼이 같은 일을 한다.

### 단계 7: 수동 승인 게이트의 의미 이해 `[AI 프롬프트]`

> "Argo CD에서 prod 환경에 수동 승인 게이트를 두는 이유와, 실무에서 어떤 승인 흐름(예: Slack 알림 + 버튼 클릭)과 연동할 수 있는지 설명해줘."

## 주의사항

- ⛔ AI가 하지 말 것: `kubectl apply`, 태그 push, `argocd app sync`를 대신 하지 말 것. 승인을 사람이 하는 것이 이 절의 내용이다
- ⛔ AI가 하지 말 것: yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch9/`에 둔다
- ⛔ AI가 하지 말 것: `syncPolicy: automated`를 그대로 두면서 수동 승인을 구현하려 하지 말 것
- ⛔ AI가 하지 말 것: dev/staging Application에도 수동 승인을 적용하지 말 것 (prod만 적용)
- ✅ AI가 해도 됨: Application yaml 작성
- ✅ AI가 해도 됨: `syncPolicy: {}` vs `syncPolicy` 삭제의 차이 설명
- ✅ AI가 해도 됨: Argo CD UI에서 수동 sync 방법 안내
- ✅ AI가 해도 됨: argocd CLI로 sync 명령 안내
- ⚠️ `kubectl apply` 후 Argo CD UI에서 Application이 "OutOfSync" 상태로 바뀌는 데 최대 3분 소요 (polling 주기)
- ⚠️ 수동 sync 전에 Argo CD UI에서 diff를 반드시 확인하는 습관 강조
- ⚠️ deploy_manifest를 **수동으로 직접 편집**해 버전을 올릴 때는 `image:` 라인과 `IMAGE_TAG` env 값을 **둘 다** 바꿔야 한다.
  하나만 바꾸면 새 ReplicaSet은 생기지만 이미지가 그대로이거나 /health의 imageTag만 어긋난다.
  (GitHub와 Jenkins 정답의 sed는 둘 다 치환한다. Jenkins 정답은 2026-10-08 전에는 `image:`만 바꿨으므로, 그 전 정답으로 배포한 매니페스트는 IMAGE_TAG가 어긋나 있을 수 있다)
