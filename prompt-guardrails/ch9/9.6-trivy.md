# 9.6 CD 강화 - 이미지 취약점 스캔 (Trivy)

> **학습자 진입 방식**:
> - `[학습자 직접 · 웹]`: GitHub Actions와 Jenkins의 실행 결과 확인
> - `[AI 프롬프트]`: 이미지 빌드 뒤 Trivy로 스캔하는 단계 추가, push, Dockerfile 수정과 push, 워크플로 끄기(프롬프트는 학습자가 처음부터 작성)
>
> 이 절부터 GitHub `ci.yaml`이 이미지를 빌드하고 매니페스트까지 고친다. Jenkins도 같은 매니페스트를 고치므로 둘을 함께 돌리지 않는다.
> GitHub로 먼저 끝까지 하고(단계 1~6), `ci.yaml`을 끈 뒤(단계 7) Jenkins로 한다(단계 8~10).

요청과 계획 검토 방식은 8.3의 "8장부터 짧게 요청하고 계획을 검토한다"와 같다.

## 사전 조건

- ch9/9.5 완료 (lint, security, coverage 게이트가 든 파이프라인이 통과하는 상태)
- 8.3/8.4의 `multi-env.yaml` 워크플로가 꺼져 있음 (8.5 단계 1). 이 절의 `ci.yaml`이 그것을 대신한다

## 실행 지침

### 단계 1: GitHub 워크플로에 build, scan, deploy `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
ci.yaml을 multi-env.yaml(8.4)과 합쳐 빌드한 이미지를 Trivy로 검사하게 해줘. 취약한 이미지가 배포되지 않게 하려는 거야. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/.github/workflows/ci.yaml
- determine-environment, build, deploy job은 multi-env.yaml에서 가져오고(그 파일은 그대로 둬) 트리거에 v* 태그를 더해
- 순서: lint → security-scan → test → build → scan → deploy
- scan job: aquasecurity/trivy-action@v0.36.0, Trivy v0.75.0, build가 push한 이미지를 검사
- CRITICAL, HIGH만, ignore-unfixed, 찾으면 실패(exit-code: '1')
- 끝나면: yaml 문법을 검사하고 바뀐 부분을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| build → scan → deploy 순서 | 검사 전에 취약한 이미지가 배포됨 |
| 찾으면 실패(exit-code: 1) | 결과만 보여 주고 통과 |
| trivy-action v0.36.0, Trivy v0.75.0 | 실행할 때마다 다른 버전 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch9/9.6/1.trivy-github.yaml`

### 단계 2: push `[AI 프롬프트]`

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
ci.yaml을 커밋하고 push해줘. 커밋 메시지는 cd: add trivy image vulnerability scan gate, push 전에 git pull --rebase 해줘.
```

- push 전에 git pull --rebase

### 단계 3: Trivy 스캔 결과 확인 `[학습자 직접 · 웹]`

Actions 탭에서 scan job의 결과 표를 본다. 이 단계에서는 Jenkins를 스캔하지 않는다.

Python 이미지에서는 CRITICAL이나 HIGH가 나올 수 있다. 나오면 scan job이 실패하고 deploy는 건너뛴다. 게이트가 동작한 것이다. 건수는 시점마다 다르다(2026-10-08에는 HIGH 4건). 하나도 안 나와 통과했으면 단계 4와 5는 읽기만 하고 단계 7로 간다.

### 단계 4: 취약점 대응 방법 이해 `[AI 프롬프트]`

짧은 질문이라 직접 친다.

```text
Trivy에서 이미지에 CRITICAL이나 HIGH 취약점이 발견됐어. 어떻게 해결할 수 있어?
```

AI가 제안하는 방법(Trivy 출력의 Target과 패키지 경로로 가른다):
1. OS 패키지(debian) → Dockerfile에 `apt-get upgrade`
2. 앱 의존성(`site-packages`의 앱 패키지) → `uv lock --upgrade-package`
3. 베이스 이미지의 pip, setuptools와 그 `_vendor` → 런타임 단계에서 `pip install` 뒤에 pip를 지운다(단계 5)
4. 학습 목적이면 `.trivyignore`나 severity 조정. 이 절의 목표(수정 → 통과)에는 사용하지 않는다

1, 2, 3은 잡는 대상이 다르다. `apt-get upgrade`는 OS 패키지만, 락파일 갱신은 앱 의존성만 해결한다. 베이스 이미지 pip가 담아 둔 vendored 패키지(`pip/_vendor`)는 둘 다로 사라지지 않는다. run-38(2026-10-08)에서 탐지된 4건(msgpack, setuptools, urllib3 2건)은 모두 3번이었다. `pip install --upgrade pip setuptools`는 효과가 없었고 pip를 지우면 0건이 됐다.

### 단계 5: Dockerfile 고치고 push `[AI 프롬프트]`

scan job 로그의 결과 표(Library와 버전이 나온 표 전체)를 프롬프트 끝에 붙여 넣는다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
Trivy가 찾은 패키지를 보고 Dockerfile을 수정해 push해줘. scan 게이트를 통과하려는 거야. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/Dockerfile
- 결과 표의 Library와 Installed Version으로 출처를 판단해. uv.lock의 버전과 다르면 베이스 이미지 pip가 담아 둔 사본(pip/_vendor)이야.
- 앱 실행에 필요 없는 것이면 지우는 쪽으로 고쳐
- 노드에서 이미지를 빌드하지 마. 앱 소스와 의존성 목록, .trivyignore, severity는 건드리지 마.
- 커밋 메시지는 fix: remove pip (trivy), push 전에 git pull --rebase
- 끝나면: Dockerfile의 바뀐 부분과 push 결과를 보여줘.
- (여기에 scan job 로그의 결과 표를 붙여 넣는다)

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| 필요 없는 패키지는 Dockerfile에서 삭제 | 앱 소스나 의존성까지 바뀜 |
| 노드에서 이미지를 빌드하지 않음 | 빌드와 스캔으로 시간이 오래 소요 |
| .trivyignore로 숨기지 않음 | 취약점을 그대로 둔 채 통과 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

결과 표는 `Total:` 줄만이 아니라 Library와 버전이 나온 표 전체를 붙인다. Trivy의 표에는 패키지가 이미지의 어느 경로에 있는지가 나오지 않는다. 그래서 표만 붙이면 AI가 출처를 확인하려고 노드에서 이미지를 직접 빌드한다(run-41에서 표를 통째로 붙였는데도 그랬고 1분쯤 걸렸다. 표가 없던 run-40에서는 스캔까지 해서 4분 넘게 걸렸다). 조건 ①이 그 단서를 주고 조건 ②가 빌드를 막는다. 그래도 빌드했다면 노드에 남은 이미지와 캐시를 3.8 단계 7의 명령으로 치운다.

✅ 정답(2026-10-08 기준, 3번일 때): `RUN pip uninstall -y pip setuptools && rm -rf /usr/local/lib/python3.14/ensurepip`를 `pip install` 다음 줄에 추가. 앱은 실행할 때 pip가 필요 없다. AI가 `pip uninstall -y pip`만 `pip install`과 같은 `RUN`에 붙여도 된다(run-41에서 그렇게 고쳐 4건이 모두 사라졌다).

## 주의사항

- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: Jenkins 스캔을 대신 하지 말 것. 단계 2, 5, 7, 9의 요청이 없을 때 커밋, push, 워크플로 끄기를 하지 말 것
- ⛔ AI가 하지 말 것: `trivy-action@master`나 `main` 브랜치의 설치 스크립트처럼 버전이 고정되지 않은 것을 쓰지 말 것
- ⛔ AI가 하지 말 것: Trivy scan job에서 `exit-code: '0'`으로 설정하지 말 것 (게이트 의미 없어짐)
- ⛔ AI가 하지 말 것: scan이 deploy보다 나중에 실행되도록 순서 설정하지 말 것
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: Dockerfile base 이미지 업그레이드 제안
- ✅ AI가 해도 됨: 취약점 무시(`.trivyignore`)나 severity 조정이 무엇인지 설명. 다만 이 절의 파일에 적용해서 통과시키지는 않는다(단계 5)
- ⚠️ Trivy는 액션(`aquasecurity/trivy-action@v0.36.0`)과 본체(`v0.75.0`) 버전을 고정한다. 취약점 DB는 실행할 때마다 최신을 받는다. 그래서 같은 이미지도 날짜에 따라 결과가 달라진다
- ⚠️ 실제 이미지 취약점 발견은 강의 시연 포인트로 활용 가능: "AI가 생성한 코드도 이미지 수준 취약점은 못 막는다"
- ⚠️ 배포까지 하는 워크플로는 하나만 켠다. 이 절의 `ci.yaml`이 8.3/8.4의 `multi-env.yaml`을 대신하므로 `multi-env.yaml`은 꺼 둔 채로 둔다(사전 조건). 둘 다 켜면 같은 push에 둘이 `deploy_manifest/`를 고쳐 rebase 충돌이 난다
- ⚠️ 9.6부터 GitHub `ci.yaml`에 deploy가 붙어 Jenkins와 같은 main 매니페스트를 고친다. Jenkins로 실습하는 동안 `ci.yaml`을 끄고, GitHub로 실습하는 동안 Jenkins 스캔을 누르지 않는다. 9.7, 9.8도 같다(`prompt-guardrails/shared/one-pipeline.md`).
- ⚠️ Jenkinsfile의 비밀값(`*_PSW`, `ARGOCD_ADMIN_PASSWORD`)은 `sh """` 안에서 `\$변수`로 넘긴다. `${...}`로 쓰면 Groovy가 값을 먼저 풀어 Console Output에 `Groovy String interpolation` 경고가 남는다(6.8 "검증 중 발견된 이슈")

    2. Trivy에 `--ignore-unfixed` 플래그 추가 → fix 없는 CVE(zlib1g CVE-2023-45853 등) 무시
  - 결과: 전체 파이프라인 통과 (lint→security→test→build→scan→deploy ✅)
