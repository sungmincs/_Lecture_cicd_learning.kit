### 단계 3: 취약점 발견 시 대응 방법 이해 `[AI 프롬프트]`

Trivy에서 CRITICAL/HIGH 취약점이 발견된 경우:

> "Trivy에서 이미지에 CRITICAL 취약점이 발견됐어. 어떻게 해결할 수 있어?"

AI가 제안하는 방법(Trivy 출력의 Target과 패키지 경로로 가른다):
1. OS 패키지(debian) → Dockerfile에 `apt-get upgrade`
2. 앱 의존성(`site-packages`의 앱 패키지) → `uv lock --upgrade-package`
3. 베이스 이미지의 pip, setuptools와 그 `_vendor` → 런타임 단계에서 `pip install` 뒤에 pip를 지운다(아래 단계 4)
4. 학습 목적이면 `.trivyignore`나 severity 조정. 이 절의 목표(수정 → 통과)에는 쓰지 않는다

> ⚠️ **1, 2, 3은 잡는 대상이 다르다.** Dockerfile의 `apt-get upgrade`는 **OS 패키지만**
> 해결하고, 락파일 갱신은 앱 의존성만 해결한다. 베이스 이미지 pip가 담아 둔
> vendored 패키지(`pip/_vendor`)는 둘 다로 사라지지 않는다. 수정 버전이 이미 나와
> 있으면 `--ignore-unfixed`로도 걸러지지 않는다. Trivy 출력의 패키지 경로를 보고 어느 쪽인지 가른다.
> run-38(2026-10-08) 실측으로 걸린 4건(msgpack, setuptools, urllib3 2건)은 모두 3번이다.
> `pip install --upgrade pip setuptools`는 효과가 없다(pip 26.2.1이 이미 최신이라 `_vendor`가 그대로). pip를 지우면 0건이 된다.

### 단계 4: 수정하고 다시 push해 통과 확인 `[AI 프롬프트]` + `[학습자 직접]`

> "Trivy 출력에서 걸린 패키지의 경로(Target, Library)를 보고, 그 패키지가 어디서 온 것인지 판단해서 Dockerfile을 고쳐줘. 앱 실행에 필요 없는 것이면 지우는 쪽으로."

AI가 고칠 때의 범위:
- 바꾸는 파일은 worklog-backend `Dockerfile` 하나다. 앱 소스와 의존성 목록은 건드리지 않는다.
- 걸린 것이 베이스 이미지 pip의 `_vendor`(단계 3의 3번)면, 런타임 단계 `pip install` 다음에 pip와 setuptools를 지우는 줄을 더하는 것이 맞다. 앱은 실행할 때 pip가 필요 없다.
- 앱 라이브러리(2번)면 `uv lock --upgrade-package`로 락파일을 올리고 다시 빌드한다. OS 패키지(1번)면 베이스 이미지 태그를 올린다.
- `.trivyignore`나 severity 완화로 통과시키지 않는다.

✅ 정답(2026-10-08 기준, 3번일 때): `RUN pip uninstall -y pip setuptools && rm -rf /usr/local/lib/python3.14/ensurepip`를 `pip install` 다음 줄에 추가.

```bash
git add Dockerfile
git commit -m "fix: remove pip from runtime image (trivy)"
git push
```

기대 결과: scan 단계 통과(Total 0) → deploy(매니페스트 갱신)까지 진행. 차단 → 원인 확인 → 수정 → 통과를 한 번에 겪는다.

> run-38(2026-10-08) 검증: GitHub(scan success, deploy success)와 Jenkins(#25 SUCCESS) 모두 통과. pip를 지운 이미지도
> `/health`가 OK이고 크기는 원래와 같다(347MB).

## 주의사항

- ⛔ AI가 하지 말 것: Trivy scan job에서 `exit-code: '0'`으로 설정하지 말 것 (게이트 의미 없어짐)
- ⛔ AI가 하지 말 것: scan이 deploy보다 나중에 실행되도록 순서 설정하지 말 것
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: Dockerfile base 이미지 업그레이드 제안
- ✅ AI가 해도 됨: 취약점 무시(ignore) 설정 방법 안내 (`.trivyignore` 등)
- ✅ AI가 해도 됨: severity 레벨 조정 (강의 목적으로 CRITICAL만 검사하도록 변경)
- ⚠️ GitHub Actions에서는 `aquasecurity/trivy-action@master` 사용 (Jenkins는 trivy 바이너리 직접 설치)
- ⚠️ 실제 이미지 취약점 발견은 강의 시연 포인트로 활용 가능: "AI가 생성한 코드도 이미지 수준 취약점은 못 막는다"
- ⚠️ **다중 deploy 워크플로우 동시 실행 금지**: ch9.6 Trivy 워크플로우 추가 시 기존 ch8.3 멀티환경(`1.multi-env-pipeline.yaml`)·ch8.4 Full CI/CD(`1.full-cicd-workflow.yaml`) 등 deploy 단계 포함 워크플로우를 **비활성화**하지 않으면 동시 실행 시 `deploy_manifest/` rebase 충돌 발생. Settings → Actions → Disable 처리 필요. 8.4 워크플로는 이 파일이 대신하므로 끈다.
- ⚠️ 9.6부터 GitHub `ci.yaml`에 deploy가 붙어 Jenkins와 같은 main 매니페스트를 고친다. Jenkins로 실습하는 동안 `ci.yaml`을 끄고, GitHub로 실습하는 동안 Jenkins 스캔을 누르지 않는다. 9.7, 9.8도 같다(`prompt-guardrails/shared/one-pipeline.md`).

## 검증 중 발견된 이슈 (강의자 참고)

- **(2026-06 기록) 당시는 OS CVE가 주였다.** **Python 이미지 CRITICAL/HIGH 취약점 발견**: `python:3.14-slim-bookworm` 기반 이미지에서 Trivy가 19개 CVE(CRITICAL:6, HIGH:13) 탐지 → 파이프라인 차단. 강의 시연 포인트.
