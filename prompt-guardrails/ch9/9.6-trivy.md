## 실행 지침

### 단계 1: 파이프라인에 Trivy 스캔 단계 추가 `[AI 프롬프트]`

사용하는 CI 플랫폼에 맞게 아래 프롬프트를 사용한다.

**GitHub Actions:**

> "Docker 이미지 빌드 후 Trivy로 취약점 스캔하는 단계를 파이프라인에 추가해줘.
> - build job 완료 후 scan job 실행 (`needs: [build]`)
> - `aquasecurity/trivy-action@master` 사용
> - CRITICAL, HIGH severity만 검사
> - 취약점 발견 시 파이프라인 실패 (`exit-code: '1'`)
> - Docker Hub username: `<dockerhub_username>`"

✅ 정답 파일 (완성 후 비교): `ch9/9.6/1.trivy-github.yaml`

**Jenkins:**

> "기존 Jenkinsfile에 Trivy 이미지 스캔 stage를 Build Image 다음에 추가해줘.
> - curl로 trivy 설치: `curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -s -- -b /usr/local/bin`
> - `trivy image --exit-code 1 --severity CRITICAL,HIGH --format table \${DOCKER_REPOSITORY}:\${IMAGE_TAG}`
> - 취약점 발견 시 파이프라인 실패"

✅ 정답 파일: `ch9/9.6/2.trivy-jenkins.groovy`

**GitLab CI:**

> "기존 .gitlab-ci.yml에 scan stage와 trivy job을 build 다음에 추가해줘.
> - image: `aquasec/trivy:latest`
> - `trivy image --exit-code 1 --severity CRITICAL,HIGH --format table \$DOCKER_REPOSITORY:\$SHORT_SHA`
> - deploy job이 trivy job 완료 후 실행되도록"

✅ 정답 파일: `ch9/9.6/3.trivy-gitlab.yml`

### 단계 2: git push + Trivy 스캔 결과 확인 `[학습자 직접]`

```bash
git add .github/workflows/  # 또는 Jenkinsfile / .gitlab-ci.yml
git commit -m "cd: add trivy image vulnerability scan gate"
git push
```

파이프라인 UI에서 Trivy 스캔 결과 테이블 확인.

> ⚠️ Python 기반 Docker 이미지는 실제 CRITICAL/HIGH 취약점이 발견될 수 있다.  
> 이것은 Trivy가 정상 동작하는 것이다. 취약점 발견 = 파이프라인 실패는 의도된 동작.

### 단계 3: 취약점 발견 시 대응 방법 이해 `[AI 프롬프트]`

Trivy에서 CRITICAL/HIGH 취약점이 발견된 경우:

> "Trivy에서 이미지에 CRITICAL 취약점이 발견됐어. 어떻게 해결할 수 있어?"

AI가 제안하는 방법:
1. Dockerfile의 base 이미지를 최신 버전으로 업그레이드
2. 취약한 라이브러리를 pyproject.toml에서 버전 고정
3. 학습 목적으로 일시적으로 severity 레벨을 `CRITICAL`만으로 조정

> ⚠️ **1과 2는 잡는 대상이 다르다.** Dockerfile의 `apt-get upgrade`는 **OS 패키지만**
> 해결한다. Python 라이브러리 취약점은 그대로 남아 게이트가 계속 막힌다.
> 그때는 `pyproject.toml`의 해당 의존성에 안전 버전 하한을 주고 `uv lock`으로
> 락파일을 갱신해야 한다. Trivy 출력의 패키지 이름을 보고 어느 쪽인지 가른다.

## 검증 중 발견된 이슈 (강의자 참고) — ch9.6 추가분

- **GitHub Actions BRANCH 버그**: `1.trivy-github.yaml`의 deploy job에서 `grep -v "^$"` 방식은 태그 빌드 시 여전히 `refs/tags/v1.0.0`을 반환. if/elif 분기 방식으로 수정됨.
- **GitLab CI `workflow.rules` [skip ci] 순서 버그**: 마지막 규칙은 무효. 첫 번째 규칙으로 이동.
- **GitLab CI docker:27-cli → docker:24**: `docker:24` + `docker:24-dind`, DinD TLS 비활성화 job 레벨 통일.
- **GITLAB_TOKEN**: GitLab CI deploy_manifest push 시 `GITLAB_TOKEN`/`gitlab.com` 사용.

## 주의사항

- ⛔ AI가 하지 말 것: Trivy scan job에서 `exit-code: '0'`으로 설정하지 말 것 (게이트 의미 없어짐)
- ⛔ AI가 하지 말 것: scan이 deploy보다 나중에 실행되도록 순서 설정하지 말 것
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: Dockerfile base 이미지 업그레이드 제안
- ✅ AI가 해도 됨: 취약점 무시(ignore) 설정 방법 안내 (`.trivyignore` 등)
- ✅ AI가 해도 됨: severity 레벨 조정 (강의 목적으로 CRITICAL만 검사하도록 변경)
- ⚠️ GitHub Actions에서는 `aquasecurity/trivy-action@master` 사용 (Jenkins/GitLab은 trivy 바이너리 직접 설치)
- ⚠️ 실제 이미지 취약점 발견은 강의 시연 포인트로 활용 가능: "AI가 생성한 코드도 이미지 수준 취약점은 못 막는다"
- ⚠️ **다중 deploy 워크플로우 동시 실행 금지**: ch9.6 Trivy 워크플로우 추가 시 기존 ch8.3 멀티환경(`1.multi-env-pipeline.yaml`)·ch8.4 Full CI/CD(`1.full-cicd-workflow.yaml`) 등 deploy 단계 포함 워크플로우를 **비활성화**하지 않으면 동시 실행 시 `deploy_manifest/` rebase 충돌 발생. Settings → Actions → Disable 처리 필요.

## 검증 중 발견된 이슈 (강의자 참고)

- **Python 이미지 CRITICAL/HIGH 취약점 발견**: `python:3.14-slim-bookworm` 기반 이미지에서 Trivy가 19개 CVE(CRITICAL:6, HIGH:13) 탐지 → 파이프라인 차단. 강의 시연 포인트.
  - ℹ️ **수치는 스캔 시점에 따라 다름**: CVE DB가 계속 갱신되고 베이스 이미지도 시간이 지나며 취약점이 누적되므로, 탐지 건수·등급은 시점마다 변한다(예: 이후 검증에선 54건 CRITICAL:11/HIGH:43). 정확한 숫자가 아니라 "취약점이 발견되어 게이트가 차단된다"는 구조에 주목.
  - 증상: Trivy scan job 실패, deploy job 스킵
  - 해결 (검증 완료):
    1. `Dockerfile`에 `RUN apt-get update && apt-get upgrade -y && rm -rf /var/lib/apt/lists/*` 추가 → fix 가능한 CVE(libgnutls30, libgssapi-krb5-2) 해결
    2. Trivy에 `--ignore-unfixed` 플래그 추가 → fix 없는 CVE(zlib1g CVE-2023-45853 등) 무시
  - 결과: 전체 파이프라인 통과 (lint→security→test→build→scan→deploy ✅)

- **다중 워크플로우 동시 deploy 충돌**: `ci(ch9.6)` 커밋이 Full CI/CD + Multi-Environment Deploy + CI/CD with Trivy Scan 3개 워크플로우를 동시 트리거 → 각 워크플로우가 `deploy_manifest/` 업데이트 커밋 경쟁 → rebase 충돌
  - 증상: `error: could not apply ... deploy: update image tag` + `CONFLICT (content): Merge conflict in deploy_manifest/worklog-backend.yaml`
  - 해결: 기존 deploy 포함 워크플로우를 GitHub Settings → Actions에서 비활성화 후 신규 워크플로우 사용
