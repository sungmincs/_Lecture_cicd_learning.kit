# 9.6 CD 강화 - 이미지 취약점 스캔 (Trivy)

> **학습자 진입 방식**:
> - `[학습자 직접]`: git push, 워크플로 끄기
> - `[학습자 직접 · 웹]`: GitHub Actions와 Jenkins의 실행 결과 확인
> - `[AI 프롬프트]`: 이미지 빌드 뒤 Trivy로 스캔하는 단계 추가, Dockerfile 수정
>
> 이 절부터 GitHub `ci.yaml`이 이미지를 빌드하고 매니페스트까지 고친다. Jenkins도 같은 매니페스트를 고치므로 둘을 함께 돌리지 않는다.
> GitHub로 먼저 끝까지 하고(단계 1~4), `ci.yaml`을 끈 뒤(단계 5) Jenkins로 한다(단계 6~7).

### 단계 2-1: Trivy 스캔 결과 확인 `[학습자 직접 · 웹]`

Actions 탭에서 scan job의 결과 표를 본다. 이 단계에서는 Jenkins를 스캔하지 않는다.

Python 이미지에서는 CRITICAL이나 HIGH가 나올 수 있다. 나오면 scan job이 실패하고 deploy는 건너뛴다. 게이트가 동작한 것이다. 건수는 시점마다 다르다(2026-10-08에는 HIGH 4건). 하나도 안 나와 통과했으면 단계 3과 4는 읽기만 하고 단계 5로 간다.

### 단계 3: 취약점 대응 방법 이해 `[AI 프롬프트]`

> "Trivy에서 이미지에 CRITICAL이나 HIGH 취약점이 발견됐어. 어떻게 해결할 수 있어?"

AI가 제안하는 방법(Trivy 출력의 Target과 패키지 경로로 가른다):
1. OS 패키지(debian) → Dockerfile에 `apt-get upgrade`
2. 앱 의존성(`site-packages`의 앱 패키지) → `uv lock --upgrade-package`
3. 베이스 이미지의 pip, setuptools와 그 `_vendor` → 런타임 단계에서 `pip install` 뒤에 pip를 지운다(단계 4)
4. 학습 목적이면 `.trivyignore`나 severity 조정. 이 절의 목표(수정 → 통과)에는 쓰지 않는다

1, 2, 3은 잡는 대상이 다르다. `apt-get upgrade`는 OS 패키지만, 락파일 갱신은 앱 의존성만 해결한다. 베이스 이미지 pip가 담아 둔 vendored 패키지(`pip/_vendor`)는 둘 다로 사라지지 않는다. run-38(2026-10-08)에서 걸린 4건(msgpack, setuptools, urllib3 2건)은 모두 3번이었다. `pip install --upgrade pip setuptools`는 효과가 없었고 pip를 지우면 0건이 됐다.

### 단계 4: Dockerfile 고치기 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Dockerfile`을 고쳐줘. Trivy 출력에서 걸린 패키지(Library, Installed Version)를 보고 그 패키지가 어디서 온 것인지 판단해서, 앱 실행에 필요 없는 것이면 지우는 쪽으로. 표의 버전이 `uv.lock`에 있는 버전과 다르면 앱 의존성이 아니라 베이스 이미지의 pip가 안에 담아 둔 사본(`pip/_vendor`)이야. 원인을 찾으려고 노드에서 이미지를 빌드하지는 마. 앱 소스와 의존성 목록은 건드리지 말고 `.trivyignore`나 severity 완화로 통과시키지도 마. 커밋과 push는 내가 할게.
> (여기에 scan job 로그의 결과 표를 붙여 넣는다)"

결과 표는 `Total:` 줄만이 아니라 Library와 버전이 나온 표 전체를 붙인다. Trivy의 표에는 패키지가 이미지의 어느 경로에 있는지가 나오지 않는다. 그래서 표만 붙이면 AI가 출처를 확인하려고 노드에서 이미지를 직접 빌드한다(run-41에서 표를 통째로 붙였는데도 그랬고 1분쯤 걸렸다. 표가 없던 run-40에서는 스캔까지 해서 4분 넘게 걸렸다). 프롬프트의 뒤 두 문장이 그 단서를 주고 빌드를 막는다. 그래도 빌드했다면 노드에 남은 이미지와 캐시를 3.8 단계 7의 명령으로 치운다.

✅ 정답(2026-10-08 기준, 3번일 때): `RUN pip uninstall -y pip setuptools && rm -rf /usr/local/lib/python3.14/ensurepip`를 `pip install` 다음 줄에 추가. 앱은 실행할 때 pip가 필요 없다. AI가 `pip uninstall -y pip`만 `pip install`과 같은 `RUN`에 붙여도 된다(run-41에서 그렇게 고쳐 4건이 모두 사라졌다).

## 주의사항

- ⛔ AI가 하지 말 것: git push, 워크플로 끄기, Jenkins 스캔을 대신 하지 말 것
- ⛔ AI가 하지 말 것: `trivy-action@master`나 `main` 브랜치의 설치 스크립트처럼 버전이 고정되지 않은 것을 쓰지 말 것
- ⛔ AI가 하지 말 것: Trivy scan job에서 `exit-code: '0'`으로 설정하지 말 것 (게이트 의미 없어짐)
- ⛔ AI가 하지 말 것: scan이 deploy보다 나중에 실행되도록 순서 설정하지 말 것
- ✅ AI가 해도 됨: 파이프라인 yaml/groovy 작성
- ✅ AI가 해도 됨: Dockerfile base 이미지 업그레이드 제안
- ✅ AI가 해도 됨: 취약점 무시(`.trivyignore`)나 severity 조정이 무엇인지 설명. 다만 이 절의 파일에 적용해서 통과시키지는 않는다(단계 4)
- ⚠️ Trivy는 액션(`aquasecurity/trivy-action@v0.36.0`)과 본체(`v0.75.0`) 버전을 고정한다. 취약점 DB는 실행할 때마다 최신을 받는다. 그래서 같은 이미지도 날짜에 따라 결과가 달라진다
- ⚠️ 실제 이미지 취약점 발견은 강의 시연 포인트로 활용 가능: "AI가 생성한 코드도 이미지 수준 취약점은 못 막는다"
- ⚠️ 배포까지 하는 워크플로는 하나만 켠다. 이 절의 `ci.yaml`이 8.3/8.4의 `multi-env.yaml`을 대신하므로 `multi-env.yaml`은 꺼 둔 채로 둔다(사전 조건). 둘 다 켜면 같은 push에 둘이 `deploy_manifest/`를 고쳐 rebase 충돌이 난다
- ⚠️ 9.6부터 GitHub `ci.yaml`에 deploy가 붙어 Jenkins와 같은 main 매니페스트를 고친다. Jenkins로 실습하는 동안 `ci.yaml`을 끄고, GitHub로 실습하는 동안 Jenkins 스캔을 누르지 않는다. 9.7, 9.8도 같다(`prompt-guardrails/shared/one-pipeline.md`).

## 검증 중 발견된 이슈 (강의자 참고)

- **(2026-06 기록) 당시는 OS CVE가 주였다.** **Python 이미지 CRITICAL/HIGH 취약점 발견**: `python:3.14-slim-bookworm` 기반 이미지에서 Trivy가 19개 CVE(CRITICAL:6, HIGH:13) 탐지 → 파이프라인 차단. 강의 시연 포인트.
  - ℹ️ **수치는 스캔 시점에 따라 다름**: CVE DB가 계속 갱신되고 베이스 이미지도 시간이 지나며 취약점이 누적되므로, 탐지 건수·등급은 시점마다 변한다(예: 이후 검증에선 54건 CRITICAL:11/HIGH:43). 정확한 숫자가 아니라 "취약점이 발견되어 게이트가 차단된다"는 구조에 주목.
  - 증상: Trivy scan job 실패, deploy job 스킵
  - 해결 (검증 완료):
    1. `Dockerfile`에 `RUN apt-get update && apt-get upgrade -y && rm -rf /var/lib/apt/lists/*` 추가 → fix 가능한 CVE(libgnutls30, libgssapi-krb5-2) 해결
    2. Trivy에 `--ignore-unfixed` 플래그 추가 → fix 없는 CVE(zlib1g CVE-2023-45853 등) 무시
  - 결과: 전체 파이프라인 통과 (lint→security→test→build→scan→deploy ✅)
  - 2026-10-08 실측(run-38): debian 0건, Python 4건(HIGH). 걸린 것은 베이스 이미지 pip의 `_vendor` urllib3, msgpack과 setuptools다. apt-get upgrade와 `--ignore-unfixed`로는 통과하지 않는다. GitHub scan job, Jenkins Scan stage 모두 실패하고 deploy, Update Manifest는 건너뛰었다.

- **다중 워크플로우 동시 deploy 충돌**: `ci(ch9.6)` 커밋이 Full CI/CD + Multi-Environment Deploy + CI/CD with Trivy Scan 3개 워크플로우를 동시 트리거 → 각 워크플로우가 `deploy_manifest/` 업데이트 커밋 경쟁 → rebase 충돌
  - 증상: `error: could not apply ... deploy: update image tag` + `CONFLICT (content): Merge conflict in deploy_manifest/worklog-backend.yaml`
  - 해결: 기존 deploy 포함 워크플로우를 GitHub Settings → Actions에서 비활성화 후 신규 워크플로우 사용
