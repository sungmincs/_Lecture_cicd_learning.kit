# 9.3 CI 강화 - Lint (ruff)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 워크플로 상태 확인, git push, 실패하는 커밋 올리기와 되돌리기
> - `[학습자 직접 · 웹]`: GitHub Actions와 Jenkins의 실행 결과 확인
> - `[AI 프롬프트]`: ruff 설정 파일, GitHub 워크플로와 Jenkinsfile에 lint 단계 추가, 실패용 코드 작성
>
> 9장은 한 절 안에서 GitHub Actions와 Jenkins를 함께 고친다. 파일은 모두 노드의 `/root/workspace/worklog-backend`(main 브랜치)에 있다.
> GitHub는 `.github/workflows/ci.yaml` 한 파일에 게이트를 쌓고, Jenkins는 8.6의 `Jenkinsfile`에 stage를 더한다.

## 사전 조건

- ch8 완료 (8.6의 Jenkinsfile이 main, develop, release/1.0.0에 있고 GitHub 워크플로는 모두 꺼져 있음)
- 노드의 backend clone이 main 브랜치이고 `git pull --rebase`까지 마친 상태
- `pyproject.toml`의 dev 의존성에 `ruff`가 있음 (기준 저장소에 이미 있다)

## 실행 지침

### 단계 0: 워크플로 상태 확인 `[학습자 직접]`

ch8 워크플로가 꺼져 있는지 본다(8.5 단계 0에서 껐다). 9.3~9.5의 GitHub `ci.yaml`은 게이트만 있고 배포가 없어 Jenkins와 겹쳐도 충돌하지 않는다. 그래서 이 구간에서는 `ci.yaml`을 켜 둔 채로 Jenkins도 스캔한다. 9.6부터는 `ci.yaml`에 deploy가 붙으므로 그때 다시 정한다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow list --all -R <github_username>/worklog-backend      # 모두 disabled_manually
cd /root/workspace/worklog-backend && git checkout main && git pull --rebase
grep -n "ruff" pyproject.toml                                     # dev 의존성에 ruff가 보인다
```

### 단계 1: ruff 설정 파일 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/ruff.toml`에 ruff lint 설정 파일을 만들어줘. E, F, W, I 룰을 활성화하고 E501(줄 길이)은 무시해줘."

✅ 정답 파일 (완성 후 비교): `ch9/9.3/ruff.toml`

### 단계 2: GitHub 워크플로에 lint job `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/.github/workflows/ci.yaml`을 새로 만들어 ruff lint job을 넣어줘. 기존 워크플로 파일은 건드리지 마. push는 내가 할게.
> - 트리거: PR(main 대상), push(main, develop, release/*). `deploy_manifest/**` 변경은 제외
> - `astral-sh/setup-uv@v5` 액션(uv 0.11.18, Python 3.14)
> - `uv sync --extra dev` 후 `uv run ruff check src/` 실행"

✅ 정답 파일 (완성 후 비교): `ch9/9.3/1.lint-github.yaml`

### 단계 3: Jenkinsfile에 Lint stage `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Jenkinsfile`에서 Init stage 바로 다음(Test 앞)에 Lint stage를 추가해줘. 나머지 stage는 그대로 둬. push는 내가 할게.
> - uv 설치: `curl -LsSf https://astral.sh/uv/0.11.18/install.sh | sh`
> - `export PATH=\"\$HOME/.local/bin:\$PATH\"`
> - `uv sync --extra dev` 후 `uv run ruff check src/` 실행"

✅ 정답 파일 (완성 후 비교): `ch9/9.3/2.lint-jenkins.groovy`

### 단계 4: git push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add ruff.toml .github/workflows/ci.yaml Jenkinsfile
git commit -m "ci: add ruff lint gate"
git pull --rebase
git push
```

### 단계 4-1: 두 파이프라인 확인 `[학습자 직접 · 웹]`

- GitHub: fork의 Actions 탭에 새 워크플로 실행이 생기고 lint job이 성공한다.
- Jenkins: `worklog-backend` job에서 'Scan Multibranch Pipeline Now'를 누른다. main 빌드의 Console Output에서 Lint stage가 Test 앞에 돌고 통과하는지 본다. Jenkins는 lint 뒤에 이미지 빌드와 매니페스트 갱신까지 한다(8.6과 같다).

### 단계 5: lint가 막는 코드 만들기 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/src/worklog/lint_demo.py`에 ruff가 오류로 잡는 코드를 일부러 만들어줘. 쓰지 않는 import처럼 단순한 것으로. 커밋과 push는 내가 할게."

### 단계 6: 실패하는 커밋 올리기 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add src/worklog/lint_demo.py
git commit -m "test: lint failure demo"
git pull --rebase
git push
```

### 단계 6-1: lint 실패 확인 `[학습자 직접 · 웹]`

fork의 Actions 탭에서 방금 실행의 lint job이 실패하는지 본다. 로그에 ruff가 잡은 룰 코드(F401 같은 것)와 파일 위치가 나온다. 이 단계에서는 Jenkins를 스캔하지 않는다. 같은 실패를 한 번 더 보는 것뿐이다.

### 단계 7: 되돌리기 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git revert --no-edit HEAD
git pull --rebase
git push
```

Actions 탭에서 lint job이 다시 성공하는지 본다.

### 단계 8: ruff가 잡아내는 오류 종류 이해 `[AI 프롬프트]`

> "ruff.toml에서 설정한 E, F, W, I 룰이 각각 어떤 종류의 오류를 잡아내는지 설명해줘."

## 트러블슈팅

### Jenkins 빌드가 `downloading uv ...`에서 멈춰 끝나지 않는다

에이전트가 uv를 내려받는 연결이 끊긴 채로 기다리는 것이다. 설치 스크립트의 내려받기에는 시간 제한이 없다(run-40에서 21분 동안 멈췄다). 빌드 화면에서 중단(Abort)하고 'Scan Multibranch Pipeline Now'를 다시 누른다. 다시 돌리면 몇 초에 끝난다.
