# 9.8 CD 강화 - 자동 롤백 (Argo Rollouts AnalysisTemplate)

> **학습자 진입 방식**:
> - `[학습자 직접]`: `kubectl apply`, rollout 상태 확인
> - `[AI 프롬프트]`: Argo Rollouts AnalysisTemplate + canary 배포 중 자동 롤백 설정

## 사전 조건

- ch7 완료 (Argo Rollouts 설치 및 canary 배포 동작 확인)
- `worklog-backend` Service가 default namespace에 존재 (stable Service 겸용, ch7.7에서 생성)
- worklog-backend가 `/health` endpoint를 노출하는 상태

## 핵심 개념: 왜 canary 전용 Service가 필요한가

자동 롤백의 핵심은 AnalysisRun이 **"새 버전(canary)만"** 평가하는 것이다. 그런데 canary 배포(replica 비율
방식)에서는 하나의 Service(`worklog-backend`)가 stable·canary pod를 **모두** 가리킨다. 이 공유 Service를
분석이 폴링하면, canary 비중이 20%일 때 요청의 ~80%가 **정상 stable pod**로 가서 `/health`가 OK를 반환한다.
→ **망가진 새 버전을 배포해도 분석이 통과해 그대로 승격된다**(자동 롤백이 동작하지 않음).

이를 막으려면 **canary pod만 가리키는 전용 Service**를 두고 분석이 그것을 폴링해야 한다. Argo Rollouts는
Rollout에 `stableService`/`canaryService`를 선언하면 각 Service의 selector에 `rollouts-pod-template-hash`를
자동 주입해 stable Service=구버전 pod만, canary Service=새버전 pod만 가리키게 만든다(서비스메시 없이도 격리 가능).
+ `failureLimit: 0`(1회 실패=즉시 롤백)을 함께 써야 결정적으로 차단된다.

> 참고: ch7.6의 Canary는 단일 Service(트래픽 분할 학습)였다. 여기서 Service를 분리하는 건 **분석을 위한 격리**가
> 목적이며, trafficRouting(서비스메시)을 추가하는 것과는 다르다.

## 실행 지침

### 단계 1: AnalysisTemplate 작성 `[AI 프롬프트]`

> "Argo Rollouts AnalysisTemplate을 만들어줘.
> - 이름: `success-rate`
> - 30초 간격으로 health check
> - URL: `http://{{args.service-name}}.default.svc.cluster.local/health` (FQDN 형식)
> - 실패 허용 횟수: 0회 (1회라도 실패하면 즉시 롤백)
> - service-name을 인수로 받도록 설정"

✅ 정답 파일 (완성 후 비교): `ch9/9.8/1.analysis-template.yaml`

> ⚠️ URL은 반드시 FQDN 형식 (`<service-name>.default.svc.cluster.local`) 사용.  
> 단축 형식 (`http://{{args.service-name}}/health`)은 AnalysisRun Pod에서 DNS 해석 실패.
> ⚠️ `failureLimit: 0`은 결정적 차단을 위한 교육용 설정. 실무에선 일시적 blip 흡수를 위해 1~2로 튜닝하기도 한다.

### 단계 2: canary 전용 Service 작성 `[AI 프롬프트]`

> "worklog-backend-canary 라는 이름의 Service를 만들어줘. selector는 app: worklog-backend, 포트 80→80.
> (Argo Rollouts가 canaryService로 참조하면 pod-hash를 자동 주입해 canary pod만 선택함)"

✅ 정답 파일: `ch9/9.8/3.worklog-backend-canary-service.yaml`

### 단계 3: AnalysisTemplate을 포함한 Rollout 작성 `[AI 프롬프트]`

> "Argo Rollouts Rollout yaml을 만들어줘.
> - 이름: `worklog-backend`
> - canary 전략 사용, **stableService: worklog-backend / canaryService: worklog-backend-canary**
> - canary 배포 단계: 20% → 30초 대기 → 40% → 30초 대기 → 80% → 30초 대기
> - AnalysisTemplate `success-rate` 연결 (**service-name: worklog-backend-canary** — canary 전용 Service)
> - 이미지: `<dockerhub_username>/worklog-backend:<image_tag>`
> - imagePullSecrets: `dockerhub-creds`
> - MongoDB 환경변수 포함:
>   - MONGO_HOST: `worklog-mongodb.default.svc.cluster.local`
>   - MONGO_INITDB_ROOT_USERNAME: secretKeyRef (worklog-mongodb-creds, key: username)
>   - MONGO_INITDB_ROOT_PASSWORD: secretKeyRef (worklog-mongodb-creds, key: password)
> - livenessProbe, readinessProbe: `/health` endpoint"

✅ 정답 파일: `ch9/9.8/2.rollout-with-analysis.yaml`

### 단계 4: 적용 `[학습자 직접]`

```bash
kubectl apply -f ch9/9.8/1.analysis-template.yaml
kubectl apply -f ch9/9.8/3.worklog-backend-canary-service.yaml
kubectl apply -f ch9/9.8/2.rollout-with-analysis.yaml
kubectl get analysistemplate,svc
kubectl argo rollouts get rollout worklog-backend --watch
```

### 단계 5: 롤아웃 상태 확인 `[학습자 직접]`

```bash
# rollout 진행 상태 확인
kubectl argo rollouts get rollout worklog-backend

# AnalysisRun 상태 확인
kubectl get analysisrun

# AnalysisRun 상세 확인
kubectl describe analysisrun <analysisrun-name>
```

canary weight가 20% → 40% → 80% → 100%로 진행되면서 AnalysisRun이 Running 상태인 것 확인.
정상 버전이면 끝까지 승격(Healthy)된다.

### 단계 6: 자동 롤백 실제 시연 `[학습자 직접]`

자동 롤백이 **실제로 동작하는지** 보려면 `/health`가 실패하는(또는 OK가 아닌) "망가진" 이미지로 업데이트해 본다.

```bash
# 망가진 버전으로 업데이트 — 과정 제공 데모 이미지(공개) 사용
# (sysnet4admin/worklog-backend:broken-health = /health가 HTTP 200이지만 body가 "FAIL")
kubectl argo rollouts set image worklog-backend \
  worklog-backend=sysnet4admin/worklog-backend:broken-health

# 롤백 관찰: canary 전용 Service를 폴링한 분석이 실패 → 즉시 Abort
kubectl argo rollouts get rollout worklog-backend --watch
```

기대 결과:
```
Status:   ✖ Degraded
Message:  RolloutAborted: ... Metric "success-rate" assessed Failed due to failed (1) > failureLimit (0)
Images:   <username>/worklog-backend:<직전_정상_태그> (stable)   ← 이전 정상 버전 유지됨
```

> 💡 **여기가 핵심**: 공유 Service였다면 망가진 canary가 정상 stable 응답에 가려 승격됐을 것이다.
> canary 전용 Service + `failureLimit: 0` 덕분에 분석이 새 버전만 보고 결정적으로 차단·롤백한다.
>
> ⚠️ 데모 이미지 `sysnet4admin/worklog-backend:broken-health`(공개, 멀티아키 amd64+arm64)는 과정에서 제공한다.
> `/health`가 **HTTP 200 + `{"health":"FAIL"}`**를 반환 → pod는 Ready지만 분석만 실패시킨다.
> (단순히 존재하지 않는 태그를 쓰면 pod가 readiness 실패로 멈출 뿐 — 분석 실패와 다른 경로라 데모가 안 됨.)
> 재현 레시피: app의 `health.py` 반환값 `"health": "OK"` → `"FAIL"` 한 줄 변경 후 buildx 멀티아키 빌드·push.

> "Argo Rollouts에서 stableService/canaryService 분리와 AnalysisTemplate을 사용한 자동 롤백이 어떤 조건에서 트리거되는지, 그리고 failureLimit과 interval 설정이 어떤 의미인지 설명해줘."

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username | ❌ 반드시 확인 |

## 주의사항

- ⛔ AI가 하지 말 것: 분석을 **공유 Service(worklog-backend)**에 붙이지 말 것 — canary 전용 Service(worklog-backend-canary)를 폴링해야 새 버전만 평가됨. 공유 Service면 broken 버전도 정상 stable 응답에 가려 승격되어 자동 롤백이 동작하지 않음 (검증된 함정).
- ⛔ AI가 하지 말 것: Rollout에 `stableService`/`canaryService` 누락 — 둘 다 선언해야 Argo가 selector를 격리함.
- ⛔ AI가 하지 말 것: AnalysisTemplate URL에서 단축 DNS 형식 사용 (`http://worklog-backend/health`) — FQDN 필수
- ⛔ AI가 하지 말 것: MongoDB 환경변수 누락 (MONGO_HOST, USERNAME, PASSWORD 모두 필요)
- ⛔ AI가 하지 말 것: ch7 Argo Rollouts 미설치 상태에서 진행하지 말 것 (CRD 없음)
- ✅ AI가 해도 됨: AnalysisTemplate yaml 작성, Rollout yaml 작성
- ✅ AI가 해도 됨: AnalysisRun 상태 분석 (Running/Successful/Failed/Error)
- ✅ AI가 해도 됨: health check 실패 원인 분석
- ✅ AI가 해도 됨: successCondition 조건 설명 (`result == "OK"`)
- ⚠️ worklog-backend `/health` endpoint는 `{"health":"OK","imageTag":"..."}` JSON을 반환함 → `jsonPath: "{$.health}"`로 추출 후 `result == "OK"` 문자열 비교 사용. 숫자 조건(`>= 0.95`)은 사용 불가.
- ⛔ AI가 하지 말 것: `result[0] == "OK"` 사용 — Argo Rollouts web metric에서 `result`는 string이므로 `[0]` 인덱싱 시 `type string[int] is undefined` 오류 발생. `result == "OK"` 로 비교.
- ⚠️ `kubectl argo rollouts` 명령은 kubectl argo rollouts 플러그인 설치 필요 (ch7에서 설치 완료 가정)
- ⚠️ imagePullSecrets `dockerhub-creds` Secret이 클러스터에 있어야 이미지 pull 가능
