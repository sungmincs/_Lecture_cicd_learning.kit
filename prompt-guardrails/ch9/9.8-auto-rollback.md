# 9.8 CD 강화 - 자동 롤백 (Argo Rollouts AnalysisTemplate)

> **학습자 진입 방식**:
> - `[학습자 직접]`: Argo CD 자동 sync 끄기, `kubectl apply`, rollout 상태 확인, 망가진 이미지로 롤백 보기, 정리
> - `[AI 프롬프트]`: Argo Rollouts AnalysisTemplate + canary 배포 중 자동 롤백 설정

## 사전 조건

- ch7 완료 (Argo Rollouts 설치 및 canary 배포 동작 확인)
- `worklog-backend` Service가 default namespace에 있음 (stable Service로 쓴다. 6.5의 Argo CD Application `worklog-backend`가 만든 것)
- MongoDB가 default namespace에 있음 (7.7)
- worklog-backend가 `/health` endpoint를 노출하는 상태

## 핵심 개념: 왜 canary 전용 Service가 필요한가

자동 롤백의 핵심은 AnalysisRun이 **"새 버전(canary)만"** 평가하는 것이다. 그런데 canary 배포(replica 비율
방식)에서는 하나의 Service(`worklog-backend`)가 stable·canary pod를 **모두** 가리킨다. 이 공유 Service를
분석이 폴링하면, canary 비중이 20%일 때 요청의 ~80%가 **정상 stable pod**로 가서 `/health`가 OK를 반환한다.
→ **망가진 새 버전을 배포해도 분석이 통과해 그대로 승격된다**(자동 롤백이 동작하지 않음).

이를 막으려면 **canary pod만 가리키는 전용 Service**를 두고 분석이 그것을 폴링해야 한다. Argo Rollouts는
Rollout에 `stableService`/`canaryService`를 선언하면 각 Service의 selector에 `rollouts-pod-template-hash`를
자동 주입해 stable Service=구버전 pod만, canary Service=새버전 pod만 가리키게 만든다(서비스메시 없이도 격리 가능).
+ `failureLimit: 0`(1회 실패=즉시 롤백)을 함께 써야 결정적으로 차단된다.

> 참고: ch7.6의 Canary는 단일 Service(트래픽 분할 학습)였다. 여기서 Service를 분리하는 건 **분석을 위한 격리**가
> 목적이며, trafficRouting(서비스메시)을 추가하는 것과는 다르다.

## 실행 지침

### 단계 0: Argo CD 자동 sync 끄기와 작업 폴더 `[학습자 직접]`

7.3과 같은 준비다. default의 `worklog-backend`는 Argo CD가 Deployment로 관리하고 자동 sync(selfHeal) 중이다. 이 절은 같은 이름의 Rollout을 kubectl로 올리고, Argo Rollouts가 `worklog-backend` Service의 selector를 고친다. 자동 sync가 켜져 있으면 Argo CD가 그것을 되돌린다. 그래서 끄고, Deployment도 지운다. 단계 8에서 되돌린다.

```bash
argocd app set worklog-backend --sync-policy none
kubectl delete deployment worklog-backend
mkdir -p /root/ch9
grep "image:" /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml      # 지금 main의 태그
```

이 절에서 쓰는 태그는 둘이다. `<image_tag>`는 `buildtest1`(3.5), `<new_tag>`는 위 명령에 보인 태그다.

### 단계 1: AnalysisTemplate 작성 `[AI 프롬프트]`

> "Argo Rollouts AnalysisTemplate을 만들어서 컨트롤 플레인 노드의 `/root/ch9/1.analysis-template.yaml`로 저장해줘. 적용은 내가 할게.
> - 이름: `success-rate`
> - 30초 간격으로 health check
> - URL: `http://{{args.service-name}}.default.svc.cluster.local/health` (FQDN 형식)
> - 응답 JSON의 `health` 값이 `OK`면 성공 (`jsonPath: \"{$.health}\"`, `successCondition: result == \"OK\"`)
> - 실패 허용 횟수: 0회 (1회라도 실패하면 즉시 롤백)
> - service-name을 인수로 받도록 설정"

✅ 정답 파일 (완성 후 비교): `ch9/9.8/1.analysis-template.yaml`

URL은 FQDN 형식(`<service-name>.default.svc.cluster.local`)으로 쓴다. 분석은 argo-rollouts 네임스페이스의 컨트롤러가 요청하므로 짧은 이름(`http://worklog-backend-canary/health`)은 찾지 못한다.
`failureLimit: 0`은 결과가 분명하게 보이도록 한 교육용 설정이다. 실무에서는 잠깐의 실패를 흡수하려고 1~2로 두기도 한다.

### 단계 4: 적용 `[학습자 직접]`

```bash
cd /root/ch9
grep "image:" 2.rollout-with-analysis.yaml      # 플레이스홀더가 아니라 실제 값인지 확인
kubectl apply -f 1.analysis-template.yaml
kubectl apply -f 3.worklog-backend-canary-service.yaml
kubectl apply -f 2.rollout-with-analysis.yaml
kubectl get analysistemplate,svc
kubectl argo rollouts get rollout worklog-backend --watch      # Healthy가 되면 Ctrl+C
```

첫 적용은 Canary 단계 없이 바로 Healthy가 된다(이전 버전이 없으므로).

### 단계 5: 정상 버전으로 업데이트해 분석 통과 확인 `[학습자 직접]`

```bash
kubectl argo rollouts set image worklog-backend \
  worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl argo rollouts get rollout worklog-backend --watch      # Healthy가 되면 Ctrl+C. 2분쯤 걸린다
kubectl get analysisrun                                         # Successful
```

Paused 단계(Step 1/6, 3/6, 5/6)를 거쳐 Healthy가 되고 AnalysisRun이 Successful인 것을 확인한다.
정답 Rollout은 replicas가 1이라 ActualWeight는 Pod 수 때문에 setWeight 20, 40, 80 단계 모두 50으로 보인다(run-38 실측). 단계(Step)가 넘어가는 것을 본다.

### 단계 6: 자동 롤백 실제 시연 `[학습자 직접]`

`/health`가 OK가 아닌 "망가진" 이미지로 업데이트한다. 과정에서 제공하는 공개 데모 이미지를 쓴다.

```bash
# sysnet4admin/worklog-backend:broken-health 는 /health가 HTTP 200이지만 본문이 {"health":"FAIL"} 이다
kubectl argo rollouts set image worklog-backend \
  worklog-backend=sysnet4admin/worklog-backend:broken-health
kubectl argo rollouts get rollout worklog-backend --watch      # Degraded가 되면 Ctrl+C. 1분 안쪽
kubectl get analysisrun                                         # 마지막 것이 Failed
```

기대 결과:
```
Status:   ✖ Degraded
Message:  RolloutAborted: ... Metric "success-rate" assessed Failed due to failed (1) > failureLimit (0)
Images:   <dockerhub_username>/worklog-backend:<new_tag> (stable)   ← 이전 정상 버전이 그대로 남는다
```

공유 Service였다면 망가진 canary가 정상 stable의 응답에 가려 승격됐을 것이다. canary 전용 Service와 `failureLimit: 0` 덕분에 분석이 새 버전만 보고 막는다.

데모 이미지는 Pod가 Ready가 되지만 분석만 실패하게 만든 것이다. 없는 태그를 쓰면 Pod가 뜨지 못해 멈출 뿐이라 분석 실패와 다른 경로가 된다.
만드는 방법: 앱의 `health.py`에서 `"health": "OK"`를 `"FAIL"`로 한 줄 바꿔 빌드한다.

## 주의사항

- ⛔ AI가 하지 말 것: `kubectl apply`와 `set image`를 대신 하지 말 것. yaml은 `/root/ch9/`에 둔다
- ⛔ AI가 하지 말 것: 분석을 **공유 Service(worklog-backend)**에 붙이지 말 것 — canary 전용 Service(worklog-backend-canary)를 폴링해야 새 버전만 평가됨. 공유 Service면 broken 버전도 정상 stable 응답에 가려 승격되어 자동 롤백이 동작하지 않음 (검증된 함정).
- ⛔ AI가 하지 말 것: Rollout에 `stableService`/`canaryService` 누락 — 둘 다 선언해야 Argo가 selector를 격리함.
- ⛔ AI가 하지 말 것: AnalysisTemplate URL에서 단축 DNS 형식 사용 (`http://worklog-backend/health`) — FQDN 필수
- ⛔ AI가 하지 말 것: MongoDB 환경변수 누락 (MONGO_HOST, USERNAME, PASSWORD 모두 필요)
- ⛔ AI가 하지 말 것: ch7 Argo Rollouts 미설치 상태에서 진행하지 말 것 (CRD 없음)
- ✅ AI가 해도 됨: AnalysisTemplate yaml 작성, Rollout yaml 작성
- ✅ AI가 해도 됨: AnalysisRun 상태 분석 (Running/Successful/Failed/Error)
- ✅ AI가 해도 됨: health check 실패 원인 분석
- ✅ AI가 해도 됨: successCondition 조건 설명 (`result == "OK"`)
- ⚠️ worklog-backend `/health` endpoint는 `{"health":"OK","imageTag":"..."}` JSON을 반환함 → `jsonPath: "{$.health}"`로 추출 후 `result == "OK"` 문자열 비교 사용. 숫자 조건(`>= 0.95`)은 사용 불가.
- ⛔ AI가 하지 말 것: `result[0] == "OK"` 사용 — Argo Rollouts web metric에서 `result`는 string이므로 `[0]` 인덱싱 시 `type string[int] is undefined` 오류 발생. `result == "OK"` 로 비교.
- ⚠️ `kubectl argo rollouts` 명령은 kubectl argo rollouts 플러그인 설치 필요 (ch7에서 설치 완료 가정)
- ⚠️ `dockerhub-creds`는 private 이미지일 때만 필요하다. Docker Hub 이미지가 public이면 없어도 pull되고 Pod 이벤트에 `FailedToRetrieveImagePullSecret` 경고만 남는다. 이 Secret은 6.5 단계 5에서 만들었다.
