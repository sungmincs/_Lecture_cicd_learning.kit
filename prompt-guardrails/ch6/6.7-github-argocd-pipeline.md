# 6.7 [GitHub] Argo CD 파이프라인 구현

> **학습자 진입 방식**:
> - `[학습자 직접]`: 워크플로 켜기, 매니페스트 확인, git push, 파이프라인이 올린 커밋 받기, Argo CD 확인
> - `[학습자 직접 · 웹]`: write 권한 활성화, Secrets 확인, Actions 결과 확인
> - `[AI 프롬프트]`: 파이프라인 yaml 수정 (build + deploy_manifest 업데이트 + git push)
>
> 이 절부터 파이프라인이 fork의 main에 커밋을 올린다. 그래서 노드의 clone이 뒤처진다. **이 절 뒤로는 커밋한 뒤 push하기 전에 항상 `git pull --rebase`를 한다**(add, commit, pull --rebase, push 순서).

## 실행 지침

### 단계 0: 이 절의 워크플로만 켜기 `[학습자 직접]`

5.5 단계 0에서 끈 `build-pipeline.yaml`을 다시 켠다. 이 절에서 그 파일을 고친다(단계 3). 다른 워크플로는 꺼진 채로 둔다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow enable build-pipeline.yaml -R <github_username>/worklog-backend
gh workflow list --all -R <github_username>/worklog-backend      # build-pipeline만 active
```

### 단계 1: GitHub Actions write 권한 활성화 `[학습자 직접 · 웹]`

파이프라인에서 저장소에 git push하려면 write 권한이 필요하다.

저장소 → Settings → Actions → General → Workflow permissions
→ **Read and write permissions** 선택 → Save

> ⚠️ 이 설정 없이 git push 단계에서 `403 Permission denied` 오류 발생

### 단계 2: GitHub Secrets 확인 `[학습자 직접 · 웹]`

저장소 → Settings → Secrets and variables → Actions

| Secret 이름 | 값 |
|---|---|
| `DOCKERHUB_TOKEN` | Docker Hub Access Token (5.3 단계 1-1에서 이미 등록) |

새로 넣을 것은 없다. Docker Hub username은 5.3처럼 파이프라인 yaml에 직접 적는다.

### 단계 3: 파이프라인 yaml 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/.github/workflows/build-pipeline.yaml`을 Argo CD GitOps 방식으로 고쳐줘. 새 파일을 만들지 말고 같은 파일을 고쳐줘.
> - 워크플로 이름은 `worklog backend pipeline (Argo CD)`
> - 테스트와 이미지 빌드·push는 지금 그대로(태그는 full SHA와 8자 short SHA)
> - build 뒤에 deploy job 추가: `deploy_manifest/worklog-backend.yaml`의 image 필드와 `# IMAGE_TAG` 주석이 붙은 IMAGE_TAG 값을 8자 short SHA로 바꾸고 같은 저장소 main에 커밋·push. push 전에 `git pull --rebase -X theirs origin main`
> - 워크플로에 `permissions: contents: write`
> - `deploy_manifest/**`만 바뀐 push는 다시 돌지 않게 `paths-ignore`
> - Docker Hub username: `<dockerhub_username>`"

✅ 정답 파일 (완성 후 비교): `ch6/6.7/1.build-and-argocd-sync.yaml`

5.3이나 5.4에서 만든 워크플로우 파일(`.github/workflows/build-pipeline.yaml`)을 이 내용으로 바꾼다. 새 파일로 두면 같은 push에 5장 빌드와 6.7 빌드가 함께 돈다.

### 단계 4: 파이프라인이 고칠 두 줄 확인 `[학습자 직접]`

### 단계 5: git push `[학습자 직접]`

```bash

```

### 단계 5-1: 파이프라인 확인 `[학습자 직접 · 웹]`

GitHub → Actions 탭 → `worklog backend pipeline (Argo CD)`의 init-and-test, build, deploy가 모두 성공했는지 본다.
deploy가 끝나면 저장소의 커밋 목록에 `deploy: update image tag` 커밋이 하나 더 생긴다. 이 커밋으로는 워크플로가 다시 돌지 않는다(`paths-ignore`).

### 단계 6: 파이프라인이 올린 커밋 받기와 Argo CD 확인 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git pull --rebase                                              # 파이프라인이 올린 매니페스트 커밋을 받는다
grep -n "image:\|IMAGE_TAG" deploy_manifest/worklog-backend.yaml     # buildtest1이 8자 short SHA로 바뀌었다
argocd app get worklog-backend --refresh                       # Git을 지금 다시 읽게 한다. OutOfSync가 보였다가 곧 Synced로 바뀐다
argocd app wait worklog-backend --sync --health --timeout 300  # 배포가 끝날 때까지 기다린다
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'   # 같은 short SHA
```

Argo CD는 Git을 약 3분 간격으로 확인한다. 파이프라인이 끝난 직후에 `--refresh` 없이 보면 아직 옛 커밋에 `Synced`이고 이미지도 그대로다. 고장이 아니라 아직 안 본 것이다. 기다리면 스스로 감지하고, `--refresh`는 그 확인을 지금 하게 한다.

`git pull --rebase`를 빼먹고 다음에 커밋해서 push하면 `rejected (fetch first)`가 난다. 이 절 뒤로는 커밋한 뒤 push 전에 항상 한다. 고친 파일을 커밋하지 않은 채로 하면 `You have unstaged changes`로 멈추므로 순서는 add, commit, pull --rebase, push다.

## 검증 중 발견된 이슈 (강의자 참고)

- **deploy 단계 `git push` 충돌**: 저장소에 다른 워크플로우가 동시에 실행되는 경우 `git push` 전에 이미 다른 커밋이 쌓여 `rejected - fetch first` 에러 발생.
  **수정**: `git push origin main` 직전에 `git pull --rebase -X theirs origin main` 추가. 충돌 시 이번 실행의 매니페스트를 남긴다(참조 파일에 반영됨).

- **GitHub Actions write 권한 미설정**: deploy 단계의 `git push`가 403 Permission denied로 실패.
  **수정**: 저장소 → Settings → Actions → General → Workflow permissions → Read and write permissions 선택.

- ✅ AI가 해도 됨: write 권한 활성화 경로 안내
- ✅ AI가 해도 됨: git push 403 오류 원인 분석
- ✅ AI가 해도 됨: `${{ github.sha }}` 등 GitHub Actions 내장 변수 설명
- ⚠️ **`paths-ignore: deploy_manifest/**` 설정 시 빈 커밋으로는 파이프라인 미트리거**: deploy job이 manifest를 변경·push하면 `paths-ignore`에 의해 다음 push가 차단됨 — 정상 동작. 파이프라인을 다시 트리거하려면 소스 코드 파일을 실제로 변경해야 함.
- ⚠️ **(run-16, #92) deploy_manifest의 IMAGE_TAG env에 `# IMAGE_TAG` inline 주석 필수**: deploy job의 sed가 `s|value: .* # IMAGE_TAG|value: ${SHA} # IMAGE_TAG|` 패턴으로 매칭하므로, `deploy_manifest/worklog-backend.yaml`의 `value:` 라인 끝에 `# IMAGE_TAG` 주석이 있어야 갱신됨(없으면 IMAGE_TAG env가 옛 값으로 남음). 정답 `ch5/5.3/deploy_manifest/worklog-backend.yaml`에 반영됨.
