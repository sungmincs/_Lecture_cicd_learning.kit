# 6.2 GitOps 개념과 Argo CD (왜 선언적 배포인가)

> **학습자 진입 방식**: 개념 섹션 — 실습 없음. GitOps가 무엇이고 왜 필요한지, Argo CD가 그걸 어떻게 구현하는지 이해한 뒤 6.3으로 진행.

## 이 장의 목적

ch5까지 CI 파이프라인으로 코드를 빌드해 이미지를 Docker Hub에 올리는 것까지 자동화했다. 하지만 **클러스터에 배포하는 일은 여전히 수동**이다 — `kubectl set image`로 직접 태그를 바꿔야 한다(ch3.8에서 그 불편함을 직접 겪었다).

ch6은 이 마지막 수동 단계를 없앤다. **Git에 매니페스트를 commit하면 클러스터가 알아서 그 상태로 맞춰지는** GitOps를 도입하고, 그 구현체로 **Argo CD**를 설치·운영한다. 이 장이 끝나면 "배포 = git push"가 된다.

## 명령형 배포의 한계 (지금까지의 방식)

`kubectl set image`, `kubectl apply`로 그때그때 클러스터를 바꾸는 방식을 **명령형(imperative)** 이라 한다. 편리하지만 구조적 문제가 있다.

- **드리프트(drift)**: 클러스터에 실제 떠 있는 것과 Git/문서의 내용이 같은지 보장할 수 없다. 누가 `kubectl edit`으로 한 줄 바꿔도 아무도 모른다.
- **"왜"가 안 남는다**: 명령은 실행 순간에만 의미가 있어, "누가 언제 왜 이 배포를 했는지"가 기록되지 않는다.
- **추적·롤백이 어렵다**: "이전 상태"가 무엇이었는지 명령 이력에만 의존한다.

## GitOps: 선언적 배포

GitOps는 **"Git에 적힌 매니페스트가 의도한 상태(desired state)이고, 클러스터는 그것을 계속 따라간다"** 는 관점이다.

| 구분 | 명령형 (지금까지) | 선언형 / GitOps (ch6~) |
|---|---|---|
| 배포 방법 | `kubectl set image ...` | 매니페스트를 Git에 commit |
| 기준(진실) | 클러스터의 현재 상태 | **Git 저장소** |
| 변경 이력 | 명령 실행 이력(휘발) | git history (누가/언제/왜) |
| 드리프트 | 감지 못 함 | 자동 감지·복원 |

> 핵심 전환: **클러스터를 직접 바꾸지 않는다.** Git을 바꾸면, 배포 도구가 그 차이를 감지해 클러스터를 맞춘다.

## Argo CD가 하는 일

Argo CD는 GitOps를 구현하는 쿠버네티스 컨트롤러다.

- **동기화(sync)**: Git의 매니페스트와 클러스터 상태를 비교(diff)해, 다르면 Git 쪽으로 맞춘다.
- **자동 sync**: `deploy_manifest/`의 이미지 태그가 바뀌면 감지해 자동 배포한다.
- **self-heal / 드리프트 감지**: 누가 클러스터를 직접 수정해도 Git 상태로 되돌린다.
- **시각화**: UI로 "지금 무엇이 어떤 상태로 떠 있는지"를 한눈에 보여준다.

> CI(GitHub Actions/Jenkins/GitLab)는 빌드·push·매니페스트 갱신까지만 하고, **실제 배포는 Argo CD에 위임**한다. CI가 클러스터를 직접 건드리지 않는 것이 GitOps의 핵심이다.

## 진행 방법 (이 장의 흐름)

1. **설치**: Argo CD를 클러스터에 설치하고 UI/CLI로 접근한다.
2. **첫 배포**: worklog-backend를 Argo CD Application으로 등록해 Git 기반 배포를 체험한다.
3. **알림**: 배포 결과를 Slack으로 알린다.
4. **CI 연동**: GitHub/Jenkins/GitLab CI가 매니페스트를 갱신하면 Argo CD가 자동 배포하도록 잇는다.
