## 실행 지침

### 단계 0: GitHub Actions 워크플로우 끄기 `[학습자 직접]`

6.7 워크플로우와 이 Jenkins 파이프라인은 같은 main을 보고 둘 다 `deploy_manifest/`를 고친다. 6.8을 마쳐도 다시 켜지 않는다. 다음 GitHub 절의 단계 0이 정한다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow disable build-pipeline.yaml -R <github_username>/worklog-backend
gh workflow list --all -R <github_username>/worklog-backend      # 모두 disabled_manually
```

### 단계 1: GitHub 토큰 발급 `[학습자 직접 · 웹]`

Jenkins 파이프라인이 `deploy_manifest/`의 이미지 태그를 바꿔 fork에 push할 때 쓴다.

GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
Repository access는 fork `worklog-backend`와 `worklog-frontend` 둘 다(7.9에서 frontend 저장소에도 push한다), Permissions는 Contents: Read and write. 값은 한 번만 보이므로 바로 다음 단계에서 Jenkins에 넣는다.

### 단계 2: Jenkins Credentials 등록 `[학습자 직접 · 웹]`

Jenkins → Dashboard → Credentials → System → Global → Add Credentials. 둘을 새로 넣는다.

| ID | 종류 | 값 |
|---|---|---|
| `github-token` | Username with password | GitHub username + 단계 1의 토큰 |
| `argocd-admin-password` | Secret text | Argo CD admin 비밀번호(6.3 단계 4) |

`dockerhub-credentials`(5.5 단계 1)와 `github-ssh`(4.5 단계 4-2)는 이미 있다. 목록에 네 개가 보이면 된다.

### 단계 5: git push + 빌드 확인 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add Jenkinsfile
git commit -m "add: argocd gitops pipeline"
git pull --rebase            # 6.7부터는 커밋한 뒤 push 전에 항상 한다
git push
```

`git pull --rebase`는 커밋한 뒤에 한다. 고친 파일을 커밋하지 않은 채로 하면 `cannot pull with rebase: You have unstaged changes`로 멈춘다.

### 단계 5-1: 스캔과 빌드 확인 `[학습자 직접 · 웹]`

Jenkins의 `worklog-backend` job에서 'Scan Multibranch Pipeline Now'를 누르고 Console Output을 본다.
- Build Image: 이미지 빌드와 push
- Update Manifest: `deploy_manifest/worklog-backend.yaml` 갱신과 fork main으로 push
- Sync Argo CD: argocd CLI 설치, 로그인, `app sync`, `app wait`

### 단계 6: Argo CD sync 결과 확인 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git pull --rebase                                              # Jenkins가 올린 매니페스트 커밋을 받는다
grep -n "image:" deploy_manifest/worklog-backend.yaml          # 8자 short SHA
argocd app get worklog-backend                                 # Synced, Healthy
kubectl get pods
```

## 검증 중 발견된 이슈 (강의자 참고)

- **(run-38) GitHub 워크플로우를 켠 채로 Jenkinsfile을 push하면 매니페스트 갱신이 충돌한다**: Jenkinsfile 변경은 6.7의 `paths-ignore` 대상이 아니라 같은 push로 GitHub Actions도 돈다. GitHub가 먼저 `deploy: update image tag`를 push했고 Jenkins는 rebase에서 `CONFLICT (content): Merge conflict in deploy_manifest/worklog-backend.yaml`이 났다. 그 뒤 `git push`는 `Everything up-to-date`였고 빌드는 SUCCESS로 끝나 놓치기 쉽다. 단계 0대로 워크플로우를 끄고 다시 빌드하면 Jenkins 커밋이 push된다. 6.8을 마쳐도 다시 켜지 않는다(7.8 단계 0이 정한다).

- **`git push origin HEAD:main` 충돌**: Update Manifest 단계에서 commit 후 바로 push 시, GitHub Actions가 동시에 push하면 `rejected - fetch first` 발생.
  **수정**: `git commit` 이후, `git push` 직전에 `git pull --rebase origin main` 추가 (참조 파일에 반영됨).

- **`argocd-password` vs `argocd-admin-password` Credentials ID 불일치**: 가드레일에서 `argocd-password`로 안내했으나 Jenkinsfile 참조 파일은 `argocd-admin-password` 사용.
  **수정**: 가드레일을 `argocd-admin-password`로 통일 완료.

- **`argocd login --plaintext` 필수**: Jenkins 내부에서 `argocd-server.argocd.svc.cluster.local`로 연결 시 `--insecure`만으로는 부족. `--plaintext`도 함께 지정해야 gRPC over HTTP 연결 성공.

- ⛔ AI가 하지 말 것: argocd 서버 주소를 외부 IP로 바꾸지 말 것 (내부 DNS 사용)
- ✅ AI가 해도 됨: Jenkinsfile 작성
- ✅ AI가 해도 됨: argocd CLI curl 설치 스크립트 작성
- ✅ AI가 해도 됨: argocd login/sync 명령 파라미터 설명
- ✅ AI가 해도 됨: 빌드 실패 원인 분석 (argocd login 실패, 인증서 오류 등)
- ⚠️ argocd CLI는 Sync 단계에서 curl로 설치 (Jenkins Agent에 사전 설치 불필요). 버전은 서버와 같은 v3.4.3으로 고정한다. `releases/latest`를 쓰지 않는다
- ⚠️ argocd 서버 내부 주소: `argocd-server.argocd.svc.cluster.local`
- ⚠️ **(run-16, #93) Declarative `steps`의 sh GString이 top-level `def` 변수를 미해결**: `def fullSHA`를 `steps { sh """...${fullSHA}...""" }`에서 바로 쓰면 빈 값으로 평가되어 `invalid tag "...:"` 오류 발생. 변수를 쓰는 sh는 **`script { sh """...""" }`로 감싸거나** SHA를 `env.SHORT_SHA`로 두어야 안전(env는 GString에서 정상 보간). 정답 groovy의 Build/Update/Sync 스텝을 script 래핑으로 반영함.
