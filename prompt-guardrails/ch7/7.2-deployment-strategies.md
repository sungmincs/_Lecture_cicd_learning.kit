# 7.2 배포 전략 개요 (Rolling Update / Blue-Green / Canary)

> **학습자 진입 방식**: 개념 섹션 — 실습 없음. 배포 전략의 차이와 선택 기준을 이해한 뒤 7.3으로 진행.

## 이 챕터에서 다루는 것

ch7에서는 K8s 기본 배포를 넘어, 무중단·점진 배포를 구현하는 **배포 전략**을 다룬다. 새 버전을 어떻게 내보내느냐에 따라 장애 위험과 롤백 속도가 달라진다. 본격 실습(7.3 Rolling, 7.5 Blue-Green, 7.6 Canary) 전에 세 전략의 동작과 트레이드오프를 잡는다.

## 세 가지 전략 비교

| 전략 | 동작 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|---|
| **Rolling Update** | Pod를 순차 교체(`maxSurge`/`maxUnavailable`) | K8s 기본, 추가 도구 불필요 | 신·구 버전이 일시 공존, 즉시 롤백 어려움 | 하위호환 보장되는 일반 업데이트 |
| **Blue-Green** | active/preview 두 환경 → 검증 후 한 번에 전환 | 즉시 컷오버·즉시 롤백, 버전 안 섞임 | 리소스 2배 필요 | 전환 리스크를 최소화해야 하는 릴리스 |
| **Canary** | 트래픽을 5%→20%→…→100% 점진 이동 | 실사용 트래픽으로 단계 검증, 위험 최소 | 전환이 느림, 관측·분석 필요 | 영향도 큰 변경의 안전한 점진 출시 |

> A/B 테스팅은 Canary와 메커니즘이 비슷하나, "위험 분산"이 아니라 **기능/지표 비교**가 목적이라는 점이 다르다.

## K8s 기본 vs Argo Rollouts

- **Rolling Update**는 K8s `Deployment`가 기본 제공한다.
- **Blue-Green·Canary**는 트래픽 가중치 제어가 필요해, 본 강의에서는 **Argo Rollouts**(7.4에서 설치)로 구현한다. `Rollout` 리소스가 `Deployment`를 대체하며 전환 단계·승인·분석을 선언적으로 다룬다.

## 선택 기준 (요약)

- 하위호환이 보장되고 단순하면 → **Rolling Update**
- 전환 순간의 리스크를 0으로 만들고 즉시 롤백이 필요하면 → **Blue-Green**
- 실트래픽으로 단계 검증하며 천천히 내보내려면 → **Canary**
