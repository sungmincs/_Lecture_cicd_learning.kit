# 7.8 [GitHub] 마이크로서비스 배포 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 워크플로 확인, git push, 파이프라인이 올린 커밋 받기, Argo CD 확인
> - `[학습자 직접 · 웹]`: frontend 저장소의 write 권한과 Secrets 등록, Actions 실행 결과 확인, 브라우저 접속
> - `[AI 프롬프트]`: frontend와 backend 파이프라인 yaml 작성
>
> 저장소가 둘이다. frontend는 `/root/workspace/worklog-frontend`(main 브랜치), backend는 `/root/workspace/worklog-backend`다.
> 명령 블록의 첫 줄 `cd`가 어느 저장소인지 알려 준다.

## 사전 조건

- ch6/6.7 완료 (backend 저장소에 write 권한이 켜져 있고 Secret `DOCKERHUB_TOKEN`이 등록됨)
- ch7/7.7 완료 (두 저장소에 `deploy_manifest/`가 있고 Argo CD Application `worklog-frontend`, `worklog-backend`가 자동 sync 중)
- 노드의 frontend clone이 `main` 브랜치임 (7.7 단계 3)

## 실행 지침

### 단계 0: 앞 절 파이프라인이 꺼져 있는지 확인 `[학습자 직접]`

backend의 6.7 워크플로(`build-pipeline.yaml`)는 6.8 단계 0에서 껐다. 꺼져 있는지 본다. 이 절에서 backend에 새 워크플로 파일을 만들기 때문에 둘 다 켜 두면 같은 push에 두 번 빌드한다. frontend는 처음 만드는 것이라 끌 것이 없다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow list --all -R <github_username>/worklog-backend       # 모두 disabled_manually
gh workflow list --all -R <github_username>/worklog-frontend      # 아무것도 없음
```

`active`가 보이면 `gh workflow disable <파일 이름> -R <github_username>/worklog-backend`로 끈다.

### 단계 1: frontend 저장소의 write 권한 켜기 `[학습자 직접 · 웹]`

파이프라인이 저장소에 git push하려면 write 권한이 필요하다. backend는 6.7 단계 1에서 했다. frontend 저장소에서 같은 설정을 한다.

GitHub의 fork `worklog-frontend` → Settings → Actions → General → Workflow permissions → **Read and write permissions** → Save

fork한 저장소는 Actions 탭에 "Workflows aren't being run on this forked repository"가 보일 수 있다. 보이면 **I understand my workflows, go ahead and enable them**을 누른다.

### 단계 2: 두 저장소에 Secrets 등록 `[학습자 직접 · 웹]`

이 절의 파이프라인은 Docker Hub username도 Secret으로 읽는다. 6.7까지의 backend 워크플로는 username을 yaml에 직접 적었으므로 backend 저장소에는 `DOCKERHUB_TOKEN`만 있다.

각 fork → Settings → Secrets and variables → Actions → New repository secret

| 저장소 | Secret 이름 | 값 |
|---|---|---|
| `worklog-frontend` | `DOCKERHUB_USERNAME` | Docker Hub username |
| `worklog-frontend` | `DOCKERHUB_TOKEN` | Docker Hub Access Token. 5.3 단계 1에서 발급한 값을 보관해 두지 않았으면 같은 방법으로 새로 발급한다 |
| `worklog-backend` | `DOCKERHUB_USERNAME` | Docker Hub username. `DOCKERHUB_TOKEN`은 5.3 단계 1-1에서 이미 넣었다 |

backend에 `DOCKERHUB_USERNAME`을 빠뜨리면 단계 7의 build job이 `Username required`로 실패한다. 그때는 Secret을 넣고 Actions 탭에서 Re-run failed jobs를 누른다.

### 단계 3: Frontend 파이프라인 yaml 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-frontend/.github/workflows/build-deploy.yaml`에 frontend GitHub Actions 파이프라인을 만들어줘. push는 내가 할게.
> - main 브랜치 push에 트리거, deploy_manifest/** 변경은 제외 (paths-ignore)
> - permissions: contents write
> - 이미지: `${{ secrets.DOCKERHUB_USERNAME }}/worklog-frontend`, 태그는 git SHA 앞 8자
> - multi-arch 빌드 (linux/amd64, linux/arm64)
> - build job → deploy job 순서
> - deploy job: deploy_manifest/worklog-frontend.yaml의 image 줄을 새 태그로 바꿔 커밋하고, `git pull --rebase -X theirs origin main` 뒤에 push
> - 같은 브랜치의 실행이 겹치지 않게 concurrency 그룹 설정 (cancel-in-progress: false)"

✅ 정답 파일 (완성 후 비교): `ch7/7.8/1.frontend-build-deploy.yaml`

### 단계 4: Backend 파이프라인 yaml 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/.github/workflows/build-deploy.yaml`에 backend GitHub Actions 파이프라인을 새 파일로 만들어줘. 기존 `build-pipeline.yaml`은 건드리지 마. push는 내가 할게.
> - main 브랜치 push에 트리거, deploy_manifest/** 변경은 제외 (paths-ignore)
> - permissions: contents write
> - test job (uv 0.11.18 설치 스크립트, `uv sync --extra dev`, TESTING=true로 pytest와 coverage) → build job → deploy job 순서
> - 이미지: `${{ secrets.DOCKERHUB_USERNAME }}/worklog-backend`, 태그는 git SHA 앞 8자, multi-arch 빌드 (linux/amd64, linux/arm64)
> - deploy job: deploy_manifest/worklog-backend.yaml의 image 줄과 `# IMAGE_TAG` 주석이 붙은 IMAGE_TAG 값을 새 태그로 바꿔 커밋하고, `git pull --rebase -X theirs origin main` 뒤에 push
> - 같은 브랜치의 실행이 겹치지 않게 concurrency 그룹 설정 (cancel-in-progress: false)"

✅ 정답 파일 (완성 후 비교): `ch7/7.8/2.backend-build-deploy.yaml`

6.7의 파이프라인과 다른 점은 Argo CD를 부르는 단계가 없다는 것이다. 매니페스트를 고쳐 push하면 끝이고, 자동 sync가 켜진 Argo CD가 알아서 배포한다. Argo CD에 로그인할 비밀번호도 파이프라인에 필요 없다.

### 단계 5: frontend 파이프라인 push `[학습자 직접]`

```bash
cd /root/workspace/worklog-frontend
git add .github/workflows/build-deploy.yaml
git commit -m "cicd: add frontend build and deploy pipeline"
git pull --rebase
git push
```

### 단계 6: backend 파이프라인 push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add .github/workflows/build-deploy.yaml
git commit -m "cicd: add backend build and deploy pipeline"
git pull --rebase
git push
```

### 단계 7: 파이프라인 실행 결과 확인 `[학습자 직접 · 웹]`

두 fork의 Actions 탭에서 방금 push한 커밋의 실행이 성공하는지 본다. 워크플로 이름은 AI가 지은 것이라 정답 파일의 `Frontend Build and Deploy`, `Backend Build and Deploy`와 다를 수 있다(run-40에서 backend는 `worklog backend build-deploy`였다). 이름이 달라도 동작은 같다. frontend는 Node 의존성을 두 아키텍처로 설치해서 backend보다 오래 걸린다(backend 2분, frontend 4분 안팎).
끝나면 각 저장소의 커밋 목록에 `deploy: update ... image to <8자>` 커밋이 하나씩 생긴다. 이 커밋은 `deploy_manifest/`만 바꾸므로 파이프라인이 다시 돌지 않는다.

### 단계 8: 파이프라인이 올린 커밋 받기와 Argo CD 확인 `[학습자 직접]`

```bash
cd /root/workspace/worklog-frontend && git pull --rebase && grep "image:" deploy_manifest/worklog-frontend.yaml
cd /root/workspace/worklog-backend  && git pull --rebase && grep "image:" deploy_manifest/worklog-backend.yaml

argocd app get worklog-frontend --refresh | grep -E "Sync Status|Health Status"
argocd app get worklog-backend  --refresh | grep -E "Sync Status|Health Status"
kubectl get deployment worklog-frontend worklog-backend -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image
```

기대 결과: 두 매니페스트의 태그가 방금 push한 커밋의 8자 SHA이고, 두 Deployment의 이미지가 그 태그다. `--refresh` 직후에는 `OutOfSync`나 `Progressing`이 보일 수 있다. 잠시 뒤 다시 보면 `Synced`, `Healthy`다.

### 단계 9: 브라우저 접속 확인 `[학습자 직접 · 웹]`

`http://worklog-frontend.myk8s.local`을 열어 화면이 나오고 할 일이 저장되는지 본다.

## 검증 중 발견된 이슈 (강의자 참고)

- **같은 저장소에 파이프라인이 둘이면 rebase 충돌 또는 옛 태그로 역행**: frontend와 backend는 저장소가 달라 서로 충돌하지 않는다. backend 저장소에 6.7 워크플로를 켜 두거나 Jenkins(7.9)를 함께 돌리면, 같은 push로 여러 파이프라인이 같은 `deploy_manifest/` 파일을 고친다.
  - 증상: `CONFLICT (content): Merge conflict in deploy_manifest/worklog-backend.yaml` → `error: could not apply ...`, 또는 늦게 끝난 실행이 옛 태그로 덮음(run-38 7.9)
  - 해결: 저장소마다 이 파일을 고치는 파이프라인을 하나만 켠다(단계 0).

- **(run-40) build job이 `failed to fetch oauth token ... auth.docker.io/token: 500`으로 실패**: 러너가 베이스 이미지를 받는 중에 Docker Hub 인증 서버가 오류를 돌려준 것이다. 워크플로 문제가 아니다. Actions의 실행 화면에서 **Re-run failed jobs**를 누른다. 다시 돌린 실행은 통과했다.

## 주의사항

- ⛔ AI가 하지 말 것: GitHub Secrets를 직접 등록하거나 Docker Hub 토큰 값을 묻지 말 것
- ⛔ AI가 하지 말 것: 워크플로에 Docker Hub username을 글자로 적지 말 것. Secrets로 읽는다
- ⛔ AI가 하지 말 것: git push를 대신 하지 말 것. push가 파이프라인을 트리거하는 것을 학습자가 직접 본다
- ⛔ AI가 하지 말 것: backend의 `build-pipeline.yaml`을 지우거나 고치지 말 것. 꺼 둔 채로 둔다
- ✅ AI가 해도 됨: 워크플로 yaml 작성, Actions 로그 해석
- ⚠️ `deploy_manifest/**`를 paths-ignore에 넣지 않으면 파이프라인이 자기가 올린 커밋으로 다시 돈다
- ⚠️ write 권한이 없으면 deploy job의 git push가 `403`으로 실패한다(단계 1)
- ✅ deploy job은 push 전에 `git pull --rebase -X theirs origin main`을 한다. 그 사이 다른 커밋이 들어와도 push가 거절되지 않게 하기 위해서다
- ✅ 7.7에서 만든 Argo CD Application 두 개가 있어야 매니페스트 변경이 배포된다
