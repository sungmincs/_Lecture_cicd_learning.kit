# 7.8 [GitHub] 마이크로서비스 배포 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: GitHub Secrets 등록, write 권한 활성화, git push
> - `[AI 프롬프트]`: frontend/backend 각 파이프라인 yaml 작성

## 사전 조건

- ch5/5.3 또는 5.4 완료 (GitHub Actions 파이프라인 이해)
- ch7/7.7 완료 (두 저장소에 `deploy_manifest/`가 있고 Argo CD Application `worklog-frontend`, `worklog-backend`가 자동 sync 중)
- GitHub에 worklog-frontend-mock, worklog-backend 저장소 존재 (학습자 fork)

## 실행 지침

### 단계 0: 앞 절 파이프라인 끄기 `[학습자 직접]`

backend의 6.7 워크플로가 꺼져 있는지 본다(6.8 단계 0에서 껐다). 켜져 있으면 끈다. 이 절에서 backend에 새 워크플로를 만들기 때문에 둘 다 켜 두면 같은 push에 두 번 빌드한다. frontend는 처음 만드는 것이라 끌 것이 없다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

### 단계 1: GitHub Actions write 권한 활성화 `[학습자 직접]`

파이프라인에서 저장소에 git push하려면 write 권한이 필요하다.

저장소 → Settings → Actions → General → Workflow permissions
→ **Read and write permissions** 선택 → Save

> ⚠️ 두 저장소(worklog-frontend-mock, worklog-backend) 모두 설정 필요

### 단계 2: GitHub Secrets 등록 `[학습자 직접]`

두 저장소 모두에서: Settings → Secrets and variables → Actions

| Secret 이름 | 값 |
|---|---|
| `DOCKERHUB_USERNAME` | Docker Hub username |
| `DOCKERHUB_TOKEN` | Docker Hub Access Token |

### 단계 3: Frontend 파이프라인 yaml 작성 `[AI 프롬프트]`

> "worklog-frontend-mock GitHub Actions 파이프라인 만들어줘.
> - main 브랜치 push 시 트리거, deploy_manifest/** 변경은 제외 (paths-ignore)
> - Docker Hub username: `<dockerhub_username>`, image: `<dockerhub_username>/worklog-frontend-mock`
> - 이미지 태그: git SHA 앞 8자리
> - multi-arch 빌드 (linux/amd64, linux/arm64)
> - build job → deploy job 순서
> - deploy job: deploy_manifest/worklog-frontend.yaml의 image 필드 업데이트 후 git push"

✅ 정답 파일 (완성 후 비교): `ch7/7.8/1.frontend-build-deploy.yaml`

### 단계 4: Backend 파이프라인 yaml 작성 `[AI 프롬프트]`

> "worklog-backend GitHub Actions 파이프라인 만들어줘.
> - main 브랜치 push 시 트리거, deploy_manifest/** 변경은 제외 (paths-ignore)
> - Docker Hub username: `<dockerhub_username>`, image: `<dockerhub_username>/worklog-backend`
> - test job (uv, TESTING=true, pytest) → build job → deploy job 순서
> - 이미지 태그: git SHA 앞 8자리, multi-arch 빌드
> - deploy job: deploy_manifest/worklog-backend.yaml의 image 필드 및 IMAGE_TAG 환경변수 업데이트 후 git push
> - git push 전에 git pull --rebase origin main 실행"

✅ 정답 파일 (완성 후 비교): `ch7/7.8/2.backend-build-deploy.yaml`

### 단계 5: 파이프라인 적용 `[학습자 직접]`

단계 3, 4에서 AI가 만든 파일을 그대로 쓴다. 정답 파일(`ch7/7.8/1.frontend-build-deploy.yaml`, `2.backend-build-deploy.yaml`)은 비교용이다. 파일 이름은 두 저장소 모두 `.github/workflows/build-deploy.yaml`로 둔다.

```bash
# Frontend 저장소에서
git add .github/workflows/build-deploy.yaml
git commit -m "cicd: add frontend build and deploy pipeline"
git push origin main

# Backend 저장소에서
git add .github/workflows/build-deploy.yaml
git commit -m "cicd: add backend build and deploy pipeline"
git push origin main
```

### 단계 6: 파이프라인 실행 결과 확인 `[학습자 직접]`

- GitHub → Actions 탭에서 각 파이프라인 성공 여부 확인
- Docker Hub에서 새 이미지 태그 확인
- Argo CD에서 자동 sync 확인

접속 확인: `http://worklog-frontend.myk8s.local`

## 검증 중 발견된 이슈 (강의자 참고)

- **같은 저장소에 파이프라인이 둘이면 rebase 충돌 또는 옛 태그로 역행**: frontend와 backend는 저장소가 달라 서로 충돌하지 않는다. backend 저장소에 6.7 워크플로우를 남겨 두거나 Jenkins(7.9)를 함께 켜면, 같은 push로 여러 파이프라인이 같은 `deploy_manifest/` 파일을 고친다.
  - 증상: `CONFLICT (content): Merge conflict in deploy_manifest/worklog-backend.yaml` → `error: could not apply ...`, 또는 늦게 끝난 실행이 옛 태그로 덮음(run-38 7.9)
  - 해결: 저장소마다 이 파일을 고치는 파이프라인을 하나만 켠다.

## 주의사항

- ⛔ `<dockerhub_username>`을 임의로 채우지 말 것
- ⛔ `deploy_manifest/**`를 paths-ignore에 포함시켜야 무한 루프 방지
- ⛔ write 권한 없이 git push 시 `403 Permission denied` 오류 발생
- ✅ deploy job은 push 전에 `git pull --rebase -X theirs origin main`을 한다. 그 사이 다른 커밋이 들어와도 push가 거절되지 않게 하기 위해서다
- ✅ Frontend와 Backend는 독립 저장소에서 독립 파이프라인으로 운영
- ✅ 7.7에서 만든 Argo CD Application 두 개가 있어야 매니페스트 변경이 배포된다
