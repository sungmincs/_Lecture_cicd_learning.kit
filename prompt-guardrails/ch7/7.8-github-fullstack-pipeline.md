# 7.8 [GitHub] 마이크로서비스 배포 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 워크플로 확인, Argo CD와 배포 확인
> - `[학습자 직접 · 웹]`: frontend 저장소의 Actions 설정과 Secrets 등록, Actions 실행 결과 확인, 브라우저 접속
> - `[AI 프롬프트]`: frontend와 backend 파이프라인 yaml 작성(빈칸을 학습자가 채움), 저장소 2개에 push, 파이프라인이 올린 커밋 받기
>
> 저장소가 둘이다. frontend는 `/root/workspace/worklog-frontend`(main 브랜치), backend는 `/root/workspace/worklog-backend`다.
> 명령 블록의 첫 줄 `cd`가 어느 저장소인지 알려 준다.

## 사전 조건

- ch6/6.7 완료 (backend 저장소에 write 권한이 켜져 있고 Secret `DOCKERHUB_TOKEN`이 등록됨)
- ch7/7.7 완료 (저장소 2개에 `deploy_manifest/`가 있고 Argo CD Application `worklog-frontend`, `worklog-backend`가 자동 sync 중)
- 노드의 frontend clone이 `main` 브랜치임 (7.7 단계 3)

## 실행 지침

### 단계 1: 앞 절 파이프라인이 꺼져 있는지 확인 `[학습자 직접]`

backend의 6.7 워크플로(`build-pipeline.yaml`)는 6.8 단계 1에서 껐다. 꺼져 있는지 본다. 이 절에서 backend에 새 워크플로 파일을 만들기 때문에 둘 다 켜 두면 같은 push에 2번 빌드한다. frontend는 처음 만드는 것이라 끌 것이 없다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow list --all -R <github_username>/worklog-backend       # 모두 disabled_manually
gh workflow list --all -R <github_username>/worklog-frontend      # 아무것도 없음
```

`active`가 보이면 `gh workflow disable <파일 이름> -R <github_username>/worklog-backend`로 끈다.

### 단계 2: frontend 저장소의 Actions 설정 `[학습자 직접 · 웹]`

파이프라인이 저장소에 git push하려면 write 권한이 필요하다. backend는 6.7 단계 2에서 했다. frontend 저장소에서 같은 설정을 한다.

GitHub의 fork `worklog-frontend` → Settings → Actions → General → Workflow permissions → **Read and write permissions** → Save

fork한 저장소는 Actions 탭에 "Workflows aren't being run on this forked repository"가 보일 수 있다. 보이면 **I understand my workflows, go ahead and enable them**을 누른다.

### 단계 3: 저장소 2개에 Secrets 등록 `[학습자 직접 · 웹]`

이 절의 파이프라인은 Docker Hub username도 Secret으로 읽는다. 6.7까지의 backend 워크플로는 username을 yaml에 직접 적었으므로 backend 저장소에는 `DOCKERHUB_TOKEN`만 있다.

각 fork → Settings → Secrets and variables → Actions → New repository secret

| 저장소 | Secret 이름 | 값 |
|---|---|---|
| `worklog-frontend` | `DOCKERHUB_USERNAME` | Docker Hub username |
| `worklog-frontend` | `DOCKERHUB_TOKEN` | Docker Hub Access Token. 5.3 단계 2에서 발급한 값을 보관해 두지 않았으면 같은 방법으로 새로 발급한다 |
| `worklog-backend` | `DOCKERHUB_USERNAME` | Docker Hub username. `DOCKERHUB_TOKEN`은 5.3 단계 3에서 이미 넣었다 |

backend에 `DOCKERHUB_USERNAME`을 등록하지 않으면 단계 8의 build job이 `Username required`로 실패한다. 그때는 Secret을 넣고 Actions 탭에서 Re-run failed jobs를 누른다.

### 단계 4: Frontend 파이프라인 yaml 작성 `[AI 프롬프트]`

`[채우기: ...]` 2줄은 학습자가 작성한다. 프롬프트 전체를 복사해 붙여 넣고 그 자리를 작성한 뒤 보낸다. 이 절에서 배울 내용이 그 자리에 있다.


```text
frontend의 GitHub Actions 파이프라인을 만들어줘. 이미지를 빌드하고 매니페스트의 태그만 바꿔 배포는 Argo CD에 맡기려는 거야.
파일: /root/workspace/worklog-frontend/.github/workflows/build-deploy.yaml
조건:
- main push에 트리거, permissions: contents write
- [채우기: 파이프라인이 자기가 올린 커밋으로 다시 실행되지 않게 하는 조건]
- 이미지: ${{ secrets.DOCKERHUB_USERNAME }}/worklog-frontend, 태그는 SHA 앞 8자, amd64와 arm64
- build job 다음에 deploy job, concurrency(cancel-in-progress: false)
- [채우기: deploy job이 할 일. 어느 파일의 어느 줄을 바꿔 커밋하는지]
- deploy job은 push 전에 git pull --rebase -X theirs origin main
끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.
```

직접 쓴 줄은 아래 예시와 비교한다. 표현이 달라도 뜻이 같으면 된다. 빈칸을 쓴 뒤에 펼친다.

<details>
<summary>예시 보기</summary>

| 빈칸 | 예시 | 이 줄이 필요한 이유 |
|---|---|---|
| 다시 실행되지 않게 하는 조건 | `deploy_manifest/**` 경로만 바뀐 push는 paths-ignore로 무시해줘 | 매니페스트만 수정한 push로 빌드와 배포가 다시 실행되지 않게 한다 |
| deploy job이 할 일 | `deploy_manifest/worklog-frontend.yaml`의 image 줄을 새 태그로 바꿔 커밋하고 push해줘 | 배포는 Argo CD가 매니페스트를 보고 한다. 파이프라인은 매니페스트만 바꾼다 |

</details>

✅ 정답 파일 (완성 후 비교): `ch7/7.8/1.frontend-build-deploy.yaml`

### 단계 5: Backend 파이프라인 yaml 작성 `[AI 프롬프트]`

backend는 frontend와 구조가 같다. 다른 부분 2가지를 학습자가 작성한다.

```text
backend의 GitHub Actions 파이프라인을 새 파일로 만들어줘. frontend와 같은 방식으로 빌드하고 매니페스트만 바꾸려는 거야.
파일: /root/workspace/worklog-backend/.github/workflows/build-deploy.yaml
조건:
- 구조는 /root/workspace/worklog-frontend의 build-deploy.yaml과 같게, 이미지만 ${{ secrets.DOCKERHUB_USERNAME }}/worklog-backend
- [채우기: frontend와 다른 부분 1. build job 앞에 할 일]
- [채우기: frontend와 다른 부분 2. 매니페스트에서 image 줄과 함께 바꿀 줄]
- 기존 build-pipeline.yaml은 그대로 둬.
끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.
```

<details>
<summary>예시 보기</summary>

| 빈칸 | 예시 | 이 줄이 필요한 이유 |
|---|---|---|
| build job 앞에 할 일 | build job 앞에 test job을 둬줘. 테스트 내용은 기존 `build-pipeline.yaml`의 init-and-test job과 같게 | 테스트를 통과한 코드만 이미지로 만든다(5.3, 6.7과 같다) |
| image 줄과 함께 바꿀 줄 | `# IMAGE_TAG` 주석이 붙은 IMAGE_TAG 값도 새 태그로 바꿔줘 | 7.7의 backend 매니페스트는 `/health`에 태그를 보여 주려고 IMAGE_TAG를 갖고 있다 |

</details>

✅ 정답 파일 (완성 후 비교): `ch7/7.8/2.backend-build-deploy.yaml`

6.7처럼 매니페스트를 고쳐 push하면 끝이고, 자동 sync가 켜진 Argo CD가 알아서 배포한다. 6.8의 Jenkins와 달리 Argo CD에 sync를 요청하지 않으므로 Argo CD 비밀번호도 파이프라인에 필요 없다. 6.7과 다른 부분은 Docker Hub username을 yaml에 적지 않고 Secret `DOCKERHUB_USERNAME`으로 읽는다는 것이다.

### 단계 6: 저장소 2개에 push `[AI 프롬프트]`

git add, commit, push는 ch3부터 손으로 여러 번 했다. 이 절부터는 AI에게 맡기고, push로 파이프라인이 시작되는 것은 단계 7에서 Actions 탭으로 직접 본다.

```text
저장소 2개에서 방금 만든 build-deploy.yaml을 커밋하고 push해줘. push하면 파이프라인 2개가 시작돼.
조건:
- 커밋 메시지: frontend는 cicd: add frontend build and deploy pipeline, backend는 cicd: add backend build and deploy pipeline
- push 전에 git pull --rebase
끝나면: 저장소 2개의 push 결과를 보여줘.
```

기대 결과: 저장소 2개에 커밋이 1개씩 push되고 `main -> main`이 보인다.

### 단계 7: 파이프라인 실행 결과 확인 `[학습자 직접 · 웹]`

fork 2개의 Actions 탭에서 방금 push한 커밋의 실행이 성공하는지 본다. 워크플로 이름은 AI가 지은 것이라 정답 파일의 `Frontend Build and Deploy`, `Backend Build and Deploy`와 다를 수 있다(run-40에서 backend는 `worklog backend build-deploy`였다). 이름이 달라도 동작은 같다. frontend는 Node 의존성을 아키텍처 2개로 설치해서 backend보다 오래 걸린다(backend 2분, frontend 약 4분).
끝나면 각 저장소의 커밋 목록에 `deploy: update ... image to <8자>` 커밋이 하나씩 생긴다. 이 커밋은 `deploy_manifest/`만 바꾸므로 파이프라인이 다시 돌지 않는다.

### 단계 8: 파이프라인이 올린 커밋 받기 `[AI 프롬프트]`

```text
저장소 2개에서 파이프라인이 올린 커밋을 git pull --rebase로 받아 와줘. 받지 않으면 다음 push가 거절돼.
끝나면: 매니페스트 2개의 image 줄을 보여줘.
```

기대 결과: 매니페스트 2개의 태그가 단계 7에서 본 커밋 해시의 앞 8자다. 받지 않으면 다음 push가 거절된다.

### 단계 9: Argo CD와 배포 확인 `[학습자 직접]`

AI가 보여 준 태그를 클러스터에서 직접 확인한다.

```bash
argocd app get worklog-frontend --refresh | grep -E "Sync Status|Health Status"
argocd app get worklog-backend  --refresh | grep -E "Sync Status|Health Status"
kubectl get deployment worklog-frontend worklog-backend -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image
```

기대 결과: Deployment 2개의 이미지가 단계 8에서 본 태그다. `--refresh` 직후에는 `OutOfSync`나 `Progressing`이 보일 수 있다. 잠시 뒤 다시 보면 `Synced`, `Healthy`다.

### 단계 10: 브라우저 접속 확인 `[학습자 직접 · 웹]`

`http://worklog-frontend.myk8s.local`을 열어 화면이 나오고 할 일이 저장되는지 본다.

## 검증 중 발견된 이슈 (강의자 참고)

- **같은 저장소에 파이프라인이 둘이면 rebase 충돌 또는 이전 태그로 역행**: frontend와 backend는 저장소가 달라 서로 충돌하지 않는다. backend 저장소에 6.7 워크플로를 켜 두거나 Jenkins(7.9)를 함께 돌리면, 같은 push로 여러 파이프라인이 같은 `deploy_manifest/` 파일을 고친다.
  - 증상: `CONFLICT (content): Merge conflict in deploy_manifest/worklog-backend.yaml` → `error: could not apply ...`, 또는 늦게 끝난 실행이 이전 태그로 덮음(run-38 7.9)
  - 해결: 저장소마다 이 파일을 고치는 파이프라인을 하나만 켠다(단계 1).

- **(run-40) build job이 `failed to fetch oauth token ... auth.docker.io/token: 500`으로 실패**: 러너가 베이스 이미지를 받는 중에 Docker Hub 인증 서버가 오류를 돌려준 것이다. 워크플로 문제가 아니다. Actions의 실행 화면에서 **Re-run failed jobs**를 누른다. 다시 돌린 실행은 통과했다.

## 주의사항

- ⛔ AI가 하지 말 것: GitHub Secrets를 직접 등록하거나 Docker Hub 토큰 값을 묻지 말 것
- ⛔ AI가 하지 말 것: 워크플로에 Docker Hub username을 글자로 적지 말 것. Secrets로 읽는다
- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ⛔ AI가 하지 말 것: 단계 6, 8 말고는 커밋하거나 push하지 말 것. force push는 하지 말 것
- ⛔ AI가 하지 말 것: backend의 `build-pipeline.yaml`을 지우거나 고치지 말 것. 꺼 둔 채로 둔다
- ✅ AI가 해도 됨: 워크플로 yaml 작성, 단계 6의 커밋과 push, 단계 8의 git pull, Actions 로그 해석
- ⚠️ `deploy_manifest/**`를 paths-ignore에 넣지 않으면 매니페스트만 수정한 push에도 빌드와 배포가 다시 실행된다. deploy job이 GITHUB_TOKEN으로 올린 커밋은 GitHub 규칙상 새 실행을 만들지 않으므로 끝없이 반복되지는 않는다
- ⚠️ 워크플로 파일에 `permissions: contents: write`가 없고 저장소의 Workflow permissions도 Read이면 deploy job의 git push가 `403`으로 실패한다. 파일에 permissions가 있으면 단계 2 설정이 Read여도 push된다(6.7 단계 2와 같다)
- ✅ deploy job은 push 전에 `git pull --rebase -X theirs origin main`을 한다. 그 사이 다른 커밋이 들어와도 push가 거절되지 않게 하기 위해서다
- ✅ 7.7에서 만든 Argo CD Application 2개가 있어야 매니페스트 변경이 배포된다
