# 7.3 Rolling Update 배포 실습

> **학습자 진입 방식**:
> - `[학습자 직접]`: 작업 폴더와 태그 확인, imagePullSecret 생성(자격 증명), 전략 설정 확인, 이미지 업데이트, 롤백
> - `[AI 프롬프트]`: Argo CD 자동 sync 비활성화, Deployment yaml 작성(빈칸을 학습자가 채움), 적용, 정리
>
> 교체(`set image`)와 롤백(`rollout undo`)은 이 절에서 관찰할 실험이라 학습자가 직접 한다. 적용과 정리처럼 ch3부터 손으로 해 본 실행은 AI에게 맡긴다(`prompt-guardrails/shared/step-labels.md`).
>
> 7.3부터 7.7까지 만드는 yaml은 fork 저장소에 넣지 않는다. 컨트롤 플레인 노드의 `/root/ch7/`에 둔다.
> 배포 전략을 손으로 바꿔 보는 연습용 파일이고, Argo CD가 보는 `deploy_manifest/`와 섞이면 안 되기 때문이다.

## 사전 조건

- ch6 완료 (Argo CD Application `worklog-backend`가 Synced, Healthy)
- Docker Hub에 worklog-backend 이미지가 태그 2개 이상으로 있음 (3.5의 `buildtest1`, 6.7과 6.8 파이프라인이 올린 8자 SHA 태그)

## 실행 지침

### 단계 1: Argo CD 자동 sync 비활성화 `[AI 프롬프트]`

Argo CD가 자동 sync(selfHeal) 중이면 kubectl로 바꾼 내용이 저장소의 매니페스트로 바로 되돌려진다. 7.3부터 7.6까지는 kubectl로 직접 바꾸는 실습이라 먼저 비활성화한다. 7.7 단계 9에서 다시 활성화한다.

```text
Argo CD의 worklog-backend Application에서 자동 sync를 비활성화해줘. 이 절에서 kubectl로 바꾸는 내용을 Argo CD가 저장소의 매니페스트로 되돌리지 않게 하려는 거야.
끝나면: Sync Policy가 Manual인지 보여줘.
```

기대 결과: `Sync Policy:        Manual`. AI는 `argocd app set worklog-backend --sync-policy none`을 실행한다. argocd 로그인이 만료됐다고 나오면 6.4의 로그인은 비밀번호가 필요하므로 학습자가 직접 다시 한다.

### 단계 2: 작업 폴더와 태그 확인 `[학습자 직접]`

```bash
mkdir -p /root/ch7
grep "image:" /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml
```

출력에 보이는 8자 태그가 지금 클러스터에 배포된 이미지다. 이 장에서는 태그 2개를 쓴다.

| 플레이스홀더 | 쓰는 값 |
|---|---|
| `<image_tag>` | `buildtest1` (3.5에서 올린 이미지. 처음 배포에 쓴다) |
| `<new_tag>` | 위 명령에 보인 8자 SHA 태그 (업데이트에 쓴다) |

### 단계 3: imagePullSecret 만들기 `[학습자 직접]`

단계 4의 yaml부터 7장의 매니페스트는 `imagePullSecrets: dockerhub-creds`를 쓴다. Docker Hub에 로그인한 상태로 이미지를 받으려고 쓴다. 비인증 pull은 6시간에 100회로 제한돼(3.7) 실습을 반복하면 한도에 걸릴 수 있다. 토큰은 자격 증명이라 직접 넣는다.

```bash
read -rs DOCKERHUB_TOKEN    # Docker Hub Access Token을 붙여넣고 Enter. 화면과 셸 기록에 남지 않는다
kubectl create secret docker-registry dockerhub-creds \
  --docker-username=<dockerhub_username> \
  --docker-password="$DOCKERHUB_TOKEN" \
  --docker-server=https://index.docker.io/v1/
unset DOCKERHUB_TOKEN
kubectl get secret dockerhub-creds
```

이 Secret은 7.5 이후와 ch8, ch9의 매니페스트도 쓴다. 7.3 단계 9에서 지우지 않는다.

### 단계 4: Rolling Update Deployment yaml 작성 `[AI 프롬프트]`

`[채우기: ...]` 한 줄은 학습자가 작성한다. 프롬프트 전체를 복사해 붙여 넣고 그 자리를 작성한 뒤 보낸다. 이 절에서 배울 내용이 그 자리에 있다.

```text
worklog-backend의 Rolling Update Deployment yaml을 만들어줘. 교체 중에도 요청을 받는 Pod 수가 줄지 않게 하려는 거야.
파일: /root/ch7/1.worklog-backend-deployment-rolling.yaml
조건:
- replicas: 3, imagePullSecrets: dockerhub-creds
- [채우기: 교체할 때 Pod를 몇 개까지 더 만들고 몇 개까지 멈춰도 되는지]
- image: <dockerhub_username>/worklog-backend:<image_tag>, containerPort: 80
- liveness/readiness probe: /health (port 80)
참고: env는 deploy_manifest/worklog-backend.yaml(backend 저장소)의 MONGO_HOST와 Secret 참조 2개를 그대로 사용해줘.
끝나면: dry-run으로 검사하고 파일을 보여줘. 적용 전에 멈춰줘.
```

직접 쓴 줄은 아래 예시와 비교한다. 빈칸을 쓴 뒤에 펼친다.

<details>

| 멈춰도 되는 Pod 수 | maxUnavailable: 0 | 새 Pod가 Ready가 된 뒤에 기존 Pod를 내려 요청을 받는 Pod가 3개 아래로 줄지 않는다 |

### 단계 5: Deployment 배포 `[AI 프롬프트]`

```text
/root/ch7/1.worklog-backend-deployment-rolling.yaml을 클러스터에 적용해줘. 6.5에서 Argo CD가 만든 같은 이름의 Deployment를 이 파일로 바꾸는 거야.
조건:
- 적용하기 전에 image 줄에 <dockerhub_username> 같은 플레이스홀더가 남지 않았는지 보고, 남아 있으면 멈춰줘.
끝나면: rollout status로 끝날 때까지 기다린 뒤 Pod 목록을 보여줘.
```

6.5가 만든 Deployment와 이름이 같아 apply 결과가 `created`가 아니라 `configured`로 나온다. Pod는 3개가 된다.

### 단계 6: Rolling Update 전략 설정 확인 `[학습자 직접]`

```bash
kubectl describe deployment worklog-backend | grep -A5 Strategy
```

기대 결과: `StrategyType: RollingUpdate`, `RollingUpdateStrategy: 0 max unavailable, 1 max surge`

### 단계 7: 이미지 업데이트로 Rolling Update 트리거 `[학습자 직접]`

```bash
kubectl set image deployment/worklog-backend worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl rollout status deployment/worklog-backend
```

기대 결과: `1 out of 3 new replicas have been updated`부터 한 개씩 바뀌고 `successfully rolled out`으로 끝난다. maxUnavailable이 0이라 새 Pod가 Ready가 된 뒤에 기존 Pod를 하나 내린다.

### 단계 8: 롤백 실습 `[학습자 직접]`

```bash
kubectl rollout undo deployment/worklog-backend
kubectl rollout status deployment/worklog-backend
kubectl rollout history deployment/worklog-backend
kubectl get deployment worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # <image_tag>로 돌아왔다
```

### 단계 9: 리소스 정리 `[AI 프롬프트]`

```text
worklog-backend Deployment를 지워줘. 7.5에서 같은 이름의 Argo Rollouts Rollout을 만들기 때문이야.
조건:
- Service와 HTTPRoute worklog-backend, Secret dockerhub-creds는 남겨 둬.
끝나면: 남은 worklog-backend Service, HTTPRoute 그리고 dockerhub-creds Secret을 보여줘.
```

7.5의 Rollout이 같은 이름을 쓰므로 지우고 넘어간다. Service와 HTTPRoute `worklog-backend`는 그대로 둔다.

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username | ❌ 반드시 확인 |
| `<image_tag>` | 처음 배포할 이미지 태그. 단계 2의 표 | ❌ 반드시 확인 |
| `<new_tag>` | 업데이트할 이미지 태그. 단계 2의 표. Docker Hub에 실제로 있는 태그여야 한다 | ❌ 반드시 확인 |

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`과 태그를 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: Docker Hub token을 묻거나 단계 3의 Secret을 대신 만들지 말 것
- ⛔ AI가 하지 말 것: yaml을 fork 저장소(`/root/workspace/worklog-backend/`) 안에 저장하지 말 것. `/root/ch7/`에 둔다
- ⛔ AI가 하지 말 것: `kubectl set image`, `kubectl rollout undo`를 대신 실행하지 말 것. 교체와 롤백은 학습자가 직접 보는 실험이다
- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ✅ AI가 해도 됨: 단계 1의 자동 sync 비활성화, yaml 작성, 단계 5의 적용, 단계 9의 정리, `rollout status` 출력 해석
- ✅ Rolling Update는 K8s 기본 기능이다. Argo Rollouts 없이 동작한다
- ✅ 이 실습은 7.5(Blue-Green), 7.6(Canary)와 비교하는 기준이다
- ⚠️ 이 절이 끝나면 Argo CD의 `worklog-backend`는 `OutOfSync`로 보인다. 자동 sync를 꺼 두었기 때문이고 7.7에서 다시 맞춘다
