# 7.3 Rolling Update 배포 실습

> **학습자 진입 방식**:
> - `[학습자 직접]`: Argo CD 자동 sync 끄기, 작업 폴더와 태그 확인, kubectl apply, 이미지 업데이트, 롤백, 정리
> - `[AI 프롬프트]`: Rolling Update 전략 Deployment yaml 작성
>
> 7.3부터 7.7까지 만드는 yaml은 fork 저장소에 넣지 않는다. 컨트롤 플레인 노드의 `/root/ch7/`에 둔다.
> 배포 전략을 손으로 바꿔 보는 연습용 파일이고, Argo CD가 보는 `deploy_manifest/`와 섞이면 안 되기 때문이다.

## 사전 조건

- ch6 완료 (Argo CD Application `worklog-backend`가 Synced, Healthy)
- Docker Hub에 worklog-backend 이미지가 태그 2개 이상으로 있음 (3.5의 `buildtest1`, 6.7과 6.8 파이프라인이 올린 8자 SHA 태그)

## 실행 지침

### 단계 0: Argo CD 자동 sync 끄기 `[학습자 직접]`

Argo CD가 자동 sync(selfHeal) 중이면 kubectl로 바꾼 내용이 Git 상태로 바로 되돌려진다. 7.3부터 7.6까지는 kubectl로 직접 바꾸는 실습이라 먼저 끈다. 7.7 단계 9에서 다시 켠다.

```bash
argocd app set worklog-backend --sync-policy none
argocd app get worklog-backend | grep "Sync Policy"      # Manual
```

### 단계 1: 작업 폴더와 태그 확인 `[학습자 직접]`

```bash
mkdir -p /root/ch7
grep "image:" /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml
```

출력에 보이는 8자 태그가 지금 클러스터에 배포된 이미지다. 이 장에서는 태그 두 개를 쓴다.

| 플레이스홀더 | 쓰는 값 |
|---|---|
| `<image_tag>` | `buildtest1` (3.5에서 올린 이미지. 처음 배포에 쓴다) |
| `<new_tag>` | 위 명령에 보인 8자 SHA 태그 (업데이트에 쓴다) |

### 단계 2: Rolling Update Deployment yaml 작성 `[AI 프롬프트]`

> "worklog-backend를 Rolling Update 전략으로 배포하는 Kubernetes Deployment yaml을 만들어서 컨트롤 플레인 노드의 `/root/ch7/1.worklog-backend-deployment-rolling.yaml`로 저장해줘. 적용은 내가 할게.
> - replicas: 3, maxSurge: 1, maxUnavailable: 0
> - imagePullSecrets: dockerhub-creds
> - image: `<dockerhub_username>/worklog-backend:<image_tag>`, containerPort: 80
> - env는 `/root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml`의 MONGO_HOST와 worklog-mongodb-creds Secret 참조 두 개를 그대로 써줘
> - liveness/readiness probe: /health (port 80)"

✅ 정답 파일 (완성 후 비교): `ch7/7.3/1.worklog-backend-deployment-rolling.yaml`

### 단계 3: Deployment 배포 `[학습자 직접]`

```bash
cd /root/ch7
grep "image:" 1.worklog-backend-deployment-rolling.yaml      # 플레이스홀더가 아니라 실제 값인지 확인
kubectl apply -f 1.worklog-backend-deployment-rolling.yaml
kubectl rollout status deployment/worklog-backend
kubectl get pods -l app=worklog-backend
```

6.5가 만든 Deployment와 이름이 같아 apply 결과가 `created`가 아니라 `configured`로 나온다. Pod는 3개가 된다.

### 단계 4: Rolling Update 전략 설정 확인 `[학습자 직접]`

```bash
kubectl describe deployment worklog-backend | grep -A5 Strategy
```

기대 결과: `StrategyType: RollingUpdate`, `RollingUpdateStrategy: 0 max unavailable, 1 max surge`

### 단계 5: 이미지 업데이트로 Rolling Update 트리거 `[학습자 직접]`

```bash
kubectl set image deployment/worklog-backend worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl rollout status deployment/worklog-backend
```

기대 결과: `1 out of 3 new replicas have been updated`부터 한 개씩 바뀌고 `successfully rolled out`으로 끝난다. maxUnavailable이 0이라 새 Pod가 Ready가 된 뒤에 옛 Pod를 하나 내린다.

### 단계 6: 롤백 실습 `[학습자 직접]`

```bash
kubectl rollout undo deployment/worklog-backend
kubectl rollout status deployment/worklog-backend
kubectl rollout history deployment/worklog-backend
kubectl get deployment worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # <image_tag>로 돌아왔다
```

### 단계 7: 리소스 정리 `[학습자 직접]`

```bash
kubectl delete deployment worklog-backend
```

7.5의 Rollout이 같은 이름을 쓰므로 지우고 넘어간다. Service와 HTTPRoute `worklog-backend`는 그대로 둔다.

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username | ❌ 반드시 확인 |
| `<image_tag>` | 처음 배포할 이미지 태그. 단계 1의 표 | ❌ 반드시 확인 |
| `<new_tag>` | 업데이트할 이미지 태그. 단계 1의 표. Docker Hub에 실제로 있는 태그여야 한다 | ❌ 반드시 확인 |

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`과 태그를 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: yaml을 fork 저장소(`/root/workspace/worklog-backend/`) 안에 저장하지 말 것. `/root/ch7/`에 둔다
- ⛔ AI가 하지 말 것: `kubectl apply`, `kubectl set image`를 대신 실행하지 말 것. 이 절은 학습자가 교체 과정을 직접 본다
- ✅ AI가 해도 됨: yaml 작성, `rollout status` 출력 해석
- ✅ Rolling Update는 K8s 기본 기능이다. Argo Rollouts 없이 동작한다
- ✅ 이 실습은 7.5(Blue-Green), 7.6(Canary)와 비교하는 기준이다
- ⚠️ 이 절이 끝나면 Argo CD의 `worklog-backend`는 `OutOfSync`로 보인다. 자동 sync를 꺼 두었기 때문이고 7.7에서 다시 맞춘다
