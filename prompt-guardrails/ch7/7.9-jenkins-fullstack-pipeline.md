# 7.9 [Jenkins] 마이크로서비스 배포 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: GitHub 워크플로 끄기, Jenkinsfile git push, 파이프라인이 올린 커밋 받기, Argo CD 확인
> - `[학습자 직접 · 웹]`: Jenkins Credentials 확인, frontend job 만들기, 스캔과 빌드 확인, 브라우저 접속
> - `[AI 프롬프트]`: frontend와 backend Jenkinsfile 작성
>
> 저장소가 둘이다. frontend는 `/root/workspace/worklog-frontend`(main 브랜치), backend는 `/root/workspace/worklog-backend`다.

## 사전 조건

- ch6/6.8 완료 (Jenkins에 `dockerhub-credentials`, `github-token`이 있고 `worklog-backend` Multibranch job이 있음)
- 6.8 단계 1의 GitHub 토큰이 fork `worklog-frontend`에도 Contents: Read and write 권한을 가짐
- ch7/7.8 완료 (두 저장소에 `deploy_manifest/`가 있고 Argo CD Application 둘이 자동 sync 중, 노드의 두 clone이 `git pull --rebase`까지 마친 상태)

## 실행 지침

### 단계 0: GitHub Actions 워크플로 끄기 `[학습자 직접]`

두 저장소 모두 7.8 워크플로와 Jenkins가 같은 main을 보고 `deploy_manifest/`를 고친다. Jenkinsfile 변경은 `paths-ignore` 대상이 아니라 같은 push로 GitHub Actions도 돈다. 함께 켜 두면 늦게 끝난 실행이 매니페스트를 옛 태그로 되돌릴 수 있다. 7.9를 마쳐도 다시 켜지 않는다. 다음 GitHub 절의 단계 0이 정한다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow disable build-deploy.yaml -R <github_username>/worklog-frontend
gh workflow disable build-deploy.yaml -R <github_username>/worklog-backend
gh workflow list --all -R <github_username>/worklog-frontend      # 모두 disabled_manually
gh workflow list --all -R <github_username>/worklog-backend       # 모두 disabled_manually
```

### 단계 1: Jenkins Credentials 확인 `[학습자 직접 · 웹]`

Jenkins → Dashboard → Jenkins 관리 → Credentials → System → Global. 새로 넣는 것은 없고 아래 둘이 있는지 본다.

| 종류 | ID | 값 |
|---|---|---|
| Username with password | `dockerhub-credentials` | Docker Hub username + Access Token (5.5에서 등록) |
| Username with password | `github-token` | GitHub username + Personal Access Token (6.8에서 등록) |

### 단계 2: Frontend Jenkinsfile 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-frontend/Jenkinsfile`에 frontend Jenkins 파이프라인을 만들어줘. push는 내가 할게.
> - agent: `agent { label 'jenkins-jenkins-agent' }` (컨트롤러에는 docker가 없다. 4.5, 5.5와 같은 라벨)
> - Credentials: dockerhub-credentials, github-token
> - 이미지: `<Docker Hub username>/worklog-frontend`, username은 dockerhub-credentials에서 읽기. 태그는 `git rev-parse --short=8 HEAD`
> - `--platform`을 주지 않고 에이전트 노드의 아키텍처 하나로만 빌드 (docker build 뒤 docker push). 로컬 에이전트에서 멀티 아키텍처로 빌드하면 메모리가 모자란다
> - 단계: Init → Build Image → Update Manifest
> - Update Manifest: deploy_manifest/worklog-frontend.yaml의 image 줄을 새 태그로 바꿔 커밋하고, `git pull --rebase origin main` 뒤에 GitHub의 main에 push
> - push할 저장소: github-token의 username 아래 `worklog-frontend`"

✅ 정답 파일 (완성 후 비교): `ch7/7.9/1.frontend-build-deploy.groovy`

### 단계 3: Backend Jenkinsfile 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Jenkinsfile`을 새 내용으로 바꿔줘. push는 내가 할게.
> - agent: `agent { label 'jenkins-jenkins-agent' }`
> - Credentials: dockerhub-credentials, github-token
> - 이미지: `<Docker Hub username>/worklog-backend`, username은 dockerhub-credentials에서 읽기. 태그는 `git rev-parse --short=8 HEAD`
> - multi-arch 빌드 (linux/amd64, linux/arm64, docker buildx)
> - 단계: Init → Run Test (uv 0.11.18 설치 스크립트, `uv sync --extra dev`, TESTING=true로 pytest와 coverage) → Build Image → Update Manifest
> - Update Manifest: deploy_manifest/worklog-backend.yaml의 image 줄과 `# IMAGE_TAG` 주석이 붙은 IMAGE_TAG 값을 새 태그로 바꿔 커밋하고, `git pull --rebase origin main` 뒤에 GitHub의 main에 push
> - push할 저장소: github-token의 username 아래 `worklog-backend`
> - 6.8에 있던 argocd CLI 설치와 sync 단계는 빼줘. 자동 sync가 켜져 있어 필요 없다"

✅ 정답 파일 (완성 후 비교): `ch7/7.9/2.backend-build-deploy.groovy`

### 단계 4: frontend Multibranch job 만들기 `[학습자 직접 · 웹]`

Jenkins → New Item → 이름 `worklog-frontend` → Multibranch Pipeline → OK.
Branch Sources에서 Add source → Git을 고르고 Project Repository에 `https://github.com/<github_username>/worklog-frontend.git`를 넣는다. 공개 저장소라 Credentials는 비워 둔다.
Build Configuration은 by Jenkinsfile 그대로 두고 Save를 누른다. backend job은 6.8에서 쓰던 `worklog-backend`를 그대로 쓴다.

저장하면 Jenkins가 한 번 스캔한다. 아직 Jenkinsfile을 push하지 않았으므로 빌드할 브랜치를 찾지 못한다. `mock` 브랜치에도 Jenkinsfile이 없어 대상이 아니다.

## 검증 중 발견된 이슈 (강의자 참고)

- **(run-38) GitHub 워크플로를 켠 채로 Jenkinsfile을 push하면 frontend 매니페스트가 옛 태그로 되돌아갔다**: `0d5222e` push로 시작한 GitHub 실행이 4분 넘게 걸리는 사이 Jenkins #2가 `c251ea2f`로 매니페스트를 갱신했다. 늦게 끝난 GitHub 실행이 `git pull --rebase -X theirs`로 `0d5222e2`를 덮었고, 클러스터에는 옛 커밋 이미지가 배포됐다. backend는 같은 커밋을 Jenkins, 7.8, 6.7이 세 번 빌드했다. 단계 0대로 워크플로를 끄고 진행한다.

- **(run-38) `agent any`로 컨트롤러에 배정되면 `docker: not found`**: 컨트롤러 실행기(numExecutors: 2)에는 docker가 없다. 정답 파일은 `agent { label 'jenkins-jenkins-agent' }`를 쓴다.

- **Frontend Jenkinsfile의 `git push` 실패**: `git push origin HEAD:main` 전에 `git pull --rebase origin main`이 없으면, 그 사이 다른 커밋이 올라온 경우 `! [rejected] HEAD -> main (fetch first)`가 난다. 정답 파일은 커밋 뒤, push 직전에 pull --rebase를 한다.

- **(run-15) Frontend 멀티 아키텍처 빌드에서 메모리 부족**: frontend(Node/yarn)를 `--platform linux/amd64,linux/arm64`로 빌드하면 Jenkins 에이전트(로컬 VM 노드)에서 다른 아키텍처를 QEMU로 에뮬레이션하며 메모리를 다 쓴다. 에이전트 Pod가 offline과 online을 반복하고 빌드가 멈춘다. backend(Python/uv)는 가벼워서 멀티 아키텍처로도 된다.
  - 증상: 콘솔에 `... seems to be removed or offline (InterruptedException)` 반복, 노드 `free`가 수십 MB
  - 해결: frontend는 `--platform` 없이 에이전트 노드의 아키텍처 하나로 빌드한다(2026-10-10 정답 파일 반영). 멀티 아키텍처 이미지는 7.8처럼 GitHub의 러너에서 만든다.

## 주의사항

- ⛔ AI가 하지 말 것: Jenkinsfile에 username이나 토큰을 글자로 적지 말 것. `credentials()`로 읽는다
- ⛔ AI가 하지 말 것: `agent any`를 쓰지 말 것. 컨트롤러 실행기로 배정되면 `docker: not found`로 실패한다(run-38)
- ⛔ AI가 하지 말 것: git push와 Jenkins 스캔을 대신 하지 말 것
- ✅ AI가 해도 됨: Jenkinsfile 작성, Console Output 해석
- ⚠️ 이 절을 하는 동안 두 저장소의 GitHub Actions 워크플로를 끈다(단계 0). 같은 매니페스트를 두 도구가 고치면 늦게 끝난 쪽이 옛 태그로 덮는다
- ⚠️ Credentials ID가 Jenkinsfile의 `credentials()` 호출과 글자까지 같아야 한다
- ⚠️ frontend와 backend 빌드를 함께 돌리지 않는다. 하나가 끝난 뒤 다음 것을 스캔한다
- ⚠️ frontend push가 `403`이면 6.8 단계 1의 토큰에 fork `worklog-frontend`가 빠진 것이다. GitHub에서 토큰의 Repository access에 저장소를 더한다
- ✅ 7.7에서 만든 Argo CD Application 두 개가 있어야 매니페스트 변경이 배포된다
