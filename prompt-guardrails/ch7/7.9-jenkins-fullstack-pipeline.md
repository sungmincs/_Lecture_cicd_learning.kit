## 사전 조건

- ch5/5.5 또는 5.6 완료 (Jenkins 파이프라인 이해)

## 실행 지침

### 단계 0: GitHub Actions 워크플로우 끄기 `[학습자 직접]`

두 저장소 모두 7.8 워크플로우(backend는 6.7 것이 남아 있으면 그것도)와 Jenkins가 같은 main을 보고 `deploy_manifest/`를 고친다. Jenkinsfile 변경은 `paths-ignore` 대상이 아니라 같은 push로 GitHub Actions도 돈다. 함께 켜 두면 늦게 끝난 실행이 매니페스트를 옛 태그로 되돌릴 수 있다. 저장소 → Actions → 해당 워크플로우 → Disable workflow. 7.9를 마쳐도 다시 켜지 않는다. 다음 GitHub 절의 단계 0이 정한다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

## 검증 중 발견된 이슈 (강의자 참고)

- **(run-38) GitHub 워크플로우를 켠 채로 Jenkinsfile을 push하면 frontend 매니페스트가 옛 태그로 되돌아갔다**: `0d5222e` push로 시작한 GitHub 실행이 4분 넘게 걸리는 사이 Jenkins #2가 `c251ea2f`로 매니페스트를 갱신했다. 늦게 끝난 GitHub 실행이 `git pull --rebase -X theirs`로 `0d5222e2`를 덮었고, 클러스터에는 옛 커밋 이미지가 배포됐다. backend는 같은 커밋을 Jenkins, 7.8, 6.7이 세 번 빌드했다. 단계 0대로 워크플로우를 끄고 진행한다.

- **(run-38) `agent any`로 컨트롤러에 배정되면 `docker: not found`**: 컨트롤러 실행기(numExecutors: 2)에는 docker가 없다. 참조 파일은 `agent { label 'jenkins-jenkins-agent' }`로 고쳤다.

- **Frontend Jenkinsfile `git push` 실패 — `git pull --rebase` 누락**: ch7.9 frontend Jenkinsfile에 `git push origin HEAD:main` 전에 `git pull --rebase origin main`이 없으면, GitHub Actions가 먼저 push한 경우 `rejected` 오류 발생.
  - 증상: `! [rejected] HEAD -> main (fetch first)`
  - 해결: `deploy_manifest/` commit 후, `git push` 직전에 `git pull --rebase origin main` 추가 (참조 파일 `ch7/7.9/1.frontend-build-deploy.groovy`에 이미 반영됨).

- **Frontend 멀티아치 빌드 메모리 OOM (run-15 발견)**: frontend(Node/yarn)를 `--platform linux/amd64,linux/arm64`로 빌드하면, Jenkins 에이전트(로컬 VM 노드)에서 amd64가 QEMU 에뮬레이션으로 yarn install/build를 수행하며 메모리가 폭증한다. 에이전트 Pod가 `InterruptedException`으로 offline/online을 반복하며 빌드가 사실상 멈춘다(backend Python/uv는 상대적으로 가벼워 멀티아치 성공).
  - 증상: 콘솔에 `... seems to be removed or offline (InterruptedException)` 반복, 빌드 미완료. 노드 `free` 수십 MB.
  - 해결: frontend는 **VM 아키텍처에 맞춘 단일 플랫폼**(`--platform linux/arm64` 또는 Intel은 `linux/amd64`)으로 빌드. 멀티아치가 필요하면 클라우드 러너(GitHub/GitLab)에서 수행. 참조 파일 `ch7/7.9/1.frontend-build-deploy.groovy`에 단일 플랫폼(arm64)으로 반영됨.

## 주의사항

- ⛔ `<dockerhub_username>`, `<github_username>`을 임의로 채우지 말 것
- ⛔ `agent any`를 쓰지 말 것. 컨트롤러 실행기(numExecutors: 2)로 배정되면 `docker: not found`로 실패한다(run-38)
- ⛔ 7.9 실습 중에는 두 저장소의 GitHub Actions 워크플로우를 끈다(단계 0). 같은 매니페스트를 두 도구가 고치면 늦게 끝난 쪽이 옛 태그로 덮는다. 7.9를 마쳐도 다시 켜지 않는다
- ⛔ Jenkins Credentials ID가 Jenkinsfile의 `credentials()` 호출과 정확히 일치해야 함
- ⛔ 메모리 제약 환경에서는 frontend와 backend 파이프라인을 동시에 실행하지 말 것 — 순차 실행
- ✅ `docker buildx`를 사용하므로 BuildKit 지원 확인 필요
- ✅ GitHub token에 저장소 `contents: write` 권한이 있어야 git push 가능
- ✅ 7.7에서 만든 Argo CD Application 두 개가 있어야 매니페스트 변경이 배포된다
