# 7.9 [Jenkins] 마이크로서비스 배포 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: Argo CD와 배포 확인
> - `[학습자 직접 · 웹]`: Jenkins Credentials 확인, frontend job 만들기, 스캔과 빌드 확인, 브라우저 접속
> - `[AI 프롬프트]`: GitHub 워크플로 비활성화, frontend와 backend Jenkinsfile 작성(빈칸을 학습자가 채움), Jenkinsfile push, 파이프라인이 올린 커밋 받기
>
> 저장소가 둘이다. frontend는 `/root/workspace/worklog-frontend`(main 브랜치), backend는 `/root/workspace/worklog-backend`다.

## 사전 조건

- ch6/6.8 완료 (Jenkins에 `dockerhub-credentials`, `github-token`이 있고 `worklog-backend` Multibranch job이 있음)
- 6.8 단계 2의 GitHub 토큰이 fork `worklog-frontend`에도 Contents: Read and write 권한을 가짐
- ch7/7.8 완료 (저장소 2개에 `deploy_manifest/`가 있고 Argo CD Application 둘이 자동 sync 중, 노드의 clone 2개가 `git pull --rebase`까지 마친 상태)

## 실행 지침

### 단계 1: GitHub Actions 워크플로 비활성화 `[AI 프롬프트]`

저장소 2개 모두 7.8 워크플로와 Jenkins가 같은 main을 보고 `deploy_manifest/`를 고친다. Jenkinsfile 변경은 `paths-ignore` 대상이 아니라 같은 push로 GitHub Actions도 돈다. 함께 활성화해 두면 늦게 끝난 실행이 매니페스트를 이전 태그로 되돌릴 수 있다. 7.9를 마쳐도 다시 활성화하지 않는다. 다음 GitHub 절의 단계 1이 정한다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```text
저장소 2개의 GitHub Actions 워크플로 build-deploy.yaml을 비활성화해줘. 이 절에서는 Jenkins가 같은 매니페스트를 고치므로, 함께 실행되면 늦게 끝난 쪽이 이전 태그로 되돌려.
조건:
- 대상 저장소: <github_username>/worklog-frontend, <github_username>/worklog-backend
끝나면: 저장소 2개의 gh workflow list --all 결과를 보여줘. 모두 disabled_manually여야 해.
```

### 단계 2: Jenkins Credentials 확인 `[학습자 직접 · 웹]`

Jenkins → Jenkins 관리 → Credentials → System → Global. 새로 넣는 것은 없고 아래 둘이 있는지 본다.

| 종류 | ID | 값 |
|---|---|---|
| Username with password | `dockerhub-credentials` | Docker Hub username + Access Token (5.5에서 등록) |
| Username with password | `github-token` | GitHub username + Personal Access Token (6.8에서 등록) |

## 검증 중 발견된 이슈 (강의자 참고)

- **(run-38) GitHub 워크플로를 켠 채로 Jenkinsfile을 push하면 frontend 매니페스트가 이전 태그로 되돌아갔다**: `0d5222e` push로 시작한 GitHub 실행이 4분 넘게 걸리는 사이 Jenkins #2가 `c251ea2f`로 매니페스트를 갱신했다. 늦게 끝난 GitHub 실행이 `git pull --rebase -X theirs`로 `0d5222e2`를 덮었고, 클러스터에는 이전 커밋 이미지가 배포됐다. backend는 같은 커밋을 Jenkins, 7.8, 6.7이 3번 빌드했다. 단계 1대로 워크플로를 끄고 진행한다.

- **(run-38) `agent any`로 컨트롤러에 배정되면 `docker: not found`**: 컨트롤러 실행기(numExecutors: 2)에는 docker가 없다. 정답 파일은 `agent { label 'jenkins-jenkins-agent' }`를 쓴다.

- **Frontend Jenkinsfile의 `git push` 실패**: `git push origin HEAD:main` 전에 `git pull --rebase origin main`이 없으면, 그 사이 다른 커밋이 올라온 경우 `! [rejected] HEAD -> main (fetch first)`가 난다. 정답 파일은 커밋 뒤, push 직전에 pull --rebase를 한다.

- **(run-15) Frontend 멀티 아키텍처 빌드에서 메모리 부족**: frontend(Node/yarn)를 `--platform linux/amd64,linux/arm64`로 빌드하면 Jenkins 에이전트(로컬 VM 노드)에서 다른 아키텍처를 QEMU로 에뮬레이션하며 메모리를 다 쓴다. 에이전트 Pod가 offline과 online을 반복하고 빌드가 멈춘다. backend(Python/uv)는 가벼워서 멀티 아키텍처로도 된다.
  - 증상: 콘솔에 `... seems to be removed or offline (InterruptedException)` 반복, 노드 `free`가 수십 MB
  - 해결: frontend는 `--platform` 없이 에이전트 노드의 아키텍처 하나로 빌드한다(2026-10-10 정답 파일 반영). 멀티 아키텍처 이미지는 7.8처럼 GitHub의 러너에서 만든다.

## 주의사항

- ⛔ AI가 하지 말 것: Jenkinsfile에 username이나 토큰을 글자로 적지 말 것. `credentials()`로 읽는다
- ⛔ AI가 하지 말 것: `agent any`를 쓰지 말 것. 컨트롤러 실행기로 배정되면 `docker: not found`로 실패한다(run-38)
- ⛔ AI가 하지 말 것: Jenkins 스캔을 대신 하지 말 것. 단계 6, 8 말고는 커밋하거나 push하지 말고 force push는 하지 말 것
- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ✅ AI가 해도 됨: 단계 1의 워크플로 비활성화, Jenkinsfile 작성, 단계 6, 8의 커밋과 push, 단계 10의 git pull, Console Output 해석
- ⚠️ 이 절을 하는 동안 저장소 2개의 GitHub Actions 워크플로를 끈다(단계 1). 같은 매니페스트를 도구 2개가 고치면 늦게 끝난 쪽이 이전 태그로 덮는다
- ⚠️ Credentials ID가 Jenkinsfile의 `credentials()` 호출과 글자까지 같아야 한다
- ⚠️ frontend와 backend 빌드를 함께 돌리지 않는다. 하나가 끝난 뒤 다음 것을 스캔한다
- ⚠️ frontend push가 `403`이면 6.8 단계 2의 토큰에 fork `worklog-frontend`가 빠진 것이다. GitHub에서 토큰의 Repository access에 저장소를 더한다
- ✅ 7.7에서 만든 Argo CD Application 2개가 있어야 매니페스트 변경이 배포된다
- ⚠️ Jenkinsfile의 비밀값(`*_PSW`, `ARGOCD_ADMIN_PASSWORD`)은 `sh """` 안에서 `\$변수`로 넘긴다. `${...}`로 쓰면 Groovy가 값을 먼저 풀어 Console Output에 `Groovy String interpolation` 경고가 남는다(6.8 "검증 중 발견된 이슈")
