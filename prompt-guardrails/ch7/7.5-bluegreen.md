# 7.5 Blue-Green 배포 실습

> **학습자 진입 방식**:
> - `[학습자 직접]`: 이미지 업데이트, preview 확인, promote
> - `[AI 프롬프트]`: Rollout yaml 작성(빈칸을 학습자가 채움), Active/Preview Service yaml 작성, 적용

## 사전 조건

- ch7/7.4 완료 (Argo Rollouts 컨트롤러와 kubectl 플러그인 설치)
- ch7/7.3 완료 (worklog-backend Deployment를 지운 상태. Deployment와 Rollout이 같은 이름이면 Pod가 양쪽에서 뜬다)
- Docker Hub에 worklog-backend 이미지가 태그 2개 이상으로 있음 (`<image_tag>`, `<new_tag>`는 7.3 단계 2의 표)

## 실행 지침

> 참고: 6.5의 `worklog-backend` Service와 HTTPRoute가 남아 있다. 이 Service는 라벨이 같아 Blue-Green 양쪽 Pod를 모두 가리킨다. 그래서 외부 주소 `worklog-backend.myk8s.local`로는 전환을 확인할 수 없고, 단계 5에서 active와 preview Service에 따로 요청한다.

### 단계 1: Blue-Green Rollout yaml 작성 `[AI 프롬프트]`

`[채우기: ...]` 한 줄은 학습자가 작성한다. 프롬프트 전체를 복사해 붙여 넣고 그 자리를 작성한 뒤 보낸다. 이 절에서 배울 내용이 그 자리에 있다.

```text
worklog-backend의 Blue-Green Rollout yaml을 만들어줘. v2를 preview로 먼저 확인한 뒤 사람이 전환하려는 거야.
파일: /root/ch7/1.worklog-backend-rollout-bluegreen.yaml
조건:
- replicas: 3, revisionHistoryLimit: 2, imagePullSecrets: dockerhub-creds
- image: <dockerhub_username>/worklog-backend:<image_tag>, containerPort: 80
- activeService: worklog-backend-active, previewService: worklog-backend-preview
- [채우기: preview를 확인하기 전에 active가 자동으로 전환되지 않게 하는 설정]
참고: env와 probe는 /root/ch7/1.worklog-backend-deployment-rolling.yaml과 같게 해줘.
끝나면: dry-run으로 검사하고 파일을 보여줘. 적용 전에 멈춰줘.
```

| 자동으로 전환되지 않게 | autoPromotionEnabled: false | 기본값은 true라서 v2 Pod가 준비되면 바로 전환된다. false여야 preview를 확인하고 사람이 promote한다 |

✅ 정답 파일 (완성 후 비교): `ch7/7.5/1.worklog-backend-rollout-bluegreen.yaml`

### 단계 2: Active/Preview 서비스 yaml 작성 `[AI 프롬프트]`

```text
worklog-backend-active와 worklog-backend-preview Service 2개를 한 파일로 만들어줘. Rollout이 v1과 v2 Pod를 이 둘에 나눠 연결하려는 거야.
파일: /root/ch7/2.worklog-backend-services-bluegreen.yaml
조건:
- Service 2개 모두 selector: app=worklog-backend, port: 80, targetPort: 80
끝나면: dry-run으로 검사하고 파일을 보여줘. 적용 전에 멈춰줘.
```

✅ 정답 파일 (완성 후 비교): `ch7/7.5/2.worklog-backend-services-bluegreen.yaml`

### 단계 3: Blue-Green 리소스 배포 `[AI 프롬프트]`

```text
/root/ch7의 2.worklog-backend-services-bluegreen.yaml과 1.worklog-backend-rollout-bluegreen.yaml을 이 순서로 적용해줘. Rollout이 Service 2개를 참조하므로 Service가 먼저 있어야 해.
끝나면: Rollout이 Healthy가 될 때까지 기다린 뒤 kubectl argo rollouts get rollout worklog-backend 결과를 보여줘.
```

기대 결과: Pod 3개가 Running이고 revision 1에 `stable,active`가 붙는다. Rollout이 Service 2개를 참조하므로 Service를 먼저 적용한다.

### 단계 4: 이미지 업데이트로 Blue-Green 배포 트리거 `[학습자 직접]`

```bash
kubectl argo rollouts set image worklog-backend worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl argo rollouts get rollout worklog-backend --watch      # Status가 Paused가 되면 Ctrl+C
```

기대 결과: 새 ReplicaSet(revision 2)의 Pod 3개가 뜨고 `preview`가 붙는다. revision 1은 `stable,active` 그대로다. Status는 `Paused`, Message는 `BlueGreenPause`다. Pod가 모두 6개다.

### 단계 5: Preview 확인 `[학습자 직접]`

preview Service는 ClusterIP이고 외부 경로(HTTPRoute)가 없다. 컨트롤 플레인 노드에서 ClusterIP로 직접 요청한다.

```bash
curl -s http://$(kubectl get svc worklog-backend-preview -o jsonpath='{.spec.clusterIP}')/health; echo      # 새 버전이 응답하는지 본다
kubectl get svc worklog-backend-active worklog-backend-preview -o custom-columns=NAME:.metadata.name,HASH:.spec.selector.rollouts-pod-template-hash
kubectl get rs -l app=worklog-backend -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image
```

Service 2개의 selector에 Argo Rollouts가 `rollouts-pod-template-hash`를 붙여 놓았다. 값이 서로 다르면 Service 2개가 서로 다른 ReplicaSet을 가리키는 것이다.
세 번째 명령에서 그 HASH가 어느 이미지인지 본다. ReplicaSet 이름 끝이 HASH다. preview의 HASH는 신규 태그(8자 태그), active의 HASH는 기존 태그(buildtest1)다.
`/health`의 `imageTag`로는 버전 2개를 구분할 수 없다. 이 절의 Rollout에는 `IMAGE_TAG` env가 없어 양쪽 모두 `Unknown`으로 나온다(이 env는 7.7의 매니페스트부터 넣는다).

### 단계 6: 수동 Promote `[학습자 직접]`

```bash
kubectl argo rollouts promote worklog-backend
kubectl argo rollouts get rollout worklog-backend --watch      # revision 1의 Pod가 사라지면 Ctrl+C
kubectl get svc worklog-backend-active worklog-backend-preview -o custom-columns=NAME:.metadata.name,HASH:.spec.selector.rollouts-pod-template-hash
```

기대 결과: active Service가 새 버전으로 바로 바뀐다(Service 2개의 HASH가 같아진다). 이전 버전 Pod는 scaleDownDelaySeconds(기본 30초) 동안 남았다가 0으로 줄어든다.

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`과 태그를 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch7/`에 둔다
- ⛔ AI가 하지 말 것: `promote`를 대신 실행하지 말 것. 승격을 사람이 결정하는 것이 이 절의 내용이다
- ⛔ AI가 하지 말 것: `kubectl argo rollouts set image`를 대신 실행하지 말 것. 교체는 학습자가 직접 보는 실험이다
- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ✅ AI가 해도 됨: yaml 작성, 단계 3의 적용, `get rollout` 출력 해석
- ✅ `autoPromotionEnabled: false`라서 preview를 확인한 뒤 사람이 승격한다
- ✅ `kubectl argo rollouts abort worklog-backend`로 배포를 중단하고 이전 버전에 머물 수 있다
