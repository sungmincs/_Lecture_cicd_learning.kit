# 7.5 Blue-Green 배포 실습

> **학습자 진입 방식**:
> - `[학습자 직접]`: kubectl apply, rollout 상태 확인, 이미지 업데이트, preview 확인, promote
> - `[AI 프롬프트]`: Rollout yaml 작성 (Blue-Green 전략), Active/Preview Service yaml 작성

## 사전 조건

- ch7/7.4 완료 (Argo Rollouts 컨트롤러와 kubectl 플러그인 설치)
- ch7/7.3 완료 (worklog-backend Deployment를 지운 상태. Deployment와 Rollout이 같은 이름이면 Pod가 양쪽에서 뜬다)
- Docker Hub에 worklog-backend 이미지가 태그 2개 이상으로 있음 (`<image_tag>`, `<new_tag>`는 7.3 단계 1의 표)

## 실행 지침

> 참고: 6.5의 `worklog-backend` Service와 HTTPRoute가 남아 있다. 이 Service는 라벨이 같아 Blue-Green 양쪽 Pod를 모두 가리킨다. 그래서 외부 주소 `worklog-backend.myk8s.local`로는 전환을 확인할 수 없고, 단계 5에서 active와 preview Service를 따로 부른다.

### 단계 1: Blue-Green Rollout yaml 작성 `[AI 프롬프트]`

> "Argo Rollouts Blue-Green 전략으로 worklog-backend를 배포하는 Rollout yaml을 만들어서 컨트롤 플레인 노드의 `/root/ch7/1.worklog-backend-rollout-bluegreen.yaml`로 저장해줘. 적용은 내가 할게.
> - replicas: 3, revisionHistoryLimit: 2, imagePullSecrets: dockerhub-creds
> - image: `<dockerhub_username>/worklog-backend:<image_tag>`, containerPort: 80
> - activeService: worklog-backend-active, previewService: worklog-backend-preview
> - autoPromotionEnabled: false (수동 승격)
> - env와 probe는 `/root/ch7/1.worklog-backend-deployment-rolling.yaml`과 같게"

✅ 정답 파일 (완성 후 비교): `ch7/7.5/1.worklog-backend-rollout-bluegreen.yaml`

### 단계 2: Active/Preview 서비스 yaml 작성 `[AI 프롬프트]`

> "worklog-backend-active, worklog-backend-preview 두 개의 Kubernetes Service yaml을 한 파일로 만들어서 컨트롤 플레인 노드의 `/root/ch7/2.worklog-backend-services-bluegreen.yaml`로 저장해줘.
> selector: app=worklog-backend, port: 80, targetPort: 80"

✅ 정답 파일 (완성 후 비교): `ch7/7.5/2.worklog-backend-services-bluegreen.yaml`

### 단계 3: Blue-Green 리소스 배포 `[학습자 직접]`

```bash
cd /root/ch7
kubectl apply -f 2.worklog-backend-services-bluegreen.yaml
kubectl apply -f 1.worklog-backend-rollout-bluegreen.yaml
kubectl argo rollouts get rollout worklog-backend --watch      # Healthy가 되면 Ctrl+C
```

기대 결과: Pod 3개가 Running이고 revision 1에 `stable,active`가 붙는다. Rollout이 두 Service를 참조하므로 Service를 먼저 적용한다.

### 단계 4: 이미지 업데이트로 Blue-Green 배포 트리거 `[학습자 직접]`

```bash
kubectl argo rollouts set image worklog-backend worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl argo rollouts get rollout worklog-backend --watch      # Status가 Paused가 되면 Ctrl+C
```

기대 결과: 새 ReplicaSet(revision 2)의 Pod 3개가 뜨고 `preview`가 붙는다. revision 1은 `stable,active` 그대로다. Status는 `Paused`, Message는 `BlueGreenPause`다. Pod가 모두 6개다.

### 단계 5: Preview 확인 `[학습자 직접]`

preview Service는 ClusterIP이고 외부 경로(HTTPRoute)가 없다. 컨트롤 플레인 노드에서 ClusterIP로 직접 요청한다.

```bash
curl -s http://$(kubectl get svc worklog-backend-preview -o jsonpath='{.spec.clusterIP}')/health; echo      # 새 버전이 응답하는지 본다
kubectl get svc worklog-backend-active worklog-backend-preview -o custom-columns=NAME:.metadata.name,HASH:.spec.selector.rollouts-pod-template-hash
kubectl get rs -l app=worklog-backend -o custom-columns=HASH:.metadata.labels.rollouts-pod-template-hash,IMAGE:.spec.template.spec.containers[0].image,READY:.status.readyReplicas
```

두 Service의 selector에 Argo Rollouts가 `rollouts-pod-template-hash`를 붙여 놓았다. 값이 서로 다르면 두 Service가 서로 다른 ReplicaSet을 가리키는 것이다.
세 번째 명령에서 그 HASH가 어느 이미지인지 본다. preview의 HASH는 새 태그, active의 HASH는 이전 태그다.
`/health`의 `imageTag`로는 두 버전을 구분할 수 없다. 이 절의 Rollout에는 `IMAGE_TAG` env가 없어 양쪽 모두 `Unknown`으로 나온다(이 env는 7.7의 매니페스트부터 넣는다).

### 단계 6: 수동 Promote `[학습자 직접]`

```bash
kubectl argo rollouts promote worklog-backend
kubectl argo rollouts get rollout worklog-backend --watch      # revision 1의 Pod가 사라지면 Ctrl+C
kubectl get svc worklog-backend-active worklog-backend-preview -o custom-columns=NAME:.metadata.name,HASH:.spec.selector.rollouts-pod-template-hash
```

기대 결과: active Service가 새 버전으로 바로 바뀐다(두 Service의 HASH가 같아진다). 이전 버전 Pod는 scaleDownDelaySeconds(기본 30초) 동안 남았다가 0으로 줄어든다.

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`과 태그를 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch7/`에 둔다
- ⛔ AI가 하지 말 것: `promote`를 대신 실행하지 말 것. 승격을 사람이 결정하는 것이 이 절의 내용이다
- ✅ AI가 해도 됨: yaml 작성, `get rollout` 출력 해석
- ✅ `autoPromotionEnabled: false`라서 preview를 확인한 뒤 사람이 승격한다
- ✅ `kubectl argo rollouts abort worklog-backend`로 배포를 중단하고 이전 버전에 머물 수 있다
