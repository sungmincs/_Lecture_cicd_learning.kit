### 단계 5: Argo CD Application 생성 (frontend, backend) `[학습자 직접]`

Argo CD가 `deploy_manifest/` 경로를 감시하도록 frontend Application을 만들고, backend는 6.5에서 만든 Application의 자동 sync를 다시 켠다. frontend Application은 frontend 저장소에 `deploy_manifest/`가 있어야 만들어진다.

```bash
# worklog-frontend Application
argocd app create worklog-frontend \
  --repo https://github.com/<github_username>/worklog-frontend-mock \
  --path deploy_manifest \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace default \
  --sync-policy automated

# worklog-backend Application은 6.5에서 만들었다. 7.3에서 끈 자동 sync를 다시 켠다
argocd app set worklog-backend --sync-policy automated --self-heal --auto-prune
```

기대 결과: backend Application이 Synced/Healthy. backend Deployment는 Git의 `deploy_manifest/worklog-backend.yaml` 내용(replicas, 이미지)으로 바뀐다.

## 트러블슈팅

### 배포는 정상인데 외부 접속이 503 (NGF 데이터플레인 stale)

ch7.3~7.6의 배포 전략 실습(Rolling/Blue-Green/Canary)처럼 Pod·Service를 짧은 시간에 반복 재생성한 직후, 외부(LB `192.168.1.99`) 접속이 `503 Service Temporarily Unavailable`(nginx)을 반환할 수 있다.

- **확인**: 제어플레인은 정상이다 — HTTPRoute `Accepted=True/ResolvedRefs=True`, Gateway `Programmed=True`, `kubectl get endpoints worklog-backend`에 Pod IP 존재. **클러스터 내부에서 Service를 직접 호출하면 200**(앱 정상). 즉 NGINX Gateway Fabric 데이터플레인이 새 upstream(Pod IP)을 따라잡지 못한 상태다.
- **해결**:
  ```bash
  kubectl rollout restart deployment/nginx-gateway -n nginx-gateway
  ```
  컨트롤러 재시작으로 데이터플레인이 재동기화되며 즉시 200으로 복구된다. (Argo sync로 Pod가 다시 재생성되면 재발할 수 있으므로, Pod IP가 바뀌는 대규모 재배포 후 503이면 앱/매니페스트보다 NGF를 먼저 의심한다.)
