# 7.7 전체 스택 매니페스트 확인 및 적용

> **학습자 진입 방식**:
> - `[학습자 직접]`: frontend를 main 브랜치로 바꿔 이미지 빌드, kubectl apply, 저장 확인, frontend 저장소에 매니페스트 넣기, Argo CD Application 생성
> - `[학습자 직접 · 웹]`: 브라우저에서 할 일을 저장해 보기
> - `[AI 프롬프트]`: MongoDB, backend, frontend 매니페스트 yaml 작성
>
> 3장의 frontend는 `mock` 브랜치였다. 가짜 데이터를 브라우저 안에서 돌려주므로 backend가 없어도 화면이 나왔다.
> 이 절부터 `main` 브랜치의 진짜 frontend를 쓴다. 화면에서 저장하면 backend를 거쳐 MongoDB에 남는다.
> 세 구성요소(frontend, backend, MongoDB)가 처음으로 이어지는 절이다.

## 사전 조건

- ch6 완료 (Argo CD Application `worklog-backend`가 있음. 7.3 단계 0에서 자동 sync를 꺼 둔 상태)
- ch7/7.6 완료 (Canary Rollout `worklog-backend`가 클러스터에 있음. 단계 5에서 지운다)
- 3.3에서 clone한 `/root/workspace/worklog-frontend`가 `mock` 브랜치이고 커밋하지 않은 수정이 없음
- 3.5에서 한 `docker login`이 노드에 남아 있음
- 클러스터에 `dockerhub-creds` Secret이 있음 (6.5 단계 5)
- 호스트의 hosts 파일에 `worklog-frontend.myk8s.local`이 있음 (3.6)

### 단계 9: Argo CD Application 생성 (frontend)과 backend 자동 sync 다시 켜기 `[학습자 직접]`

Argo CD Application은 서비스마다 하나다. frontend는 여기서 새로 만들고, backend는 6.5에서 만든 것의 자동 sync를 다시 켠다.

```bash
argocd app create worklog-frontend \
  --repo https://github.com/<github_username>/worklog-frontend \
  --path deploy_manifest \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace default \
  --sync-policy automated --self-heal --auto-prune

# 7.3 단계 0에서 끈 자동 sync를 다시 켠다
argocd app set worklog-backend --sync-policy automated --self-heal --auto-prune

argocd app wait worklog-frontend worklog-backend --health --sync --timeout 300
argocd app list
kubectl get deployment worklog-backend worklog-frontend
```

기대 결과: 두 Application이 Synced, Healthy다. backend Deployment는 Git의 `deploy_manifest/worklog-backend.yaml` 내용으로 바뀐다. 단계 2의 파일은 replicas 2였지만 Git은 1이라 Pod가 1개로 줄고, 이미지도 Git에 적힌 태그가 된다. kubectl로 적용한 것보다 Git이 우선한다는 것을 여기서 본다.

## 트러블슈팅

### 배포는 정상인데 외부 접속이 503 (NGF 데이터플레인이 뒤처짐)

7.3부터 7.6까지 Pod와 Service를 짧은 시간에 여러 번 다시 만든 직후에는, 외부(LB `192.168.1.99`) 접속이 `503 Service Temporarily Unavailable`(nginx)을 돌려줄 수 있다.

- **확인**: HTTPRoute가 `Accepted=True`, `ResolvedRefs=True`이고 `kubectl get endpoints worklog-backend`에 Pod IP가 있다. 클러스터 안에서 Service를 직접 부르면 200이다. 앱은 정상이고 NGINX Gateway Fabric이 새 Pod IP를 따라잡지 못한 상태다.
- **해결**:
  ```bash
  kubectl rollout restart deployment/nginx-gateway -n nginx-gateway
  ```
  Pod IP가 바뀌는 재배포 뒤에 503이 나오면 앱과 매니페스트보다 NGF를 먼저 본다.

### 브라우저에 `Blocked request. This host is not allowed`

Vite 개발 서버가 모르는 호스트 이름의 요청을 막은 것이다. frontend `main`의 `vite.config.ts`에 `allowedHosts: [".myk8s.local"]`이 있어야 한다.
`git log --oneline -3 -- vite.config.ts`로 그 줄이 들어온 커밋이 보이는지 확인한다. 없으면 fork가 오래된 것이므로 GitHub의 fork 화면에서 **Sync fork**를 누르고 단계 3부터 다시 한다.

### 노드 디스크가 걱정될 때

단계 3의 빌드는 노드의 Docker에 이미지와 빌드 캐시를 남긴다. 이미지는 Docker Hub에 올라갔으므로 지워도 된다. 꼭 해야 하는 일은 아니다. `df -h /`가 80%를 넘으면 3.8 단계 7의 명령(`docker image prune -a -f`, `docker builder prune -a -f`)으로 치운다.

### frontend Pod가 `ImagePullBackOff`

단계 3의 push가 끝나지 않았는데 단계 5로 넘어간 경우다. `docker push`가 `failed to fetch oauth token ... 504 Gateway Timeout`으로 끝났다면 Docker Hub 쪽의 일시 오류이므로 같은 명령을 다시 친다(run-40에서 15분 사이 여러 번 났다).
push가 성공한 뒤에는 `kubectl rollout restart deployment/worklog-frontend`로 Pod를 다시 만든다. 기다려도 스스로 다시 받지만 간격이 최대 5분까지 늘어난다.

### `/api/v1/todos`가 500 또는 응답 없음

backend가 MongoDB에 닿지 못한 것이다. `kubectl logs -l app=worklog-backend --tail=20`을 보고, `kubectl get svc worklog-mongodb`와 Secret `worklog-mongodb-creds`가 있는지 확인한다.

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`, `<github_username>`을 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: 단계 1, 2, 4의 yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch7/`에 둔다. 저장소에 넣는 것은 단계 8에서 학습자가 한다
- ⛔ AI가 하지 말 것: `docker build`, `kubectl apply`, `argocd app create`를 대신 실행하지 말 것
- ✅ AI가 해도 됨: yaml 작성, Pod 로그 해석, 프록시 동작 설명
- ✅ MongoDB Secret의 비밀번호는 실습용 데모 값이다. backend 저장소의 `deploy_manifest/`에도 같은 Secret이 있다. 실무에서는 비밀값을 Git에 두지 않는다
- ⚠️ 이 MongoDB에는 볼륨이 없다. Pod가 다시 뜨면 저장한 할 일이 사라진다. 배포 흐름을 보는 실습이라 볼륨은 다루지 않는다
- ⚠️ frontend `main`은 `mock`보다 화면이 단순하다. mock은 화면을 보여 주려고 만든 것이고, main은 backend와 실제로 주고받는 것이다
