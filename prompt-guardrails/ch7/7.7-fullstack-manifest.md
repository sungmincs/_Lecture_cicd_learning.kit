## 실행 지침

### 단계 1: MongoDB 매니페스트 작성 `[AI 프롬프트]`

> "MongoDB를 Kubernetes에 배포하는 yaml 만들어줘.
> - Secret (MONGO_INITDB_ROOT_USERNAME, MONGO_INITDB_ROOT_PASSWORD)
> - Deployment (image: mongo:8.0, port: 27017, Secret 환경변수 참조)
> - Service (port: 27017)"

✅ 정답 파일 (완성 후 비교): `ch7/7.7/1.mongodb-manifest.yaml`

### 단계 2: Backend 매니페스트 작성 `[AI 프롬프트]`

> "worklog-backend를 MongoDB에 연결하여 배포하는 yaml 만들어줘.
> - Secret (worklog-mongodb-creds: username, password base64)
> - Deployment (imagePullSecrets: dockerhub-creds, image: `<dockerhub_username>/worklog-backend:<image_tag>`)
> - MONGO_HOST: worklog-mongodb.default.svc.cluster.local
> - IMAGE_TAG 환경변수 포함
> - liveness/readiness probe: /health (port 80)
> - Service (ClusterIP, port 80)
> - HTTPRoute (hostname: worklog-backend.myk8s.local, parentRef: nginx-gateway)"

✅ 정답 파일 (완성 후 비교): `ch7/7.7/2.worklog-backend-with-db.yaml`

### 단계 3: Frontend 매니페스트 작성 `[AI 프롬프트]`

> "worklog-frontend-mock을 배포하는 yaml 만들어줘.
> - Deployment (imagePullSecrets: dockerhub-creds, image: `<dockerhub_username>/worklog-frontend-mock:<image_tag>`)
> - VITE_API_URL: http://worklog-backend.default.svc.cluster.local:80
> - port: 5173, liveness/readiness probe: / (port 5173)
> - Service (port 8080 → targetPort 5173)
> - HTTPRoute (hostname: worklog-frontend.myk8s.local, parentRef: nginx-gateway)"

✅ 정답 파일 (완성 후 비교): `ch7/7.7/3.worklog-frontend-manifest.yaml`

### 단계 4: 전체 스택 배포 `[학습자 직접]`

```bash
kubectl apply -f 1.mongodb-manifest.yaml
kubectl get pods -l app=mongodb
kubectl get svc mongodb

kubectl apply -f 2.worklog-backend-with-db.yaml
kubectl logs -l app=worklog-backend --tail=20

kubectl apply -f 3.worklog-frontend-manifest.yaml
kubectl get pods
```

접속 확인: `http://worklog-frontend.myk8s.local`

### 단계 5: Argo CD Application 생성 (frontend, backend) `[학습자 직접]`

Argo CD가 `deploy_manifest/` 경로를 감시하도록 Application 2개를 생성한다.

```bash
# worklog-frontend Application
argocd app create worklog-frontend \
  --repo https://github.com/<github_username>/worklog-frontend-mock \
  --path deploy_manifest \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace default \
  --sync-policy automated

# worklog-backend Application
argocd app create worklog-backend \
  --repo https://github.com/<github_username>/worklog-backend \
  --path deploy_manifest \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace default \
  --sync-policy automated
```

## 트러블슈팅

### 배포는 정상인데 외부 접속이 503 (NGF 데이터플레인 stale)

ch7.3~7.6의 배포 전략 실습(Rolling/Blue-Green/Canary)처럼 Pod·Service를 짧은 시간에 반복 재생성한 직후, 외부(LB `192.168.1.99`) 접속이 `503 Service Temporarily Unavailable`(nginx)을 반환할 수 있다.

- **확인**: 제어플레인은 정상이다 — HTTPRoute `Accepted=True/ResolvedRefs=True`, Gateway `Programmed=True`, `kubectl get endpoints worklog-backend`에 Pod IP 존재. **클러스터 내부에서 Service를 직접 호출하면 200**(앱 정상). 즉 NGINX Gateway Fabric 데이터플레인이 새 upstream(Pod IP)을 따라잡지 못한 상태다.
- **해결**:
  ```bash
  kubectl rollout restart deployment/nginx-gateway -n nginx-gateway
  ```
  컨트롤러 재시작으로 데이터플레인이 재동기화되며 즉시 200으로 복구된다. (Argo sync로 Pod가 다시 재생성되면 재발할 수 있으므로, Pod IP가 바뀌는 대규모 재배포 후 503이면 앱/매니페스트보다 NGF를 먼저 의심한다.)

## 주의사항

- ⛔ `<dockerhub_username>`을 임의로 채우지 말 것
- ⛔ MongoDB Secret의 비밀번호는 학습용 — 실무에서는 강력한 비밀번호 사용
- ✅ Backend는 worklog-mongodb-creds Secret을 통해 MongoDB에 연결
- ✅ Frontend는 HTTPRoute를 통해 외부 접속 가능
- ✅ Argo CD Application은 worklog-frontend, worklog-backend 두 개 별도 생성
