# 7.6 Canary 배포 실습

> **학습자 진입 방식**:
> - `[학습자 직접]`: Blue-Green 리소스 정리, kubectl apply, 이미지 업데이트, promote
> - `[AI 프롬프트]`: Canary 전략 Rollout yaml 작성, Service yaml 작성

## 사전 조건

- ch7/7.5 완료 (Blue-Green Rollout과 Service 둘이 클러스터에 있음. 단계 1에서 지운다)
- Docker Hub에 worklog-backend 이미지가 태그 2개 이상으로 있음 (`<image_tag>`, `<new_tag>`는 7.3 단계 1의 표)

## 실행 지침

### 단계 1: Blue-Green 리소스 정리 `[학습자 직접]`

```bash
kubectl delete rollout worklog-backend
kubectl delete svc worklog-backend-active worklog-backend-preview
```

### 단계 2: Canary Rollout yaml 작성 `[AI 프롬프트]`

> "Argo Rollouts Canary 전략으로 worklog-backend를 배포하는 Rollout yaml을 만들어서 컨트롤 플레인 노드의 `/root/ch7/1.worklog-backend-rollout-canary.yaml`로 저장해줘. 적용은 내가 할게.
> - replicas: 5, revisionHistoryLimit: 2, imagePullSecrets: dockerhub-creds
> - image: `<dockerhub_username>/worklog-backend:<image_tag>`, containerPort: 80
> - Canary 단계: 20%(수동 pause) → 40%(30s) → 60%(30s) → 80%(30s) → 100%
> - env와 probe는 `/root/ch7/1.worklog-backend-deployment-rolling.yaml`과 같게"

✅ 정답 파일 (완성 후 비교): `ch7/7.6/1.worklog-backend-rollout-canary.yaml`

### 단계 3: Canary용 Service yaml 작성 `[AI 프롬프트]`

> "worklog-backend Service yaml을 만들어서 컨트롤 플레인 노드의 `/root/ch7/2.worklog-backend-service-canary.yaml`로 저장해줘.
> selector: app=worklog-backend, port: 80, targetPort: 80, 포트 이름은 `http`"

✅ 정답 파일 (완성 후 비교): `ch7/7.6/2.worklog-backend-service-canary.yaml`

### 단계 4: Canary 리소스 배포 `[학습자 직접]`

```bash
cd /root/ch7
kubectl apply -f 2.worklog-backend-service-canary.yaml
kubectl apply -f 1.worklog-backend-rollout-canary.yaml
kubectl argo rollouts get rollout worklog-backend --watch      # Healthy가 되면 Ctrl+C
```

기대 결과: Pod 5개가 Running이다. 처음 배포는 비교할 이전 버전이 없어 단계를 거치지 않고 바로 100%가 된다. Service는 6.5가 만든 것과 이름이 같아 `configured`나 `unchanged`로 나온다. 포트 이름 `http`도 6.5의 Service(Git의 `deploy_manifest`)와 같게 맞춘 것이다. 이름이 다르면 외부 주소가 503이 된다(7.7 트러블슈팅).

### 단계 5: 이미지 업데이트로 Canary 배포 트리거 `[학습자 직접]`

```bash
kubectl argo rollouts set image worklog-backend worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl argo rollouts get rollout worklog-backend --watch      # Status가 Paused가 되면 Ctrl+C
```

기대 결과: 새 버전 Pod 1개(`canary`)와 이전 버전 Pod 4개(`stable`)가 함께 있다. `SetWeight: 20`, `Step: 1/8`에서 멈춘다.

### 단계 6: Canary 단계 수동 진행 `[학습자 직접]`

```bash
kubectl argo rollouts promote worklog-backend
kubectl argo rollouts get rollout worklog-backend --watch      # Step 8/8, Healthy가 되면 Ctrl+C
```

기대 결과: 40% → 30초 뒤 60% → 30초 뒤 80% → 30초 뒤 100%로 스스로 진행한다. 1분 30초쯤 걸린다.

### 단계 7: 최종 검증 `[학습자 직접]`

```bash
kubectl get pods -l app=worklog-backend
kubectl argo rollouts get rollout worklog-backend
```

기대 결과: Pod 5개가 모두 새 버전이고 Status가 Healthy다. Rollout은 7.7 단계 5에서 지운다.

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username | ❌ 반드시 확인 |
| `<image_tag>` | 처음 배포할 이미지 태그 (7.3 단계 1의 표) | ❌ 반드시 확인 |
| `<new_tag>` | Canary로 내보낼 새 이미지 태그 (7.3 단계 1의 표) | ❌ 반드시 확인 |

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`과 태그를 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch7/`에 둔다
- ⛔ AI가 하지 말 것: `promote`를 대신 실행하지 말 것
- ✅ AI가 해도 됨: yaml 작성, `get rollout` 출력 해석
- ✅ 첫 번째 `pause: {}`는 기한 없이 기다린다. `promote`를 쳐야 넘어간다
- ✅ 그 뒤의 `pause: {duration: 30s}`는 30초 뒤 스스로 넘어간다
- ✅ `kubectl argo rollouts abort worklog-backend`로 언제든 Canary를 중단하고 이전 버전으로 돌아갈 수 있다
- ✅ 이 실습의 Rollout에는 trafficRouting이 없다. Argo Rollouts는 setWeight를 Pod 수로 맞춘다(replicas 5에서 20%는 새 버전 Pod 1개). Service 하나가 두 버전 Pod를 함께 가리키므로 요청도 대략 그 비율로 나뉜다. 요청 단위로 정확히 나누려면 Gateway API 같은 trafficRouting 설정이 필요하다
