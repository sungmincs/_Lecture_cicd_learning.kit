# 7.6 Canary 배포 실습

> **학습자 진입 방식**:
> - `[학습자 직접]`: 이미지 업데이트, promote, 최종 확인
> - `[AI 프롬프트]`: Blue-Green 리소스 정리, Canary 전략 Rollout yaml 작성(빈칸을 학습자가 채움), Service yaml 작성, 적용

## 사전 조건

- ch7/7.5 완료 (Blue-Green Rollout과 Service 둘이 클러스터에 있음. 단계 1에서 지운다)
- Docker Hub에 worklog-backend 이미지가 태그 2개 이상으로 있음 (`<image_tag>`, `<new_tag>`는 7.3 단계 2의 표)

## 실행 지침

### 단계 1: Blue-Green 리소스 정리 `[AI 프롬프트]`

```text
7.5의 Blue-Green 리소스를 지워줘. 같은 이름으로 Canary Rollout을 만들기 위해서야.
조건:
- 지울 것: Rollout worklog-backend, Service worklog-backend-active와 worklog-backend-preview
- Service worklog-backend는 남겨 둬. 단계 4에서 같은 이름으로 다시 적용해.
끝나면: 남은 Rollout과 Service 목록을 보여줘.
```

### 단계 2: Canary Rollout yaml 작성 `[AI 프롬프트]`

`[채우기: ...]` 한 줄은 학습자가 작성한다. 프롬프트 전체를 복사해 붙여 넣고 그 자리를 작성한 뒤 보낸다. 이 절에서 배울 내용이 그 자리에 있다.

```text
worklog-backend의 Canary Rollout yaml을 만들어줘. v2로 가는 요청을 조금씩 늘리되 처음에는 사람이 확인하려는 거야.
파일: /root/ch7/1.worklog-backend-rollout-canary.yaml
조건:
- replicas: 5, revisionHistoryLimit: 2, imagePullSecrets: dockerhub-creds
- image: <dockerhub_username>/worklog-backend:<image_tag>, containerPort: 80
- [채우기: Canary 단계. 처음 비율과 거기서 멈추는 방식, 그다음 비율들과 기다리는 시간]
참고: env와 probe는 /root/ch7/1.worklog-backend-deployment-rolling.yaml과 같게 해줘.
끝나면: dry-run으로 검사하고 파일을 보여줘. 적용 전에 멈춰줘.
```

<details>
<summary>예시 보기</summary>

| 빈칸 | 예시 | 이 줄이 필요한 이유 |
|---|---|---|
| Canary 단계 | 20%(수동 pause) → 40%(30s) → 60%(30s) → 80%(30s) → 100% | 20%에서 사람이 v2를 확인하고 promote하면 나머지는 30초씩 기다리며 자동으로 늘린다 |

</details>

비율과 시간이 예시와 달라도 된다. 단계 5, 6의 Step과 SetWeight 숫자가 그에 맞게 달라진다.

✅ 정답 파일 (완성 후 비교): `ch7/7.6/1.worklog-backend-rollout-canary.yaml`

### 단계 3: Canary용 Service yaml 작성 `[AI 프롬프트]`

```text
worklog-backend Service yaml을 만들어줘. Canary에서는 Service 하나가 v1과 v2 Pod를 함께 가리켜.
파일: /root/ch7/2.worklog-backend-service-canary.yaml
조건:
- selector: app=worklog-backend, port: 80, targetPort: 80
- 포트 이름은 http. 6.5의 Service(저장소의 deploy_manifest)와 이름이 같아야 외부 주소가 503이 되지 않아.
끝나면: dry-run으로 검사하고 파일을 보여줘. 적용 전에 멈춰줘.
```

✅ 정답 파일 (완성 후 비교): `ch7/7.6/2.worklog-backend-service-canary.yaml`

### 단계 4: Canary 리소스 배포 `[AI 프롬프트]`

```text
/root/ch7의 2.worklog-backend-service-canary.yaml과 1.worklog-backend-rollout-canary.yaml을 이 순서로 적용해줘.
끝나면: Rollout이 Healthy가 될 때까지 기다린 뒤 kubectl argo rollouts get rollout worklog-backend 결과를 보여줘.
```

기대 결과: Pod 5개가 Running이다. 처음 배포는 비교할 이전 버전이 없어 단계를 거치지 않고 바로 100%가 된다. Service는 6.5가 만든 것과 이름이 같아 `configured`나 `unchanged`로 나온다. 포트 이름 `http`도 6.5의 Service(저장소의 `deploy_manifest`)와 같게 맞춘 것이다. 이름이 다르면 외부 주소가 503이 된다(7.7 트러블슈팅).

### 단계 5: 이미지 업데이트로 Canary 배포 트리거 `[학습자 직접]`

```bash
kubectl argo rollouts set image worklog-backend worklog-backend=<dockerhub_username>/worklog-backend:<new_tag>
kubectl argo rollouts get rollout worklog-backend --watch      # Status가 Paused가 되면 Ctrl+C
```

기대 결과: 새 버전 Pod 1개(`canary`)와 이전 버전 Pod 4개(`stable`)가 함께 있다. `SetWeight: 20`, `Step: 1/8`에서 멈춘다.

### 단계 6: Canary 단계 수동 진행 `[학습자 직접]`

```bash
kubectl argo rollouts promote worklog-backend
kubectl argo rollouts get rollout worklog-backend --watch      # Step 8/8, Healthy가 되면 Ctrl+C
```

기대 결과: 40% → 30초 뒤 60% → 30초 뒤 80% → 30초 뒤 100%로 스스로 진행한다. 약 2분 걸린다(run-41 1분 48초).

### 단계 7: 최종 검증 `[학습자 직접]`

```bash
kubectl get pods -l app=worklog-backend
kubectl argo rollouts get rollout worklog-backend
```

기대 결과: Pod 5개가 모두 새 버전이고 Status가 Healthy다. Rollout은 7.7 단계 5에서 지운다.

## 플레이스홀더

| 플레이스홀더 | 설명 | AI가 임의로 채워도 되는가? |
|---|---|---|
| `<dockerhub_username>` | 학습자의 Docker Hub username | ❌ 반드시 확인 |
| `<image_tag>` | 처음 배포할 이미지 태그 (7.3 단계 2의 표) | ❌ 반드시 확인 |
| `<new_tag>` | Canary로 내보낼 새 이미지 태그 (7.3 단계 2의 표) | ❌ 반드시 확인 |

## 주의사항

- ⛔ AI가 하지 말 것: `<dockerhub_username>`과 태그를 임의로 채우지 말 것
- ⛔ AI가 하지 말 것: yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch7/`에 둔다
- ⛔ AI가 하지 말 것: `set image`와 `promote`를 대신 실행하지 말 것. 교체와 단계 진행은 학습자가 직접 보는 실험이다
- ⛔ AI가 하지 말 것: 프롬프트에 `[채우기: ...]`가 남은 채로 들어오면 짐작해 작성하거나 이 파일의 예시를 넣지 말 것. 학습자에게 작성해 달라고 되묻는다
- ✅ 학습자가 작성한 줄은 표현을 예시로 바꾸지 말고 그대로 따른다. 뜻이 예시와 다르면 파일을 만든 뒤 어디가 다른지 알려 준다
- ✅ AI가 해도 됨: 단계 1의 정리, yaml 작성, 단계 4의 적용, `get rollout` 출력 해석
- ✅ 첫 번째 `pause: {}`는 기한 없이 기다린다. `promote`를 쳐야 넘어간다
- ✅ 그 뒤의 `pause: {duration: 30s}`는 30초 뒤 스스로 넘어간다
- ✅ `kubectl argo rollouts abort worklog-backend`로 언제든 Canary를 중단하고 이전 버전으로 돌아갈 수 있다
- ✅ 이 실습의 Rollout에는 trafficRouting이 없다. Argo Rollouts는 setWeight를 Pod 수로 맞춘다(replicas 5에서 20%는 새 버전 Pod 1개). Service 하나가 버전 2개 Pod를 함께 가리키므로 요청도 대략 그 비율로 나뉜다. 요청 단위로 정확히 나누려면 Gateway API 같은 trafficRouting 설정이 필요하다
