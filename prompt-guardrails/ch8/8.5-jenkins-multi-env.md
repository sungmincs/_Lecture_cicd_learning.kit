## 실행 지침

### 단계 1: 멀티환경 namespace 생성 `[학습자 직접]`

```bash
kubectl create namespace dev
kubectl create namespace staging
kubectl create namespace prod
```

### 단계 2: Jenkins Credentials 확인 `[학습자 직접]`

Jenkins → Dashboard → Credentials → System → Global

| ID | 종류 | 용도 |
|---|---|---|
| `dockerhub-credentials` | Username with password | Docker Hub login |
| `github-token` | Username with password | deploy_manifest/ git push (Username=GitHub username, Password=PAT) |

### 단계 3: Multibranch Pipeline 설정 `[학습자 직접]`

Jenkins → New Item → Multibranch Pipeline

- Branch Sources: GitHub (또는 Git)
- Repository: 학습자 worklog-backend fork
- Discover branches: All branches
- Discover tags: 활성화 (v* 태그 트리거용)
- Build Configuration → Script Path: `Jenkinsfile`

> Multibranch Pipeline이어야 `env.BRANCH_NAME`/`env.TAG_NAME`이 채워진다.

### 단계 4: Jenkinsfile 작성 `[AI 프롬프트]`

> "worklog-backend Jenkins 멀티환경 파이프라인을 만들어줘.
> - 단일 `agent any` (전체 pipeline 레벨, stage별 중복 금지)
> - environment: DOCKER_REPOSITORY, DOCKERHUB_CREDENTIALS(credentials('dockerhub-credentials')), GITHUB_CREDENTIALS(credentials('github-token'))
> - stage 'Init Variables': script 블록에서 env.SHORT_SHA, env.COMMIT_MESSAGE 세팅, env.TAG_NAME/env.BRANCH_NAME 분기로 env.TARGET_ENV, env.TARGET_NAMESPACE, env.IMAGE_TAG 결정
>   - v* 태그 → prod / 태그명 그대로

### 단계 5: Jenkins 멀티환경 매핑 흐름 설명 `[AI 프롬프트]`

> "Jenkins Multibranch Pipeline에서 env.BRANCH_NAME과 env.TAG_NAME이 어떻게 채워지는지, 그리고 release/1.0.0 같은 슬래시 포함 브랜치에서 git push HEAD:${BRANCH_NAME}이 안전한 이유를 설명해줘."

### 단계 6: 브랜치/태그별 트리거 확인 `[학습자 직접]`

```bash
# develop 브랜치
git checkout -b develop && git push -u origin develop

# release 브랜치
git checkout -b release/1.0.0 && git push -u origin release/1.0.0

# v* 태그
git tag v1.0.0 && git push origin v1.0.0
```

Jenkins UI → Multibranch Pipeline → 각 브랜치/태그 빌드의 Console Output에서 TARGET_ENV / IMAGE_TAG 값을 확인한다.

## 트러블슈팅

### Docker socket 권한 오류 (VM 재시작 후 발생)

```
ERROR: failed to initialize builder backend-builder: permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

Jenkins 파드가 실행 중인 노드에서:
```bash
chmod 666 /var/run/docker.sock
```

> **원인**: VM 재시작 후 docker.sock이 `root:docker` 소유(660)로 초기화. Jenkins 파드(UID/GID 1000)가 접근 불가.

## 주의사항

- ⛔ AI가 하지 말 것: stage 안에 `agent any` 중복 선언 (env 변수가 손실됨 — pipeline 레벨 단일 선언만)
- ⛔ AI가 하지 말 것: 전역 `def TARGET_ENV = ...` 같은 def 변수 사용 (Groovy sandbox 호환성 이슈)
- ⛔ AI가 하지 말 것: namespace 생성을 Jenkinsfile에서 자동화하지 말 것
- ⚠️ VirtualBox VM 아키텍처에 맞춘 단일 플랫폼 사용 권장 (ARM Mac → `linux/arm64`, Intel → `linux/amd64`). 멀티 아키텍처 빌드는 QEMU 에뮬레이션으로 VM 과부하 유발
- ✅ AI가 해도 됨: Jenkinsfile groovy 작성 (분기 + build + deploy + post)
- ✅ AI가 해도 됨: env.BRANCH_NAME/env.TAG_NAME 사용법 안내
- ✅ AI가 해도 됨: Multibranch Pipeline 설정 가이드
- ⚠️ env.BRANCH_NAME은 슬래시 포함(`release/1.0.0`)도 그대로 들어옴 — `startsWith('release/')`로 매칭
- ⚠️ 모든 변수는 `env.*` 로 통일 (전역 def 변수 사용 금지)
- ⚠️ Test stage에 `agent any`를 다시 쓰면 Init Variables 결과 env가 사라짐
- ⚠️ **(run-16, #94) 검증용 파라미터화 파이프라인의 첫 빌드 등록 순서**: Multibranch가 아닌 파라미터화 방식으로 develop/release/tag를 재현할 때, Declarative `parameters {}`는 **파이프라인이 한 번 실행된 후에야** job에 등록됨. 따라서 **첫 빌드는 일반 `build`(기본값)로 트리거**해 parameters를 등록한 뒤, 이후부터 `buildWithParameters`를 사용해야 함(첫 호출부터 buildWithParameters하면 큐에 안 들어감). 실무 Multibranch에서는 `env.BRANCH_NAME`이 자동 채워져 해당 없음.
- ⚠️ **Jenkins 절 실습 중에는 GitHub Actions 워크플로우를 비활성화한다**: worklog-backend는 Actions와 Jenkins가 같은 main을 본다. Jenkinsfile을 push하면 Actions도 트리거돼 둘 다 `deploy_manifest/`를 push하고 rebase 충돌이 난다. Settings → Actions → 해당 워크플로우 Disable. ch9로 넘어갈 때 다시 켠다.
- ⚠️ `chmod 666 /var/run/docker.sock`은 **에이전트 Pod이 뜬 노드에서** 실행한다. control plane이 아니다. 노드 확인은 `kubectl get pod -n jenkins -o wide`, 접속은 `cd ch2/2.4 && vagrant ssh <노드명> -c 'sudo chmod 666 /var/run/docker.sock'`. 워커 노드는 비밀번호 SSH가 막혀 있어 `vagrant ssh`로 들어간다.
