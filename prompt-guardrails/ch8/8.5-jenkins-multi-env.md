# 8.5 [Jenkins] PR/Branch/Tag 기반 멀티환경 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: 태그(v*) 만들고 push, 환경별 배포 확인

### 단계 3: Jenkinsfile 작성 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
backend의 Jenkinsfile을 멀티환경 파이프라인으로 바꿔줘. 8.3의 규칙을 Jenkins로 구현하려는 거야. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/Jenkinsfile
- TAG_NAME과 BRANCH_NAME으로 환경과 이미지 태그를 정함: v* 태그는 prod와 태그 이름, release/*는 staging과 staging-<해시 8자>, 그 외는 dev와 dev-<해시 8자>
- 배포 커밋(마지막 커밋 작성자가 jenkins)은 빌드하지 않음, 태그 빌드는 예외
- stage: Test(uv 0.11.18), Build(amd64, arm64), Update Manifest
- 매니페스트의 image와 IMAGE_TAG를 바꿔 트리거된 브랜치에, 태그 빌드는 main에 push
- 참고: agent label과 Credential은 지금 Jenkinsfile(7.9)을 따라줘.
- 끝나면: 파일을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| 작성자가 jenkins인 배포 커밋은 건너뜀 | 스캔마다 배포 커밋을 다시 빌드 |
| v* 태그를 가장 먼저 검사 | 태그 빌드가 dev로 정해짐 |
| 태그 빌드는 main에 push | 태그 이름으로 push하다 already exists |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

AI가 만든 파일에 위 3줄이 있는지 직접 보고 싶으면 노드에서 아래를 실행한다.

```bash
grep -n "TAG_NAME\|jenkins\|HEAD:" /root/workspace/worklog-backend/Jenkinsfile
```

✅ 정답 파일 (완성 후 비교): `ch8/8.5/1.multi-env-pipeline.groovy`

```text
Jenkins Multibranch Pipeline에서 env.BRANCH_NAME과 env.TAG_NAME이 어떻게 채워지는지, 태그 빌드에서 BRANCH_NAME에 무엇이 들어가는지, 그래서 매니페스트를 어느 브랜치에 push해야 하는지 설명해줘.
```

### 단계 5: 브랜치 3개에 Jenkinsfile 넣고 push `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
새 Jenkinsfile을 main, develop, release/1.0.0 브랜치 3개에 넣어 push해줘. push하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- main에서 커밋 메시지 ci: jenkins multi-env로 커밋하고 git pull --rebase 뒤 push
- develop과 release/1.0.0은 pull한 뒤 git checkout main -- Jenkinsfile로 가져와 같은 메시지로 커밋하고 push
- 끝나면: 브랜치 3개의 push 결과를 보여주고 main으로 돌아와서 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| 브랜치 3개 모두에 같은 Jenkinsfile | 그 브랜치는 이전 Jenkinsfile로 빌드 |
| 브랜치마다 push 전에 pull | 배포 커밋 때문에 push가 거절됨 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 6: 태그 만들고 push `[학습자 직접]`

태그는 main 위에 붙인다. 8.3, 8.4에서 쓴 v1.0.0, v1.1.0과 다른 이름이다.

```bash
cd /root/workspace/worklog-backend
```

### 단계 7: Multibranch job에 태그 탐색 추가 `[학습자 직접 · 웹]`

Jenkins → `worklog-backend`(4.5에서 만든 job) → Configure → Branch Sources(Git) → Behaviours → Add → **Discover tags**

- 새 job을 만들지 않는다. 같은 저장소를 job 2개가 보면 배포 커밋이 2번 생긴다.
- Script Path는 그대로 `Jenkinsfile`.

> Multibranch Pipeline이어야 `env.BRANCH_NAME`/`env.TAG_NAME`이 채워진다.

**이 단계는 반드시 단계 5 뒤에 한다.** 설정을 저장하면 Jenkins가 바로 스캔을 돌린다. 그때 8.3에서 만든 develop과 release/1.0.0 브랜치가 처음 잡혀 빌드된다. 새 Jenkinsfile을 올리기 전에 저장하면 브랜치 3개가 7.9의 이전 Jenkinsfile로 빌드된다. 이전 Jenkinsfile은 매니페스트를 항상 main에 push하므로 main은 엉뚱한 태그로 바뀌고 develop과 release 빌드는 rebase 충돌로 실패한다(run-40에서 실제로 그랬다).

### 단계 8: 빌드 확인과 태그 빌드 `[학습자 직접 · 웹]`

단계 7의 저장으로 스캔이 한 번 돌았다. `worklog-backend` job에 main, develop, release/1.0.0 빌드가 돌고 있는지 본다. 안 돌았으면 'Scan Multibranch Pipeline Now'를 누른다. 빌드 3개가 함께 돌아 5분쯤 걸린다. 브랜치 job은 스캔으로 빌드되지만 태그 job은 만들어지기만 하고 빌드되지 않는다(Jenkins 기본 동작). 태그 job(`v1.2.0` 등)을 열어 **지금 빌드** 메뉴를 누른다. main 빌드가 끝난 뒤에 누른다. main 빌드와 태그 빌드는 둘 다 main의 매니페스트를 고치므로, 태그 빌드가 나중에 끝나야 prod에 태그 이미지가 남는다.

각 브랜치와 태그 빌드의 Console Output에서 TARGET_ENV와 IMAGE_TAG 값을 확인한다.

| 빌드 | TARGET_ENV | IMAGE_TAG |
|---|---|---|
| main | dev | `dev-<커밋 해시 앞 8자>` |
| develop | dev | `dev-<커밋 해시 앞 8자>` |
| release/1.0.0 | staging | `staging-<커밋 해시 앞 8자>` |
| v1.2.0 | prod | `v1.2.0` |

## 검증 중 발견된 이슈 (강의자 참고)

run-38에서 찾은 아래 문제 2개는 정답 파일에 반영했다(2026-10-08, 8.5, 8.6, 9.3~9.6 Jenkinsfile 공통).

- **태그 빌드가 매니페스트를 태그 이름으로 push해 실패하던 문제**: 태그 빌드에서는 `BRANCH_NAME`에도 태그 이름이 들어가 `! [rejected] HEAD -> v1.x.x (already exists)`가 났다.
  정답은 이제 `def branch = env.TAG_NAME ? 'main' : env.BRANCH_NAME`으로 main에 push한다. prod Application이 main을 보므로 태그 이미지가 prod 매니페스트에 들어간다.
- **스캔할 때마다 Jenkins가 자기 배포 커밋을 다시 빌드하던 문제**: Init 단계에서 마지막 커밋 작성자가 `jenkins`면 `NOT_BUILT`로 끝낸다. GitHub의 `paths-ignore`와 같은 역할이다.
  태그 빌드는 예외다. main 최신 커밋(대개 배포 커밋)에 태그를 붙이기 때문이다.
- 함께 고친 것: Update Manifest가 `image:` 줄과 `IMAGE_TAG` 값을 함께 바꾼다(GitHub 정답과 같음).

## 트러블슈팅

### 워커 노드 디스크가 80%를 넘을 때

워커에는 2가지가 쌓인다. 배포할 때마다 쿠버네티스가 내려받은 이미지(태그가 바뀔 때마다 새로 받고 옛것은 남는다)와, Jenkins 에이전트가 그 노드의 Docker로 빌드하며 남긴 이미지와 빌드 캐시다. 보통은 손댈 필요가 없다. kubelet이 85%를 넘으면 쓰지 않는 쿠버네티스 이미지를 스스로 지워 80%로 내린다. 정리 없이 10장까지 간 run-35~39에서도 디스크 문제는 없었다.

Docker 쪽은 kubelet이 치우지 않는다. 직접 비우고 싶을 때는 Jenkins 빌드가 돌고 있지 않을 때 아래를 실행한다.

```bash
for w in 101 102 103; do
  sshpass -p vagrant ssh -o StrictHostKeyChecking=no root@192.168.1.$w '
    hostname; df -h / | tail -1
    crictl rmi --prune >/dev/null 2>&1                                                  # 쿠버네티스가 받아 둔 이미지 중 쓰지 않는 것
    docker ps -q --filter name=buildx_buildkit | xargs -r docker rm -f >/dev/null     # 빌드가 끝나도 남아 있는 buildx 빌더
    docker system prune -a -f | tail -1                                                # Docker의 쓰지 않는 이미지와 빌드 캐시
    docker volume prune -a -f | tail -1                                                # 빌더가 쓰던 볼륨'
done
sleep 60       # containerd가 지운 것을 실제로 비우는 데 1분쯤 걸린다
for w in 101 102 103; do sshpass -p vagrant ssh -o StrictHostKeyChecking=no root@192.168.1.$w 'hostname; df -h / | tail -1'; done
```

run-40에서는 한 워커가 76%에서 47%로 내려갔다. 돌고 있는 Pod가 쓰는 이미지는 지워지지 않는다. 노드의 루트는 30GiB다(가상 디스크는 64GiB이고 Ubuntu 설치 기본값이 절반만 할당한다).

### Docker socket 권한 오류

```
ERROR: failed to initialize builder backend-builder: permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

에이전트 Pod의 docker 그룹이 노드의 docker 그룹 GID와 맞지 않을 때 난다. 해결은 5.6 트러블슈팅과 같다(JCasC 에이전트 Pod 템플릿의 `supplementalGroups`를 노드 GID로 맞춘다. 이 강의 노드는 988).

## 주의사항

- ⛔ AI가 하지 말 것: stage 안에 agent 중복 선언(env 변수가 손실됨, pipeline 레벨 단일 선언만), 또는 `agent any`(컨트롤러로 가면 docker: not found)
- ⛔ AI가 하지 말 것: 전역 `def TARGET_ENV = ...` 같은 def 변수 사용 (Groovy sandbox 호환성 이슈)
- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: namespace 생성을 Jenkinsfile에서 자동화하지 말 것
- ⛔ AI가 하지 말 것: 태그 만들기와 태그 push, Jenkins 화면 조작(태그 탐색, 스캔, 지금 빌드)을 대신 하지 말 것
- ⛔ AI가 하지 말 것: 단계 1, 5, 9의 요청이 없을 때 커밋, push, 워크플로 비활성화를 하지 말 것
- ⚠️ backend는 멀티 아키텍처(amd64, arm64)로 빌드한다. 스캔 한 번에 브랜치 셋이 함께 빌드되므로 에이전트가 끊기면(`InterruptedException`) 프롬프트의 플랫폼을 노드 아키텍처 하나로 바꾼다(ARM 맥은 `linux/arm64`, Intel은 `linux/amd64`)
- ✅ AI가 해도 됨: Jenkinsfile groovy 작성 (분기 + build + deploy + post)
- ✅ AI가 해도 됨: env.BRANCH_NAME/env.TAG_NAME 사용법 안내
- ✅ AI가 해도 됨: Multibranch Pipeline 설정 가이드
- ⚠️ env.BRANCH_NAME은 슬래시 포함(`release/1.0.0`)도 그대로 들어옴 — `startsWith('release/')`로 매칭
- ⚠️ 모든 변수는 `env.*` 로 통일 (전역 def 변수 사용 금지)
- ⚠️ Test stage에 agent를 다시 선언하면 Init 결과 env가 사라짐
- ⚠️ **(run-16, #94) 검증용 파라미터화 파이프라인의 첫 빌드 등록 순서**: Multibranch가 아닌 파라미터화 방식으로 develop/release/tag를 재현할 때, Declarative `parameters {}`는 **파이프라인이 한 번 실행된 후에야** job에 등록됨. 따라서 **첫 빌드는 일반 `build`(기본값)로 트리거**해 parameters를 등록한 뒤, 이후부터 `buildWithParameters`를 사용해야 함(첫 호출부터 buildWithParameters하면 큐에 안 들어감). 실무 Multibranch에서는 `env.BRANCH_NAME`이 자동 채워져 해당 없음.
- ⚠️ **Jenkins 절 실습 중에는 GitHub Actions 워크플로우를 비활성화한다**: worklog-backend는 Actions와 Jenkins가 같은 main을 본다. Jenkinsfile을 push하면 Actions도 트리거돼 둘 다 `deploy_manifest/`를 push하고 rebase 충돌이 난다. 8.5 단계 1에서 AI가 끈다. ch9 9.3 단계 1에서 다시 정한다.
