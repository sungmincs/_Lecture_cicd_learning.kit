## 실행 지침

### 단계 0: 앞 절 파이프라인 끄기 `[학습자 직접]`

### 단계 1: 멀티환경 namespace 생성 `[학습자 직접]`

### 단계 2: Jenkins Credentials 확인 `[학습자 직접]`

Jenkins → Dashboard → Credentials → System → Global

| ID | 종류 | 용도 |
|---|---|---|
| `dockerhub-credentials` | Username with password | Docker Hub login |
| `github-token` | Username with password | deploy_manifest/ git push (Username=GitHub username, Password=PAT) |

### 단계 3: 4.5 Multibranch job에 태그 탐색 추가 `[학습자 직접]`

Jenkins → `worklog-backend`(4.5에서 만든 job) → Configure → Branch Sources(Git) → Behaviours → Add → **Discover tags**

- 새 job을 만들지 않는다. 같은 저장소를 두 job이 보면 배포 커밋이 두 번 생긴다.
- Script Path는 그대로 `Jenkinsfile`.

> Multibranch Pipeline이어야 `env.BRANCH_NAME`/`env.TAG_NAME`이 채워진다.

### 단계 4: Jenkinsfile 작성 `[AI 프롬프트]`

> "worklog-backend Jenkins 멀티환경 파이프라인을 만들어줘.
> - pipeline 레벨에 `agent { label 'jenkins-jenkins-agent' }` 한 번만 선언(stage별 중복 금지. agent any는 docker가 없는 컨트롤러로 갈 수 있다)
> - environment: DOCKER_REPOSITORY, DOCKERHUB_CREDENTIALS(credentials('dockerhub-credentials')), GITHUB_CREDENTIALS(credentials('github-token'))
> - stage 'Init': script 블록에서 마지막 커밋 작성자가 jenkins면(배포 커밋) 태그 빌드가 아닐 때 빌드하지 않고 끝낸다. env.SHORT_SHA를 세팅하고 env.TAG_NAME/env.BRANCH_NAME 분기로 env.TARGET_ENV, env.NAMESPACE, env.IMAGE_TAG 결정
>   - v* 태그 → prod / 태그명 그대로
>   - develop branch → dev / dev-{short_sha}
>   - release/* branch → staging / staging-{short_sha}
>   - 그 외 → dev / dev-{short_sha}
> - stage 'Test': uv 설치 후 pytest + coverage
> - stage 'Build': docker buildx amd64/arm64 멀티 아키텍처 push
> - stage 'Update Manifest': deploy_manifest/worklog-backend.yaml의 image와 IMAGE_TAG env value를 sed로 업데이트, `git push origin HEAD:<브랜치>`. 브랜치는 태그 빌드면 main, 아니면 BRANCH_NAME
> - post: success/failure 알림
> - 전역 def 변수 금지 — env.* 만 사용 (Groovy sandbox 호환성)
> - Docker Hub username: `<dockerhub_username>`
> - GitHub username: `<github_username>`"

✅ 정답 파일 (완성 후 비교): `ch8/8.5/1.multi-env-pipeline.groovy`

### 단계 5: Jenkins 멀티환경 매핑 흐름 설명 `[AI 프롬프트]`

> "Jenkins Multibranch Pipeline에서 env.BRANCH_NAME과 env.TAG_NAME이 어떻게 채워지는지, 태그 빌드에서 BRANCH_NAME에 무엇이 들어가는지, 그래서 매니페스트를 어느 브랜치에 push해야 하는지 설명해줘."

### 단계 6: 브랜치/태그별 트리거 확인 `[학습자 직접]`

develop, release/1.0.0 브랜치와 v1.0.0 태그는 8.3에서 이미 만들었다. 브랜치를 새로 만들지 않고, 단계 4의 Jenkinsfile을 main에 커밋해 push한 뒤 나머지 두 브랜치에도 넣는다.

```bash
# 세 브랜치 모두에 Jenkinsfile이 있어야 한다(Multibranch는 브랜치마다 그 브랜치의 Jenkinsfile을 쓴다)
git checkout main && git add Jenkinsfile && git commit -m "ci: jenkins multi-env" && git pull --rebase && git push
for b in develop release/1.0.0; do
  git checkout $b && git pull && git checkout main -- Jenkinsfile && git commit -m "ci: jenkins multi-env" && git push
done

# v* 태그 (main 위에, 8.3, 8.4에서 쓴 v1.0.0, v1.1.0과 다른 이름)
git checkout main && git pull && git tag v1.2.0 && git push origin v1.2.0
```

push 뒤 'Scan Multibranch Pipeline Now'를 누른다. 브랜치 job은 스캔으로 빌드되지만 태그 job은 만들어지기만 하고 빌드되지 않는다(Jenkins 기본 동작). 태그 job(`v1.2.0` 등)을 열어 **Build Now**를 누른다.

Jenkins UI → Multibranch Pipeline → 각 브랜치/태그 빌드의 Console Output에서 TARGET_ENV / IMAGE_TAG 값을 확인한다.

## 검증 중 발견된 이슈 (강의자 참고)

run-38에서 찾은 아래 두 문제는 정답 파일에 반영했다(2026-10-08, 8.5, 8.6, 9.3~9.6 Jenkinsfile 공통).

- **태그 빌드가 매니페스트를 태그 이름으로 push해 실패하던 문제**: 태그 빌드에서는 `BRANCH_NAME`에도 태그 이름이 들어가 `! [rejected] HEAD -> v1.x.x (already exists)`가 났다.
  정답은 이제 `def branch = env.TAG_NAME ? 'main' : env.BRANCH_NAME`으로 main에 push한다. prod Application이 main을 보므로 태그 이미지가 prod 매니페스트에 들어간다.
- **스캔할 때마다 Jenkins가 자기 배포 커밋을 다시 빌드하던 문제**: Init 단계에서 마지막 커밋 작성자가 `jenkins`면 `NOT_BUILT`로 끝낸다. GitHub의 `paths-ignore`와 같은 역할이다.
  태그 빌드는 예외다. main 최신 커밋(대개 배포 커밋)에 태그를 붙이기 때문이다.
- 함께 고친 것: Update Manifest가 `image:` 줄과 `IMAGE_TAG` 값을 함께 바꾼다(GitHub 정답과 같음).

## 트러블슈팅

### Docker socket 권한 오류

```
ERROR: failed to initialize builder backend-builder: permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

에이전트 Pod의 docker 그룹이 노드의 docker 그룹 GID와 맞지 않을 때 난다. 해결은 5.6 트러블슈팅과 같다(JCasC 에이전트 Pod 템플릿의 `supplementalGroups`를 노드 GID로 맞춘다. 이 강의 노드는 988).

- ⛔ AI가 하지 말 것: stage 안에 agent 중복 선언(env 변수가 손실됨, pipeline 레벨 단일 선언만), 또는 `agent any`(컨트롤러로 가면 docker: not found)
- ⛔ AI가 하지 말 것: 전역 `def TARGET_ENV = ...` 같은 def 변수 사용 (Groovy sandbox 호환성 이슈)
- ⛔ AI가 하지 말 것: namespace 생성을 Jenkinsfile에서 자동화하지 말 것
- ⚠️ VirtualBox VM 아키텍처에 맞춘 단일 플랫폼 사용 권장 (ARM Mac → `linux/arm64`, Intel → `linux/amd64`). 멀티 아키텍처 빌드는 QEMU 에뮬레이션으로 VM 과부하 유발
- ✅ AI가 해도 됨: Jenkinsfile groovy 작성 (분기 + build + deploy + post)
- ✅ AI가 해도 됨: env.BRANCH_NAME/env.TAG_NAME 사용법 안내
- ✅ AI가 해도 됨: Multibranch Pipeline 설정 가이드
- ⚠️ env.BRANCH_NAME은 슬래시 포함(`release/1.0.0`)도 그대로 들어옴 — `startsWith('release/')`로 매칭
- ⚠️ 모든 변수는 `env.*` 로 통일 (전역 def 변수 사용 금지)
- ⚠️ Test stage에 agent를 다시 선언하면 Init 결과 env가 사라짐
- ⚠️ **(run-16, #94) 검증용 파라미터화 파이프라인의 첫 빌드 등록 순서**: Multibranch가 아닌 파라미터화 방식으로 develop/release/tag를 재현할 때, Declarative `parameters {}`는 **파이프라인이 한 번 실행된 후에야** job에 등록됨. 따라서 **첫 빌드는 일반 `build`(기본값)로 트리거**해 parameters를 등록한 뒤, 이후부터 `buildWithParameters`를 사용해야 함(첫 호출부터 buildWithParameters하면 큐에 안 들어감). 실무 Multibranch에서는 `env.BRANCH_NAME`이 자동 채워져 해당 없음.
- ⚠️ **Jenkins 절 실습 중에는 GitHub Actions 워크플로우를 비활성화한다**: worklog-backend는 Actions와 Jenkins가 같은 main을 본다. Jenkinsfile을 push하면 Actions도 트리거돼 둘 다 `deploy_manifest/`를 push하고 rebase 충돌이 난다. 8.5 단계 0에서 끈다. ch9 9.3 단계 0에서 다시 정한다.
