# 8.3 [GitHub] PR/Branch/Tag 기반 멀티환경 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: namespace 생성(dev/staging/prod), GitHub Secrets/Environments 확인, 브랜치(develop, release/*)·태그(v*) 생성, git push
> - `[AI 프롬프트]`: 멀티환경 워크플로 yaml 작성 (트리거 매핑 + determine-environment job + build + deploy)

- ch5/5.3 완료 (단일 환경 빌드 파이프라인 동작 확인)
- ch6/6.5 완료 (Argo CD Application + `deploy_manifest/` 경로 등록)

- GitHub Actions write 권한 활성화 (Settings → Actions → General → Workflow permissions → Read and write)

## 실행 지침

### 단계 1: 멀티환경 namespace 생성 `[학습자 직접]`

```bash
kubectl create namespace dev
kubectl create namespace staging
kubectl create namespace prod
```

> 실무에서는 환경별 클러스터 분리가 표준이지만, 학습 환경 제약상 namespace 분리로 구현한다.

### 단계 2: GitHub Secrets 확인 `[학습자 직접]`

저장소 → Settings → Secrets and variables → Actions

| Secret 이름 | 값 |
|---|---|
| `DOCKERHUB_TOKEN` | Docker Hub Access Token (ch5에서 이미 등록) |

### 단계 3: GitHub Environments 생성 (선택) `[학습자 직접]`

저장소 → Settings → Environments → New environment

- `dev`, `staging`, `prod` 3개 생성
- prod에는 Required reviewers 설정으로 수동 승인 게이트를 둘 수 있다

### 단계 4: 멀티환경 워크플로 yaml 작성 `[AI 프롬프트]`

> "worklog-backend GitHub Actions 멀티환경 파이프라인을 만들어줘.
> - 트리거: PR(main 대상), push(main/develop/release/*), tag(v*)
> - `deploy_manifest/**` 경로 변경은 트리거 제외 (무한 루프 방지)
> - determine-environment job에서 트리거 종류로 environment/namespace/image_tag 결정
>   - PR → dev / namespace=dev / image_tag=pr-{번호}
>   - develop branch → dev / dev-{short_sha}
>   - release/* branch → staging / staging-{short_sha}
>   - v* tag → prod / 태그명 그대로
> - init-and-test job: uv 기반 pytest + coverage
> - build job: docker buildx로 amd64/arm64 멀티 아키텍처 빌드 및 push
> - deploy job: deploy_manifest/worklog-backend.yaml의 image 필드를 sed로 업데이트하고 같은 브랜치에 push
>   - `git push origin HEAD:${BRANCH}` 형태 (브랜치 동적 지정)
> - notify-success-result/notify-failure-result job
> - Docker Hub username: `<dockerhub_username>`"

✅ 정답 파일 (완성 후 비교): `ch8/8.3/1.multi-env-pipeline.yaml`

### 단계 5: 멀티환경 트리거 매핑 흐름 설명 `[AI 프롬프트]`

> "방금 만든 워크플로에서 PR/branch/tag별로 namespace와 image_tag가 어떻게 결정되는지, `paths-ignore: deploy_manifest/**`가 왜 필요한지 설명해줘."

### 단계 6: 검증용 브랜치/태그 생성 + 트리거 확인 `[학습자 직접]`

```bash
# develop 브랜치 트리거 (dev namespace)
git checkout -b develop
git push -u origin develop

# release 브랜치 트리거 (staging namespace)
git checkout -b release/1.0.0
git push -u origin release/1.0.0

# tag 트리거 (prod namespace)
git tag v1.0.0
git push origin v1.0.0
```

GitHub → Actions 탭에서 트리거별 image_tag와 namespace 값이 의도대로 분기되는지 확인한다.

### 단계 7: namespace별 배포 결과 확인 `[학습자 직접]`

```bash
kubectl get deploy,pod -n dev
kubectl get deploy,pod -n staging
kubectl get deploy,pod -n prod
```

> 이 단계에서는 Argo CD가 namespace를 분기하지 않으므로, deploy_manifest/worklog-backend.yaml의 metadata.namespace 또는 `kubectl apply -n` 적용 방식은 9.5 단계에서 Argo CD Application 3개로 분리한다.

## 검증 중 발견된 이슈 (강의자 참고)

- **태그 빌드에서 deploy job `git push` 실패 — BRANCH 결정 로직 버그**: v* 태그 빌드 시 `${GITHUB_REF#refs/heads/}`가 `refs/tags/v1.0.0`을 그대로 반환하여 `git push origin HEAD:refs/tags/v1.0.0`이 실행되고 `[rejected] already exists` 오류 발생.
  - 증상: `! [rejected] HEAD -> v1.0.0 (already exists)`
  - 해결: deploy job에서 BRANCH 결정 시 `refs/tags/*` 패턴 명시적 처리 — 태그 빌드에서는 BRANCH=main으로 설정 (참조 파일 `ch8/8.3/1.multi-env-pipeline.yaml`에 이미 반영됨).
  - 수정된 코드:
    ```bash
    if [[ "${{ github.ref }}" == refs/tags/* ]]; then
      BRANCH="main"
    elif [[ "${{ github.event_name }}" == "pull_request" ]]; then
      BRANCH="${{ github.head_ref }}"
    else
      BRANCH="${{ github.ref_name }}"
    fi
    ```

## 주의사항

- ⛔ AI가 하지 말 것: namespace 생성을 워크플로 안에서 자동화하지 말 것 (학습자 직접 kubectl 실행)
- ⛔ AI가 하지 말 것: `paths-ignore: deploy_manifest/**` 누락 (deploy job의 git push가 무한 루프 유발)
- ⛔ AI가 하지 말 것: deploy job의 push 대상을 `main`으로 고정 (반드시 트리거 브랜치로 동적 지정)
- ⛔ AI가 하지 말 것: 태그 빌드에서 `${GITHUB_REF#refs/heads/}` 만으로 BRANCH 결정 (태그를 refs/tags/v* 형태 그대로 반환하여 push 실패)
- ✅ AI가 해도 됨: GitHub Actions yaml 작성 (determine-environment + build + deploy + notify)
- ✅ AI가 해도 됨: PR 번호, short SHA, tag 이름 추출 bash 스니펫 작성
- ✅ AI가 해도 됨: `${{ github.ref }}`, `${{ github.event_name }}` 등 GitHub Actions 컨텍스트 설명
- ⚠️ image_tag 규칙: PR=`pr-N`, develop=`dev-shortsha`, release/*=`staging-shortsha`, v*=태그명
- ⚠️ GitHub Actions write 권한이 없으면 deploy job의 git push가 403으로 실패함
- ⚠️ 태그 빌드에서 deploy_manifest 업데이트는 main 브랜치에 push — 태그는 push 대상이 아님
- ⚠️ **워크플로우 비활성화 주의** (4차 검증 발견): 저장소 Actions 탭에서 워크플로우가 수동으로 비활성화(`disabled_manually`)된 경우 push해도 트리거되지 않음.
  실습 전 확인:
  ```bash
  # 비활성화된 워크플로우 확인
  gh api repos/<username>/worklog-backend/actions/workflows \
    --jq '.workflows[] | select(.state == "disabled_manually") | .name'
  # 활성화
  gh api -X PUT repos/<username>/worklog-backend/actions/workflows/<id>/enable
  ```
  또는 GitHub 웹 → Actions 탭 → 워크플로우 → "Enable workflow" 버튼 클릭.
- ⚠️ **새 브랜치 최초 push가 run을 안 만드는 간헐 현상**: develop/release 같은 브랜치를 처음 생성·push할 때
  GitHub Actions가 워크플로우를 트리거하지 않는 경우가 드물게 있다(여러 검증에서 재현).
  → 빈 커밋 하나를 더 push하면 정상 트리거된다: `git commit --allow-empty -m "trigger" && git push`.
