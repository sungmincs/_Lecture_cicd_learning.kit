### 단계 5: 멀티환경 트리거 매핑 흐름 설명 `[AI 프롬프트]`

> "방금 만든 워크플로에서 PR/branch/tag별로 namespace와 image_tag가 어떻게 결정되는지, `paths-ignore: deploy_manifest/**`가 왜 필요한지 설명해줘."

### 단계 5-1: 워크플로를 main에 push `[학습자 직접]`

단계 4에서 만든 파일은 아직 작업 트리에만 있다. main에 올려야 브랜치와 태그를 만들 때 그 워크플로가 돈다.

```bash
git checkout main
git add .github/workflows/multi-env.yaml
git commit -m "ci: multi-env pipeline"
git push
```

이 push 자체가 main 분기(dev, `dev-<sha>`)로 한 번 돈다. Actions 탭에서 성공을 확인하고 `git pull`로 deploy job이 남긴 배포 커밋을 받는다.

### 단계 6: 검증용 브랜치/태그 생성 + 트리거 확인 `[학습자 직접]`

main의 최신 커밋은 deploy job이 남긴 배포 커밋(deploy_manifest만 변경)이다. 그래서 브랜치만 만들어 push하면 `paths-ignore`에 걸려 실행되지 않는다. 브랜치마다 소스 한 줄을 바꾼 커밋을 하나 올려 push한다. 브랜치와 태그는 모두 main에서 만든다.

```bash
# develop 브랜치 트리거 (dev namespace)
git checkout main && git pull
git checkout -b develop main && echo "# develop" >> README.md && git commit -am "chore: trigger develop" && git push -u origin develop

# release 브랜치 트리거 (staging namespace)
git checkout main
git checkout -b release/1.0.0 main && echo "# release" >> README.md && git commit -am "chore: trigger release" && git push -u origin release/1.0.0

# tag 트리거 (prod namespace). 태그는 main 위에 붙인다
git checkout main
git tag v1.0.0
git push origin v1.0.0
```

> 태그 push에는 `paths-ignore`가 적용되지 않아 main 최신 커밋에 그대로 붙여도 실행된다.

GitHub → Actions 탭에서 트리거별 image_tag와 namespace 값이 의도대로 분기되는지 확인한다.

### 단계 7: namespace별 배포 결과 확인 `[학습자 직접]`

```bash
kubectl get deploy,pod -n dev
kubectl get deploy,pod -n staging
kubectl get deploy,pod -n prod
kubectl get deploy worklog-backend -n default -o jsonpath='{.spec.template.spec.containers[0].image}'
```

> 이 절에서는 dev, staging, prod namespace가 아직 비어 있는 것이 정상이다. 파이프라인은 브랜치별 매니페스트만 바꾸고, namespace별 배포는 8.4에서 Argo CD Application 3개로 붙인다. 지금은 6.5 Application(`worklog-backend`)이 main을 보므로 main push와 v* 태그 빌드 결과가 default namespace에 반영된다.

## 검증 중 발견된 이슈 (강의자 참고)

- **태그 빌드에서 deploy job `git push` 실패 — BRANCH 결정 로직 버그**: v* 태그 빌드 시 `${GITHUB_REF#refs/heads/}`가 `refs/tags/v1.0.0`을 그대로 반환하여 `git push origin HEAD:refs/tags/v1.0.0`이 실행되고 `[rejected] already exists` 오류 발생.
  - 증상: `! [rejected] HEAD -> v1.0.0 (already exists)`
  - 해결: deploy job에서 BRANCH 결정 시 `refs/tags/*` 패턴 명시적 처리 — 태그 빌드에서는 BRANCH=main으로 설정 (참조 파일 `ch8/8.3/1.multi-env-pipeline.yaml`에 이미 반영됨).
  - 수정된 코드:
    ```bash
    if [[ "${{ github.ref }}" == refs/tags/* ]]; then
      BRANCH="main"
    elif [[ "${{ github.event_name }}" == "pull_request" ]]; then
      BRANCH="${{ github.head_ref }}"
    else
      BRANCH="${{ github.ref_name }}"
    fi
    ```

- ✅ AI가 해도 됨: GitHub Actions yaml 작성 (determine-environment + build + deploy + notify)
- ✅ AI가 해도 됨: PR 번호, short SHA, tag 이름 추출 bash 스니펫 작성
- ✅ AI가 해도 됨: `${{ github.ref }}`, `${{ github.event_name }}` 등 GitHub Actions 컨텍스트 설명
- ⚠️ image_tag 규칙: PR=`pr-N`, develop과 main push=`dev-shortsha`, release/*=`staging-shortsha`, v*=태그명
- ⚠️ GitHub Actions write 권한이 없으면 deploy job의 git push가 403으로 실패함

- ⚠️ **워크플로우 비활성화 주의** (4차 검증 발견): 저장소 Actions 탭에서 워크플로우가 수동으로 비활성화(`disabled_manually`)된 경우 push해도 트리거되지 않음.
  실습 전 확인:
  ```bash
  # 비활성화된 워크플로우 확인
  gh api repos/<username>/worklog-backend/actions/workflows \
    --jq '.workflows[] | select(.state == "disabled_manually") | .name'
  # 활성화
  gh api -X PUT repos/<username>/worklog-backend/actions/workflows/<id>/enable
  ```
  또는 GitHub 웹 → Actions 탭 → 워크플로우 → "Enable workflow" 버튼 클릭.
- ⚠️ **새 브랜치 push가 run을 안 만드는 경우**: 브랜치를 만든 커밋이 배포 커밋(deploy_manifest만 변경)이면 `paths-ignore`에 걸린다.
  이 파이프라인을 한 번 돌린 뒤에는 main 최신 커밋이 늘 배포 커밋이라 매번 생긴다(run-38 확인).
  → 소스를 바꾼 커밋을 올려 다시 push한다(단계 6).
