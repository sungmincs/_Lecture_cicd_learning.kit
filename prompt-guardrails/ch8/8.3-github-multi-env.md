# 8.3 [GitHub] PR/Branch/Tag 기반 멀티환경 파이프라인

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 워크플로 확인, namespace 생성(dev/staging/prod), 태그(v*) 만들고 push, 배포 결과 확인
> - `[학습자 직접 · 웹]`: GitHub Secrets와 Environments 확인, Actions 실행 결과 확인
> - `[AI 프롬프트]`: 멀티환경 워크플로 yaml 작성(프롬프트는 학습자가 처음부터 작성), main push, 검증용 브랜치(develop, release/*) 만들고 push, 배포 커밋 받기

## 8장부터 짧게 요청하고 계획을 검토한다

8장부터 AI에게는 짧게 요청한다. 무엇을 왜 하는지만 적고 "계획부터 보여줘"로 끝낸다. 세부 조건(파일 경로, 버전, 이름, 참고할 파일)은 이 가드레일의 단계마다 있는 **AI가 따를 조건**에 있고 AI가 읽어 따른다. 실무에서 팀의 규칙을 AGENTS.md 같은 규칙 파일에 두고 요청은 짧게 하는 것과 같다.

- AI는 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다. dry-run, `argocd app diff`, `terraform plan`처럼 실행 전에 미리 보는 단계다.
- 학습자는 단계마다 있는 **계획에서 확인할 것** 표로 계획을 검토한다. 표의 항목은 5장부터 7장까지 [채우기]로 직접 넣어 본 조건이다.
- 계획이 맞으면 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘"), 빠진 항목이 있으면 그 항목만 1줄로 요청한다.
- push, 커밋 받기, 활성화 전환처럼 기계적인 요청은 계획 없이 바로 맡긴다.

## 실행 지침

### 단계 1: 앞 절 파이프라인 끄기 `[학습자 직접]`

backend의 7.8 워크플로가 꺼져 있는지 본다(7.9 단계 1에서 껐다). 켜져 있으면 끈다. 7.8 워크플로는 main push마다 매니페스트를 고치는데, 이 절의 prod는 main 매니페스트를 본다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow list --all -R <github_username>/worklog-backend      # 모두 disabled_manually
```

`active`가 보이면 `gh workflow disable <파일 이름> -R <github_username>/worklog-backend`로 끈다.

### 단계 2: 멀티환경 namespace 생성 `[학습자 직접]`

```bash
kubectl create namespace dev
kubectl create namespace staging
kubectl create namespace prod
```

> 실무에서는 환경별 클러스터 분리가 표준이지만, 학습 환경 제약상 namespace 분리로 구현한다.

### 단계 3: GitHub Secrets 확인 `[학습자 직접 · 웹]`

저장소 → Settings → Secrets and variables → Actions

| Secret 이름 | 값 |
|---|---|
| `DOCKERHUB_TOKEN` | Docker Hub Access Token (ch5에서 이미 등록) |
| `DOCKERHUB_USERNAME` | Docker Hub username (7.8에서 이미 등록) |

### 단계 4: GitHub Environments 생성 (선택) `[학습자 직접 · 웹]`

저장소 → Settings → Environments → New environment

- `dev`, `staging`, `prod` 3개 생성
- prod에는 Required reviewers 설정으로 수동 승인 게이트를 둘 수 있다

### 단계 5: 멀티환경 워크플로 yaml 작성 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
backend에 멀티환경 GitHub Actions 파이프라인을 새 파일 multi-env.yaml로 만들어줘. 브랜치와 태그에 따라 dev, staging, prod로 나눠 배포하려는 거야. 파일을 만들기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/.github/workflows/multi-env.yaml
- 트리거별 환경과 이미지 태그: main 대상 PR은 dev와 pr-<번호>, develop과 main은 dev와 dev-<해시 8자>, release/*는 staging과 staging-<해시 8자>, v* 태그는 prod와 태그 이름
- deploy_manifest/** 경로만 바뀐 push는 paths-ignore로 무시
- job: 환경 결정, 테스트(uv 0.11.18), amd64와 arm64 빌드, 매니페스트 수정, 알림
- 매니페스트의 image 줄과 IMAGE_TAG 값을 바꿔 트리거된 브랜치에 push, 태그 빌드는 main에 push
- 참고: job 구성은 같은 폴더의 build-deploy.yaml(7.8)을 따라줘.
- 끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| deploy_manifest/**는 paths-ignore | 매니페스트만 바뀐 push도 빌드 |
| 브랜치 빌드는 그 브랜치에 push | 모든 환경이 main의 매니페스트를 수정 |
| 태그 빌드는 main에 push | 태그 이름으로 push하다 already exists |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

Docker Hub username과 토큰은 참고 파일(7.8)이 Secrets에서 읽는 방식을 따른다. 기존 워크플로 파일은 "새 파일로"라고 적으면 건드리지 않는다.

AI가 만든 파일에 필수 3줄이 있는지 직접 보고 싶으면 노드에서 아래를 실행한다. 줄 번호는 달라도 된다.

```bash
grep -n "paths-ignore\|BRANCH=\|git push origin" /root/workspace/worklog-backend/.github/workflows/multi-env.yaml
```

✅ 정답 파일 (완성 후 비교): `ch8/8.3/1.multi-env-pipeline.yaml`

### 단계 6: 멀티환경 트리거 매핑 흐름 설명 `[AI 프롬프트]`

짧은 질문이라 직접 친다.

```text
방금 만든 워크플로에서 PR, 브랜치, 태그별로 namespace와 image_tag가 어떻게 정해지는지, paths-ignore: deploy_manifest/**가 왜 필요한지 설명해줘.
```

### 단계 7: 워크플로를 main에 push `[AI 프롬프트]`

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
multi-env.yaml을 커밋하고 main에 push해줘. 커밋 메시지는 ci: multi-env pipeline, push 전에 git pull --rebase 해줘.
```

**AI가 따를 조건**

- 커밋 메시지는 ci: multi-env pipeline
- push 전에 git pull --rebase
- 끝나면: push 결과를 보여줘.

AI가 보여 주는 push 결과에 `main -> main`이 보이면 된다.

### 단계 8: main 실행 확인 `[학습자 직접 · 웹]`

이 push 자체가 main 분기(dev, `dev-<커밋 해시 앞 8자>`)로 한 번 돈다. fork의 Actions 탭에서 성공을 확인한다. deploy job이 main에 배포 커밋을 하나 남긴다. 단계 9의 첫 줄이 그 커밋을 받는다.

### 단계 9: 검증용 브랜치 만들기 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
develop과 release/1.0.0 브랜치를 main에서 만들어 push해줘. 브랜치 2개가 dev와 staging으로 나뉘는지 보려는 거야. push하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 먼저 main에서 git pull --rebase로 배포 커밋을 받아
- 브랜치마다 README.md 끝에 한 줄(# develop, # release)을 더해 커밋하고 push해. 배포 커밋만 있으면 paths-ignore 조건에 해당해 실행되지 않아.
- 커밋 메시지는 chore: trigger develop, chore: trigger release
- 끝나면: 브랜치 2개의 push 결과를 보여주고 main으로 돌아와서 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| main의 배포 커밋을 먼저 받음 | 브랜치에 이전 매니페스트가 들어감 |
| 브랜치마다 소스를 바꾼 커밋 | paths-ignore 조건에 해당해 실행되지 않음 |
| 끝나면 main으로 돌아옴 | 다음 단계의 태그가 다른 브랜치에 붙음 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 10: 태그 만들고 push `[학습자 직접]`

prod 배포는 사람이 태그로 정한다. 태그는 main 위에 붙인다.

```bash
cd /root/workspace/worklog-backend
git checkout main
git tag v1.0.0
git push origin v1.0.0
```

> 태그 push에는 `paths-ignore`가 적용되지 않아 main 최신 커밋에 그대로 붙여도 실행된다.

### 단계 11: 트리거별 결과 확인 `[학습자 직접 · 웹]`

fork의 Actions 탭에 실행이 3개 더 생긴다(develop, release/1.0.0, v1.0.0). 각 실행의 determine-environment job 로그에서 image_tag와 namespace가 아래처럼 갈렸는지 본다.

| 트리거 | environment | image_tag |
|---|---|---|
| develop push | dev | `dev-<커밋 해시 앞 8자>` |
| release/1.0.0 push | staging | `staging-<커밋 해시 앞 8자>` |
| v1.0.0 태그 | prod | `v1.0.0` |

### 단계 12: 배포 커밋 받기 `[AI 프롬프트]`

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
파이프라인이 올린 배포 커밋을 받아 와줘. 끝나면 main, develop, release/1.0.0의 deploy_manifest/worklog-backend.yaml image 줄을 보여줘.
```

**AI가 따를 조건**

- main은 git pull --rebase, develop과 release/1.0.0은 git fetch 뒤 git show origin/<브랜치>로 읽어
- 끝나면: 브랜치 3개의 deploy_manifest/worklog-backend.yaml image 줄을 보여줘.

기대 결과: main은 `v1.0.0`, develop은 `dev-<sha>`, release/1.0.0은 `staging-<sha>`.

### 단계 13: namespace별 배포 결과 확인 `[학습자 직접]`

```bash
argocd app get worklog-backend --refresh | grep -E "Sync Status|Health Status"
kubectl get deploy,pod -n dev
kubectl get deploy,pod -n staging
kubectl get deploy,pod -n prod
```

## 검증 중 발견된 이슈 (강의자 참고)

- **태그 빌드에서 deploy job `git push` 실패 — BRANCH 결정 로직 버그**: v* 태그 빌드 시 `${GITHUB_REF#refs/heads/}`가 `refs/tags/v1.0.0`을 그대로 반환하여 `git push origin HEAD:refs/tags/v1.0.0`이 실행되고 `[rejected] already exists` 오류 발생.
  - 증상: `! [rejected] HEAD -> v1.0.0 (already exists)`
  - 해결: deploy job에서 BRANCH 결정 시 `refs/tags/*` 패턴 명시적 처리 — 태그 빌드에서는 BRANCH=main으로 설정 (참조 파일 `ch8/8.3/1.multi-env-pipeline.yaml`에 이미 반영됨).
  - 수정된 코드:
    ```bash
    if [[ "${{ github.ref }}" == refs/tags/* ]]; then
      BRANCH="main"
    elif [[ "${{ github.event_name }}" == "pull_request" ]]; then
      BRANCH="${{ github.head_ref }}"
    else
      BRANCH="${{ github.ref_name }}"
    fi
    ```

## 주의사항

- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: 태그 만들기와 태그 push를 대신 하지 말 것(prod 배포를 정하는 단계라 학습자가 한다)
- ⛔ AI가 하지 말 것: 단계 7, 9, 12의 요청이 없을 때 커밋, push, 브랜치 만들기를 하지 말 것
- ⛔ AI가 하지 말 것: namespace 생성을 워크플로 안에서 자동화하지 말 것 (학습자 직접 kubectl 실행)
- ⛔ AI가 하지 말 것: `paths-ignore: deploy_manifest/**` 누락 (deploy job의 git push가 무한 루프 유발)
- ⛔ AI가 하지 말 것: deploy job의 push 대상을 `main`으로 고정 (반드시 트리거 브랜치로 동적 지정)
- ⛔ AI가 하지 말 것: 태그 빌드에서 `${GITHUB_REF#refs/heads/}` 만으로 BRANCH 결정 (태그를 refs/tags/v* 형태 그대로 반환하여 push 실패)
- ✅ AI가 해도 됨: GitHub Actions yaml 작성 (determine-environment + build + deploy + notify)
- ✅ AI가 해도 됨: PR 번호, short SHA, tag 이름 추출 bash 스니펫 작성
- ✅ AI가 해도 됨: `${{ github.ref }}`, `${{ github.event_name }}` 등 GitHub Actions 컨텍스트 설명
- ⚠️ image_tag 규칙: PR=`pr-N`, develop과 main push=`dev-shortsha`, release/*=`staging-shortsha`, v*=태그명
- ⚠️ GitHub Actions write 권한이 없으면 deploy job의 git push가 403으로 실패함
- ⚠️ 태그 빌드에서 deploy_manifest 업데이트는 main 브랜치에 push — 태그는 push 대상이 아님
- ⚠️ 꺼 둔 워크플로(`disabled_manually`)는 push해도 실행되지 않는다. 이 절에서 새로 만드는 `multi-env.yaml`은 처음부터 켜져 있다. 안 돌면 Actions 탭에서 상태부터 본다(`shared/one-pipeline.md`)
- ⚠️ **새 브랜치 push가 run을 안 만드는 경우**: 브랜치를 만든 커밋이 배포 커밋(deploy_manifest만 변경)이면 `paths-ignore` 조건에 해당한다.
  이 파이프라인을 한 번 돌린 뒤에는 main 최신 커밋이 늘 배포 커밋이라 매번 생긴다(run-38 확인).
  → 소스를 바꾼 커밋을 올려 다시 push한다(단계 9).
