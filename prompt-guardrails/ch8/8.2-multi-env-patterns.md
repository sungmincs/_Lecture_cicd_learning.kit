# 8.2 멀티환경 배포의 개념 (namespace 분리 + PR/Branch/Tag 패턴)

> **학습자 진입 방식**: 개념+준비 섹션 — 본격 실습 없음. 멀티환경 배포의 두 축(환경 분리·트리거 매핑)을 이해하고 8.3으로 진행.

## 이 챕터에서 다루는 것

지금까지(ch5~ch7)는 사실상 하나의 환경에 배포했다. 하지만 실무에서는 코드가 **dev에서 검증 → staging에서 리허설 → prod로 승격**되며, **어떤 브랜치/태그가 어느 환경으로 가는지**가 파이프라인으로 강제된다. ch8은 이 표준 패턴을 GitHub Actions와 Jenkins 두 도구로 각각 구현한다. 그 전에 모든 도구에 공통으로 깔리는 두 가지 개념을 잡는다.

## 축 1: 환경 분리 — namespace

실무에서는 환경별로 클러스터를 분리하는 것이 표준이지만, 학습 환경 제약상 **하나의 클러스터 안에서 namespace로 dev/staging/prod를 논리적으로 분리**한다.

| namespace | 용도 |
|---|---|
| `dev` | 개발 중 코드의 상시 배포·확인 |
| `staging` | 릴리스 후보 검증(프로덕션 리허설) |
| `prod` | 실제 서비스 |

> namespace 분리는 **논리적 격리**다. 완전한 보안 격리가 필요하면 별도 클러스터를 쓴다. 환경 간 트래픽 차단·자원 제한이 필요하면 NetworkPolicy·ResourceQuota를 추가하지만, 이 강의 범위 밖이다.

## 축 2: 트리거 매핑 — PR / Branch / Tag

"무엇이 어느 환경으로 가는가"를 Git 이벤트로 결정한다. 두 도구가 문법은 달라도 이 매핑은 동일하다.

| 트리거 | 환경 | 이미지 태그 규칙 |
|---|---|---|
| PR (main 대상) | dev (프리뷰) | `pr-{번호}` |
| `develop` 브랜치 push | dev | `dev-{short_sha}` |
| `release/*` 브랜치 push | staging | `staging-{short_sha}` |
| `v*` 태그 push | prod | 태그명(`v1.0.0`) |

> 이 매핑이 ch8의 핵심이다. 각 도구 실습(8.3~8.6)에서 이 표를 그대로 구현한다. GitHub는 `determine-environment` job, Jenkins는 `BRANCH_NAME`/`TAG_NAME`으로 구현한다.

## 실습에 들어가기 전에 갖춰져 있어야 하는 것

아래는 상태만 적은 것이다. 만드는 명령은 각 절의 단계에 있다.

- 7.9까지 마쳐 backend fork의 GitHub 워크플로가 모두 꺼져 있다(8.3 단계 0에서 확인한다)
- Docker Hub 토큰이 GitHub Secrets(5.3)와 Jenkins Credentials(5.5)에 들어 있고, GitHub 토큰이 Jenkins Credentials(6.8)에 들어 있다
- Argo CD Application `worklog-backend`가 fork의 `deploy_manifest/`를 보고 있다(6.5)
- `dev`, `staging`, `prod` namespace와 `develop`, `release/1.0.0` 브랜치, `v*` 태그는 아직 없다. 8.3 단계 1과 단계 6에서 만든다. 브랜치는 모두 main에서 만들므로 main과 같은 Dockerfile을 쓴다

## 다음 단계

- **8.3** [GitHub] 멀티환경 파이프라인
- **8.4** [GitHub] Full CI/CD (Argo CD 연동)
- **8.5** [Jenkins] 멀티환경 파이프라인
- **8.6** [Jenkins] Full CI/CD (Argo CD 연동)
