## 검증 중 발견된 이슈 (강의자 참고)

- **태그 빌드에서 update-manifest job `git push` 실패 — BRANCH 결정 로직 버그**: v* 태그 빌드 시 `${GITHUB_REF#refs/heads/}`가 `refs/tags/v1.0.0`을 그대로 반환하여 push 실패.
  - 해결: ch8.3와 동일한 if/elif 분기 적용 (참조 파일 `ch8/8.4/1.full-cicd-workflow.yaml`에 반영됨)

- **Argo CD `targetRevision: 'release/*'` 와일드카드 미지원**:
  - 증상: `worklog-backend-staging` Application이 `ComparisonError: Unable to resolve 'release/*' to a commit SHA` 로 Unknown 상태
  - 원인: Argo CD는 `targetRevision`에 glob 패턴/와일드카드를 지원하지 않음. 특정 브랜치명이나 태그, 커밋 SHA만 사용 가능
  - 해결: `targetRevision: release/1.0.0` (또는 현재 활성 release 브랜치명)으로 명시
  - 실무 대응: release 브랜치가 새로 생성될 때마다 CI 파이프라인에서 Argo CD Application의 `targetRevision`을 업데이트하거나, Argo CD ApplicationSet으로 동적 생성
  - 참조 파일 `ch8/8.4/2.argocd-apps-multi-env.yaml`에 `release/1.0.0`으로 수정 반영됨 (run-15에서 재확인 — `release/1.0.0` 명시 시 정상 Synced)

- **단일 클러스터 멀티환경의 HTTPRoute hostname 충돌 — Application Health=Progressing (run-15 발견)**: dev/staging/prod(+default)의 worklog-backend HTTPRoute가 **모두 같은 hostname**(`worklog-backend.myk8s.local`)을 단일 Gateway에 주장한다. NGINX Gateway Fabric은 하나만 라우팅하고 나머지 HTTPRoute의 health를 확정하지 못해, Argo CD Application이 **Synced이지만 Health=Progressing**으로 남는다(Deployment/Pod는 Running/정상, 기능은 동작).
  - 증상: `worklog-backend-dev/staging/prod` 모두 `Synced` / `Progressing`. 4개 namespace에 동일 hostname HTTPRoute 존재.
  - 원인: 같은 단일 `deploy_manifest`를 브랜치별로 쓰는 branch-per-env 구조 + 단일 클러스터/단일 Gateway. 실무는 환경별 클러스터(각자 hostname)라 발생하지 않는 학습 환경 한계다.
  - 대응(택1): ① **단일 클러스터 학습 한계로 명시**하고 넘어간다(권장 — 매니페스트 단순 유지). ② 외부 노출 검증이 필요하면 환경별 hostname(`worklog-backend-dev.myk8s.local` 등)을 매니페스트에 분기. 본 강의는 ①을 채택한다.

## 주의사항

- ⛔ AI가 하지 말 것: 워크플로에 argocd CLI 호출 추가 (automated sync에 위임이 본 절의 핵심)
- ⛔ AI가 하지 말 것: 환경별로 다른 manifest 파일을 만들지 말 것 — 같은 파일을 브랜치별로 독립 관리
- ⛔ AI가 하지 말 것: Argo CD Application의 `destination.namespace` 누락 (namespace 분기 실패)
- ⛔ AI가 하지 말 것: `targetRevision`에 `'release/*'` 와일드카드 사용 — Argo CD 미지원, ComparisonError 발생
- ✅ AI가 해도 됨: 멀티환경 워크플로 + Argo CD Application 3개 yaml 작성
- ✅ AI가 해도 됨: targetRevision에 와일드카드가 동작하지 않는 이유 설명
- ✅ AI가 해도 됨: branch-per-env GitOps 패턴의 장단점 설명
- ⚠️ staging Application의 `targetRevision`은 실제 존재하는 release 브랜치명으로 설정 (`release/1.0.0` 등)
- ⚠️ deploy_manifest/worklog-backend.yaml의 image 필드와 `# IMAGE_TAG` 마커는 sed 치환 대상이므로 형식 변경 금지
- ⚠️ Argo CD Application 3개가 모두 같은 path를 보지만 targetRevision으로 분리됨
