# 8.4 [GitHub] Full CI/CD (Argo CD 자동 sync, 멀티환경 GitOps)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 브랜치 확인, Application 상태 확인, 태그(v*) 만들고 push, 환경별 배포 확인
> - `[학습자 직접 · 웹]`: Actions 실행 결과 확인
> - `[AI 프롬프트]`: Argo CD Application 3개 작성과 적용, 워크플로 수정(작성 프롬프트는 학습자가 처음부터 작성), 브랜치 3개에 워크플로 넣고 push, 트리거 커밋, 배포 커밋 받기

## 사전 조건

- ch8/8.3 완료 (PR/Branch/Tag 트리거 매핑 동작 확인)
- ch6/6.5 완료 (Argo CD 설치, automated sync 정책 이해)
- fork에 `main`, `develop`, `release/1.0.0` 브랜치와 `v1.0.0` 태그가 있음 (8.3 단계 9, 10)
- `dev`, `staging`, `prod` namespace가 있음 (8.3 단계 2)
- `deploy_manifest/worklog-backend.yaml` 단일 파일이 브랜치별로 독립 관리됨

요청과 계획 검토 방식은 8.3의 "8장부터 짧게 요청하고 계획을 검토한다"와 같다.

## 실행 지침

### 단계 1: 브랜치 확인과 작업 폴더 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend && git fetch -q && git branch -r      # origin/main, origin/develop, origin/release/1.0.0
mkdir -p /root/ch8
```

이 절에서 브랜치와 환경은 아래처럼 대응한다.

| 환경 | 모니터링 대상 (Argo CD) | 트리거 |
|---|---|---|
| dev | `develop` 브랜치의 `deploy_manifest/` | develop push, develop에서 main으로 연 PR(다른 브랜치에서 연 PR은 이미지만 빌드되고 dev에는 반영되지 않음) |
| staging | `release/*` 브랜치의 `deploy_manifest/` | release/* push |
| prod | `main` 브랜치의 `deploy_manifest/` | v* 태그 push |

> 단일 파일이지만 브랜치별로 독립 → namespace는 Argo CD Application `destination.namespace`에서 결정한다.

### 단계 2: Argo CD Application 3개 작성 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
worklog-backend의 Argo CD Application 3개를 한 파일로 만들어줘. 환경마다 다른 브랜치를 보고 다른 네임스페이스에 배포하려는 거야. 파일을 만들기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/ch8/2.argocd-apps-multi-env.yaml
- 이름은 worklog-backend-dev, worklog-backend-staging, worklog-backend-prod
- dev는 develop 브랜치를 dev 네임스페이스에, staging은 release/1.0.0 브랜치를 staging에, prod는 main 브랜치를 prod에 배포
- 저장소 https://github.com/<github_username>/worklog-backend.git의 deploy_manifest, 자동 sync(prune, selfHeal), CreateNamespace=false
- 참고: 형식은 /root/workspace/argocd-application.yaml(6.5)과 같게 해줘.
- 끝나면: kubectl apply --dry-run=client로 검사하고 파일을 보여줘. 적용 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| staging은 release/1.0.0 브랜치 | release/*로 적으면 ComparisonError |
| Application마다 다른 네임스페이스 | Application 3개가 같은 곳에 배포 |
| 자동 sync(prune, selfHeal) | push해도 배포되지 않음 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch8/8.4/2.argocd-apps-multi-env.yaml`

### 단계 4: Application 상태 확인 `[학습자 직접]`


## 검증 중 발견된 이슈 (강의자 참고)

- **태그 빌드에서 update-manifest job `git push` 실패 — BRANCH 결정 로직 버그**: v* 태그 빌드 시 `${GITHUB_REF#refs/heads/}`가 `refs/tags/v1.0.0`을 그대로 반환하여 push 실패.
  - 해결: ch8.3와 동일한 if/elif 분기 적용 (참조 파일 `ch8/8.4/1.full-cicd-workflow.yaml`에 반영됨)

- **Argo CD `targetRevision: 'release/*'` 와일드카드 미지원**:
  - 증상: `worklog-backend-staging` Application이 `ComparisonError: Unable to resolve 'release/*' to a commit SHA` 로 Unknown 상태
  - 원인: Argo CD는 `targetRevision`에 glob 패턴/와일드카드를 지원하지 않음. 특정 브랜치명이나 태그, 커밋 SHA만 사용 가능
  - 해결: `targetRevision: release/1.0.0` (또는 현재 활성 release 브랜치명)으로 명시
  - 실무 대응: release 브랜치가 새로 생성될 때마다 CI 파이프라인에서 Argo CD Application의 `targetRevision`을 업데이트하거나, Argo CD ApplicationSet으로 동적 생성
  - 참조 파일 `ch8/8.4/2.argocd-apps-multi-env.yaml`에 `release/1.0.0`으로 수정 반영됨 (run-15에서 재확인 — `release/1.0.0` 명시 시 정상 Synced)

- **단일 클러스터 멀티환경의 HTTPRoute hostname 충돌 — Application Health=Progressing (run-15 발견)**: dev/staging/prod(+default)의 worklog-backend HTTPRoute가 **모두 같은 hostname**(`worklog-backend.myk8s.local`)을 단일 Gateway에 주장한다. NGINX Gateway Fabric은 하나만 라우팅하고 나머지 HTTPRoute의 health를 확정하지 못해, Argo CD Application이 **Synced이지만 Health=Progressing**으로 남는다(Deployment/Pod는 Running/정상, 기능은 동작).
  - 증상: `worklog-backend-dev/staging/prod` 모두 `Synced` / `Progressing`. 4개 namespace에 동일 hostname HTTPRoute 존재.
  - 원인: 같은 단일 `deploy_manifest`를 브랜치별로 쓰는 branch-per-env 구조 + 단일 클러스터/단일 Gateway. 실무는 환경별 클러스터(각자 hostname)라 발생하지 않는 학습 환경 한계다.
  - 대응(택1): ① **단일 클러스터 학습 한계로 명시**하고 넘어간다(권장 — 매니페스트 단순 유지). ② 외부 노출 검증이 필요하면 환경별 hostname(`worklog-backend-dev.myk8s.local` 등)을 매니페스트에 분기. 본 강의는 ①을 채택한다.

## 주의사항

- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: 태그 만들기와 태그 push를 대신 하지 말 것(prod 배포를 정하는 단계라 학습자가 한다)
- ⛔ AI가 하지 말 것: 단계 3, 6, 9, 12의 요청이 없을 때 적용, 커밋, push를 하지 말 것
- ⛔ AI가 하지 말 것: Application yaml을 fork 저장소 안에 저장하지 말 것. `/root/ch8/`에 둔다
- ⛔ AI가 하지 말 것: 워크플로에 argocd CLI 호출 추가 (automated sync에 위임이 본 절의 핵심)
