### 단계 3: Full CI/CD Jenkinsfile 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Jenkinsfile`(8.5에서 만든 파일)을 Jenkins Full CI/CD 파이프라인으로 고쳐줘. Argo CD GitOps + 멀티환경 + automated sync 위임 방식. push는 내가 할게.
> - pipeline 레벨에 `agent { label 'jenkins-jenkins-agent' }` 한 번만 선언(stage별 중복 금지. agent any는 docker가 없는 컨트롤러로 갈 수 있다)
> - environment: DOCKER_REPOSITORY, DOCKERHUB_CREDENTIALS, GITHUB_CREDENTIALS
> - stage 'Init': 마지막 커밋 작성자가 jenkins면(배포 커밋) 태그 빌드가 아닐 때 빌드하지 않고 끝낸다. env.SHORT_SHA, env.COMMIT_MESSAGE 세팅, env.TAG_NAME/env.BRANCH_NAME 분기로 env.TARGET_ENV, env.NAMESPACE, env.IMAGE_TAG(8.5와 같은 규칙), env.ARGOCD_APP 결정 (worklog-backend-dev/staging/prod)

> - stage 'Update Manifest': deploy_manifest/worklog-backend.yaml image 필드와 IMAGE_TAG env value를 env.IMAGE_TAG로 sed 치환 후 `git push origin HEAD:<브랜치>`. 브랜치는 태그 빌드면 main, 아니면 env.BRANCH_NAME
> - argocd CLI를 호출하지 않는다. git push 뒤의 배포는 Argo CD automated sync에 맡긴다(6.8의 Sync Argo CD 단계가 없다)
> - 전역 def 변수 금지, env.* 만 사용
> - post: success/failure에 env.ARGOCD_APP, env.TARGET_ENV 포함
> - Docker Hub username: `<dockerhub_username>`
> - GitHub username: `<github_username>`"

### 단계 5: 멀티환경 End-to-End 검증 `[학습자 직접]`

단계 3의 Jenkinsfile을 main, develop, release/1.0.0 세 브랜치에 모두 넣는다(8.5 단계 5와 같은 방법). 그다음 각 브랜치에 트리거 커밋을 올린다.

```bash
cd /root/workspace/worklog-backend
git checkout main && git add Jenkinsfile && git commit -m "ci: jenkins full cicd" && git pull --rebase && git push
for b in develop release/1.0.0; do
  git checkout $b && git pull && git checkout main -- Jenkinsfile && git commit -m "ci: jenkins full cicd" && git push
done

# develop → dev Application (소스 변경 커밋)
git checkout develop && git pull && echo "# dev" >> README.md && git commit -am "test: dev" && git push

# release → staging Application (staging Application이 보는 release/1.0.0에 소스 변경 커밋)
git checkout release/1.0.0 && git pull && echo "# staging" >> README.md && git commit -am "test: staging" && git push

# v* tag → prod Application (반드시 main 위에, 앞 절과 다른 이름)
git checkout main && git pull && git tag v1.3.0 && git push origin v1.3.0
```

> 태그는 main 최신 커밋에 붙인다. 앞 줄에서 release/1.0.0으로 옮긴 상태로 태그를 붙이면 release 커밋에 붙는다(8.4 단계 6 참고).
> staging Application은 `release/1.0.0`만 본다. 새 release 브랜치를 만들면 `argocd app set worklog-backend-staging --revision <새 브랜치>`로 바꿔야 staging에 반영된다(run-38에서 release/1.2.0 결과는 staging에 배포되지 않았다).

### 단계 5-1: 스캔과 빌드 확인 `[학습자 직접 · 웹]`

Jenkins의 `worklog-backend` job에서 'Scan Multibranch Pipeline Now'를 누른다. 브랜치 job은 스캔으로 빌드되지만 태그 job은 만들어지기만 하고 빌드되지 않는다(Jenkins 기본 동작). 태그 job(`v1.3.0`)을 열어 **Build Now**를 누른다. main 빌드가 끝난 뒤에 누른다. main 빌드와 태그 빌드는 둘 다 main의 매니페스트를 고치므로, 태그 빌드가 나중에 끝나야 prod에 태그 이미지가 남는다.

Console Output에서 TARGET_ENV와 ARGOCD_APP이 의도대로 갈렸는지 확인한다(develop은 worklog-backend-dev, release/1.0.0은 worklog-backend-staging, v1.3.0은 worklog-backend-prod).

### 단계 6: 환경별 배포 확인 `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend && git checkout main && git pull --rebase
for e in dev staging prod; do argocd app get worklog-backend-$e --refresh | grep -E "^Name|Sync Status|Health Status"; done
for e in dev staging prod; do kubectl get deploy worklog-backend -n $e -o jsonpath='{.metadata.namespace}{"  "}{.spec.template.spec.containers[0].image}{"\n"}'; done
```

기대 결과: dev는 `dev-<sha>`, staging은 `staging-<sha>`, prod는 `v1.3.0` 이미지다.

## 검증 중 발견된 이슈 (강의자 참고)

run-38에서 찾은 아래 두 문제는 정답 파일에 반영했다(2026-10-08, 8.5, 8.6, 9.3~9.6 Jenkinsfile 공통).

- **태그 빌드가 매니페스트를 태그 이름으로 push해 실패하던 문제**: 태그 빌드에서는 `BRANCH_NAME`에도 태그 이름이 들어가 `! [rejected] HEAD -> v1.x.x (already exists)`가 났다.
  정답은 이제 `def branch = env.TAG_NAME ? 'main' : env.BRANCH_NAME`으로 main에 push한다. prod Application이 main을 보므로 태그 이미지가 prod 매니페스트에 들어간다.
- **스캔할 때마다 Jenkins가 자기 배포 커밋을 다시 빌드하던 문제**: Init 단계에서 마지막 커밋 작성자가 `jenkins`면 `NOT_BUILT`로 끝낸다. GitHub의 `paths-ignore`와 같은 역할이다.
  태그 빌드는 예외다. main 최신 커밋(대개 배포 커밋)에 태그를 붙이기 때문이다.
- 함께 고친 것: Update Manifest가 `image:` 줄과 `IMAGE_TAG` 값을 함께 바꾼다(GitHub 정답과 같음).

## 트러블슈팅

### Docker socket 권한 오류

```
ERROR: failed to initialize builder backend-builder (backend-builder0): permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

에이전트 Pod의 docker 그룹이 노드의 docker 그룹 GID와 맞지 않을 때 난다. 해결은 5.6 트러블슈팅과 같다(JCasC 에이전트 Pod 템플릿의 `supplementalGroups`를 노드 GID로 맞춘다. 이 강의 노드는 988).

### Jenkins 빌드 중 VM 과부하 (multi-arch 빌드)

`linux/amd64,linux/arm64` 멀티 아키텍처 buildx는 VirtualBox VM에서 QEMU 에뮬레이션으로 CPU/메모리 과부하를 유발할 수 있다.

- **Apple Silicon Mac (ARM64) + VirtualBox**: 모든 VM이 arm64이므로 `--platform linux/arm64` 단일 플랫폼 사용
- **Intel/AMD (x86_64) + VirtualBox**: 모든 VM이 amd64이므로 `--platform linux/amd64` 단일 플랫폼 사용

현재 사용 중인 플랫폼 확인: `kubectl get nodes -o jsonpath="{range .items[*]}{.status.nodeInfo.architecture}\n{end}"`
