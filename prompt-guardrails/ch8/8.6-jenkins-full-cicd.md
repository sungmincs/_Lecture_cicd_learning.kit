# 8.6 [Jenkins] Full CI/CD (Argo CD 자동 sync, 멀티환경 GitOps)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 8.4에서 만든 Argo CD Application 3개 확인, 태그(v*) 만들고 push, 환경별 배포 확인
> - `[학습자 직접 · 웹]`: Jenkins Credentials 확인, 스캔과 빌드 확인
> - `[AI 프롬프트]`: Jenkinsfile 수정(작성 프롬프트는 학습자가 처음부터 작성), 브랜치 3개에 Jenkinsfile 넣고 트리거 커밋 push, 배포 커밋 받기

- ch8/8.5 완료 (Jenkins 멀티환경 파이프라인 동작 확인, GitHub 워크플로 비활성화)

요청과 계획 검토 방식은 8.3의 "8장부터 짧게 요청하고 계획을 검토한다"와 같다.

## 실행 지침

### 단계 1: 기존 Argo CD Application 재사용 확인 `[학습자 직접]`

```bash
argocd app list | grep worklog-backend
```

ch8/8.4에서 생성한 3개 Application(`worklog-backend-dev/staging/prod`)이 모두 `Synced`인지 확인한다(Health `Progressing`은 8.4의 hostname 충돌 때문이며 정상이다). 이 절은 동일한 Argo CD Application 구성을 Jenkins로 트리거할 뿐이다.

### 단계 2: Jenkins Credentials 확인 `[학습자 직접 · 웹]`

Jenkins → Jenkins 관리 → Credentials → System → Global에서 아래 둘이 있는지 본다.

| ID | 종류 | 용도 |
|---|---|---|
| `dockerhub-credentials` | Username with password | Docker Hub login |
| `github-token` | Username with password | deploy_manifest/ git push |

> ⚠️ argocd-password Credential은 필요 없음 — argocd CLI를 직접 호출하지 않는다.

### 단계 3: Jenkinsfile을 Argo CD 흐름으로 수정하기 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
8.5에서 만든 Jenkinsfile을 고쳐줘. 환경마다 Argo CD Application이 배포하게 하려는 거야. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/Jenkinsfile (새 파일을 만들지 말고 이 파일을 고쳐)
- Init stage에서 Application 이름(ARGOCD_APP)도 정함: worklog-backend-dev, -staging, -prod
- Build는 환경 태그와 커밋 해시 앞 8자, 태그 2개로 push
- argocd CLI는 부르지 않음. 배포는 Argo CD 자동 sync에 맡김
- 성공과 실패 알림에 ARGOCD_APP과 TARGET_ENV를 출력
- 끝나면: 바뀐 부분을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| argocd login과 sync를 부르지 않음 | Jenkins에 Argo CD 비밀번호가 필요 |
| 이미지 태그 2개(환경, 해시 8자) | 어느 커밋의 이미지인지 알 수 없음 |
| 배포 커밋 건너뛰기 유지 | 스캔마다 배포 커밋을 다시 빌드 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch8/8.6/1.full-cicd-pipeline.groovy`

### 단계 4: argocd CLI를 부르지 않는 이유 설명 `[AI 프롬프트]`

짧은 질문이라 직접 친다.

```text
6.8의 Jenkinsfile은 argocd CLI로 로그인해서 sync했는데, 8.6은 git push만 하고 Argo CD automated sync에 맡겨. 방식 2개의 장단점을 비교해줘.
```

### 단계 5: 브랜치 3개에 Jenkinsfile 넣고 트리거 커밋 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
수정한 Jenkinsfile을 main, develop, release/1.0.0 브랜치 3개에 넣고 develop과 release/1.0.0에는 트리거 커밋도 올려 push해줘. push하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- main에서 커밋 메시지 ci: jenkins full cicd로 커밋하고 git pull --rebase 뒤 push
- develop과 release/1.0.0은 pull한 뒤 git checkout main -- Jenkinsfile로 가져와 같은 메시지로 커밋
- 브랜치 2개는 README.md 끝에 한 줄(# dev, # staging)을 더해 test: dev, test: staging으로 한 번 더 커밋한 뒤 push
- 끝나면: 브랜치 3개의 push 결과를 보여주고 main으로 돌아와서 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| 브랜치 3개 모두에 같은 Jenkinsfile | 그 브랜치는 이전 Jenkinsfile로 빌드 |
| develop과 release는 소스를 바꾼 커밋 | 배포 커밋 건너뛰기에 해당해 빌드되지 않음 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

> staging Application은 `release/1.0.0`만 본다. 새 release 브랜치를 만들면 `argocd app set worklog-backend-staging --revision <새 브랜치>`로 바꿔야 staging에 반영된다(run-38에서 release/1.2.0 결과는 staging에 배포되지 않았다).

### 단계 6: 태그 만들고 push `[학습자 직접]`

태그는 main 위에 붙인다. 앞 절과 다른 이름이다.

```bash
cd /root/workspace/worklog-backend
git checkout main && git pull
git tag v1.3.0
git push origin v1.3.0
```

### 단계 7: 스캔과 빌드 확인 `[학습자 직접 · 웹]`

Jenkins의 `worklog-backend` job에서 'Scan Multibranch Pipeline Now'를 누른다. 브랜치 job은 스캔으로 빌드되지만 태그 job은 만들어지기만 하고 빌드되지 않는다(Jenkins 기본 동작). 태그 job(`v1.3.0`)을 열어 **지금 빌드** 메뉴를 누른다. main 빌드가 끝난 뒤에 누른다. main 빌드와 태그 빌드는 둘 다 main의 매니페스트를 고치므로, 태그 빌드가 나중에 끝나야 prod에 태그 이미지가 남는다.

Console Output에서 TARGET_ENV와 ARGOCD_APP이 의도대로 갈렸는지 확인한다(develop은 worklog-backend-dev, release/1.0.0은 worklog-backend-staging, v1.3.0은 worklog-backend-prod).

### 단계 8: 배포 커밋 받기 `[AI 프롬프트]`

짧은 요청이라 계획 없이 바로 맡긴다. 8.5 단계 9와 같다.

```text
backend 저장소의 main에서 git pull --rebase로 Jenkins가 올린 배포 커밋을 받아 와줘. 받지 않으면 다음 push가 거절돼.
끝나면: main의 deploy_manifest/worklog-backend.yaml image 줄을 보여줘.
```

### 단계 9: 환경별 배포 확인 `[학습자 직접]`

```bash
for e in dev staging prod; do argocd app get worklog-backend-$e --refresh | grep -E "^Name|Sync Status|Health Status"; done
for e in dev staging prod; do kubectl get deploy worklog-backend -n $e -o jsonpath='{.metadata.namespace}{"  "}{.spec.template.spec.containers[0].image}{"\n"}'; done
```

기대 결과: dev는 `dev-<sha>`, staging은 `staging-<sha>`, prod는 `v1.3.0` 이미지다. refresh 직후에는 prod가 `OutOfSync`로 잠시 보일 수 있다(run-41에서 18초 뒤 Synced).

## 검증 중 발견된 이슈 (강의자 참고)

run-38에서 찾은 아래 문제 2개는 정답 파일에 반영했다(2026-10-08, 8.5, 8.6, 9.3~9.6 Jenkinsfile 공통).

- **태그 빌드가 매니페스트를 태그 이름으로 push해 실패하던 문제**: 태그 빌드에서는 `BRANCH_NAME`에도 태그 이름이 들어가 `! [rejected] HEAD -> v1.x.x (already exists)`가 났다.
  정답은 이제 `def branch = env.TAG_NAME ? 'main' : env.BRANCH_NAME`으로 main에 push한다. prod Application이 main을 보므로 태그 이미지가 prod 매니페스트에 들어간다.
- **스캔할 때마다 Jenkins가 자기 배포 커밋을 다시 빌드하던 문제**: Init 단계에서 마지막 커밋 작성자가 `jenkins`면 `NOT_BUILT`로 끝낸다. GitHub의 `paths-ignore`와 같은 역할이다.
  태그 빌드는 예외다. main 최신 커밋(대개 배포 커밋)에 태그를 붙이기 때문이다.
- 함께 고친 것: Update Manifest가 `image:` 줄과 `IMAGE_TAG` 값을 함께 바꾼다(GitHub 정답과 같음).

## 트러블슈팅

### Docker socket 권한 오류

```
ERROR: failed to initialize builder backend-builder (backend-builder0): permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

에이전트 Pod의 docker 그룹이 노드의 docker 그룹 GID와 맞지 않을 때 난다. 해결은 5.6 트러블슈팅과 같다(JCasC 에이전트 Pod 템플릿의 `supplementalGroups`를 노드 GID로 맞춘다. 이 강의 노드는 988).

### Jenkins 빌드 중 VM 과부하 (multi-arch 빌드)

`linux/amd64,linux/arm64` 멀티 아키텍처 buildx는 VirtualBox VM에서 QEMU 에뮬레이션으로 CPU/메모리 과부하를 유발할 수 있다.

- **Apple Silicon Mac (ARM64) + VirtualBox**: 모든 VM이 arm64이므로 `--platform linux/arm64` 단일 플랫폼 사용
- **Intel/AMD (x86_64) + VirtualBox**: 모든 VM이 amd64이므로 `--platform linux/amd64` 단일 플랫폼 사용

현재 사용 중인 플랫폼 확인: `kubectl get nodes -o jsonpath="{range .items[*]}{.status.nodeInfo.architecture}\n{end}"`

- ⛔ AI가 하지 말 것: stage 안에 agent 중복 선언(env 손실), 또는 `agent any`(컨트롤러로 가면 docker: not found)
- ⛔ AI가 하지 말 것: 전역 def 변수 사용 (Groovy sandbox 호환성)
- ⛔ AI가 하지 말 것: `git push origin HEAD:main` 같은 고정 브랜치 push. 브랜치 빌드는 트리거 브랜치(env.BRANCH_NAME)로, 태그 빌드는 main으로 push한다
- ⚠️ backend는 멀티 아키텍처로 빌드한다. 에이전트가 끊기면 플랫폼을 노드 아키텍처 하나로 바꾼다(아래 트러블슈팅)
- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: 태그 만들기와 태그 push, Jenkins 화면 조작(스캔, 지금 빌드)을 대신 하지 말 것
- ⛔ AI가 하지 말 것: 단계 5, 8의 요청이 없을 때 커밋과 push를 하지 말 것
- ✅ AI가 해도 됨: Jenkinsfile 작성 + GitOps 흐름 설명
- ✅ AI가 해도 됨: automated sync가 git push를 감지하는 메커니즘 설명
- ✅ AI가 해도 됨: env.TAG_NAME이 비어있을 때 분기 우선순위 안내

- ⚠️ env 변수는 반드시 `env.*` (전역 def는 금지)
- ⚠️ Jenkins Multibranch Pipeline에서 develop/release/* 브랜치와 v* 태그 Discovery 모두 활성화
