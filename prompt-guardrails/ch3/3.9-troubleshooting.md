# 3.9 CI/CD 특화 트러블슈팅

> **학습자 진입 방식**: CI/CD 파이프라인에서 배포할 때 가장 자주 만나는 3가지 K8s 오류를
> 재현하고 진단 명령 패턴을 익힙니다.
> - `[학습자 직접]`: 시나리오 1 재현(이미 써 본 `set image`), 모든 시나리오의 진단과 복구
> - `[AI 프롬프트]`: 시나리오 2, 3 재현(아래 "AI가 오류를 만들 때의 범위"), 원인 분석, 흐름도

## 사전 조건

- ch3.6 완료 (kubectl apply 경험, worklog 스택 배포 경험)
- ch3.8 완료 (단계 6에서 worklog 스택을 지운 상태)

## 왜 이 오류들이 "CI/CD 특화"인가?

> "K8s 오브젝트 자체는 문제 없어도, CI/CD 파이프라인이 배포할 때 이 오류들이 가장 많이 발생합니다":
>
> - **ImagePullBackOff**: 파이프라인이 push 전에 deploy하거나, 태그 오타, registry 인증 누락
> - **CrashLoopBackOff**: 새 버전 이미지에 환경변수 누락, 설정 오류, 앱 버그
> - **readinessProbe 실패**: 배포는 됐는데 앱이 아직 준비 안 됨 → 트래픽 차단 → 파이프라인 타임아웃

## 시나리오 1: ImagePullBackOff

### 오류 재현 `[학습자 직접]`

```bash
kubectl set image deployment/worklog-backend \
  worklog-backend=<dockerhub_username>/worklog-backend:wrong-tag
```

### 진단 `[학습자 직접]`

```bash
kubectl get pods
kubectl describe pod <pod-name>
# Events 섹션에서 "Failed to pull image" 메시지 확인
kubectl get events --sort-by='.lastTimestamp' | grep -i "failed\|error" | tail -10
```

### AI와 분석 `[AI 프롬프트]`

> "kubectl describe pod 결과를 붙여줄게. ImagePullBackOff가 발생한 이유와 해결 방법을 알려줘"

### 복구 `[학습자 직접]`

```bash
kubectl set image deployment/worklog-backend \
  worklog-backend=<dockerhub_username>/worklog-backend:buildtest1
kubectl rollout status deployment/worklog-backend
```

**강사 보충 포인트:**
- CI/CD에서 ImagePullBackOff 3대 원인: ① 잘못된 태그 ② push 전에 deploy ③ imagePullSecrets 누락
- 파이프라인 설계 원칙: `docker push` 완전히 완료 후 `kubectl set image`

## 시나리오 2: CrashLoopBackOff

### 오류 재현 `[AI 프롬프트]`

> "worklog-backend Deployment에 CrashLoopBackOff가 나는 상황을 만들어줘. 원인은 설명하지 마. 내가 진단해 볼게."

AI가 고르는 방법은 매번 조금씩 다를 수 있다. 아래 범위 안이면 된다. 진단 순서는 같다.

### 증상 관찰 `[학습자 직접]`

```bash
kubectl get pods -w    # 새 Pod가 Error → CrashLoopBackOff, RESTARTS가 늘어난다. Ctrl+C로 멈춘다
```

### 오류 패턴 이해 `[AI 프롬프트]`

> "CrashLoopBackOff와 ImagePullBackOff의 차이가 뭐야?
> CrashLoopBackOff는 이미지를 성공적으로 pull했는데도 왜 실패하는 거야?"

### 진단 명령 `[학습자 직접]`

```bash
kubectl get pods
kubectl logs <pod-name>
kubectl logs <pod-name> --previous    # 이전 컨테이너 로그 (재시작 후 사라지기 전)
kubectl describe pod <pod-name>       # Events + Exit Code 확인
```

### AI와 분석 `[AI 프롬프트]`

> "kubectl logs 결과를 붙여줄게. CrashLoopBackOff 원인이 뭔지 분석해줘"

### 복구 `[학습자 직접]`

```bash
kubectl rollout undo deployment/worklog-backend
kubectl rollout status deployment/worklog-backend
kubectl get deployment worklog-backend -o jsonpath='{.spec.template.spec.containers[0].args}{"\n"}'   # 빈 줄이면 정상
```

**강사 보충 포인트:**
- 재현 중에도 기존 Pod는 Running으로 남는다. rolling update가 새 Pod가 준비될 때까지 옛 Pod를 지우지 않기 때문이다. 서비스는 끊기지 않지만 배포는 끝나지 않는다
- `--previous` 플래그: 이미 종료된 이전 컨테이너 로그 → CrashLoop 첫 번째 오류 확인에 필수
- CI/CD에서 CrashLoop 주요 원인: ① 환경변수 누락 ② Secret 이름 오타 ③ 새 이미지의 앱 버그
- Exit Code 1: 앱 로직 오류 / Exit Code 137: OOM killed / Exit Code 143: K8s SIGTERM (liveness 실패·rolling update로 인한 강제 종료)

## 시나리오 3: readinessProbe 실패

### 오류 재현 `[AI 프롬프트]`

> "worklog-backend Deployment의 readinessProbe가 실패해 Pod가 Running인데 Ready가 되지 않는 상황을 만들어줘. 원인은 설명하지 마."

### 증상 관찰 `[학습자 직접]`

```bash
kubectl rollout status deployment/worklog-backend --timeout=60s    # 파이프라인의 배포 대기처럼 시간 초과로 끝난다
```

### 오류 패턴 이해 `[AI 프롬프트]`

> "Pod가 Running 상태인데 kubectl get endpoints에서 worklog-backend가 없거나,
> 앱에 접속이 안 되는 경우 어떤 가능성이 있어?"

### 진단 `[학습자 직접]`

```bash
kubectl describe pod <pod-name>
# Conditions: Ready=False, Events: Readiness probe failed 확인

kubectl get endpoints worklog-backend
# 새 Pod IP는 빠져 있다. rolling update 중이라 기존 Pod IP는 남아 있다(Pod가 하나뿐이고 모두 실패하면 <none>)
# ⚠️ K8s 1.33+ 에서 다음 경고 출력됨 (기능 정상 동작):
# "Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice"
# → 경고는 무해. 대신 EndpointSlice로 Pod별 ready를 본다:
kubectl get endpointslices -l kubernetes.io/service-name=worklog-backend \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} ready={.conditions.ready}{"\n"}{end}'
# 기존 Pod는 ready=true, 새 Pod는 ready=false

# Pod 안에서 health endpoint를 직접 호출한다. 이미지에 curl이 없어 python을 쓴다
kubectl exec <pod-name> -- python -c "import urllib.request as u; print(u.urlopen('http://localhost/health').read().decode())"
# {"health":"OK",...} → 앱은 정상. probe 설정(경로나 포트)이 앱과 맞지 않는 것이다
```

### AI와 분석 `[AI 프롬프트]`

> "describe pod 결과에서 Readiness probe failed가 보여. readinessProbe 경로나 포트가 앱과 맞지 않는지 분석해줘"

### 복구 `[학습자 직접]`

```bash
kubectl rollout undo deployment/worklog-backend
kubectl rollout status deployment/worklog-backend
```

**강사 보충 포인트:**
- readinessProbe 실패 = Pod는 Running이지만 Service의 Endpoints에서 제외됨 → 트래픽 없음
- CI/CD 맥락: 새 버전 배포 후 앱 초기화 중 readiness 실패 → `kubectl rollout status` 타임아웃
- 해결 방향: probe의 경로·포트가 앱과 맞는지 확인, `initialDelaySeconds` 증가, 앱 startup 시간 확인 (worklog backend의 `/health`는 DB 연결을 확인하지 않는다)

## AI가 오류를 만들 때의 범위 (시나리오 2, 3)

AI가 쓰는 방법은 매번 달라도 된다. 아래만 지킨다.

- 바꾸는 대상은 `worklog-backend` Deployment 하나다. 이미지, Secret, Service, MongoDB, 다른 네임스페이스는 건드리지 않는다.
- 시나리오 2(CrashLoopBackOff): 컨테이너가 시작하자마자 종료되는 설정만 바꾼다. 예: `args`나 `command`로 이미지의 시작 명령(`fastapi run main.py --port 80`)을 없는 파일이나 잘못된 인자로 덮어쓰기.
  이미지 태그를 바꾸지 않는다(그건 시나리오 1이다). Secret 참조를 깨뜨리면 CrashLoop가 아니라 CreateContainerConfigError가 난다.
- 시나리오 3(readiness 실패): readinessProbe의 경로나 포트를 앱과 맞지 않게 바꾼다. 앱은 정상으로 떠 있어야 한다.
  backend의 `/health`는 MongoDB 연결을 확인하지 않으므로 DB를 멈추는 방법으로는 재현되지 않는다.
- `kubectl rollout undo deployment/worklog-backend` 한 번으로 되돌아가야 한다. 한 번에 한 가지만 바꾼다.
- 오류를 만든 직후에는 "오류 상황을 만들었다, 진단해 보라"까지만 말하고 원인은 설명하지 않는다. Claude Code는 실행한 명령을 화면에 보여 주므로 명령 자체는 숨겨지지 않는다. 학습자는 그 명령을 바로 읽지 말고 증상(`get pods`, `describe`, `logs`)부터 보고, 진단을 마친 뒤 명령과 맞춰 본다.
- run-38에서 쓴 예: 시나리오 2는 `args`를 `["run","nope.py","--port","80"]`로, 시나리오 3은 probe 경로를 `/healthz`로 바꿨다(둘 다 `rollout undo`로 복구 확인).

## 트러블슈팅 판단 흐름도 `[AI 프롬프트]`

> "K8s Pod 오류 트러블슈팅 순서를 판단 흐름도로 정리해줘. kubectl get pods 상태에 따라 다음에 무슨 명령을 써야 하는지"

```
kubectl get pods
  ├─ Pending          → kubectl describe pod (리소스 부족? 노드 선택 실패?)
  ├─ ImagePullBackOff → kubectl describe pod (이미지 태그? registry 인증?)
  ├─ CrashLoopBackOff → kubectl logs --previous (앱 오류? 환경변수 누락?)
  ├─ Running (접속 ✗) → kubectl describe pod + kubectl get endpoints (readiness? port?)
  └─ Running (접속 ✅) → kubectl logs (앱 동작 정상 확인)
```

## 주의사항

- ✅ AI가 해도 됨: 오류 로그 분석, 원인 설명, 해결 방법 안내, 흐름도 정리
- ✅ 학습자가 직접 해야 함: `kubectl describe`, `kubectl logs`, `kubectl exec`, 시나리오 1 재현, 복구(`rollout undo`)
- ⛔ AI가 하지 말 것: 시나리오 1 재현을 대신 실행하지 말 것(이미 아는 명령이라 학습자가 직접 친다). 시나리오 2, 3은 "AI가 오류를 만들 때의 범위" 안에서만 만든다
- ⛔ AI가 하지 말 것: 오류를 만든 직후 원인을 먼저 말하지 말 것. 진단은 학습자가 한다
- 이 섹션의 핵심: **진단 명령 암기가 아니라** "어떤 오류 → 어떤 명령" 판단 흐름 학습

## 💬 질문해보기

> "livenessProbe랑 readinessProbe가 어떻게 달라?"
> (→ readiness: 트래픽을 받을 준비 됐는지 (Endpoints에서 추가/제거). liveness: 앱이 살아있는지 (실패 시 Pod 재시작). CI/CD 배포 중엔 readiness가 더 중요 — 준비 안 된 Pod에 트래픽 가면 사용자 오류.)

> "CrashLoopBackOff가 계속 되면 K8s가 알아서 고쳐줘?"
> (→ 고쳐주지 않음. 재시작 간격만 점점 늘림 (10s → 20s → 40s → ... 최대 5분). 앱 코드나 환경변수 문제는 사람이 고쳐야. liveness 실패로 재시작하는 경우와 달리, CrashLoop는 앱 자체 문제.)
