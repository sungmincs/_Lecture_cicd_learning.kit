# 3.9 CI/CD 특화 트러블슈팅

> **학습자 진입 방식**: CI/CD 파이프라인에서 배포할 때 가장 자주 만나는 3가지 K8s 오류를
> 직접 재현하고 진단 명령 패턴을 익힙니다.

## 사전 조건

- ch3.6 완료 (kubectl apply 경험, worklog 스택 배포 경험)
- 진단용 worklog 스택 재배포 (cleanup 후 재배포)

```bash
kubectl apply -f /root/_Lecture_cicd_learning.kit/ch3/3.6/worklog_manifests
kubectl get pods
```

## 왜 이 오류들이 "CI/CD 특화"인가?

> "K8s 오브젝트 자체는 문제 없어도, CI/CD 파이프라인이 배포할 때 이 오류들이 가장 많이 발생합니다":
>
> - **ImagePullBackOff**: 파이프라인이 push 전에 deploy하거나, 태그 오타, registry 인증 누락
> - **CrashLoopBackOff**: 새 버전 이미지에 환경변수 누락, 설정 오류, 앱 버그
> - **readinessProbe 실패**: 배포는 됐는데 앱이 아직 준비 안 됨 → 트래픽 차단 → 파이프라인 타임아웃

---

## 시나리오 1: ImagePullBackOff `[학습자 직접 재현]`

### 오류 재현

```bash
kubectl set image deployment/worklog-backend \
  worklog-backend=<dockerhub_username>/worklog-backend:wrong-tag
```

### 진단 `[학습자 직접]`

```bash
kubectl get pods
kubectl describe pod <pod-name>
# Events 섹션에서 "Failed to pull image" 메시지 확인
kubectl get events --sort-by='.lastTimestamp' | grep -i "failed\|error" | tail -10
```

### AI와 분석 `[AI 프롬프트]`

> "kubectl describe pod 결과를 붙여줄게. ImagePullBackOff가 발생한 이유와 해결 방법을 알려줘"

### 복구 `[학습자 직접]`

```bash
kubectl set image deployment/worklog-backend \
  worklog-backend=<dockerhub_username>/worklog-backend:buildtest1
kubectl rollout status deployment/worklog-backend
```

**강사 보충 포인트:**
- CI/CD에서 ImagePullBackOff 3대 원인: ① 잘못된 태그 ② push 전에 deploy ③ imagePullSecrets 누락
- 파이프라인 설계 원칙: `docker push` 완전히 완료 후 `kubectl set image`

## 시나리오 2: CrashLoopBackOff `[AI 프롬프트 중심]`

### 오류 패턴 이해

> "CrashLoopBackOff와 ImagePullBackOff의 차이가 뭐야?
> CrashLoopBackOff는 이미지를 성공적으로 pull했는데도 왜 실패하는 거야?"

### 진단 명령 `[학습자 직접]`

```bash
kubectl get pods
kubectl logs <pod-name>
kubectl logs <pod-name> --previous    # 이전 컨테이너 로그 (재시작 후 사라지기 전)
kubectl describe pod <pod-name>       # Events + Exit Code 확인
```

### AI와 분석 `[AI 프롬프트]`

> "kubectl logs 결과를 붙여줄게. CrashLoopBackOff 원인이 뭔지 분석해줘"

**강사 보충 포인트:**
- `--previous` 플래그: 이미 종료된 이전 컨테이너 로그 → CrashLoop 첫 번째 오류 확인에 필수
- CI/CD에서 CrashLoop 주요 원인: ① 환경변수 누락 ② Secret 이름 오타 ③ 새 이미지의 앱 버그
- Exit Code 1: 앱 로직 오류 / Exit Code 137: OOM killed / Exit Code 143: K8s SIGTERM (liveness 실패·rolling update로 인한 강제 종료)

## 시나리오 3: readinessProbe 실패 `[AI 프롬프트 중심]`

### 오류 패턴 이해

> "Pod가 Running 상태인데 kubectl get endpoints에서 worklog-backend가 없거나,
> 앱에 접속이 안 되는 경우 어떤 가능성이 있어?"

### 진단 `[학습자 직접]`

```bash
kubectl describe pod <pod-name>
# Conditions: Ready=False, Events: Readiness probe failed 확인

kubectl get endpoints worklog-backend
# 정상이면 IP 표시, readiness 실패면 <none>
# ⚠️ K8s 1.33+ 에서 다음 경고 출력됨 (기능 정상 동작):
# "Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice"
# → 경고는 무해. 대신 아래 명령 사용 가능:
kubectl get endpointslices -l kubernetes.io/service-name=worklog-backend

kubectl exec -it <pod-name> -- curl -s localhost:80/health
# Pod 내부에서 직접 health endpoint 테스트
# ⚠️ python:3.14-slim-bookworm 기반 이미지에는 curl 없음
# → 대안: kubectl port-forward 또는 wget 사용
```

### AI와 분석 `[AI 프롬프트]`

> "describe pod 결과에서 Readiness probe failed가 보여. health endpoint가 /health인데 왜 실패하는지 분석해줘"

**강사 보충 포인트:**
- readinessProbe 실패 = Pod는 Running이지만 Service의 Endpoints에서 제외됨 → 트래픽 없음
- CI/CD 맥락: 새 버전 배포 후 앱 초기화 중 readiness 실패 → `kubectl rollout status` 타임아웃
- 해결 방향: `initialDelaySeconds` 증가, 앱 startup 시간 확인, DB 연결 로그 확인

## 트러블슈팅 판단 흐름도 `[AI 프롬프트]`

> "K8s Pod 오류 트러블슈팅 순서를 판단 흐름도로 정리해줘. kubectl get pods 상태에 따라 다음에 무슨 명령을 써야 하는지"

```
kubectl get pods
  ├─ Pending          → kubectl describe pod (리소스 부족? 노드 선택 실패?)
  ├─ ImagePullBackOff → kubectl describe pod (이미지 태그? registry 인증?)
  ├─ CrashLoopBackOff → kubectl logs --previous (앱 오류? 환경변수 누락?)
  ├─ Running (접속 ✗) → kubectl describe pod + kubectl get endpoints (readiness? port?)
  └─ Running (접속 ✅) → kubectl logs (앱 동작 정상 확인)
```

## 💬 질문해보기

> "livenessProbe랑 readinessProbe가 어떻게 달라?"
> (→ readiness: 트래픽을 받을 준비 됐는지 (Endpoints에서 추가/제거). liveness: 앱이 살아있는지 (실패 시 Pod 재시작). CI/CD 배포 중엔 readiness가 더 중요 — 준비 안 된 Pod에 트래픽 가면 사용자 오류.)

> "CrashLoopBackOff가 계속 되면 K8s가 알아서 고쳐줘?"
> (→ 고쳐주지 않음. 재시작 간격만 점점 늘림 (5s → 10s → 20s → ... → 5분). 앱 코드나 환경변수 문제는 사람이 고쳐야. liveness 실패로 재시작하는 경우와 달리, CrashLoop는 앱 자체 문제.)
