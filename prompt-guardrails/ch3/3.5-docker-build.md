# 3.5 Worklog 앱 Docker 이미지 빌드 및 Docker Hub Push

> **학습자 진입 방식**: 본 챕터는 학습자가 **명령을 직접 입력**하는 것을 기본으로 합니다.
> - `[학습자 직접]`: `docker build`, `docker push`, `docker login` (핵심 체험 대상)
> - `[학습자 직접 · 웹]`: Docker Hub 가입, 토큰 발급, 저장소 확인
> - `[AI 프롬프트]`: 없음. 막히거나 에러가 나면 AI에 자연어로 질문 — 예: "이 에러 왜 나?", "docker login은 어떻게 해?"

## 사전 조건

- ch3.3 완료 (`/root/workspace/worklog-frontend/`가 `mock` 브랜치, `/root/workspace/worklog-backend/` 존재)
- **ch2.11 완료** (컨트롤 플레인 노드에 Docker 설치됨)

## 실행 지침

### 단계 1: Docker Hub 가입 / 로그인 `[학습자 직접 · 웹]`

- https://hub.docker.com 접속 → 계정이 없으면 가입
- 가입 후 username을 기억 (이후 `<dockerhub_username>` 자리)

> 💡 **gh CLI와 별개**: GitHub의 `gh auth login`과 Docker Hub의 `docker login`은 별개입니다. Docker Hub는 별도 계정·비밀번호.

### 단계 2: 두 저장소와 브랜치 확인 `[학습자 직접]`

컨트롤 플레인 노드 안에서(접속해 있지 않으면 `ssh root@192.168.1.10`):

```bash
ls /root/workspace
# worklog-backend  worklog-frontend  (두 개 존재해야 함)
git -C /root/workspace/worklog-frontend branch --show-current
# mock
```

ch3.3 단계 3·4에서 받았으므로 두 폴더가 보이고 frontend는 `mock` 브랜치여야 한다. 없으면 3.3 단계 3부터 다시 한다.

### 단계 3: Frontend(mock) 이미지 빌드 `[학습자 직접]`

```bash
cd /root/workspace/worklog-frontend
docker build . -t <dockerhub_username>/worklog-frontend:mock-buildtest1
```

> 💡 1분 남짓 걸립니다(run-40에서 73초). 베이스 이미지를 받고 이미지 안에서 `yarn install`을 처음부터 합니다. 3.3에서 만든 작업 폴더의 `node_modules`는 `.dockerignore`에 적혀 있어 이미지에 들어가지 않습니다.

빌드 확인:
```bash
docker images | grep worklog-frontend
```

> 💡 **이미지 이름과 태그**: 이미지 이름은 저장소 이름과 같은 `worklog-frontend`이고, mock 브랜치로 만든 것은 태그 앞에 `mock-`을 붙인다. 7장에서 `main`으로 만드는 이미지와 Docker Hub의 같은 저장소 안에서 구분하기 위해서다.

### 단계 4: Push 시도 (의도적 실패) `[학습자 직접]`

```bash
docker push <dockerhub_username>/worklog-frontend:mock-buildtest1
```

기대 결과: **실패**합니다. 메시지는 Docker 버전에 따라 다음 중 하나:
```
denied: requested access to the resource is denied
```
또는:
```
push access denied, repository does not exist or may require authorization:
server message: insufficient_scope: authorization failed
```

> ⚠️ **이 실패는 의도된 학습 포인트입니다.**
>
> **학습자가 명령을 직접 입력해서 실패 메시지를 자신의 눈으로 확인**하는 것이 가장 효과적입니다. "왜 안 되지?" 하는 순간의 체감이 다음 단계의 `docker login`의 의미를 단단히 만듭니다.
>
> AI에게 push를 위임하는 경우에도, AI는 학습자에게 명령을 안내하고 학습자가 직접 실행하여 실패를 보도록 유도해야 합니다. AI가 알아서 login 후 push까지 처리하면 학습 효과가 소실됩니다.

### 단계 5: Docker Hub login + push 재시도 `[학습자 직접]`

> ⚠️ **반드시 컨트롤 플레인 노드 안에서 (ssh 세션 안에서) 진행하세요.**
> 호스트의 Docker Desktop login과 노드(cp-k8s)의 docker는 별개입니다. 호스트에서 login해도 노드의 `/root/.docker/config.json`은 빈 상태라 push가 계속 실패합니다.

> ⛔⛔ **로그인은 반드시 Docker Hub Access Token(`dckr_pat_…`)으로만 한다 — 계정 비밀번호 절대 금지.**
> - cp-k8s의 `/root/.docker/config.json`은 자격증명을 **평문 base64로 저장**한다(credsStore 없음). 계정 비밀번호를 쓰면 그 비번이 평문으로 디스크에 남고, cp는 `ssh root@192.168.1.10`(비번 `vagrant`)로 접근 가능해 **계정 전체가 노출** 위험에 놓인다.
> - 토큰은 **스코프 제한(repo:write/read)** 과 **개별 폐기**가 가능해, 유출돼도 피해가 한정되고 즉시 무효화할 수 있다.
> - **AI 지침**: 이 절에서 `docker login`을 안내·실행할 때는 **항상 Access Token만** 쓰도록 안내한다. 계정 비밀번호 입력을 제안하거나 대신 입력하지 말 것. 토큰이 없으면 먼저 발급(아래)을 안내한다. 토큰 값은 로그/raw에 `<token>`으로 가린다.

**0) (토큰 없으면) Access Token 발급** — Docker Hub 웹 → Account Settings → Security → **New Access Token** → 권한 **Read & Write** → 생성된 `dckr_pat_…` 복사(이 화면에서만 보임).

**표준 방법 — 대화형 입력(토큰이 셸 히스토리·프로세스 인자에 전혀 남지 않음):**
```bash
# 컨트롤 플레인 노드 안에서
docker login -u <dockerhub_username>
# Password:  ← 계정 비밀번호가 아니라 Access Token(dckr_pat_…)을 붙여넣는다 (화면에 표시되지 않음)
```
기대 출력:
```
i Info → A Personal Access Token (PAT) can be used instead.
         To create a PAT, visit https://app.docker.com/settings

Password:
WARNING! Your credentials are stored unencrypted in '/root/.docker/config.json'.
Configure a credential helper to remove this warning. ...

Login Succeeded
```
→ `Login Succeeded` 표시. **핵심: Password 자리에 계정 비밀번호가 아니라 Access Token을 붙여넣는다.** 대화형 입력은 tty에서 숨김으로 읽히므로 토큰이 셸 히스토리·`ps`(프로세스 인자)에 남지 않는다.

> 💡 **자동화/CI에서만** 토큰을 **시크릿 저장소에서 stdin으로** 전달한다:
> ```bash
> cat ~/dckr_pat.txt | docker login -u <dockerhub_username> --password-stdin   # 또는 secret manager에서 주입
> ```
> ⚠️ 대화형 환경에서 `echo "<토큰>" | docker login --password-stdin`은 **토큰이 셸 히스토리에 그대로 남으므로 쓰지 않는다**(echo 리터럴 금지). 사람이 직접 칠 때는 위의 대화형 `docker login -u <user>` 방식이 표준이다.

로그인 확인:
```bash
cat /root/.docker/config.json
# "auths"의 "https://index.docker.io/v1/"에 인증 정보가 들어 있어야 함 (빈 {} 이면 login 실패)
```

로그인 성공 후 다시 push:
```bash
docker push <dockerhub_username>/worklog-frontend:mock-buildtest1
```

기대 결과: 각 layer가 push되며 마지막에 digest 출력.

## 트러블슈팅

### `Cannot connect to the Docker daemon at unix:///var/run/docker.sock`
ch2.11이 완료되지 않은 상태입니다. ch2.11 단계를 먼저 진행.

### `denied / push access denied / authorization failed`
정상 — 단계 4의 의도적 실패. 단계 5의 `docker login` 후 재시도하면 해결.

### `Error response from daemon: Get "https://registry-1.docker.io/v2/": ...`
네트워크 문제. 컨트롤 플레인 노드의 외부 네트워크 확인:
```bash
ping -c 3 registry-1.docker.io
```

### `unauthorized: incorrect username or password`
- Password 자리에 Access Token(`dckr_pat_…`)을 넣었는지 확인한다.
- 토큰 권한이 Read & Write인지, 토큰이 폐기되지 않았는지 확인한다.
- 계정 비밀번호는 쓰지 않는다(단계 5).

### `Get "https://registry-1.docker.io/v2/library/...": authentication required`
push할 이미지 이름 형식이 잘못된 경우입니다. **이름이 `<dockerhub_username>/...`로 시작**해야 합니다. `library/`나 다른 username으로 시작하면 권한 없음.

### `failed to solve: ... no match for platform in manifest`
arm64 환경(Apple Silicon)에서 base image의 arm64 변형이 없을 때 발생. 본 강의 mock·backend Dockerfile의 base image(`node:24-bookworm-slim`, `python:3.14-slim-bookworm`)는 arm64 지원하므로 정상 동작해야 함. 발생 시 base image tag 확인.

### 빌드가 매우 느림
첫 빌드는 base image 다운로드 + yarn/pip install 때문에 시간이 걸립니다. 소스를 고치지 않고 다시 빌드하면 레이어 캐시로 바로 끝납니다. frontend는 소스를 고치면 `yarn install`이 다시 돕니다(3.4 단계 2).

### push가 성공한 것 같은데 다음 단계에서 또 `denied` 발생
1차 login이 cp-k8s 외부(host의 Docker Desktop 등)에서 진행됐을 가능성. cp-k8s 안에서 직접 docker login 다시 실행. 단계 5의 ⚠️ 박스 참고.

### `docker login`을 했는데 `cat /root/.docker/config.json`이 `{"auths": {}}`
login 자체가 실패했거나 다른 머신/세션에서 진행됨. cp-k8s에 ssh 세션 안에서 직접 다시 실행.

## 주의사항

- ⛔ AI가 하지 말 것: **단계 4 전에 `docker login`을 미리 안내**하지 말 것. 의도적 push 실패가 학습 포인트.
- ⛔ AI가 하지 말 것: 단계 4의 `denied` 에러를 "문제"로 다루지 말 것. 에러의 의미를 설명한 뒤 단계 5로 진행.
- ⛔ AI가 하지 말 것: `<dockerhub_username>`, `<github_username>`을 임의로 채우지 말 것.
- ⛔ AI가 하지 말 것: vagrant 사용자로 접속하라고 안내하지 말 것 — 본 강의 표준은 `ssh root@192.168.1.10`.
- ⛔ AI가 하지 말 것: 학습자가 직접 명령을 입력하지 않고 AI에게 push 진행을 위임하면, login credential을 AI가 처리하려 하지 말 것 — credential은 학습자가 직접 `docker login`으로 입력.
- ⛔⛔ AI가 하지 말 것: **`docker login`에 Docker Hub 계정 비밀번호를 사용/제안/대신 입력하지 말 것.** 반드시 **Access Token(`dckr_pat_…`)만** 사용한다. 이유: cp의 `/root/.docker/config.json`은 평문 base64 저장(credsStore 없음)이라 계정 비번이 평문으로 남고 cp는 `ssh root@192.168.1.10`(`vagrant`)로 접근 가능 → 계정 전체 노출. 토큰은 스코프 제한·개별 폐기 가능.
- ✅ AI가 해도 됨: 토큰 발급 경로 안내(Docker Hub → Account Settings → Security → New Access Token, Read & Write) 및 **대화형 `docker login -u <user>` 후 Password에 Access Token 붙여넣기**를 표준으로 안내(토큰이 히스토리·argv에 안 남음). 자동화/CI에서만 시크릿 저장소→`--password-stdin` 사용하고, 대화형에서 `echo "<token>" | ...`(echo 리터럴)은 히스토리에 남으므로 금지. 토큰 값은 로그/raw에 `<token>`으로 가린다.
- ⛔ AI가 하지 말 것: AI가 단계 3~6의 명령을 자동 실행해버려서 학습자가 실패 메시지를 못 보게 만들지 말 것 — 단계 4의 실패는 학습자의 눈으로 직접 확인되어야 함.
- ⛔ AI가 하지 말 것: `docker build`, `docker push`를 학습자 대신 실행하지 말 것 — 이 명령들은 체험 대상.
- ✅ AI가 해도 됨: 빌드 출력 단계(layer 별 진행) 해석 안내.
- ✅ AI가 해도 됨: Dockerfile 내부 단계(multi-stage build, ENTRYPOINT 등) 설명.
- ✅ AI가 해도 됨: 트러블슈팅 항목과 무관한 오류 발생 시 추가 진단.
