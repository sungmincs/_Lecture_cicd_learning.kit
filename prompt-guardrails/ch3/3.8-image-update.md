# 3.8 이미지 업데이트와 수동 재배포 — "왜 CI/CD가 필요한가"

> **학습자 진입 방식**: 코드 변경 → 빌드 → push → K8s 재배포의 전체 흐름을 **수동으로** 체험합니다.
> 이 불편함이 ch4~에서 CI/CD 자동화를 배우는 동기가 됩니다.

## 사전 조건

- ch3.6 완료 (worklog 스택이 K8s에 배포되어 브라우저에서 접속 가능한 상태. 3.6은 배포 확인까지이고, 코드 변경부터 정리까지는 이 절이 맡는다)
- `http://worklog-frontend.myk8s.local` 정상 접속 확인 완료

## 실행 지침

### 단계 1: 코드 변경 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-frontend/`(mock 브랜치) 소스코드에서 'Summary'라는 텍스트를 찾아서 'Dates'로 바꿔줘. 커밋과 push는 하지 마."

AI가 파일 위치를 찾아 수정합니다. 학습자가 눈으로 변경 확인.

### 단계 2: 이미지 재빌드 & push `[학습자 직접]`

```bash
cd /root/workspace/worklog-frontend
docker build . -t <dockerhub_username>/worklog-frontend:mock-buildtest2
docker push <dockerhub_username>/worklog-frontend:mock-buildtest2
```

소스 한 곳만 고쳤는데 빌드가 3.5만큼 또는 그보다 오래 걸린다(run-40에서 117초). 3.4에서 본 대로 `COPY .`이 `yarn install`보다 앞에 있어 설치가 처음부터 다시 돌기 때문이다.

> 💡 **buildtest2 태그**: 새 버전임을 구분하는 태그. 실무에서는 git commit SHA나 semver를 사용.

### 단계 3: K8s에 새 이미지 배포 `[학습자 직접]`

```bash
kubectl set image deployment/worklog-frontend \
  worklog-frontend=<dockerhub_username>/worklog-frontend:mock-buildtest2
kubectl rollout status deployment/worklog-frontend
```

### 단계 4: 변경 확인 `[학습자 직접]`

브라우저에서 `http://worklog-frontend.myk8s.local` 새로고침 → "Summary" → "Dates" 변경 확인

### 단계 5: 수동 배포의 문제점 토론 `[AI 프롬프트]`

> "내가 방금 한 작업을 매번 수동으로 해야 한다면 어떤 문제가 생길 수 있어?
> CI/CD 파이프라인이 이 과정을 자동화하면 구체적으로 어떤 단계가 없어지는 거야?"

**강사 보충 포인트:**
- 방금 한 일: 코드 수정 → 빌드 → push → set image → 확인 (5단계, ~10분)
- CI/CD 자동화: git push 하나로 나머지 4단계 자동 실행
- 실수 가능성: 이미지 태그 오타, push 빠뜨림, 잘못된 클러스터에 배포
- 팀 협업: 10명이 각자 수동 배포하면 누가 무엇을 배포했는지 추적 불가
- 감사 불가: 언제 누가 어떤 이미지를 배포했는지 기록 없음

### 단계 6: Cleanup `[학습자 직접]`

```bash
kubectl delete -f /root/_Lecture_cicd_learning.kit/ch3/3.6/worklog_manifests
git -C /root/workspace/worklog-frontend checkout -- .     # 단계 1에서 고친 소스를 되돌린다
git -C /root/workspace/worklog-frontend status --short    # 아무것도 안 나오면 깨끗하다
```

삭제 출력 끝에 `secrets "worklog-mongodb-creds" not found` 오류가 한 줄 나온다. 같은 Secret이 backend와 mongodb 매니페스트 두 곳에 적혀 있어 두 번째 삭제가 대상을 못 찾는 것이다. 나머지는 모두 지워졌으므로 그대로 넘어간다(3.9 정리도 같다).

소스를 되돌려 두는 이유: 7장에서 같은 폴더를 `main` 브랜치로 바꿔 쓴다. 고친 것이 남아 있으면 브랜치 전환이 막힌다.

### 단계 7: 빌드가 남긴 것을 보고 치우기 `[학습자 직접]`

3.5와 3.8에서 이미지를 세 번 빌드했다. 빌드할 때마다 노드 디스크에 두 가지가 남는다. 만든 이미지, 그리고 다음 빌드를 빠르게 하려고 Docker가 보관하는 단계별 결과물(빌드 캐시)이다. 얼마나 쌓였는지 본다.

```bash
df -h /                  # 노드 디스크 전체
docker system df         # Docker가 쓰는 양. Images와 Build Cache 줄을 본다
docker images
```

3장의 이미지는 Docker Hub에 올라가 있고, 클러스터는 거기서 받아 쓴다. 노드의 Docker에 남은 것은 지워도 된다.

```bash
docker image prune -a -f       # 컨테이너가 쓰지 않는 이미지를 모두 지운다
docker builder prune -a -f     # 빌드 캐시를 모두 지운다
docker system df               # Images와 Build Cache가 0B
df -h /                        # Use%가 내려갔다
```

기대 결과: 지우기 전에는 Images가 2.5GB, Build Cache가 1.7GB 안팎이고, 지운 뒤에는 둘 다 0B다. 디스크는 2~3GB 비워진다(run-40에서 53%가 45%로).

이미지를 먼저 지우고 캐시를 지운다. 이미지가 남아 있으면 그 이미지와 겹치는 캐시는 지워지지 않는다. `docker image prune`이 출력하는 `Total reclaimed space`는 아주 작게 나올 수 있다. 이미지와 캐시가 같은 데이터를 나눠 쓰기 때문이고, 실제로 비워진 양은 마지막의 `df -h /`로 본다.

노드 한 대에 이미지 보관소가 둘 있다는 것도 여기서 본다. 위 명령은 Docker의 것만 지웠다. Pod가 쓰는 이미지는 쿠버네티스(containerd)가 따로 받아서 보관하고, 아래 명령으로 보인다.

```bash
crictl images | head                                        # 쿠버네티스가 받아 둔 이미지. docker images에는 안 보인다
kubectl describe node cp-k8s | grep -E "DiskPressure"       # False면 정상
```

쿠버네티스가 받아 둔 이미지는 kubelet이 관리한다. 디스크가 85%를 넘으면 쓰지 않는 이미지를 스스로 지워 80%로 내리고, 그래도 남은 공간이 15% 아래면 `DiskPressure`를 `True`로 바꾸고 Pod를 내보낸다. Docker로 빌드한 이미지와 빌드 캐시는 kubelet이 치우지 않는다. 그래서 빌드를 하는 서버(CI 서버)는 실무에서 정리 명령을 주기적으로 돌게 걸어 둔다.

이 강의의 노드는 루트가 30GiB이고 처음에 17GiB쯤 비어 있다. 한 번 따라가는 동안 모자라지 않으므로 이 정리를 다시 할 필요는 없다. 여기서는 빌드가 무엇을 남기는지 보는 것이 목적이다.

## 트러블슈팅

### `kubectl set image` 후 새 Pod가 ImagePullBackOff

buildtest2 이미지가 push되지 않았거나 태그 오타. 확인:
```bash
kubectl describe pod <pod-name>
# Events: Failed to pull image ... → push 상태 확인
docker push <dockerhub_username>/worklog-frontend:mock-buildtest2
```

### 브라우저에서 텍스트가 안 바뀜

캐시 문제일 가능성. Hard refresh (`Ctrl+Shift+R` 또는 `Cmd+Shift+R`). 또는:
```bash
kubectl rollout status deployment/worklog-frontend
# 새 Pod가 Running인지 확인
kubectl get pods -l app=worklog-frontend
```

- ✅ AI가 해도 됨: 코드 텍스트 수정, yaml 이미지 태그 교체, 배포 흐름 설명

> ch5에서 git tag 기반 자동 태깅 다룸.)
