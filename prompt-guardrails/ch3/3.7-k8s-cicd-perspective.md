## 실행 지침

### 핵심 질문 1: 왜 Deployment인가? `[AI 프롬프트]`

```bash
cat /root/_Lecture_cicd_learning.kit/ch3/3.6/worklog_manifests/worklog-backend.yaml
```

> "이 Deployment 매니페스트에서 `image: <dockerhub_username>/worklog-backend:buildtest1` 부분이
> CI/CD에서 어떤 의미를 가지는지 설명해줘.
> 파이프라인이 새 버전을 배포할 때 실제로 어떤 kubectl 명령을 실행하게 되는 거야?"

**강사 보충 포인트:**
- `kubectl set image deployment/worklog-backend worklog-backend=<image>:<new-tag>` = CI/CD 파이프라인의 "배포" 단계
- k8s kit에서 배운 롤링 업데이트가 바로 이 시점에 일어남
- 이미지 태그 = 버전 = 배포 단위 → "어떤 버전을 배포할지"를 파이프라인이 결정
- GitOps(ch6)에서는 yaml 파일의 태그를 git push로 변경 → Argo CD가 자동 감지 → 배포

### 핵심 질문 2: 왜 Secret인가? `[AI 프롬프트]`

```bash
# Secret 값 확인 (base64 디코딩)
echo "cm9vdA==" | base64 -d    # → root
echo "bXlwYXNzdzByZA==" | base64 -d  # → mypassw0rd
```

> "K8s Secret이 CI/CD 파이프라인 보안과 어떤 관계가 있어?
> 파이프라인 로그에 DB 비밀번호가 찍히는 게 왜 위험하고, Secret이 그 문제를 어떻게 해결하는 거야?"

**강사 보충 포인트:**
- k8s kit: "민감 정보를 Pod 외부에 분리"
- CI/CD 맥락: GitHub Actions 로그 → PR마다 공개 가능 → 비번이 찍히면 재앙
- Secret = 파이프라인(코드/로그)과 런타임(Pod) 사이의 경계선
- 실무 패턴: 파이프라인은 Secret 이름(`worklog-mongodb-creds`)만 yaml에 참조, 실제 값은 K8s가 런타임에 env로 주입

### 핵심 질문 3: 왜 imagePullSecrets인가? `[AI 프롬프트]`

> "K8s가 Docker Hub에서 이미지를 pull할 때 왜 imagePullSecrets가 필요한 거야?
> Docker Hub의 rate limit이 뭐고, CI/CD에서 anonymous pull이 문제가 되는 이유는 뭐야?"

**강사 보충 포인트:**
- Docker Hub rate limit: 비인증 100 pull/6h, 인증 200 pull/6h, 유료 무제한
- CI/CD: PR마다 이미지 pull → 팀 단위로 rate limit 금방 소진 → `ImagePullBackOff`
- Private registry(ECR, GCR, Harbor) 사용 시 인증 필수 (ch4+ 실제 파이프라인에서 imagePullSecrets 추가)
- imagePullSecrets 생성 방법 (참고):
  ```bash
  kubectl create secret docker-registry dockerhub-creds \
    --docker-username=<dockerhub_username> \
    --docker-password=<dockerhub_password>
  ```

### 종합 정리 `[AI 프롬프트]`

> "방금 얘기한 세 가지(Deployment 이미지 태그 업데이트, Secret, imagePullSecrets)가
> CI/CD 파이프라인 전체 흐름에서 어떻게 연결되는지 단계별로 설명해줘"

예상 흐름:
```
코드 push →
CI: docker build + push (새 태그) →
CD: kubectl set image (Deployment 이미지 태그 변경) →
K8s: imagePullSecrets로 registry 인증 → 새 이미지 pull →
Pod 환경변수에 Secret 값 주입 →
rolling update 완료
```

## 💬 질문해보기

> "Deployment 말고 Pod에 직접 이미지 넣어서 배포하면 안 돼?"
> (→ Pod는 K8s가 직접 관리 안 함. 죽으면 재시작 없음. CI/CD 파이프라인이 새 이미지로 배포하려면 반드시 Deployment를 통해야 롤링 업데이트와 재시작 보장 가능.)

> "Secret이 base64라서 누가 decode하면 보이는 거 아니야? 그게 무슨 보안이야?"
> (→ Secret은 암호화가 아니라 "인코딩"이 맞음. K8s의 보안은 RBAC + etcd encryption at rest로. base64는 단순 포맷, 실제 보호는 K8s 접근 제어가 담당. Secret의 가치는 "코드/로그에서 분리"에 있음.)
