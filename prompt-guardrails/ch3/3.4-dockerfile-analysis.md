### 단계 2: Dockerfile 구조 분석 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Dockerfile`이 어떤 구조로 되어 있는지 단계별로 설명해줘"

> "`/root/workspace/worklog-frontend/Dockerfile`(mock 브랜치)은 어떤 구조로 되어 있는지 설명해줘"

**예상 답변 핵심 포인트:**
- 단일 스테이지 구조: `node:24-bookworm-slim` → `yarn install` → `yarn dev` 실행
- `yarn install`과 같은 `RUN` 줄에서 `yarn cache clean`을 한다. yarn이 내려받은 파일의 사본(캐시)은 실행에 쓰이지 않는데, 지우지 않으면 이미지에 수백 MB가 더 들어간다. 다른 `RUN` 줄에서 지우면 앞 레이어에 이미 들어가 있어 이미지가 줄지 않는다. backend Dockerfile의 `pip install --no-cache-dir`도 같은 목적이다
- `.dockerignore`에 `node_modules`와 `.git`이 적혀 있다. `COPY . /app`은 폴더 전체를 복사하는데, 3.3에서 `yarn install`로 만든 `node_modules`(약 370MB)가 작업 폴더에 있다. 이 파일이 없으면 그것까지 이미지에 들어간다. 그러면 손으로 빌드한 이미지와 CI가 새로 clone해서 빌드한 이미지의 내용이 달라진다. `.dockerignore`는 어디서 빌드하든 같은 이미지가 나오게 한다
- 이 Dockerfile은 `COPY .`이 `yarn install`보다 앞에 있다. 그래서 소스를 한 줄만 고쳐도 설치가 처음부터 다시 돈다. 3.8에서 이것을 직접 겪는다. 단계 3의 나쁜 패턴에 해당하고, backend Dockerfile이 좋은 패턴이다
- `ENV VITE_API_URL`이 선언돼 있지만 현재 mock 소스는 이 값을 읽지 않는다. API는 상대 경로(`/api/v1/...`)로 부르고 MSW가 가로챈다.
- `worklog-frontend`의 `mock` 브랜치는 개발 서버(Vite dev server) 기반 — 학습 단계에서는 프로덕션 빌드 불필요
- Dockerfile 하단의 주석(`# FROM nginx:1.25-bookworm`)은 프로덕션용 nginx 멀티스테이지 패턴의 예시 (활성화 안 됨)

> 💡 멀티스테이지 빌드 개념을 설명하고 싶다면 backend Dockerfile을 중심으로 설명합니다. frontend의 mock 브랜치는 의도적으로 단순한 dev server 구조를 사용합니다.

### 단계 3: 레이어 캐시와 CI/CD 빌드 시간 연결 `[AI 프롬프트]`

> "Dockerfile에서 COPY 명령의 순서가 왜 중요한지, CI/CD 빌드 시간과 어떤 관계가 있는지 설명해줘"

**예상 답변 핵심 포인트 (uv 기준):**

> ⚠️ **4차 검증 확인 사항**: `worklog-backend` Dockerfile이 **poetry → uv**로 전환됨 (2026-05-28 기준).
> - 빌드 스테이지 추가: `ghcr.io/astral-sh/uv:python3.14-bookworm-slim AS uv_builder`. 실행 이미지는 `python:3.14-slim-bookworm` 그대로
> - lock 파일: `poetry.lock` → `uv.lock`
> - export 명령: `poetry export` → `uv export --no-dev --no-hashes --no-emit-project`

현재 backend Dockerfile (uv 기반):
```dockerfile
FROM ghcr.io/astral-sh/uv:python3.14-bookworm-slim AS uv_builder

COPY ./pyproject.toml ./uv.lock /
RUN uv export --no-dev --no-hashes --no-emit-project -o requirements.txt

FROM python:3.14-slim-bookworm

WORKDIR /app/worklog
COPY ./src/worklog /app/worklog
COPY --from=uv_builder /requirements.txt /tmp/requirements.txt

RUN pip install --no-cache-dir -r /tmp/requirements.txt

ENTRYPOINT ["fastapi"]
CMD ["run", "main.py", "--port", "80"]
```

- Docker 레이어 캐시: 이전 레이어가 변경되면 이후 레이어 캐시 무효화
- backend Dockerfile 패턴: `COPY pyproject.toml uv.lock` → `RUN uv export` → `COPY src/` → 의존성 변경 없으면 `pip install` 캐시 유지
- CI/CD에서: 소스 코드만 변경됐을 때 의존성 재설치 없이 빌드 → 시간 단축
- 나쁜 패턴: `COPY . .` → `RUN pip install` → 코드 변경 때마다 full install
