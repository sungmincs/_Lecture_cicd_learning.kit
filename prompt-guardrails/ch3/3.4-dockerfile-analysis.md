### 단계 3: 레이어 캐시와 CI/CD 빌드 시간 연결 `[AI 프롬프트]`

> "Dockerfile에서 COPY 명령의 순서가 왜 중요한지, CI/CD 빌드 시간과 어떤 관계가 있는지 설명해줘"

**예상 답변 핵심 포인트 (uv 기준):**

> ⚠️ **4차 검증 확인 사항**: `worklog-backend` Dockerfile이 **poetry → uv**로 전환됨 (2026-05-28 기준).
> - base 이미지: `python:3.14-slim-bookworm` → `ghcr.io/astral-sh/uv:python3.14-bookworm-slim`
> - lock 파일: `poetry.lock` → `uv.lock`
> - export 명령: `poetry export` → `uv export --no-dev --no-hashes --no-emit-project`

현재 backend Dockerfile (uv 기반):
```dockerfile
FROM ghcr.io/astral-sh/uv:python3.14-bookworm-slim AS uv_builder

COPY ./pyproject.toml ./uv.lock /
RUN uv export --no-dev --no-hashes --no-emit-project -o requirements.txt

FROM python:3.14-slim-bookworm

WORKDIR /app/worklog
COPY ./src/worklog /app/worklog
COPY --from=uv_builder /requirements.txt /tmp/requirements.txt

RUN pip install --no-cache-dir -r /tmp/requirements.txt

ENTRYPOINT ["fastapi"]
CMD ["run", "main.py", "--port", "80"]
```

- Docker 레이어 캐시: 이전 레이어가 변경되면 이후 레이어 캐시 무효화
- backend Dockerfile 패턴: `COPY pyproject.toml uv.lock` → `RUN uv export` → `COPY src/` → 의존성 변경 없으면 `pip install` 캐시 유지
- CI/CD에서: 소스 코드만 변경됐을 때 의존성 재설치 없이 빌드 → 시간 단축
- 나쁜 패턴: `COPY . .` → `RUN pip install` → 코드 변경 때마다 full install

## 💬 질문해보기

> "멀티스테이지 빌드 안 하면 어떻게 돼?"
> (→ 빌드 도구(node_modules, yarn, gcc 등)가 최종 이미지에 포함 → 이미지 크기 수백 MB 증가 → Docker Hub push 느려짐 → K8s pod 시작 느려짐. 보안 취약점 표면적도 증가.)

> "Dockerfile FROM에 있는 `node:24-bookworm-slim`이 뭐야? slim이 뭔지?"
> (→ `bookworm` = Debian 12 코드명. `slim` = 최소화 변형(불필요한 패키지 제거, 이미지 크기 감소). 보안 패치된 LTS base image 선택이 CI/CD 빌드의 기본.)
