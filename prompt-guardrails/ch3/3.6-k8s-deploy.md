## 실행 지침

### 단계 2: Gateway에 할당된 LB의 External IP 확인

NGINX Gateway Fabric controller는 각 Gateway 객체별로 LoadBalancer Service를
default namespace에 자동 생성합니다. controller 자체 설치 시 `nginx-gateway`라는
이름의 Gateway가 default ns에 만들어져 있고, 거기에 대응하는 LB Service는
`nginx-gateway-nginx`(`<gateway-name>-<gatewayClass-name>` 패턴)입니다.

```bash
kubectl get gateway nginx-gateway -o wide
```

기대 출력:
```
NAME            CLASS   ADDRESS        PROGRAMMED   AGE
nginx-gateway   nginx   192.168.1.XX   True         10m
```

또는 자동 생성된 LoadBalancer Service에서 직접 조회:
```bash
kubectl get svc nginx-gateway-nginx
```

기대 출력:
```
NAME                  TYPE           CLUSTER-IP      EXTERNAL-IP    PORT(S)
nginx-gateway-nginx   LoadBalancer   10.xxx.xxx.xxx  192.168.1.XX   80:32XXX/TCP
```

> ⚠️ **EXTERNAL-IP가 `<pending>` 이면**: MetalLB IPAddressPool이 적용되지 않은 상태입니다. extra_k8s_pkgs.sh의 `(sleep 540 && apply ...)&` 백그라운드 작업이 vagrant up 종료 후 약 9~10분에 도달하므로, vagrant up 직후엔 `<pending>`이 정상입니다. 충분히 기다리거나, 즉시 진행해야 하면 트러블슈팅의 `MetalLB IPAddressPool 누락` 참조하여 수동 apply.

EXTERNAL-IP 값(예: `192.168.1.99`)을 메모해두세요. 다음 단계의 hosts 파일에 이 IP를 씁니다.

### 단계 3: 호스트 머신 hosts 파일 수정

**호스트 머신** (학습자 본인 macOS/Windows)의 hosts 파일에 다음을 추가:

```
<EXTERNAL-IP>  worklog-frontend.myk8s.local
<EXTERNAL-IP>  worklog-backend.myk8s.local
```

`<EXTERNAL-IP>`는 단계 2의 값(예: `192.168.1.99`).

OS별 hosts 파일 위치:

- **macOS / Linux**: `sudo vi /etc/hosts`
- **Windows**: 메모장을 **관리자 권한**으로 실행 → `C:\Windows\System32\drivers\etc\hosts` 편집

> ⚠️ hosts 파일은 학습자의 **호스트 머신에서 수정**합니다. control plane 노드 안이 아닙니다.

### 단계 4: 매니페스트 image 필드 수정 `[AI 프롬프트]`

매니페스트의 image 필드는 `<dockerhub_username>` placeholder로 되어 있습니다.
`sed` 문법을 배우는 단계가 아니므로 AI에게 요청합니다.

**학습자 입력 예시:**
> "내 Docker Hub username은 `sysnet4admin`이야. manifests에 반영해줘."

AI가 치환 후 결과를 보여줍니다. 학습자가 확인:
```bash
[root@cp-k8s worklog_manifests]# grep image: worklog-frontend.yaml worklog-backend.yaml
# worklog-frontend.yaml:        image: sysnet4admin/worklog-frontend-mock:buildtest1
# worklog-backend.yaml:         image: sysnet4admin/worklog-backend:buildtest1
```

> 💡 **frontend는 `-mock` suffix**: ch3에서 frontend는 MSW mock을 포함한 이미지(`worklog-frontend-mock`)를 사용합니다. ch3.3에서도 이 이름으로 build/push 했습니다. backend는 suffix 없이 `worklog-backend`.

### 단계 6: Pod / Service / Gateway / HTTPRoute / PVC 상태 확인

```bash
[root@cp-k8s 3.6]# kubectl get pods,svc,gateway,httproute,pvc
```

기대:
- `worklog-frontend-*`, `worklog-backend-*`, `worklog-mongodb-*` 세 Pod 모두 `Running` (1~2분 소요)
- service `worklog-frontend`, `worklog-backend`, `worklog-mongodb` 표시
- httproute `worklog-frontend`, `worklog-backend` 두 개 표시 (각각 parent `nginx-gateway` 참조)
- pvc `pvc-worklog-mongodb` `Bound`
- gateway는 신규 생성하지 않습니다 — controller가 설치 시 만든 default ns의 `nginx-gateway`를 두 HTTPRoute가 공유

```bash
[root@cp-k8s 3.6]# kubectl get httproute -o wide
# NAME               HOSTNAMES                          AGE
# worklog-backend    ["worklog-backend.myk8s.local"]    1m
# worklog-frontend   ["worklog-frontend.myk8s.local"]   1m
```

> 💡 **mongodb가 가장 먼저 Ready되어야** backend의 readinessProbe(`/health`)가 통과합니다. mongodb는 NFS PVC를 mount하므로 PVC binding + 컨테이너 시작에 시간이 더 들 수 있음.

### 단계 7: 호스트 브라우저에서 앱 접속

호스트 머신의 브라우저에서:

- Frontend: `http://worklog-frontend.myk8s.local`
- Backend (Swagger): `http://worklog-backend.myk8s.local`

기대 결과:
- Frontend UI가 표시되며, 백엔드와 정상 통신 (mock 응답이 아닌 진짜 backend Pod 응답)
- UI에서 작업 기록 추가 → backend `/api/...` → MongoDB에 저장 → 화면 새로고침 시 유지

> 💡 **ch3.3와의 차이점**: ch3.3의 mock은 MSW가 브라우저에서 가짜 응답을 만들었지만, 본 챕터에선 진짜 backend Pod + MongoDB Pod로 연결됩니다. UI에서 추가한 데이터가 실제로 MongoDB에 저장되고 Pod이 재시작되어도 유지됩니다 (NFS PV).

## 트러블슈팅

### EXTERNAL-IP가 `<pending>` (MetalLB IPAddressPool 누락)

```bash
kubectl get ipaddresspool -n metallb-system
# No resources found
```

extra_k8s_pkgs.sh의 background sleep이 fail한 경우 (구버전 잔재). 본 강의의 신규 vagrant up부터는 이 문제가 발생하지 않도록 extra_k8s_pkgs.sh가 수정되었습니다. 기존 cluster 재가동 시에만 발생.

수동 apply:
```bash
kubectl apply -f https://raw.githubusercontent.com/sysnet4admin/IaC/main/k8s/extra-pkgs/v1.35/metallb-l2mode.yaml
kubectl apply -f https://raw.githubusercontent.com/sysnet4admin/IaC/main/k8s/extra-pkgs/v1.35/metallb-iprange.yaml
```

### Gateway가 `PROGRAMMED=False` 또는 `ADDRESS`가 비어 있음

NGINX Gateway Fabric controller가 정상 동작 중인지 확인:
```bash
kubectl get pods -n nginx-gateway
# nginx-gateway-XXX  1/1  Running
```

`PROGRAMMED=False` 지속 시 controller 로그:
```bash
kubectl logs -n nginx-gateway -l app.kubernetes.io/name=nginx-gateway --tail=30
```

### Pod ImagePullBackOff 또는 ErrImagePull

```bash
kubectl describe pod worklog-frontend-XXX
# Events: ... Failed to pull image "<dockerhub_username>/worklog-frontend-mock:buildtest1" ...
```

원인 후보:
1. 매니페스트 image 필드의 username이 본인 Docker Hub username과 다름 → 단계 4 재확인
2. 이미지 이름 오타 (예: `worklog-frontend` vs `worklog-frontend-mock`)
3. Docker Hub에 push 안 됨 → `docker images | grep worklog` 또는 https://hub.docker.com 확인
4. 이미지가 private이고 imagePullSecrets 없음 → 본 강의는 public 가정

### worklog-mongodb Pod CrashLoopBackOff

NFS storage class가 default가 아니거나 PVC binding 실패. 진단:
```bash
kubectl get pvc
# STATUS가 Bound가 아니면 문제
kubectl get storageclass
# managed-nfs-storage에 (default) 표시되어야 함
```

### worklog-backend readinessProbe 실패 (`/health` 응답 없음)

backend가 mongodb에 connection 실패하면 `/health`가 503. 보통 mongodb Pod이 늦게 Ready되어 발생.

```bash
kubectl logs worklog-backend-XXX | tail -20
# MongoDB connection ... 등 확인
```

기다리면 자동 회복. 1-2분 후 readinessProbe 통과.

### 호스트 브라우저에서 `worklog-frontend.myk8s.local` 접속 불가

체크리스트:
1. hosts 파일이 호스트 머신의 `/etc/hosts` (macOS/Linux) 또는 `C:\Windows\System32\drivers\etc\hosts`에 수정되어 있는가?
2. hosts 파일의 IP가 단계 2의 EXTERNAL-IP와 일치하는가?
3. `kubectl get gateway nginx-gateway`의 ADDRESS와 일치하는가? (HTTPRoute가 attach된 Gateway)
4. `kubectl get httproute`에서 두 HTTPRoute가 표시되는가?
5. `curl -H "Host: worklog-frontend.myk8s.local" http://<EXTERNAL-IP>/` 직접 테스트

같은 192.168.1.0/24 네트워크에 다른 K8s cluster(MetalLB 사용)가 동시 가동 중이면 IP 충돌 가능 — `arp -an | grep 192.168.1.XX`로 응답 MAC이 의도한 cluster 노드의 것인지 확인.

## 💬 질문해보기

> "Pod이 3개 떴는데 왜 Service는 3개고 HTTPRoute는 2개야?"
> (→ mongodb는 cluster 내부에서만 접근(ClusterIP), 외부 공개 필요 없음 → HTTPRoute 없음. frontend/backend만 외부 노출.)

> "ch3.3에서는 MSW가 가짜 응답 주던데, 지금은 진짜 backend랑 어떻게 연결돼?"
> (→ frontend Pod의 `VITE_API_URL` env가 `http://worklog-backend.default.svc.cluster.local:80`. 같은 namespace의 backend Service를 통해 통신. cluster DNS가 그 이름을 해석.)

> "Gateway랑 HTTPRoute는 왜 분리되어 있어? 옛날엔 Ingress 한 객체였잖아"
> (→ Gateway API 설계 의도. Gateway는 인프라 담당자(어떤 listener·port·TLS), HTTPRoute는 앱 담당자(어떤 host·path → 어떤 service)로 책임 분리. 한 Gateway를 여러 HTTPRoute가 공유하는 게 본 강의 패턴. Ingress보다 모던하고 확장성 좋은 표준.)

> "buildtest1 → buildtest2로 어떻게 갈아끼웠는데 다운타임이 거의 없어?"
> (→ K8s Deployment의 기본 strategy는 RollingUpdate. 새 Pod이 Ready되어야 옛 Pod이 Terminating. 무중단 배포의 가장 기본 형태. ch7에서 Blue-Green, Canary 등 더 정교한 전략 다룸.)

> "이게 진짜 운영이라면 매번 kubectl edit으로 image 태그 바꾸는 거야?"
> (→ 아니. ch4부터 GitHub Actions / Jenkins / GitLab CI 같은 도구로 자동화. ch6+ Argo CD로 GitOps로 발전.)
