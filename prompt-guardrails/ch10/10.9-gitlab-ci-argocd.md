# 10.9 [GitLab] 실습 1: CI로 빌드하고 Argo CD로 EKS에 배포

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 파이프라인 확인, 노드에 GitLab 저장소 clone, 첫 push(토큰 입력), 배포 확인
> - `[학습자 직접 · 웹]`: GitLab 가입과 전화번호 인증, 저장소 가져오기, 토큰 발급과 CI/CD Variables 등록, 파이프라인 확인
> - `[AI 프롬프트]`: `.gitlab-ci.yml` 작성, Argo CD가 보는 저장소 바꾸기(프롬프트는 학습자가 처음부터 작성), 10.6과의 차이 질문

## 사전 조건

- ch10.7 완료 (EKS의 Application `worklog-backend`가 학습자 GitHub fork의 `deploy_manifest/`를 자동 sync 중)
- 노드의 argocd CLI가 EKS의 Argo CD에 로그인된 상태 (10.5 단계 11)
- Docker Hub Access Token (5.3에서 발급. 보관해 두지 않았으면 새로 발급한다)

## 이 실습이 확인하는 것

CI가 하는 일은 GitHub Actions(10.6 Part B)와 같다. 테스트, 이미지 빌드, `deploy_manifest/`의 이미지 태그 갱신까지다.
클러스터에 반영하는 것은 Argo CD의 자동 sync다. 그래서 **이 파이프라인에는 AWS 자격 증명이 필요 없다.** Argo CD가 Git을
당겨 가는 구조(pull)이기 때문이다. 바뀌는 것은 Argo CD가 보는 Git 저장소 하나뿐이다.

## 실행 지침

### 단계 1: 앞 절 파이프라인 확인 `[학습자 직접]`

Jenkins는 스캔을 누르지 않으면 돌지 않는다. GitHub 워크플로는 10.7 단계 1에서 모두 껐다. 확인만 한다. Argo CD는 아직 GitHub fork를 본다.

```bash
gh workflow list --all -R <github_username>/worklog-backend
# 모두 disabled_manually
argocd app get worklog-backend | grep -E "Repo:|Sync Status"
```

### 단계 2: GitLab 가입 `[학습자 직접 · 웹]`

https://gitlab.com 에서 계정을 만든다. 새 계정은 공유 러너를 쓰기 전에 **전화번호 인증**이 필요하다. 인증 전에는 첫 파이프라인이
"계정을 인증해야 합니다"로 멈춘다. 그 화면의 버튼으로 인증한다. 과금은 없다.

| 순서 | 할 일 | 설명 |
|---|---|---|
| 1 | https://gitlab.com에서 계정 만들기 | 무료 계정 |
| 2 | 전화번호 인증 | 공유 러너를 사용하려면 필요 |

### 단계 3: fork 가져오기 `[학습자 직접 · 웹]`

GitLab → New project → **Import project** → **Repository by URL**. 위치는 **개인 네임스페이스**(`<gitlab_username>`)다. 그룹 안에 만들면 그룹의 공개 범위를 넘을 수 없어서, 그룹이 private이면 프로젝트도 private가 되고 Argo CD가 읽지 못한다.

원본(`sungmincs/worklog-backend`)이 아니라 **학습자의 GitHub fork**를 가져온다. 10.5에서 ALB Ingress로 바꾼 `deploy_manifest/`가 함께 들어와야 Argo CD가 같은 매니페스트를 그대로 동기화한다.

| 항목 | 입력 | 설명 |
|---|---|---|
| New project | Import project → Repository by URL | 가져오기 |
| Git repository URL | https://github.com/<github_username>/worklog-backend.git | 내 fork |
| Project name | worklog-backend | 개인 네임스페이스 |
| Visibility | Public | Argo CD가 읽음 |

### 단계 4: 토큰과 Variables `[학습자 직접 · 웹]`

GitLab → User Settings → Access Tokens → Add new token. scope는 **`api`** 하나를 고른다. 이 토큰을 3곳에 쓴다. 노드에서 push할 때(단계 8), 파이프라인이 매니페스트를 push할 때(아래 `GITLAB_TOKEN`), 10.10에서 Terraform state를 옮길 때다.

가져온 프로젝트 → Settings → CI/CD → Variables에 등록한다.

| 변수명 | 값 | Masked |
|---|---|---|
| DOCKERHUB_USERNAME | Docker Hub username |  |
| DOCKERHUB_TOKEN | Docker Hub Access Token(5.3) | 선택 |
| GITLAB_TOKEN | 방금 발급한 토큰 | 선택 |

### 단계 5: 노드에 clone `[학습자 직접]`

폴더 이름을 `worklog-backend-gitlab`으로 달리해 GitHub fork의 clone과 구분한다. 공개 프로젝트라 clone에는 인증이 필요 없다. `credential.helper`는 처음 한 번 입력한 토큰을 8시간 동안 메모리에만 둔다. `deploy_manifest`에 Ingress가 보이고 HTTPRoute는 없어야 한다.

```bash
git clone https://gitlab.com/<gitlab_username>/worklog-backend.git /root/workspace/worklog-backend-gitlab
cd /root/workspace/worklog-backend-gitlab
git config credential.helper 'cache --timeout=28800'
grep "kind:" deploy_manifest/worklog-backend.yaml
```

### 단계 6: .gitlab-ci.yml 작성 `[AI 프롬프트]`

CI가 하는 일은 GitHub Actions(10.6 Part B)와 같다. 테스트, 이미지 빌드, `deploy_manifest/`의 이미지 태그 갱신까지다. 클러스터에 반영하는 것은 Argo CD의 자동 sync다. 그래서 이 파이프라인에는 AWS 자격 증명이 필요 없다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
GitLab CI 파이프라인을 만들어줘. 테스트, 이미지 빌드, 매니페스트 태그 수정과 push까지 하고 배포는 EKS의 Argo CD가 해. 파일을 만들기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend-gitlab/.gitlab-ci.yml
- stages: test(uv로 pytest와 coverage), build, deploy
- workflow:rules는 main 브랜치 push에만 파이프라인을 만들어.
- build: docker:24와 docker:24-dind로 linux/amd64 이미지를 빌드해 push
- 이미지는 <dockerhub_username>/worklog-backend, 태그는 커밋 SHA 앞 8자
- deploy: 태그를 바꾸고 메시지에 [skip ci]를 붙인 커밋을 GITLAB_TOKEN으로 main에 push
- Variables: DOCKERHUB_USERNAME, DOCKERHUB_TOKEN, GITLAB_TOKEN
- AWS 자격 증명과 kubectl은 넣지 마.
- 끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| deploy 커밋 메시지에 [skip ci] | 배포 커밋이 파이프라인을 다시 실행 |
| build의 플랫폼이 linux/amd64 | EKS에서 exec format error |
| AWS 키와 kubectl 없음 | 여러 CI에 클러스터 키 저장 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch10/10.9/1.build-and-gitops.yml`

### 단계 7: Argo CD 저장소 변경 `[AI 프롬프트]`

같은 매니페스트를 가져왔으므로 바꾼 직후에는 클러스터에 변화가 없다. 이제부터 GitHub fork에 push해도 EKS는 움직이지 않는다. 기준 저장소가 GitLab으로 넘어갔기 때문이다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
EKS Argo CD의 worklog-backend가 보는 저장소를 GitLab 프로젝트로 바꿔줘. 바꾸기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- argocd context가 EKS의 Argo CD인지 먼저 확인해.
- argocd app set worklog-backend --repo https://gitlab.com/<gitlab_username>/worklog-backend.git
- 끝나면: argocd app get worklog-backend --refresh의 Repo와 Sync Status를 보여줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| argocd context가 EKS의 Argo CD | 로컬 Argo CD의 Application이 바뀜 |
| 새 저장소 주소가 GitLab 프로젝트 | GitHub fork를 계속 배포 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 8: push `[학습자 직접]`

처음 push할 때 사용자 이름과 비밀번호를 묻는다. Username에는 GitLab 사용자 이름을, Password에는 단계 4의 토큰을 붙여 넣는다(화면에 보이지 않는다). 자격 증명을 입력하는 단계라 학습자가 직접 한다.

```bash
cd /root/workspace/worklog-backend-gitlab
git add .gitlab-ci.yml
git commit -m "ci: GitLab build and GitOps pipeline"
git push origin main
```

### 단계 9: 파이프라인 확인 `[학습자 직접 · 웹]`

GitLab → Build → Pipelines에서 test → build → deploy가 모두 통과하는지 본다. deploy가 만든 `[skip ci]` 커밋에는 `skipped` 상태의 줄이 하나 생기고 job은 돌지 않는다. 그 줄이 `running`이면 커밋 메시지에 `[skip ci]`가 빠진 것이다.

| 위치 | 확인 항목 | 설명 |
|---|---|---|
| Build → Pipelines | test, build, deploy | 모두 통과, 약 1분 40초 |
| 다음 줄 | skipped | [skip ci] 커밋의 줄 |

### 단계 10: Argo CD 반영 확인 `[학습자 직접]`

Argo CD는 약 3분마다 저장소를 확인한다. `--refresh`는 그 확인을 지금 하게 한다.

```bash
git pull --rebase
grep "image:" deploy_manifest/worklog-backend.yaml
argocd app get worklog-backend --refresh | grep -E "Sync Status|Health Status"
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
```

### 단계 11: 10.6과 비교 `[AI 프롬프트]`

짧은 질문이라 직접 친다.

```text
10.6 Part B(GitHub Actions)와 방금 만든 GitLab 파이프라인을 비교해줘. 파일 구조, 단계 표현, 변수 관리가 어떻게 다른지 설명해줘. 그리고 10.6 Part B에는 AWS 키가 필요했는데 이 파이프라인에는 왜 필요 없는지도.
```

## 주의사항

- ⛔ AI가 하지 말 것: GitLab Variables를 대신 등록하거나 토큰을 묻지 말 것. 토큰 값을 파일에 적지 말 것
- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다(run-41에서 AI가 정답 파일을 읽어 그대로 썼다)
- ⛔ AI가 하지 말 것: GitLab으로의 git push를 대신 하지 말 것(토큰 입력). `argocd app set`은 단계 7의 요청이 있을 때만 하고, 그 전에 argocd context가 EKS의 Argo CD인지 확인한다
- ⛔ AI가 하지 말 것: 이 파이프라인에 AWS 자격 증명이나 `kubectl` 직접 배포를 넣지 말 것. 배포는 Argo CD의 몫이다
- ⛔ AI가 하지 말 것: deploy 커밋 메시지에서 `[skip ci]`를 빼지 말 것. GitLab은 이 메시지가 있는 커밋의 파이프라인을 실행하지 않고 job 없는 skipped로 남긴다(GitLab 문서 Pipelines의 Skip a pipeline). 빠지면 GITLAB_TOKEN으로 한 push가 새 파이프라인을 만들어 끝없이 반복된다. workflow:rules에 같은 규칙을 둘 필요는 없다
- ⛔ AI가 하지 말 것: `git pull --rebase ... || true`로 쓰지 말 것. 충돌하면 push가 아무것도 올리지 않고 성공으로 끝난다
- ✅ AI가 해도 됨: `.gitlab-ci.yml` 작성, `[skip ci]` 원리 설명, 10.6과 10.7과의 비교
- ⚠️ script 항목에 콜론과 공백(`: `)이 들어가면 작은따옴표로 감싼다. 안 감싸면 YAML 파서가 매핑으로 읽어 파이프라인이 job 0개로 실패한다. push 전에 Pipeline editor의 lint로 확인한다
- ⚠️ 가져온 `deploy_manifest/worklog-backend.yaml`에 `kind: Secret`(worklog-mongodb-creds)이 빠져 있으면 Argo CD prune이 Secret을 지운다. 학습자의 GitHub fork를 가져오면 그대로 들어온다
- ⚠️ 롤아웃 직후 ALB의 `/health`가 잠깐 502일 수 있다(10.5 주의사항)
- ⚠️ EKS는 이 실습 뒤 10.10까지 켠 채로 이어 간다. 10.10의 마지막 단계에서 지운다
