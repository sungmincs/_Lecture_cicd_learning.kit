# 10.9 [GitLab] 실습 1: CI로 빌드하고 Argo CD로 EKS에 배포

> **학습자 진입 방식**:
> - `[학습자 직접]`: 노드에 GitLab 저장소 clone, Argo CD가 보는 저장소 바꾸기, git push, 배포 확인
> - `[학습자 직접 · 웹]`: GitLab 가입과 전화번호 인증, 저장소 가져오기, 토큰 발급과 CI/CD Variables 등록, 파이프라인 확인
> - `[AI 프롬프트]`: `.gitlab-ci.yml` 작성, 10.6과의 차이 설명

## 사전 조건

- ch10.7 완료 (EKS의 Application `worklog-backend`가 학습자 GitHub fork의 `deploy_manifest/`를 자동 sync 중)
- 노드의 argocd CLI가 EKS의 Argo CD에 로그인된 상태 (10.5 단계 7)
- Docker Hub Access Token (5.3에서 발급. 보관해 두지 않았으면 새로 발급한다)

## 이 실습이 확인하는 것

CI가 하는 일은 GitHub Actions(10.6 Part B)와 같다. 테스트, 이미지 빌드, `deploy_manifest/`의 이미지 태그 갱신까지다.
클러스터에 반영하는 것은 Argo CD의 자동 sync다. 그래서 **이 파이프라인에는 AWS 자격 증명이 필요 없다.** Argo CD가 Git을
당겨 가는 구조(pull)이기 때문이다. 바뀌는 것은 Argo CD가 보는 Git 저장소 하나뿐이다.

## 실행 지침

### 단계 0: 앞 절 파이프라인 정리 `[학습자 직접]`

Jenkins는 스캔을 누르지 않으면 돌지 않는다. GitHub 워크플로는 10.7 단계 0에서 모두 껐다. 확인만 한다.

```bash
gh workflow list --all -R <github_username>/worklog-backend      # 모두 disabled_manually
cd /root/workspace/worklog-backend && git pull --rebase           # 10.7 Part B가 올린 배포 커밋을 받는다
```

### 단계 1: GitLab.com 가입 `[학습자 직접 · 웹]`

- https://gitlab.com 에서 계정을 만든다.
- 새 계정은 공유 러너를 쓰기 전에 **전화번호 인증**이 필요하다. 인증 전에는 첫 파이프라인이
  "계정을 인증해야 합니다"로 멈춘다. 그 화면의 버튼으로 인증한다. 과금은 없다.

### 단계 2: GitHub fork를 GitLab으로 가져오기 `[학습자 직접 · 웹]`

GitLab → New project → **Import project** → **Repository by URL**

- Git repository URL: `https://github.com/<github_username>/worklog-backend.git`
- Project name: `worklog-backend`
- Visibility: **Public** (Argo CD가 인증 없이 읽게 하기 위해)
- 위치: **개인 네임스페이스**(`<gitlab_username>`). 그룹 안에 만들면 그룹의 공개 범위를 넘을 수 없어서, 그룹이 private이면 프로젝트도 private가 되고 Argo CD가 읽지 못한다

원본(`sungmincs/worklog-backend`)이 아니라 **학습자의 GitHub fork**를 가져온다. 10.5에서 ALB Ingress로 바꾼 `deploy_manifest/`가 함께 들어와야 Argo CD가 같은 매니페스트를 그대로 동기화한다.

### 단계 3: 토큰 발급과 CI/CD Variables 등록 `[학습자 직접 · 웹]`

GitLab → User Settings → Access Tokens → Add new token. scope는 **`api`** 하나를 고른다. 이 토큰을 세 곳에 쓴다. 노드에서 push할 때(단계 6), 파이프라인이 매니페스트를 push할 때(아래 `GITLAB_TOKEN`), 10.10에서 Terraform state를 옮길 때다.

가져온 프로젝트 → Settings → CI/CD → Variables → Add variable

| 변수명 | 값 | Masked | Protected |
|---|---|---|---|
| `DOCKERHUB_USERNAME` | Docker Hub username | | |
| `DOCKERHUB_TOKEN` | Docker Hub Access Token | ✅ | |
| `GITLAB_TOKEN` | 위에서 발급한 토큰 | ✅ | |

### 단계 4: 노드에 clone `[학습자 직접]`

```bash
cd /root/workspace
git clone https://gitlab.com/<gitlab_username>/worklog-backend.git worklog-backend-gitlab
cd worklog-backend-gitlab
git config credential.helper 'cache --timeout=28800'      # 처음 한 번 입력한 토큰을 8시간 동안 메모리에만 둔다
ls deploy_manifest/ && grep "kind:" deploy_manifest/worklog-backend.yaml      # Ingress가 보이고 HTTPRoute는 없다
```

폴더 이름을 `worklog-backend-gitlab`으로 달리해 GitHub fork의 clone과 구분한다. 공개 프로젝트라 clone에는 인증이 필요 없다.

### 단계 5: `.gitlab-ci.yml` 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend-gitlab/.gitlab-ci.yml`에 worklog-backend GitLab CI 파이프라인을 만들어줘. 10.6 Part B처럼 GitOps 방식이야. push는 내가 할게.
> - stages: test, build, deploy
> - `workflow:rules`의 맨 앞에서 커밋 메시지에 `[skip ci]`가 있으면 파이프라인을 만들지 않는다
> - test: uv로 pytest와 coverage
> - build: docker:24와 docker:24-dind로 `linux/amd64` 이미지를 빌드해서 Docker Hub에 push, 태그는 커밋 SHA 앞 8자
> - deploy: `deploy_manifest/worklog-backend.yaml`의 image 줄과 `# IMAGE_TAG` 줄을 바꾸고 `[skip ci]` 커밋으로 main에 push. 인증은 GITLAB_TOKEN
> - 이미지 저장소: `<dockerhub_username>/worklog-backend`
> - Variables: DOCKERHUB_USERNAME, DOCKERHUB_TOKEN, GITLAB_TOKEN
> - AWS 자격 증명이나 kubectl은 넣지 마. 배포는 Argo CD가 한다"

✅ 정답 파일 (완성 후 비교): `ch10/10.9/1.build-and-gitops.yml`

### 단계 6: Argo CD가 보는 저장소를 GitLab으로 바꾸기 `[학습자 직접]`

```bash
argocd app set worklog-backend --repo https://gitlab.com/<gitlab_username>/worklog-backend.git
argocd app get worklog-backend --refresh | grep -E "Repo:|Sync Status"      # Repo가 gitlab.com, Synced
```

같은 매니페스트를 가져왔으므로 바꾼 직후에는 클러스터에 변화가 없다. 이제부터 GitHub fork에 push해도 EKS는 움직이지 않는다. 기준 저장소가 GitLab으로 넘어갔기 때문이다.

### 단계 7: push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend-gitlab
git add .gitlab-ci.yml
git commit -m "ci: GitLab build and GitOps pipeline"
git push origin main
```

처음 push할 때 사용자 이름과 비밀번호를 묻는다. Username에는 GitLab 사용자 이름을, Password에는 단계 3의 토큰을 붙여 넣는다(화면에 보이지 않는다).

### 단계 7-1: 파이프라인 확인 `[학습자 직접 · 웹]`

GitLab → Build → Pipelines에서 test → build → deploy가 모두 통과하는지 본다. deploy가 만든 `[skip ci]` 커밋에는 `skipped` 상태의 줄이 하나 생기고 job은 돌지 않는다. 그 줄이 `running`이면 규칙이 잘못된 것이다.

### 단계 8: Argo CD 반영 확인 `[학습자 직접]`

```bash
git pull --rebase
grep "image:" deploy_manifest/worklog-backend.yaml
argocd app get worklog-backend --refresh | grep -E "Sync Status|Health Status"
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # 방금 파이프라인의 8자 태그
```

Argo CD는 약 3분마다 저장소를 확인한다. `--refresh`는 그 확인을 지금 하게 한다.

## 주의사항

- ⛔ AI가 하지 말 것: GitLab Variables를 대신 등록하거나 토큰을 묻지 말 것. 토큰 값을 파일에 적지 말 것
- ⛔ AI가 하지 말 것: git push와 `argocd app set`을 대신 하지 말 것
- ⛔ AI가 하지 말 것: 이 파이프라인에 AWS 자격 증명이나 `kubectl` 직접 배포를 넣지 말 것. 배포는 Argo CD의 몫이다
- ⛔ AI가 하지 말 것: `[skip ci]` 규칙을 `workflow:rules`의 맨 앞이 아닌 곳에 두지 말 것. 뒤에 두면 branch 규칙이 먼저 걸려 무한 루프가 난다
- ⛔ AI가 하지 말 것: `git pull --rebase ... || true`로 쓰지 말 것. 충돌하면 push가 아무것도 올리지 않고 성공으로 끝난다
- ✅ AI가 해도 됨: `.gitlab-ci.yml` 작성, `[skip ci]` 원리 설명, 10.6과 10.7과의 비교
- ⚠️ script 항목에 콜론과 공백(`: `)이 들어가면 작은따옴표로 감싼다. 안 감싸면 YAML 파서가 매핑으로 읽어 파이프라인이 job 0개로 실패한다. push 전에 Pipeline editor의 lint로 확인한다
- ⚠️ 가져온 `deploy_manifest/worklog-backend.yaml`에 `kind: Secret`(worklog-mongodb-creds)이 빠져 있으면 Argo CD prune이 Secret을 지운다. 학습자의 GitHub fork를 가져오면 그대로 들어온다
- ⚠️ 롤아웃 직후 ALB의 `/health`가 잠깐 502일 수 있다(10.5 주의사항)
- ⚠️ EKS는 이 실습 뒤 10.10까지 켠 채로 이어 간다. 10.10의 마지막 단계에서 지운다
