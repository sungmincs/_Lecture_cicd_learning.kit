# 10.9 [GitLab] 실습 1: CI로 빌드하고 Argo CD로 EKS에 배포

> **학습자 진입 방식**:
> - `[학습자 직접]`: GitLab 가입·전화번호 인증, 저장소 가져오기, CI/CD Variables 등록, Argo CD 소스 전환, git push
> - `[AI 프롬프트]`: `.gitlab-ci.yml` 작성, 10.6과의 차이 설명

## 사전 조건

- ch10.5 완료 (EKS에 Argo CD 설치, `worklog-backend` Application이 학습자 GitHub fork의 `deploy_manifest/`를 동기화 중)
- ch10.5 단계 9 완료 (`argocd login` 상태)
- 학습자 GitHub fork(`worklog-backend`)에 `deploy_manifest/worklog-backend.yaml` 존재 (ch5.3에서 만듦)
- 그 매니페스트의 HTTPRoute를 ALB Ingress로 바꾼 상태 (10.5 단계 7-1). EKS에는 Gateway API가 없어 HTTPRoute가 있으면 동기화가 실패한다
- Docker Hub Access Token (ch3.5에서 발급)

## 이 실습이 확인하는 것

CI가 하는 일은 GitHub Actions(10.6 Part B)와 같다. 테스트, 이미지 빌드, `deploy_manifest/`의 이미지 태그 갱신까지다.
클러스터에 반영하는 것은 Argo CD다. 그래서 **이 파이프라인에는 AWS 자격 증명이 필요 없다.** Argo CD가 Git을
당겨 가는 구조(pull)이기 때문이다. 바뀌는 것은 Argo CD가 보는 Git 저장소 하나뿐이다.

## 실행 지침

### 단계 1: GitLab.com 가입 `[학습자 직접]`

- https://gitlab.com 에서 계정을 만든다.
- 새 계정은 공유 러너를 쓰기 전에 **전화번호 인증**이 필요하다. 인증 전에는 첫 파이프라인이
  "계정을 인증해야 합니다"로 멈춘다. 그 화면의 버튼으로 인증한다. 과금은 없다.

### 단계 2: GitHub fork를 GitLab으로 가져오기 `[학습자 직접]`

GitLab → New project → **Import project** → **Repository by URL**

- Git repository URL: `https://github.com/<github_username>/worklog-backend.git`
- Project name: `worklog-backend`
- Visibility: **Public** (Argo CD가 인증 없이 읽게 하기 위해)
- 위치: **개인 네임스페이스**(`<gitlab_username>`). 그룹 안에 만들면 그룹의 공개 범위를 넘을 수 없어서, 그룹이 private이면 프로젝트도 private가 되고 Argo CD가 읽지 못한다

> 원본(`sungmincs/worklog-backend`)이 아니라 **학습자의 GitHub fork**를 가져온다. ch5~ch9에서 학습자가 만든
> `deploy_manifest/`가 함께 들어와야 Argo CD가 10.5와 같은 매니페스트를 그대로 동기화한다.

```bash
cd ~/workspace
git clone https://gitlab.com/<gitlab_username>/worklog-backend.git worklog-backend-gitlab
cd worklog-backend-gitlab
ls deploy_manifest/
```

### 단계 3: CI/CD Variables 등록 `[학습자 직접]`

저장소 → Settings → CI/CD → Variables → Add variable

| 변수명 | 값 | Masked | Protected |
|---|---|---|---|
| `DOCKERHUB_USERNAME` | Docker Hub username | | |
| `DOCKERHUB_TOKEN` | Docker Hub Access Token | ✅ | |
| `GITLAB_TOKEN` | GitLab Personal Access Token | ✅ | |

> **GITLAB_TOKEN 발급**: GitLab → User Settings → Access Tokens → Add new token, scope **`write_repository`**.
> 파이프라인이 `deploy_manifest/`를 고쳐 push할 때 쓴다.

### 단계 4: `.gitlab-ci.yml` 작성 `[AI 프롬프트]`

> "worklog-backend GitLab CI 파이프라인을 만들어줘. 10.6 Part B처럼 GitOps 방식이야.
> - stages: test, build, deploy
> - test: uv로 pytest와 coverage
> - build: docker:24 + docker:24-dind로 amd64/arm64 이미지를 빌드해서 Docker Hub에 push, 태그는 커밋 SHA 앞 8자리
> - deploy: deploy_manifest/worklog-backend.yaml의 이미지 태그를 바꾸고 `[skip ci]` 커밋으로 push
> - Docker Hub username: `<dockerhub_username>`
> - Variables: DOCKERHUB_USERNAME, DOCKERHUB_TOKEN, GITLAB_TOKEN"

✅ 정답 파일 (완성 후 비교): `ch10/10.9/1.build-and-gitops.yml`

### 단계 5: Argo CD가 보는 저장소를 GitLab으로 바꾸기 `[학습자 직접]`

```bash
argocd app set worklog-backend --repo https://gitlab.com/<gitlab_username>/worklog-backend.git
argocd app get worklog-backend
# Repo: 가 gitlab.com으로 바뀌고 Sync Status가 Synced인지 확인
```

> 같은 매니페스트를 가져왔으므로 바꾼 직후에는 클러스터에 변화가 없다. 이제부터 GitHub fork에 push해도
> 클러스터는 움직이지 않는다. 기준 저장소가 GitLab으로 넘어갔기 때문이다.

### 단계 6: push하고 파이프라인 확인 `[학습자 직접]`

```bash
git add .gitlab-ci.yml
git commit -m "ci: GitLab build and GitOps pipeline"
git push origin main
```

GitLab → Build → Pipelines에서 test → build → deploy가 모두 통과하는지 본다. deploy가 만든
`[skip ci]` 커밋은 새 파이프라인을 만들지 않아야 한다.

### 단계 7: Argo CD 반영 확인 `[학습자 직접]`

Argo CD는 기본 3분마다 저장소를 확인한다. 바로 보려면 `argocd app sync worklog-backend`.

```bash
argocd app get worklog-backend
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}'; echo
# 방금 파이프라인의 SHA 8자리 태그가 보이면 성공
```

### 단계 8: 10.6과 비교 `[AI 프롬프트]`

> "10.6 Part B(GitHub Actions + Argo CD)와 방금 만든 GitLab 파이프라인을 비교해줘. 파일 구조, 단계 표현,
> 변수 관리가 어떻게 다른지, 그리고 두 파이프라인 모두 AWS 자격 증명 없이 EKS에 배포된 이유를 설명해줘."

## 주의사항

- ⛔ AI가 하지 말 것: GitLab Variables를 대신 등록하거나 토큰 값을 파일에 적지 말 것
- ⛔ AI가 하지 말 것: 이 파이프라인에 AWS 자격 증명이나 `kubectl` 직접 배포를 넣지 말 것. 배포는 Argo CD의 몫이다
- ⛔ AI가 하지 말 것: `[skip ci]` 규칙을 `workflow:rules`의 맨 앞이 아닌 곳에 두지 말 것. 뒤에 두면 branch 규칙이 먼저 걸려 무한 루프가 난다
- ⛔ AI가 하지 말 것: `git pull --rebase ... || true`로 쓰지 말 것. 충돌하면 push가 아무것도 올리지 않고 성공으로 끝난다
- ✅ AI가 해도 됨: `.gitlab-ci.yml` 작성, `[skip ci]` 원리 설명, 10.6·10.7과의 비교
- ⚠️ script 항목에 콜론+공백(`: `)이 들어가면 작은따옴표로 감싼다. 안 감싸면 YAML 파서가 매핑으로 읽어 파이프라인이 job 0개로 실패한다. push 전에 Pipeline editor의 lint로 확인한다
- ⚠️ `GITLAB_TOKEN`은 `write_repository` scope가 있어야 한다. `read_repository`로는 push가 거부된다
- ⚠️ GitLab으로 가져온 `deploy_manifest/worklog-backend.yaml`에 `kind: Secret`(worklog-mongodb-creds)이 빠져 있으면 Argo CD prune이 Secret을 지운다. 학습자의 GitHub fork를 가져오면 ch5.3 판이 그대로 들어온다(구조 변경 전 ch6.9의 run-15 발견)
- ⚠️ EKS는 이 실습 뒤 10.10까지 켠 채로 이어 간다. 10.10의 마지막 단계에서 지운다
