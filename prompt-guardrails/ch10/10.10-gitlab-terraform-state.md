# 10.10 [GitLab] 실습 2: Terraform state를 GitLab에 맡기고 파이프라인으로 EKS 정리

> **학습자 진입 방식**:
> - `[학습자 직접]`: Terraform 폴더 옮기기, `terraform init -migrate-state`, state 확인과 노드 파일 삭제, 인프라 저장소 push(토큰 입력), 남은 것 확인
> - `[학습자 직접 · 웹]`: 인프라 프로젝트 생성, Terraform states 확인, CI/CD Variables 등록, plan 확인, destroy 버튼, Access Key 비활성화
> - `[AI 프롬프트]`: backend 설정과 `.gitlab-ci.yml` 작성, 정리 전 로드밸런서 삭제, IAM 정리와 로컬로 되돌리기(프롬프트는 학습자가 처음부터 작성)

## 사전 조건

- ch10.4 완료 (노드의 `/root/ch10/terraform-eks/`에 Terraform 파일과 `terraform.tfstate`가 있음)
- ch10.9 완료 (GitLab 계정, 전화번호 인증, scope `api` 토큰)
- 노드의 `aws configure`가 10.4에서 apply한 IAM 사용자 그대로임

## 이 실습이 확인하는 것

10.4의 state는 노드의 파일 하나다. 이 파일이 없으면 `terraform destroy`를 할 수 없고 EKS 비용이 계속 나간다. 노드는 VM이라 클러스터를 다시 만들면 사라진다.
다른 사람이나 파이프라인이 같은 인프라를 다룰 수도 없다. GitHub Actions와 Jenkins에는 state를 맡길 곳이 없어 S3 같은 저장소를 따로 만들어야 한다. GitLab은 프로젝트마다 Terraform state 저장소를 준다.

이 실습에서 state를 GitLab으로 옮기고, 10장의 마지막 정리(`terraform destroy`)를 사람 손이 아니라 파이프라인으로 한다.

### 단계 2: Terraform 폴더 옮기기 `[학습자 직접]`

복사가 아니라 옮긴다. state 파일이 2곳에 남지 않게 하기 위해서다. state 파일을 다루는 단계라 학습자가 직접 한다.
`.gitignore`를 먼저 둔다. state 파일에는 클러스터 인증서와 리소스 정보가 평문으로 들어 있다. 한 번 커밋하면 지워도 이력에 남는다.

```bash
mv /root/ch10/terraform-eks /root/workspace/eks-infra
cd /root/workspace/eks-infra
cp /root/_Lecture_cicd_learning.kit/ch10/10.10/2.terraform.gitignore .gitignore
ls -l terraform.tfstate
```

### 단계 3: backend 설정 `[AI 프롬프트]`

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
state를 GitLab 프로젝트에 두도록 /root/workspace/eks-infra에 Terraform http backend 설정을 만들어줘. 파일을 만들기 전에 계획부터 보여줘.
```

### 단계 4: state 옮기기 `[학습자 직접]`

10.9 단계 4에서 발급한 scope `api` 토큰을 쓴다. `read -rs`로 받아 화면과 명령 기록에 남기지 않는다. `<project_id>`는 단계 1의 값이다.

```bash
export TF_ADDRESS="https://gitlab.com/api/v4/projects/<project_id>/terraform/state/eks"
export TF_HTTP_ADDRESS="${TF_ADDRESS}" TF_HTTP_LOCK_ADDRESS="${TF_ADDRESS}/lock"
export TF_HTTP_UNLOCK_ADDRESS="${TF_ADDRESS}/lock"
export TF_HTTP_LOCK_METHOD=POST TF_HTTP_UNLOCK_METHOD=DELETE
export TF_HTTP_USERNAME=<gitlab_username>
read -rs TF_HTTP_PASSWORD && export TF_HTTP_PASSWORD
terraform init -migrate-state -force-copy
```

### 단계 5: plan 확인과 노드 state 삭제 `[학습자 직접]`

`plan`이 **No changes**면 state가 실제 인프라와 맞게 옮겨진 것이다. 그때 노드에 남은 state 파일을 지운다.
이전 뒤 `terraform.tfstate`는 비지만 `terraform.tfstate.backup`에 전체 state가 남는다. 그래서 둘 다 지운다.

```bash
terraform plan | grep -E "No changes|Plan:"
ls -l terraform.tfstate terraform.tfstate.backup
rm terraform.tfstate terraform.tfstate.backup
```

### 단계 11: 로드밸런서 삭제 `[AI 프롬프트]`

EKS 안에서 만든 ALB(Ingress)와 Argo CD Service의 로드밸런서는 Terraform이 모르는 AWS 리소스다. 먼저 지우지 않으면 VPC 삭제가 `DependencyViolation`으로 실패한다.
Application을 먼저 지운다. Ingress부터 지우면 Argo CD가 저장소의 상태대로 다시 만든다. context가 `local`이면 로컬 클러스터의 Application과 Ingress가 지워지므로 반드시 `eks`인지 확인한다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
EKS 안에서 만든 로드밸런서를 지워줘. terraform destroy가 VPC에서 실패하지 않게 하려는 거야. 실행하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- kubectl context가 eks인지 먼저 확인해. local이면 멈춰줘.
- kubectl delete application --all -n argocd, 그다음 kubectl delete ingress --all -A
- argocd-server Service는 ClusterIP 타입으로 바꿔줘.
- 끝나면: aws elbv2와 aws elb의 describe-load-balancers 목록이 모두 빌 때까지 기다려 결과를 보여줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| kubectl context가 eks | 로컬의 Application과 Ingress가 삭제됨 |
| Application을 Ingress보다 먼저 삭제 | Argo CD가 Ingress를 다시 생성 |
| argocd-server Service를 ClusterIP로 변경 | 로드밸런서가 남아 destroy 실패 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 13: IAM 정리와 로컬로 되돌리기 `[AI 프롬프트]`

10.5에서 Terraform 밖에서 만든 IAM 정책과 역할을 지운다(과금은 없지만 남겨 두지 않는다). kubectl과 argocd CLI를 로컬 클러스터 기준으로 되돌린다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
EKS를 지운 뒤 남은 IAM 역할과 정책을 정리하고 kubectl과 argocd를 로컬 클러스터 기준으로 되돌려줘. 실행하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- IAM 정책 AWSLoadBalancerControllerIAMPolicy를 역할 AmazonEKSLoadBalancerControllerRole에서 분리한 뒤 역할과 정책을 삭제
- kubectl context를 local로 바꾸고 eks context는 삭제
- argocd context를 로컬 Argo CD(주소가 IP)로 바꾸고 EKS 항목은 삭제
- 끝나면: kubectl get nodes와 argocd app list 결과를 보여줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| 정책을 역할에서 분리한 뒤 삭제 | 역할에 붙은 정책이라 삭제 실패 |
| kubectl context를 local로 변경 | 지운 EKS를 계속 가리킴 |
| argocd context를 로컬 Argo CD로 변경 | argocd 명령이 모두 실패 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

## 트러블슈팅

### destroy job이 실패했다

state는 GitLab에 있으므로 노드에서 그대로 이어서 지울 수 있다. 단계 4의 `TF_HTTP_*` 환경변수를 다시 넣고:

```bash
cd /root/workspace/eks-infra
terraform init
terraform destroy
```

VPC에서 `DependencyViolation`이 나면 단계 11을 빠뜨린 것이다. 남은 로드밸런서와 `k8s-`로 시작하는 보안 그룹을 확인한다.

### plan이 No changes가 아니다

- CI 변수의 키가 10.4에서 apply한 IAM 사용자의 것인지 확인한다(단계 6)
- 노드의 `terraform plan`도 같은 결과인지 본다. 노드에서 No changes면 CI 쪽 변수 문제다

### `Error acquiring the state lock`

다른 job이나 노드의 세션이 state를 잡고 있다. 그 작업이 끝났는지 확인한 뒤, 정말 멈춘 잠금이면 Operate → Terraform states에서 잠금을 해제한다.

### 로컬 클러스터의 `worklog-backend`를 다시 쓰고 싶다

fork의 `deploy_manifest`는 ALB Ingress로 바뀐 상태다. 로컬에서 다시 쓰려면 Ingress를 10.5 단계 12 이전의 HTTPRoute로 되돌려 push하고, 로컬 Argo CD에 로그인해(6.4 단계 6) 10.5 단계 1에서 끈 자동 sync를 켠다.
