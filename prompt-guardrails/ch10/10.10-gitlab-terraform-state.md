# 10.10 [GitLab] 실습 2: Terraform state를 GitLab에 맡기고 파이프라인으로 EKS 정리

> **학습자 진입 방식**:
> - `[학습자 직접]`: Terraform 폴더 옮기기, `terraform init -migrate-state`, git push, 정리 전 로드밸런서 삭제, 남은 것 확인
> - `[학습자 직접 · 웹]`: 인프라 프로젝트 생성, CI/CD Variables 등록, plan 확인, destroy 버튼
> - `[AI 프롬프트]`: backend 설정과 `.gitlab-ci.yml` 작성

## 사전 조건

- ch10.4 완료 (노드의 `/root/ch10/terraform-eks/`에 Terraform 파일과 `terraform.tfstate`가 있음)
- ch10.9 완료 (GitLab 계정, 전화번호 인증, scope `api` 토큰)
- 노드의 `aws configure`가 10.4에서 apply한 IAM 사용자 그대로임

## 이 실습이 확인하는 것

10.4의 state는 노드의 파일 하나다. 이 파일을 잃으면 `terraform destroy`를 할 수 없고 EKS 비용이 계속 나간다. 노드는 VM이라 클러스터를 다시 만들면 사라진다.
다른 사람이나 파이프라인이 같은 인프라를 다룰 수도 없다. GitHub Actions와 Jenkins에는 state를 맡길 곳이 없어 S3 같은 저장소를 따로 만들어야 한다. GitLab은 프로젝트마다 Terraform state 저장소를 준다.

이 실습에서 state를 GitLab으로 옮기고, 10장의 마지막 정리(`terraform destroy`)를 사람 손이 아니라 파이프라인으로 한다.

## 실행 지침

### 단계 1: 인프라용 GitLab 프로젝트 만들기 `[학습자 직접 · 웹]`

앱 저장소(worklog-backend)와 인프라 저장소를 나눈다. 실무에서 흔한 구성이다.

GitLab → New project → **Create blank project**

- Project name: `eks-infra`
- Visibility: **Private**
- "Initialize repository with a README"는 끈다

Settings → General에서 **Project ID**(숫자)를 확인해 둔다.

### 단계 2: Terraform 폴더를 옮기고 state가 커밋되지 않게 하기 `[학습자 직접]`

```bash
mv /root/ch10/terraform-eks /root/workspace/eks-infra
cd /root/workspace/eks-infra
cp /root/_Lecture_cicd_learning.kit/ch10/10.10/2.terraform.gitignore .gitignore
ls -l terraform.tfstate          # 10.4에서 apply한 state가 함께 왔는지 확인
```

복사가 아니라 옮긴다. state 파일이 두 곳에 남지 않게 하기 위해서다.
`.gitignore`를 먼저 둔다. state 파일에는 클러스터 인증서와 리소스 정보가 평문으로 들어 있다. 한 번 커밋하면 지워도 이력에 남는다.

### 단계 3: backend 설정 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/eks-infra/backend.tf`를 만들어줘. state를 GitLab 프로젝트의 Terraform state 저장소에 두려고 해. 주소와 인증은 파일에 적지 말고 TF_HTTP_ 환경변수로 넘길 수 있게 http backend를 부분 설정으로 써줘. `terraform init`은 내가 할게."

✅ 정답 파일 (완성 후 비교): `ch10/10.10/1.backend.tf`

### 단계 4: 노드의 state를 GitLab으로 옮기기 `[학습자 직접]`

10.9 단계 3에서 발급한 scope `api` 토큰을 쓴다.

```bash
cd /root/workspace/eks-infra
export GITLAB_PROJECT_ID=<project_id>
export TF_ADDRESS="https://gitlab.com/api/v4/projects/${GITLAB_PROJECT_ID}/terraform/state/eks"
export TF_HTTP_ADDRESS="${TF_ADDRESS}"
export TF_HTTP_LOCK_ADDRESS="${TF_ADDRESS}/lock"
export TF_HTTP_UNLOCK_ADDRESS="${TF_ADDRESS}/lock"
export TF_HTTP_LOCK_METHOD=POST
export TF_HTTP_UNLOCK_METHOD=DELETE
export TF_HTTP_USERNAME=<gitlab_username>
read -rs TF_HTTP_PASSWORD && export TF_HTTP_PASSWORD   # 토큰을 붙여 넣고 Enter (화면과 히스토리에 남지 않는다)

terraform init -migrate-state -force-copy
terraform plan | grep -E "No changes|Plan:"         # No changes. Your infrastructure matches the configuration.
```

`plan`이 **No changes**면 state가 실제 인프라와 맞게 옮겨진 것이다. 그때 노드에 남은 state 파일을 지운다.

```bash
ls -l terraform.tfstate terraform.tfstate.backup
rm terraform.tfstate terraform.tfstate.backup
```

이전 뒤 `terraform.tfstate`는 비지만 `terraform.tfstate.backup`에 전체 state가 남는다. 그래서 둘 다 지운다.

### 단계 4-1: GitLab에 올라간 state 확인 `[학습자 직접 · 웹]`

GitLab → `eks-infra` → **Operate → Terraform states**에 `eks`가 보인다.

### 단계 5: CI/CD Variables 등록 `[학습자 직접 · 웹]`

`eks-infra` → Settings → CI/CD → Variables

| 변수명 | 값 | Masked | Protected |
|---|---|---|---|
| `AWS_ACCESS_KEY_ID` | 10.3 단계 2의 Access Key ID | ✅ | ✅ |
| `AWS_SECRET_ACCESS_KEY` | 10.3 단계 2의 Secret Access Key | ✅ | ✅ |
| `AWS_REGION` | 10.3 단계 4에서 정한 리전 | | ✅ |

**10.4에서 apply한 사용자**의 키여야 한다. 10.4의 구성은 만든 사람을 클러스터 관리자로 등록한다(`enable_cluster_creator_admin_permissions`).
다른 사용자로 plan하면 그 등록을 바꾸려 해서 No changes가 나오지 않는다.

### 단계 6: 파이프라인 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/eks-infra/.gitlab-ci.yml`에 GitLab CI 파이프라인을 만들어줘. push는 내가 할게.
> - 이미지 hashicorp/terraform:1.15.7 (entrypoint 비우기)
> - state는 이 프로젝트의 Terraform state 저장소, 이름 eks. 인증은 gitlab-ci-token과 CI_JOB_TOKEN
> - plan은 main push마다 자동, 결과를 artifact로 남기기
> - apply와 destroy는 when: manual
> - GitLab Terraform 템플릿은 쓰지 마"

✅ 정답 파일 (완성 후 비교): `ch10/10.10/3.terraform-pipeline.yml`

### 단계 6-1: 인프라 저장소 push `[학습자 직접]`

```bash
cd /root/workspace/eks-infra
git init -b main
git config credential.helper 'cache --timeout=28800'
git remote add origin https://gitlab.com/<gitlab_username>/eks-infra.git
git add .
git status --short         # terraform.tfstate, .terraform/ 이 목록에 없어야 한다
git commit -m "infra: EKS terraform with GitLab-managed state"
git push -u origin main
```

Username과 Password를 물으면 10.9 단계 7과 같이 GitLab 사용자 이름과 토큰을 넣는다.

### 단계 7: plan 결과 확인 `[학습자 직접 · 웹]`

Build → Pipelines에서 plan job 로그 끝에 `No changes.`가 있는지 본다. apply와 destroy는 누르기 전까지 서 있는 버튼(manual)이다.

### 단계 8: 정리 준비. 클러스터 안의 로드밸런서를 먼저 지운다 `[학습자 직접]`

EKS 안에서 만든 ALB(Ingress)와 Argo CD Service의 로드밸런서는 Terraform이 모르는 AWS 리소스다. 먼저 지우지 않으면 VPC 삭제가 `DependencyViolation`으로 실패한다.

```bash
kubectl config current-context                             # eks 인지 반드시 확인한다
kubectl delete application --all -n argocd                 # Argo CD가 지운 것을 되살리지 않도록 Application부터
kubectl delete ingress --all -A
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "ClusterIP"}}'

# 로드밸런서가 모두 사라질 때까지 1~2분 기다린다. 두 명령 모두 빈 목록이 나오면 다음 단계로
aws elbv2 describe-load-balancers --query 'LoadBalancers[].LoadBalancerName'
aws elb describe-load-balancers --query 'LoadBalancerDescriptions[].LoadBalancerName'
```

### 단계 9: destroy 버튼 `[학습자 직접 · 웹]`

Build → Pipelines → 가장 최근 파이프라인 → **destroy** job의 실행 버튼. 10~15분 걸린다. 로그 끝의 `Destroy complete!`를 확인한다.

### 단계 10: 남은 것 확인과 로컬로 돌아가기 `[학습자 직접]`

```bash
# 과금되는 것이 남지 않았는지
aws eks list-clusters --query clusters
aws ec2 describe-nat-gateways --filter Name=state,Values=available --query 'NatGateways[].NatGatewayId'
aws elbv2 describe-load-balancers --query 'LoadBalancers[].LoadBalancerName'

# 10.5에서 Terraform 밖에서 만든 IAM 정책과 역할 (과금은 없지만 남겨 두지 않는다)
POLICY_ARN=$(aws iam list-policies --scope Local --query "Policies[?PolicyName=='AWSLoadBalancerControllerIAMPolicy'].Arn" --output text)
aws iam detach-role-policy --role-name AmazonEKSLoadBalancerControllerRole --policy-arn $POLICY_ARN
aws iam delete-role --role-name AmazonEKSLoadBalancerControllerRole
aws iam delete-policy --policy-arn $POLICY_ARN

# kubectl을 로컬 클러스터로 되돌린다
kubectl config use-context local
kubectl config delete-context eks
kubectl get nodes

# argocd CLI도 로컬 Argo CD로 되돌린다. EKS의 Argo CD는 이제 없다
argocd context                                   # 두 줄이 보인다. 주소가 IP인 쪽이 로컬이다
argocd context <local_argocd_context>
argocd context --delete <eks_argocd_context>
argocd app list                                  # 로컬 Application 목록
```

세 목록이 모두 비어 있어야 한다. AWS 콘솔의 EKS, EC2, VPC 화면도 한 번 본다. KMS 키가 `PendingDeletion`으로 남는 것은 정상이다(과금 없음, 7일 뒤 자동 삭제).

GitHub Secrets의 AWS 키, Jenkins Credentials의 AWS 키, GitLab Variables의 AWS 키는 더 쓰지 않는다. 실습을 마쳤으면 AWS 콘솔에서 그 Access Key를 비활성화하거나 지운다.

## 트러블슈팅

### destroy job이 실패했다

state는 GitLab에 있으므로 노드에서 그대로 이어서 지울 수 있다. 단계 4의 `TF_HTTP_*` 환경변수를 다시 넣고:

```bash
cd /root/workspace/eks-infra
terraform init
terraform destroy
```

VPC에서 `DependencyViolation`이 나면 단계 8을 빠뜨린 것이다. 남은 로드밸런서와 `k8s-`로 시작하는 보안 그룹을 확인한다.

### plan이 No changes가 아니다

- CI 변수의 키가 10.4에서 apply한 IAM 사용자의 것인지 확인한다(단계 5)
- 노드의 `terraform plan`도 같은 결과인지 본다. 노드에서 No changes면 CI 쪽 변수 문제다

### `Error acquiring the state lock`

다른 job이나 노드의 세션이 state를 잡고 있다. 그 작업이 끝났는지 확인한 뒤, 정말 멈춘 잠금이면 Operate → Terraform states에서 잠금을 해제한다.

### 로컬 클러스터의 `worklog-backend`를 다시 쓰고 싶다

fork의 `deploy_manifest`는 ALB Ingress로 바뀐 상태다. 로컬에서 다시 쓰려면 Ingress를 10.5 단계 8 이전의 HTTPRoute로 되돌려 push하고, 로컬 Argo CD에 로그인해(6.4 단계 5) 10.5 단계 0에서 끈 자동 sync를 켠다.

## 주의사항

- ⛔ AI가 하지 말 것: 토큰이나 AWS 키를 묻거나 `backend.tf`, `-backend-config`, `.gitlab-ci.yml`에 평문으로 적지 말 것. `-backend-config`로 넘긴 값은 `.terraform/` 아래에 남는다
- ⛔ AI가 하지 말 것: `terraform init`, `apply`, `destroy`, git push, `kubectl delete`를 대신 실행하지 말 것
- ⛔ AI가 하지 말 것: `.gitignore` 없이 `git add .`를 안내하지 말 것. state가 커밋된다
- ⛔ AI가 하지 말 것: apply와 destroy를 자동 실행(`when: manual` 제거)으로 만들지 말 것. 인프라를 바꾸는 job은 사람이 누른다
- ⛔ AI가 하지 말 것: 단계 8을 건너뛰고 destroy를 안내하지 말 것
- ⛔ AI가 하지 말 것: GitLab의 Terraform CI/CD 템플릿(`Terraform.gitlab-ci.yml`)을 쓰지 말 것. 18.0에서 제거됐다
- ✅ AI가 해도 됨: backend.tf와 `.gitlab-ci.yml` 작성, plan 결과 해석, state 저장소가 왜 필요한지 설명
- ⚠️ 단계 8의 `kubectl delete`는 context가 `eks`일 때만 한다. `local`에서 하면 로컬 클러스터의 Application과 Ingress가 지워진다
- ⚠️ 이미지 태그(`hashicorp/terraform:1.15.7`)는 노드의 Terraform 버전(10.4 단계 1)과 같다. state를 더 높은 버전으로 한 번 쓰면 낮은 버전에서 못 읽는다
- ⚠️ 이 실습이 10장의 마지막 정리다. destroy 완료를 반드시 확인한다
