# 10.10 [GitLab] 실습 2: Terraform state를 GitLab에 맡기고 파이프라인으로 EKS 정리

> **학습자 진입 방식**:
> - `[학습자 직접]`: 인프라 프로젝트 생성과 push, 토큰 발급, `terraform init -migrate-state`, CI/CD Variables 등록,
>   정리 전 LoadBalancer 삭제, destroy 버튼 누르기
> - `[AI 프롬프트]`: backend 설정과 `.gitlab-ci.yml` 작성, plan 결과 해석

## 사전 조건

- ch10.4 완료 (EKS를 학습자 PC에서 `terraform apply`로 만듦. state가 PC의 `terraform.tfstate`에 있음)
- ch10.9 완료 (GitLab 계정, 전화번호 인증)
- ch10.3에서 만든 **Terraform용 IAM 사용자의 Access Key** (10.4 apply에 쓴 그 사용자)

## 이 실습이 확인하는 것

10.4의 state는 학습자 PC의 파일 하나다. 이 파일을 잃으면 `terraform destroy`를 할 수 없고 EKS 비용이 계속 나간다.
다른 사람이나 파이프라인이 같은 인프라를 다룰 수도 없다. GitHub Actions와 Jenkins에는 state를 맡길 곳이 없어
S3 같은 저장소를 따로 만들어야 한다. GitLab은 프로젝트마다 Terraform state 저장소를 준다.

이 실습에서 state를 GitLab으로 옮기고, 10장의 마지막 정리(`terraform destroy`)를 사람 손이 아니라 파이프라인으로 한다.

## 실행 지침

### 단계 1: 인프라용 GitLab 프로젝트 만들기 `[학습자 직접]`

앱 저장소(worklog-backend)와 인프라 저장소를 나눈다. 실무에서 흔한 구성이다.

GitLab → New project → **Create blank project**

- Project name: `eks-infra`
- Visibility: **Private**
- "Initialize repository with a README"는 끈다

Settings → General에서 **Project ID**(숫자)를 확인해 둔다.

### 단계 2: Terraform 코드 옮기고 state가 커밋되지 않게 하기 `[학습자 직접]`

```bash
cp -r ~/_Lecture_cicd_learning.kit/ch10/10.4/terraform-eks ~/workspace/eks-infra
cd ~/workspace/eks-infra
cp ~/_Lecture_cicd_learning.kit/ch10/10.10/2.terraform.gitignore .gitignore
ls terraform.tfstate   # 10.4에서 apply한 state가 함께 복사됐는지 확인
```

> ⛔ `.gitignore`를 **먼저** 둔다. state 파일에는 클러스터 인증서와 리소스 정보가 평문으로 들어 있다.
> 한 번 커밋하면 지워도 이력에 남는다.

### 단계 3: backend 설정 `[AI 프롬프트]`

> "terraform-eks의 state를 GitLab 프로젝트의 Terraform state 저장소에 두려고 해. backend.tf를 만들어줘.
> 주소와 인증은 파일에 적지 말고 TF_HTTP_ 환경변수로 넘길 수 있게 http backend를 부분 설정으로 써줘."

✅ 정답 파일 (완성 후 비교): `ch10/10.10/1.backend.tf`

### 단계 4: 로컬 state를 GitLab으로 옮기기 `[학습자 직접]`

GitLab → User Settings → Access Tokens에서 scope **`api`** 토큰을 발급한다.

```bash
cd ~/workspace/eks-infra
export GITLAB_PROJECT_ID=<project_id>
export TF_ADDRESS="https://gitlab.com/api/v4/projects/${GITLAB_PROJECT_ID}/terraform/state/eks"
export TF_HTTP_ADDRESS="${TF_ADDRESS}"
export TF_HTTP_LOCK_ADDRESS="${TF_ADDRESS}/lock"
export TF_HTTP_UNLOCK_ADDRESS="${TF_ADDRESS}/lock"
export TF_HTTP_LOCK_METHOD=POST
export TF_HTTP_UNLOCK_METHOD=DELETE
export TF_HTTP_USERNAME=<gitlab_username>
read -rs TF_HTTP_PASSWORD && export TF_HTTP_PASSWORD   # 토큰을 붙여넣는다 (화면과 히스토리에 남지 않음)

terraform init -migrate-state
# "Do you want to copy existing state to the new backend?" → yes
```

확인:

- GitLab → `eks-infra` → **Operate → Terraform states**에 `eks`가 보인다
- `terraform plan` 결과가 **No changes**다. state가 실제 인프라와 맞게 옮겨졌다는 뜻이다

### 단계 5: CI/CD Variables 등록 `[학습자 직접]`

`eks-infra` → Settings → CI/CD → Variables

| 변수명 | 값 | Masked | Protected |
|---|---|---|---|
| `AWS_ACCESS_KEY_ID` | Terraform용 IAM 사용자 키 | ✅ | ✅ |
| `AWS_SECRET_ACCESS_KEY` | 〃 | ✅ | ✅ |

> 10.6에서 만든 CI용 IAM 사용자(`eks:DescribeCluster`만 있는 사용자)가 아니라 **10.4에서 apply한 사용자**의 키다.
> 10.4의 구성은 만든 사람을 클러스터 관리자로 등록한다(`enable_cluster_creator_admin_permissions`).
> 다른 사용자로 plan하면 그 등록을 바꾸려 해서 No changes가 나오지 않는다.

### 단계 6: 파이프라인 작성 `[AI 프롬프트]`

> "eks-infra의 GitLab CI 파이프라인을 만들어줘.
> - 이미지 hashicorp/terraform:1.15.7 (entrypoint 비우기)
> - state는 이 프로젝트의 Terraform state 저장소, 이름 eks. 인증은 gitlab-ci-token과 CI_JOB_TOKEN
> - plan은 main push마다 자동, 결과를 artifact로 남기기
> - apply와 destroy는 when: manual
> - GitLab Terraform 템플릿은 쓰지 마"

✅ 정답 파일 (완성 후 비교): `ch10/10.10/3.terraform-pipeline.yml`

```bash
cp ~/_Lecture_cicd_learning.kit/ch10/10.10/3.terraform-pipeline.yml .gitlab-ci.yml   # 비교 후 직접 쓴 파일을 써도 된다
git init -b main
git remote add origin https://gitlab.com/<gitlab_username>/eks-infra.git
git add .
git status   # terraform.tfstate, .terraform/ 이 목록에 없어야 한다
git commit -m "infra: EKS terraform with GitLab-managed state"
git push -u origin main
```

### 단계 7: plan 결과 확인 `[학습자 직접]`

Build → Pipelines에서 plan job 로그 끝에 `No changes.`가 있는지 본다. apply와 destroy는 회색 버튼(manual)으로 서 있다.

### 단계 8: 정리 준비. 클러스터 안의 로드밸런서를 먼저 지운다 `[학습자 직접]`

EKS 안에서 만든 ALB(Ingress)와 NLB(Argo CD Service)는 Terraform이 모르는 AWS 리소스다. 먼저 지우지 않으면
VPC 삭제가 `DependencyViolation`으로 실패한다(10.5 주의사항, 실검증 발생).

```bash
# Argo CD가 지운 것을 되살리지 않도록 Application부터 지운다
kubectl delete application --all -n argocd
kubectl delete ingress worklog
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "ClusterIP"}}'

# 로드밸런서가 모두 사라질 때까지 1~2분 기다린다. 두 명령 모두 빈 결과가 나오면 다음 단계로
# (Service의 로드밸런서는 설정에 따라 NLB나 Classic ELB로 만들어지므로 둘 다 본다)
aws elbv2 describe-load-balancers --region ap-northeast-2 --query 'LoadBalancers[].LoadBalancerName'
aws elb describe-load-balancers --region ap-northeast-2 --query 'LoadBalancerDescriptions[].LoadBalancerName'
```

### 단계 9: destroy 버튼 `[학습자 직접]`

Build → Pipelines → 가장 최근 파이프라인 → **destroy** job의 실행 버튼. 10~15분 걸린다.
`Destroy complete!`를 확인한다.

### 단계 10: 남은 것 확인 `[학습자 직접]`

- AWS 콘솔에서 EKS, EC2, VPC, NAT Gateway가 비었는지 본다
- 10.5에서 Terraform 밖에서 만든 AWS Load Balancer Controller의 IAM 정책과 역할을 지운다(IAM은 과금이 없지만 남겨 두지 않는다)
- KMS 키가 `PendingDeletion`으로 남는 것은 정상이다(과금 없음, 7일 뒤 자동 삭제)

## 트러블슈팅

### destroy job이 실패했다

state는 GitLab에 있으므로 PC에서 그대로 이어서 지울 수 있다. 단계 4의 `TF_HTTP_*` 환경변수를 다시 넣고:

```bash
cd ~/workspace/eks-infra
terraform init
terraform destroy
```

VPC에서 `DependencyViolation`이 나면 단계 8을 빠뜨린 것이다. 남은 로드밸런서와 `k8s-` 로 시작하는 보안그룹을 확인한다.

### plan이 No changes가 아니다

- CI 변수의 키가 10.4에서 apply한 IAM 사용자의 것인지 확인한다(단계 5)
- 로컬 `terraform plan`도 같은 결과인지 본다. 로컬에서 No changes면 CI 쪽 변수 문제다

### `Error acquiring the state lock`

다른 job이나 로컬 세션이 state를 잡고 있다. 그 작업이 끝났는지 확인한 뒤, 정말 멈춘 잠금이면
Operate → Terraform states에서 잠금을 해제한다.

## 주의사항

- ⛔ AI가 하지 말 것: 토큰이나 AWS 키를 `backend.tf`, `-backend-config`, `.gitlab-ci.yml`에 평문으로 적지 말 것. `-backend-config`로 넘긴 값은 `.terraform/` 아래에 남는다
- ⛔ AI가 하지 말 것: `.gitignore` 없이 `git add .`를 안내하지 말 것. state가 커밋된다
- ⛔ AI가 하지 말 것: apply와 destroy를 자동 실행(`when: manual` 제거)으로 만들지 말 것. 인프라를 바꾸는 job은 사람이 누른다
- ⛔ AI가 하지 말 것: 단계 8을 건너뛰고 destroy를 안내하지 말 것
- ⛔ AI가 하지 말 것: GitLab의 Terraform CI/CD 템플릿(`Terraform.gitlab-ci.yml`)을 쓰지 말 것. 18.0에서 제거됐다
- ✅ AI가 해도 됨: backend.tf와 `.gitlab-ci.yml` 작성, plan 결과 해석, state 저장소가 왜 필요한지 설명
- ⚠️ 이미지 태그(`hashicorp/terraform:1.15.7`)는 학습자가 로컬에서 쓰는 Terraform 버전과 맞춘다. state를 더 높은 버전으로 한 번 쓰면 낮은 버전에서 못 읽는다
- ⚠️ 이 실습이 10장의 마지막 정리다. 여기까지 EKS를 켠 채로 이어 왔으니 destroy 완료를 반드시 확인한다
