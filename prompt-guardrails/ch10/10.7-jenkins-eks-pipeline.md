### 단계 2: 에이전트에 AWS CLI/kubectl/argocd 갖추기 `[학습자 직접]`

본 강의의 Jenkins는 Kubernetes 플러그인 동적 에이전트(컨테이너)를 쓴다. **컨테이너 에이전트에서는 파이프라인 실행 중 인라인 설치가 실패한다** — 에이전트가 비-root라 `apt` 불가, `unzip` 부재로 aws CLI v2 zip 설치도 불가 (실검증에서 확인). ch5에서 `docker`를 넣은 커스텀 에이전트 이미지를 썼듯, **그 위에 3개 도구를 더한 이미지를 만들어 레지스트리에 push**하고 파드 템플릿 이미지로 교체한다.

```dockerfile
FROM <기존 에이전트 이미지>   # 예: inbound-agent + docker

USER root
RUN apt-get update && apt-get install -y --no-install-recommends unzip ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# aws CLI v2 (노드 아키텍처에 맞게: x86_64 또는 aarch64)
RUN curl -sSL "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o /tmp/awscliv2.zip \
    && unzip -q /tmp/awscliv2.zip -d /tmp && /tmp/aws/install && rm -rf /tmp/aws /tmp/awscliv2.zip

# kubectl + argocd (동일하게 아키텍처 주의)
RUN curl -sSL "https://dl.k8s.io/release/<버전>/bin/linux/amd64/kubectl" -o /usr/local/bin/kubectl && chmod +x /usr/local/bin/kubectl
RUN curl -sSL "https://github.com/argoproj/argo-cd/releases/download/<버전>/argocd-linux-amd64" -o /usr/local/bin/argocd && chmod +x /usr/local/bin/argocd

USER jenkins
```

빌드·push 후 Jenkins 관리 → Clouds → 파드 템플릿의 컨테이너 이미지를 이 이미지로 교체한다. **이미지는 반드시 레지스트리에 올린다** — 특정 노드에만 로컬 import하면 다른 노드에 스케줄될 때 ImagePullBackOff.

> VM에 직접 설치한 Jenkins(비컨테이너)라면 위 명령을 노드에서 sudo로 한 번 실행하는 것으로 충분하다.

## 검증 발견 (실배포, 2026-07-03)

- **실배포 검증 성공**: 로컬 Jenkins(k8s 동적 에이전트) → EKS로 Part A(build→update-kubeconfig→kubectl apply→rollout)·Part B(매니페스트 push→argocd sync→Synced/Healthy) 모두 그린.
- ⛔ **CI IAM 유저에 `eks:DescribeCluster` 정책 + EKS access entry 둘 다 필요** — 전자는 `update-kubeconfig`, 후자는 kubectl RBAC. 상세는 `prompt-guardrails/ch10/10.6-github-eks-pipeline.md` 단계 1.
- ⛔ deploy_manifest의 HTTPRoute는 EKS서 apply 실패 → ALB Ingress 교체 (10.5 참조).
- 로컬(arm64 Vagrant) 환경에서 겪을 수 있는 것: ①에이전트 git이 GitHub 인증서 검증 실패(`CAfile: none`) → 이미지의 `ca-certificates` 최신화, ②호스트 절전 후 노드 시계 드리프트 → AWS `Signature expired` → 시각 동기화, ③arm64→amd64 크로스빌드의 디스크 압박 → buildx 캐시 정리, ④에이전트를 DNS 건강한 노드에 nodeSelector 고정. 상세는 아래 "로컬(Vagrant, arm64) 환경 주의" 절.

## 로컬(Vagrant, arm64) 환경 주의 — 실배포 검증에서 겪은 것

- **git HTTPS 인증서 검증 실패**: Debian 에이전트의 git은 GnuTLS libcurl을 써서 GitHub의
  Sectigo ECC 인증서 체인을 검증하지 못하고 `server certificate verification failed
  (CAfile: none)`으로 checkout이 실패할 수 있다(curl·openssl은 성공).
  **에이전트 이미지의 `ca-certificates`를 최신으로 갱신**하면 해결된다. 임시로
  `git clone -c http.sslVerify=false`로 우회 가능하나 배포용은 아니다.
  ch5~ch9의 GitHub checkout에도 같은 영향이 있다.
- **노드 시계 드리프트**: 호스트 절전 후 VM 시계가 수 분 느려지면 AWS 호출이
  `InvalidSignatureException: Signature expired`로 실패한다. 실행 전 노드에서
  시각 동기화를 확인한다(`systemctl restart systemd-timesyncd` 등).
- **크로스아치 빌드 디스크 압박**: arm64 에이전트에서 `--platform linux/amd64`(EKS는
  amd64) 빌드는 QEMU로 되지만 노드 디스크를 많이 써 `ephemeral-storage` eviction으로
  빌드가 죽을 수 있다. 오래된 buildx 빌더·캐시를 정리해 여유 디스크를 확보한 뒤 진행한다.
- **에이전트 스케줄 노드**: 동적 에이전트가 DNS·도커가 건강한 노드(예: cp-k8s)에 뜨도록
  파드 템플릿 `nodeSelector`로 고정하면 레지스트리 해석 실패
  (`registry-1.docker.io ... i/o timeout`)를 피할 수 있다.

### 에이전트 이미지를 빌드타임에 갖추는 이유

기본 `inbound-agent-docker`(Debian bookworm)에는 `docker`만 있어 파이프라인이
`aws: not found`로 실패한다. 런타임 인라인 설치는 두 가지로 막힌다.

- 에이전트가 비-root라 `apt` 불가
- `unzip` 부재로 aws CLI v2 zip 설치 실패

빌드 시 root로 `unzip` + aws CLI v2 + kubectl + argocd를 넣은 커스텀 이미지를 만들어
레지스트리에 push하고 파드 템플릿 이미지로 지정한다. 로컬 클러스터가 arm64면 aws CLI는
`awscli-exe-linux-aarch64.zip`을 쓴다.
