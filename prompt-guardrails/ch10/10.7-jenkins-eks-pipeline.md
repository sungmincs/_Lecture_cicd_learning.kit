# 10.7 [Jenkins] EKS 파이프라인 (직접 배포 + Argo CD 연동)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 워크플로 끄기, 에이전트 이미지 빌드와 push, Argo CD 자동 sync 끄고 켜기, git push, 배포 확인
> - `[학습자 직접 · 웹]`: Jenkins 에이전트 이미지 교체, Credentials 등록, 스캔과 빌드 확인
> - `[AI 프롬프트]`: 에이전트 이미지 Dockerfile, Part A와 Part B Jenkinsfile 작성
>
> Jenkins는 로컬 클러스터에서 돈다. 로컬의 Jenkins가 인터넷 너머의 EKS에 배포하는 구성이다.

## 사전 조건

- ch10.6 완료 (EKS의 Application `worklog-backend`가 자동 sync 중이고 Synced)
- Jenkins에 `dockerhub-credentials`(5.5), `github-token`(6.8)이 있음
- kubectl context가 `eks`임

## 실행 지침

### 단계 0: 앞 절 파이프라인 끄기 `[학습자 직접]`

10.6의 워크플로를 끈다. Jenkinsfile을 push하면 GitHub 워크플로도 같은 push로 돈다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow disable eks-argocd.yaml -R <github_username>/worklog-backend
gh workflow list --all -R <github_username>/worklog-backend      # 모두 disabled_manually
```

### 단계 1: 에이전트 이미지 Dockerfile 작성 `[AI 프롬프트]`

지금 에이전트 이미지에는 docker만 있다. EKS에 배포하려면 aws, kubectl, argocd가 더 필요하다. 에이전트는 root가 아니라서 파이프라인 안에서 설치할 수 없다. 도구를 넣은 이미지를 새로 만든다.

> "Jenkins 에이전트 이미지에 EKS 배포 도구를 더한 Dockerfile을 컨트롤 플레인 노드의 `/root/ch10/jenkins-agent/Dockerfile`에 만들어줘. 빌드는 내가 할게.
> - 베이스 이미지는 지금 Jenkins 에이전트가 쓰는 `sungminl/inbound-agent-docker:3248.v65ecb_254c298-3-jdk17` (docker CLI가 들어 있는 이미지다)
> - root로 unzip과 ca-certificates 설치
> - AWS CLI v2 2.35.17, kubectl v1.36.0, argocd v3.4.3을 `/usr/local/bin`에 설치. 빌드하는 아키텍처(amd64 또는 arm64)에 맞는 파일을 받게 해줘
> - 마지막에 `USER jenkins`로 되돌리기"

베이스 이미지 이름은 Jenkins → Jenkins 관리 → Clouds → kubernetes → Pod Templates → `default`의 Docker image 칸에서 확인할 수 있다. 4.5의 설치 스크립트가 넣은 값이다.
로컬 클러스터의 ConfigMap(`jenkins-jenkins-jcasc-config`)에는 `jenkins/inbound-agent`라는 다른 이름이 보이는데, 그것은 차트의 기본값이고 실제로 쓰이지 않는다.

### 단계 2: 에이전트 이미지 빌드와 push `[학습자 직접]`

```bash
cd /root/ch10/jenkins-agent
docker build -t <dockerhub_username>/inbound-agent-docker:eks .
docker run --rm --entrypoint sh <dockerhub_username>/inbound-agent-docker:eks -c 'aws --version; kubectl version --client; argocd version --client | head -1'
docker push <dockerhub_username>/inbound-agent-docker:eks
```

이미지는 레지스트리에 올려야 한다. 에이전트 Pod가 어느 워커에 뜰지 모르기 때문이다.

### 단계 3: Jenkins의 에이전트 이미지 바꾸기 `[학습자 직접 · 웹]`

Jenkins → Jenkins 관리 → Clouds → kubernetes → Pod Templates → `default` → Containers의 `jnlp` → Docker image를
`<dockerhub_username>/inbound-agent-docker:eks`로 바꾸고 Save.

### 단계 4: Jenkins Credentials 등록 `[학습자 직접 · 웹]`

Jenkins → Jenkins 관리 → Credentials → System → Global

| ID | 종류 | 값 | 할 일 |
|---|---|---|---|
| `aws-access-key-id` | Secret text | 10.3 단계 2의 Access Key ID | 새로 등록 |
| `aws-secret-access-key` | Secret text | 10.3 단계 2의 Secret Access Key | 새로 등록 |
| `argocd-admin-password` | Secret text | 10.5 단계 6의 비밀번호 (EKS의 Argo CD) | 6.8에서 넣은 로컬 값을 Update로 바꾼다 |

`dockerhub-credentials`와 `github-token`은 그대로 쓴다. `argocd-admin-password`는 "이미 있다"고 지나치면 Part B의 로그인이 실패한다.

### 단계 5: Part A 전에 Argo CD 자동 sync 끄기 `[학습자 직접]`

10.6 단계 2와 같은 이유다.

```bash
argocd app set worklog-backend --sync-policy none
```

### 단계 6: Part A Jenkinsfile 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Jenkinsfile`을 EKS로 직접 배포하는 파이프라인으로 바꿔줘. push는 내가 할게.
> - pipeline 레벨에 `agent { label 'jenkins-jenkins-agent' }` 한 번만
> - environment:
>   - DOCKER_REPOSITORY=`<dockerhub_username>/worklog-backend`
>   - DOCKERHUB_CREDENTIALS = credentials('dockerhub-credentials')
>   - AWS_ACCESS_KEY_ID = credentials('aws-access-key-id'), AWS_SECRET_ACCESS_KEY = credentials('aws-secret-access-key')
>   - AWS_REGION = '<aws_region>', EKS_CLUSTER_NAME = 'cicd-learning-eks'
> - stages:
>   - Init: env.SHORT_SHA (8자)
>   - Test: uv 0.11.18 설치 스크립트, pytest와 coverage
>   - Build: docker buildx로 `linux/amd64` 이미지를 빌드해 push (EKS 노드가 amd64다), 태그는 SHORT_SHA
>   - Configure AWS: `aws eks update-kubeconfig --region ${AWS_REGION} --name ${EKS_CLUSTER_NAME}`
>   - Deploy to EKS: `deploy_manifest/worklog-backend.yaml`의 image 줄과 `# IMAGE_TAG` 줄을 sed로 바꾸고 `kubectl apply -f`, `kubectl rollout status`
> - 매니페스트를 git push하지 않는다
> - post: success/failure 알림(echo)
> - 전역 def 변수는 쓰지 말고 env.* 만 사용"

✅ 정답 파일 (완성 후 비교): `ch10/10.7/1.eks-deploy-pipeline.groovy`

### 단계 7-1: 스캔과 빌드 확인 `[학습자 직접 · 웹]`

Jenkins의 `worklog-backend` job에서 'Scan Multibranch Pipeline Now'를 누른다. main 빌드의 Console Output에서 Configure AWS와 Deploy to EKS가 성공하는지 본다.
arm64 노드에서는 amd64 이미지를 에뮬레이션으로 빌드하므로 Build stage가 평소보다 오래 걸린다.

### 단계 7-2: 클러스터와 Git이 어긋난 것 확인 `[학습자 직접]`

```bash
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # 방금 커밋의 8자 태그
argocd app get worklog-backend --refresh | grep "Sync Status"                                         # OutOfSync
```

### 단계 8: 자동 sync 다시 켜기 `[학습자 직접]`

```bash
argocd app set worklog-backend --sync-policy automated --self-heal --auto-prune
argocd app wait worklog-backend --sync --timeout 120
```

### 단계 9: Part B Jenkinsfile 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/Jenkinsfile`을 Part A에서 Argo CD GitOps 흐름으로 바꿔줘. push는 내가 할게.
> - environment에 추가: GITHUB_CREDENTIALS = credentials('github-token'), ARGOCD_ADMIN_PASSWORD = credentials('argocd-admin-password'), ARGOCD_APP_NAME = 'worklog-backend'
> - Init, Test, Build, Configure AWS는 Part A와 같다
> - Deploy to EKS 대신 두 stage:
>   - Update Manifest: sed로 매니페스트를 고쳐 커밋하고, github-token으로 `<github_username>/worklog-backend`에 `git pull --rebase` 뒤 `git push origin HEAD:${env.BRANCH_NAME}`. `kubectl apply`는 하지 않는다
>   - Sync Argo CD: `kubectl get svc argocd-server -n argocd -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'`로 서버 주소를 얻어 `argocd login --username admin --plaintext`로 로그인하고 `argocd app sync`, `argocd app wait --health --timeout 120`
> - 전역 def 변수는 쓰지 말고 env.* 만 사용"

## 트러블슈팅

### 파이프라인이 `aws: not found`(exit 127)로 실패한다

에이전트 Pod가 예전 이미지로 뜬 것이다. 단계 3에서 저장했는지, Console Output 앞부분의 Pod 정의에 `:eks` 이미지가 보이는지 확인한다.

### AWS 호출이 `Signature expired`로 실패한다

호스트가 절전에서 깨어난 뒤 VM의 시계가 느려진 것이다. 로컬 노드에서 `systemctl restart systemd-timesyncd`로 시각을 맞춘다.

### Build stage에서 에이전트가 끊긴다

arm64 노드에서 amd64 이미지를 에뮬레이션으로 빌드하면 디스크와 메모리를 많이 쓴다. 워커 디스크가 가득하면 8.5 트러블슈팅의 명령으로 비우고 다시 스캔한다.

## 주의사항

- ⛔ AI가 하지 말 것: AWS 키나 비밀번호를 묻거나 Jenkinsfile에 적지 말 것. `credentials()`로만 읽는다
- ⛔ AI가 하지 말 것: git push, Credentials 등록, 에이전트 이미지 교체, Jenkins 스캔을 대신 하지 말 것
- ⛔ AI가 하지 말 것: 파이프라인 안에서 aws, kubectl, argocd를 설치하지 말 것. 에이전트는 root가 아니라 실패한다. 단계 1의 이미지에 넣는다
- ⛔ AI가 하지 말 것: 에이전트 이미지의 베이스를 `jenkins/inbound-agent`로 바꾸지 말 것. docker CLI가 없어 Build stage가 실패한다
- ⛔ AI가 하지 말 것: stage 안에 agent를 다시 선언하거나 `agent any`를 쓰지 말 것
- ⛔ AI가 하지 말 것: Part A에서 매니페스트를 git push하지 말 것
- ⛔ AI가 하지 말 것: `argocd login`에 `--insecure`를 쓰지 말 것. `--plaintext`가 맞다
- ✅ AI가 해도 됨: Dockerfile과 Jenkinsfile 작성, Console Output 해석
- ⚠️ 에이전트 이미지를 바꾼 뒤에도 9장까지의 파이프라인은 그대로 돈다. 도구가 더해졌을 뿐이다
- ⚠️ EKS는 지우지 말고 10.8~10.10으로 이어 간다. 정리는 10.10에서 GitLab 파이프라인으로 한다

## 검증 기록

- 2026-07-03: 로컬 Jenkins에서 EKS로 Part A, Part B 통과. 그때 겪은 것: 에이전트 git의 인증서 검증 실패(`ca-certificates` 갱신으로 해결), 노드 시계 드리프트, arm64에서 amd64를 빌드할 때의 디스크 압박(`ephemeral-storage` eviction으로 빌드가 죽은 적이 있다)
- run-39(2026-10-09): 정답 파일을 `cp`하는 단계가 플레이스홀더 때문에 실패, 프롬프트와 정답의 Credential ID와 stage 이름이 달랐음, `argocd-admin-password`가 로컬 값이라 바꿔 넣어야 했음. 위 네 가지 주의는 그 run에서는 나오지 않았다
- run-40(2026-10-10): 베이스 이미지를 ConfigMap에서 찾게 했더니 AI가 실제로 쓰이지 않는 `jenkins/inbound-agent`를 골랐다. 프롬프트에 이미지 이름을 직접 적었다
