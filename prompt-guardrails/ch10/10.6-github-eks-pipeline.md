# 10.6 [GitHub] EKS 파이프라인 (직접 배포 + Argo CD 연동)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 앞 절 워크플로 끄기, Argo CD 자동 sync 끄고 켜기, git push, 배포 확인
> - `[학습자 직접 · 웹]`: GitHub Secrets 등록, Actions 실행 결과 확인
> - `[AI 프롬프트]`: Part A 워크플로(kubectl 직접 배포), Part B 워크플로(Argo CD sync) 작성

## 사전 조건

- ch10.5 완료 (EKS에 worklog와 Argo CD가 있고 Application `worklog-backend`가 Synced, argocd CLI가 EKS의 Argo CD에 로그인된 상태)
- fork의 `deploy_manifest/worklog-backend.yaml`이 ALB Ingress로 바뀌어 있음 (10.5 단계 9)
- backend fork의 Workflow permissions가 Read and write임 (6.7 단계 1)

## 9장까지와 달라지는 점

로컬 클러스터는 GitHub의 러너가 닿을 수 없는 곳에 있었다. 그래서 파이프라인은 Git의 매니페스트만 고치고, 클러스터 안의 Argo CD가 가져갔다.
EKS는 인터넷에서 닿는다. 러너가 `aws eks update-kubeconfig`로 접속해 `kubectl apply`를 직접 할 수 있다. 이 절에서 두 방식을 모두 해 본다.

- Part A: 러너가 `kubectl apply`로 직접 배포
- Part B: 러너가 매니페스트를 고쳐 push하고 `argocd app sync`를 부름

## 실행 지침

### 단계 0: 앞 절 파이프라인 끄기 `[학습자 직접]`

9장의 `ci.yaml`을 끈다. 이 절의 EKS용 워크플로가 같은 저장소 main에서 돈다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`.

```bash
gh workflow disable ci.yaml -R <github_username>/worklog-backend
gh workflow list --all -R <github_username>/worklog-backend      # 모두 disabled_manually
kubectl config current-context                                   # eks
```

### 단계 1: GitHub Secrets 등록 `[학습자 직접 · 웹]`

fork `worklog-backend` → Settings → Secrets and variables → Actions

| Secret 이름 | 값 | 용도 |
|---|---|---|
| `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` | 5.3(`DOCKERHUB_TOKEN`)과 7.8(`DOCKERHUB_USERNAME`)에서 이미 등록 | 이미지 push |
| `AWS_ACCESS_KEY_ID` | 10.3 단계 2의 Access Key ID | EKS 접근 |
| `AWS_SECRET_ACCESS_KEY` | 10.3 단계 2의 Secret Access Key | EKS 접근 |
| `AWS_REGION` | 10.3 단계 4에서 정한 리전 | `aws eks update-kubeconfig` |
| `EKS_CLUSTER_NAME` | `cicd-learning-eks` | `aws eks update-kubeconfig` |
| `ARGOCD_ADMIN_PASSWORD` | 10.5 단계 6의 비밀번호 (EKS의 Argo CD) | Part B |

10.4에서 클러스터를 만든 IAM 사용자의 키를 그대로 넣는다. 그 사용자는 클러스터 관리자로 등록돼 있어 따로 할 일이 없다.
CI 전용 IAM 사용자를 따로 만든다면 두 가지가 모두 필요하다. `eks:DescribeCluster` IAM 정책(`update-kubeconfig`가 부른다)과 EKS access entry(kubectl 권한)다.

### 단계 2: Part A 전에 Argo CD 자동 sync 끄기 `[학습자 직접]`

Part A는 Git을 고치지 않고 클러스터만 바꾼다. Argo CD가 자동 sync(selfHeal) 중이면 배포 1초 뒤에 Git의 상태로 되돌린다. Part A의 결과를 보려고 잠시 끈다.

```bash
argocd context                                         # EKS 주소에 * 표시
argocd app set worklog-backend --sync-policy none
```

### 단계 3: Part A 워크플로 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/.github/workflows/eks-deploy.yaml`에 EKS로 직접 배포하는 GitHub Actions 워크플로를 새 파일로 만들어줘. 기존 워크플로 파일은 건드리지 마. push는 내가 할게.
> - 트리거: main 브랜치 push, `deploy_manifest/**` 변경은 제외
> - env: DOCKER_REPOSITORY=`<dockerhub_username>/worklog-backend`. DOCKERHUB_TOKEN, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION, EKS_CLUSTER_NAME은 secrets
> - init-and-test job: setup-uv 액션(uv 0.11.18)으로 pytest와 coverage, outputs로 short_sha(8자)
> - build job: docker buildx로 `linux/amd64` 이미지를 빌드해 push (EKS 노드가 amd64다), 태그는 short_sha
> - deploy job:
>   - `aws-actions/configure-aws-credentials@v4`로 AWS 자격 구성
>   - `aws eks update-kubeconfig --region ${AWS_REGION} --name ${EKS_CLUSTER_NAME}`
>   - `deploy_manifest/worklog-backend.yaml`의 image 줄과 `# IMAGE_TAG` 줄을 sed로 새 태그로 바꾼 뒤 `kubectl apply -f`
>   - `kubectl rollout status deployment/worklog-backend --timeout=120s`
>   - 매니페스트를 git push하지 않는다 (이 파일의 핵심은 직접 배포다)
> - notify-success-result / notify-failure-result job"

✅ 정답 파일 (완성 후 비교): `ch10/10.6/1.eks-deploy-pipeline.yaml`

### 단계 4: Part A push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add .github/workflows/eks-deploy.yaml
git commit -m "cicd: deploy to EKS via GitHub Actions"
git pull --rebase
git push
```

### 단계 4-1: Part A 실행 확인 `[학습자 직접 · 웹]`

fork의 Actions 탭에서 방금 실행의 deploy job이 `kubectl apply`와 `rollout status`까지 성공하는지 본다.

### 단계 4-2: 클러스터와 Git이 어긋난 것 확인 `[학습자 직접]`

```bash
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # 방금 커밋의 8자 태그
grep "image:" deploy_manifest/worklog-backend.yaml                                                     # Git은 이전 태그 그대로
argocd app get worklog-backend --refresh | grep "Sync Status"                                         # OutOfSync
```

클러스터에는 새 이미지가 떴는데 Git에는 흔적이 없다. 누가 언제 무엇을 배포했는지는 Actions의 실행 기록에만 남는다.

### 단계 5: Part A를 끄고 자동 sync 다시 켜기 `[학습자 직접]`

```bash
gh workflow disable eks-deploy.yaml -R <github_username>/worklog-backend
argocd app set worklog-backend --sync-policy automated --self-heal --auto-prune
argocd app wait worklog-backend --sync --timeout 120
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'      # Git에 적힌 이전 태그로 돌아갔다
```

자동 sync를 켜자 Argo CD가 Part A의 배포를 Git의 상태로 되돌렸다. GitOps에서 클러스터를 직접 바꾸지 않는 이유가 이것이다.

### 단계 6: Part B 워크플로 작성 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/.github/workflows/eks-argocd.yaml`에 Part A(`eks-deploy.yaml`)를 바탕으로 Argo CD GitOps 흐름의 워크플로를 새 파일로 만들어줘. `eks-deploy.yaml`은 그대로 둬. push는 내가 할게.
> - env에 `ARGOCD_APP_NAME: worklog-backend` 추가
> - deploy job:
>   - AWS 자격 구성과 `aws eks update-kubeconfig`는 Part A와 같다
>   - `deploy_manifest/worklog-backend.yaml`을 sed로 고친 뒤 커밋하고, `git pull --rebase` 뒤에 같은 브랜치에 push (`git push origin HEAD:${BRANCH}`). `kubectl apply`는 하지 않는다
>   - argocd CLI v3.4.3 설치 (`argocd-linux-amd64`)
>   - `kubectl get svc argocd-server -n argocd -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'`로 ARGOCD_SERVER를 얻는다
>   - `argocd login ${ARGOCD_SERVER} --username admin --password <secrets.ARGOCD_ADMIN_PASSWORD> --plaintext`
>   - `argocd app sync`와 `argocd app wait --health --timeout 120`
> - notify job은 Part A와 같다"

✅ 정답 파일 (완성 후 비교): `ch10/10.6/2.eks-argocd-pipeline.yaml`

## 주의사항

- ⛔ AI가 하지 말 것: AWS 키나 비밀번호를 묻거나 워크플로에 평문으로 적지 말 것. Secrets로만 읽는다
- ⛔ AI가 하지 말 것: git push, Secrets 등록, 워크플로 끄기, `argocd app set`을 대신 하지 말 것
- ⛔ AI가 하지 말 것: Part A에서 매니페스트를 git push하지 말 것
- ⛔ AI가 하지 말 것: Part B에서 `paths-ignore: deploy_manifest/**`를 빼지 말 것. 자기가 올린 커밋으로 다시 돈다
- ⛔ AI가 하지 말 것: `argocd login`에 `--insecure`를 쓰지 말 것. 10.5의 Argo CD는 TLS 없이 동작해 `--plaintext`가 맞다
- ⛔ AI가 하지 말 것: 이미지를 arm64로만 빌드하지 말 것. EKS 노드는 amd64다
- ✅ AI가 해도 됨: 워크플로 yaml 작성, Actions 로그 해석, 두 방식의 비교 설명
- ⚠️ 워크플로 이름은 AI가 지은 것이라 정답 파일과 다를 수 있다. Actions 탭에서는 방금 push한 커밋으로 찾는다
- ⚠️ EKS를 다시 만들면 Argo CD의 주소와 비밀번호가 바뀐다. `ARGOCD_ADMIN_PASSWORD` Secret도 다시 넣는다
- ⚠️ EKS는 지우지 말고 10.7~10.10으로 이어 간다(정리는 10.10)
