# 10.6 [GitHub] EKS 파이프라인 (직접 배포 + Argo CD 연동)

> **학습자 진입 방식**:
> - `[학습자 직접]`: GitHub Secrets 등록(AWS 4종 + Argo CD), fork 저장소에 workflow 배치, git push
> - `[AI 프롬프트]`: Part A `1.eks-deploy-pipeline.yaml` (kubectl 직접) 작성, Part B `2.eks-argocd-pipeline.yaml` (Argo CD sync) 작성

## 사전 조건

- ch10.4 완료 (EKS 클러스터 동작 + `aws eks update-kubeconfig` 검증)
- ch10.5 완료 (Argo CD 설치 + 초기 비밀번호 추출 — Part B용)
- ch5.3 완료 (GitHub Actions 기본 빌드 파이프라인 동작 확인)
- 학습자 fork 저장소에 `deploy_manifest/worklog-backend.yaml` 존재
- GitHub Actions write 권한 활성화 (Settings → Actions → General → Workflow permissions → Read and write)

## ch10이 ch9와 다른 핵심 포인트

- **EKS는 클라우드 K8s** → GitHub Actions runner가 `aws eks update-kubeconfig`로 직접 kubeconfig 받기 가능
- 따라서 GitHub Actions에서 `kubectl apply -f deploy_manifest/worklog-backend.yaml` **직접 호출 가능**
- ch9(로컬 K8s)는 GitHub Actions에서 클러스터에 접근 불가 → `deploy_manifest/` git push 후 클러스터 내부의 Argo CD가 감지하는 패턴 필수였음
- ch10에서는 두 패턴 모두 가능 → Part A: `kubectl apply` 직접 / Part B: Argo CD sync

## 실행 지침

### 단계 1: GitHub Secrets 등록 `[학습자 직접]`

저장소 → Settings → Secrets and variables → Actions

| Secret 이름 | 값 | 용도 |
|---|---|---|
| `DOCKERHUB_TOKEN` | Docker Hub Access Token | ch5에서 이미 등록 |
| `AWS_ACCESS_KEY_ID` | IAM Access Key ID | EKS 접근 |
| `AWS_SECRET_ACCESS_KEY` | IAM Secret Access Key | EKS 접근 |
| `AWS_REGION` | `ap-northeast-2` 등 | `aws eks update-kubeconfig` |
| `EKS_CLUSTER_NAME` | `cicd-learning-eks` 등 | `aws eks update-kubeconfig` |
| `ARGOCD_ADMIN_PASSWORD` | ch10.5에서 추출한 비밀번호 | Part B 전용 |

> ⛔ **CI가 쓸 IAM 유저에는 두 가지가 모두 필요하다** (하나라도 없으면 파이프라인 실패):
> 1. **`eks:DescribeCluster` IAM 정책** — `aws eks update-kubeconfig`가 호출. 없으면 `AccessDeniedException ... eks:DescribeCluster`.
> 2. **EKS access entry** — kubectl RBAC. 없으면 401(`the server has asked for the client to provide credentials`).
>    `aws eks create-access-entry --cluster-name <cluster> --principal-arn <user-arn> --type STANDARD` 후
>    `aws eks associate-access-policy --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy --access-scope type=cluster`
>
> 클러스터 생성자(10.4의 IAM)와 같은 키를 시크릿에 쓰면 둘 다 이미 충족된다.

### 단계 2: Part A — EKS 직접 배포 워크플로 작성 `[AI 프롬프트]`

> "worklog-backend GitHub Actions EKS 배포 파이프라인을 만들어줘.
> - 트리거: main 브랜치 push
> - env: DOCKER_REPOSITORY=`<dockerhub_username>/worklog-backend`, DOCKERHUB_USERNAME=`<dockerhub_username>`, DOCKERHUB_TOKEN/AWS_REGION/EKS_CLUSTER_NAME은 secrets
> - init-and-test job: uv 기반 pytest + coverage, outputs(full_sha/short_sha/branch/commit_message)
> - build job: docker buildx amd64/arm64 멀티 아키텍처 push, tag=full_sha와 short_sha
> - deploy job:
>   - `aws-actions/configure-aws-credentials@v4`로 AWS 자격 구성
>   - `aws eks update-kubeconfig --region ${AWS_REGION} --name ${EKS_CLUSTER_NAME}`
>   - `cd deploy_manifest && sed -i 'image:...' && sed -i '# IMAGE_TAG...' worklog-backend.yaml`
>   - `kubectl apply -f worklog-backend.yaml` **직접 실행** (ch9와 달리 git push 불필요)
>   - `kubectl rollout status deployment/worklog-backend --timeout=120s`
> - notify-success-result / notify-failure-result job
> - Docker Hub username: `<dockerhub_username>`"

✅ 정답 파일 (완성 후 비교): `ch10/10.6/1.eks-deploy-pipeline.yaml`

### 단계 3: Part A 적용 + 검증 `[학습자 직접]`

### 단계 4: Part B — EKS + Argo CD 워크플로 작성 `[AI 프롬프트]`

> "Part A를 기반으로 Argo CD GitOps 흐름을 추가해줘.
> - env에 `ARGOCD_APP_NAME: worklog-backend` 추가
> - deploy job:
>   - `aws eks update-kubeconfig`
>   - Argo CD CLI 설치 (`curl -sSL ... argocd-linux-amd64`)

>   - `argocd app sync ${ARGOCD_APP_NAME}` + `argocd app wait --health --timeout 120`
> - notify job 동일
> - Docker Hub username: `<dockerhub_username>`"

## 주의사항

- ⛔ AI가 하지 말 것: AWS credentials를 워크플로 yaml에 평문으로 작성 — 반드시 GitHub Secrets 참조
- ⛔ AI가 하지 말 것: Part A에서 deploy_manifest를 git push (직접 `kubectl apply`가 본 절의 핵심)
- ⛔ AI가 하지 말 것: Part B에서 deploy 후 같은 워크플로가 재트리거되도록 push (paths-ignore: `deploy_manifest/**` 적용 또는 commit 메시지 `[skip ci]` 필요 시 명시)
- ⛔ AI가 하지 말 것: `argocd login`을 `--insecure` 없이 작성 (Argo CD self-signed 인증서)
- ✅ AI가 해도 됨: GitHub Actions yaml 작성 (init/build/deploy/notify)
- ✅ AI가 해도 됨: `aws-actions/configure-aws-credentials@v4` 사용법 설명
- ✅ AI가 해도 됨: kubectl apply 직접 vs Argo CD sync GitOps 패턴 비교
- ⚠️ **EKS 클러스터가 동작 중이어야 파이프라인 검증 가능** → 검증 끝나면 즉시 ch10.4 `terraform destroy`
- ⚠️ Part B의 ARGOCD_SERVER는 LoadBalancer가 생성한 NLB hostname → 클러스터 재생성 시 변경됨 (Secret 갱신 필요)
- ⛔ **CI IAM 유저에 `eks:DescribeCluster` IAM 정책 필요.** `aws eks update-kubeconfig`가 이 API를 호출하므로, 없으면 `AccessDeniedException ... not authorized to perform: eks:DescribeCluster`로 kubeconfig 설정 단계에서 실패한다. 아래 access entry(kubectl RBAC)와 **별개**이며 둘 다 필요하다. 별도 CI 유저면 최소 정책을 붙인다:
