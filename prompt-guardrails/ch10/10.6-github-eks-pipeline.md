# 10.6 [GitHub] EKS 파이프라인 (직접 배포 + Argo CD 연동)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 저장소와 클러스터의 상태 비교, 배포 확인
> - `[학습자 직접 · 웹]`: GitHub Secrets 등록, Actions 실행 결과 확인
> - `[AI 프롬프트]`: 앞 절 워크플로 끄기, Argo CD 자동 sync 끄고 켜기, Part A 워크플로(kubectl 직접 배포)와 Part B 워크플로(Argo CD sync) 작성, push(프롬프트는 학습자가 처음부터 작성)

## 사전 조건

- ch10.5 완료 (EKS에 worklog와 Argo CD가 있고 Application `worklog-backend`가 Synced, argocd CLI가 EKS의 Argo CD에 로그인된 상태)
- fork의 `deploy_manifest/worklog-backend.yaml`이 ALB Ingress로 바뀌어 있음 (10.5 단계 12)
- backend fork의 Workflow permissions가 Read and write임 (6.7 단계 2)

## 9장까지와 달라지는 점

로컬 클러스터는 GitHub의 러너가 닿을 수 없는 곳에 있었다. 그래서 파이프라인은 저장소의 매니페스트만 고치고, 클러스터 안의 Argo CD가 가져갔다.
EKS는 인터넷에서 닿는다. 러너가 `aws eks update-kubeconfig`로 접속해 `kubectl apply`를 직접 할 수 있다. 이 절에서 방식 2개를 모두 해 본다.

- Part A: 러너가 `kubectl apply`로 직접 배포
- Part B: 러너가 매니페스트를 고쳐 push하고 `argocd app sync`를 실행

## 실행 지침

### 단계 1: ci.yaml 비활성화 `[AI 프롬프트]`

9장의 `ci.yaml`을 끈다. 이 절의 EKS용 워크플로가 같은 저장소 main에서 돈다. 규칙과 방법은 `prompt-guardrails/shared/one-pipeline.md`. 첫 문장과 "끝나면"만 있는 짧은 요청이라 예시는 두지 않는다.

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
9장의 ci.yaml 워크플로를 비활성화하고 gh workflow list --all 결과를 보여줘. 이 절의 워크플로가 같은 main에서 실행되기 때문이야.
```

**AI가 따를 조건**

- 끝나면: gh workflow list --all 결과 보여 주기

### 단계 2: Secrets 등록 `[학습자 직접 · 웹]`

fork `worklog-backend` → Settings → Secrets and variables → Actions. `DOCKERHUB_USERNAME`과 `DOCKERHUB_TOKEN`은 5.3과 7.8에서 이미 등록했다.

10.4에서 클러스터를 만든 IAM 사용자의 키를 그대로 넣는다. 그 사용자는 클러스터 관리자로 등록돼 있어 따로 할 일이 없다.
CI 전용 IAM 사용자를 따로 만든다면 2가지가 모두 필요하다. `eks:DescribeCluster` IAM 정책(`update-kubeconfig`가 호출한다)과 EKS access entry(kubectl 권한)다.

| Secret 이름 | 값 |
|---|---|
| AWS_ACCESS_KEY_ID | 10.3 단계 2의 Access Key ID |
| AWS_SECRET_ACCESS_KEY | 10.3 단계 2의 Secret Access Key |
| AWS_REGION | 10.3 단계 4에서 정한 리전 |
| EKS_CLUSTER_NAME | cicd-learning-eks |
| ARGOCD_ADMIN_PASSWORD | 10.5 단계 9의 비밀번호(EKS의 Argo CD) |

### 단계 3: 자동 sync 비활성화 `[AI 프롬프트]`

Part A는 Git을 고치지 않고 클러스터만 바꾼다. Argo CD가 자동 sync(selfHeal) 중이면 배포 몇 초 뒤에 저장소의 상태로 되돌린다(run-39에서 1초). Part A의 결과를 보려고 잠시 끈다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
EKS Argo CD의 worklog-backend 자동 sync를 비활성화해줘. Part A의 배포를 되돌리지 않게 하려는 거야. 실행하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- argocd context가 EKS의 Argo CD(주소가 elb.amazonaws.com)인지 먼저 확인해.
- argocd app set worklog-backend --sync-policy none
- 끝나면: Sync Policy를 보여줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| argocd context가 EKS(elb 주소) | 로컬 Application이 바뀜 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 4: Part A 워크플로 `[AI 프롬프트]`

Part A: 러너가 `kubectl apply`로 직접 배포한다. 매니페스트를 git push하지 않는 것이 이 파일의 핵심이다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
EKS에 kubectl로 직접 배포하는 워크플로를 새 파일 eks-deploy.yaml로 만들어줘. 러너가 EKS에 직접 접속하는 방식이야. 파일을 만들기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/.github/workflows/eks-deploy.yaml
- 트리거: main push, deploy_manifest/** 변경은 제외
- DOCKER_REPOSITORY=<dockerhub_username>/worklog-backend, 나머지 값은 Secrets
- init-and-test(short_sha 8자), build(linux/amd64만), 성공과 실패 알림 job
- deploy job: AWS 자격 구성, update-kubeconfig, 태그 수정 뒤 kubectl apply와 rollout status
- 매니페스트는 git push하지 마. 기존 워크플로 파일도 그대로 둬.
- 참고: init-and-test와 build는 같은 폴더의 multi-env.yaml(8.4)과 같게 해줘.
- 끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| build의 플랫폼은 linux/amd64 | EKS에서 exec format error |
| 매니페스트는 git push하지 않음 | Part B와 같아져 차이가 없음 |
| 키와 계정 값은 Secrets | 키가 저장소에 평문으로 남음 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch10/10.6/1.eks-deploy-pipeline.yaml`

### 단계 6: 실행 확인 `[학습자 직접 · 웹]`

fork의 Actions 탭에서 방금 실행의 deploy job이 `kubectl apply`와 `rollout status`까지 성공하는지 본다. 워크플로 이름은 AI가 지은 것이라 정답 파일과 다를 수 있다. 방금 push한 커밋으로 찾는다.

| 위치 | 확인 항목 | 설명 |
|---|---|---|
| Actions 탭 | 방금 push한 커밋의 실행 | 실행이 1개만 표시 |
| deploy job | Configure AWS, Update kubeconfig, Deploy to EKS | 모두 성공 |
| deploy job 로그 | successfully rolled out | 전체 약 1분 40초 |

### 단계 7: 저장소와 다른 상태 확인 `[학습자 직접]`

클러스터에는 새 이미지가 떴는데 Git에는 흔적이 없다(OutOfSync). 누가 언제 무엇을 배포했는지는 Actions의 실행 기록에만 남는다.

```bash
kubectl get deploy worklog-backend -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
grep "image:" deploy_manifest/worklog-backend.yaml
argocd app get worklog-backend --refresh | grep "Sync Status"
```

### 단계 8: Part A 비활성화와 자동 sync `[AI 프롬프트]`

자동 sync를 켜면 Argo CD가 Part A의 배포를 저장소의 상태로 되돌린다. GitOps에서 클러스터를 직접 바꾸지 않는 이유가 이것이다.

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
eks-deploy.yaml을 비활성화하고 EKS Argo CD의 자동 sync를 --self-heal --auto-prune으로 다시 활성화해줘. sync를 기다린 뒤 Deployment의 이미지를 보여줘.
```

**AI가 따를 조건**

- gh workflow disable eks-deploy.yaml -R <github_username>/worklog-backend
- argocd app set worklog-backend --sync-policy automated --self-heal --auto-prune
- 끝나면: argocd app wait worklog-backend --sync --timeout 120 뒤에 Deployment의 이미지를 보여줘.

### 단계 9: Part B 워크플로 `[AI 프롬프트]`

Part B: 러너가 매니페스트를 고쳐 push하고 `argocd app sync`를 실행한다. 배포 결과(Healthy)까지 파이프라인이 기다린다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
eks-deploy.yaml을 바탕으로 배포는 Argo CD가 하는 워크플로를 새 파일 eks-argocd.yaml로 만들어줘. 파일을 만들기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/.github/workflows/eks-argocd.yaml
- env에 ARGOCD_APP_NAME: worklog-backend 추가
- deploy job: 태그를 바꿔 커밋, pull --rebase 뒤 같은 브랜치에 push. kubectl apply는 하지 마.
- argocd CLI v3.4.3(argocd-linux-amd64), 주소는 argocd-server Service의 hostname
- 로그인: secrets.ARGOCD_ADMIN_PASSWORD, --plaintext
- argocd app sync, argocd app wait --health --timeout 120
- 참고: 나머지 job과 AWS 자격 구성은 eks-deploy.yaml과 같게 하고 그 파일은 그대로 둬.
- 끝나면: yaml 문법을 검사하고 파일을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| paths-ignore 유지 | 매니페스트만 바뀐 push도 빌드 |
| argocd login에 --plaintext | 로그인 뒤 연결 종료 |
| push 전에 pull --rebase | 다른 커밋이 먼저 있으면 push 거절 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

✅ 정답 파일 (완성 후 비교): `ch10/10.6/2.eks-argocd-pipeline.yaml`

### 단계 12: 실행 확인 `[학습자 직접 · 웹]`

| deploy job | Update manifest and push, Sync Argo CD | 모두 성공 |
| deploy job 로그 | Health Status: Healthy | 전체 약 1분 50초 |

## 주의사항

- ⛔ AI가 하지 말 것: AWS 키나 비밀번호를 묻거나 워크플로에 평문으로 적지 말 것. Secrets로만 읽는다
- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: Secrets를 대신 등록하지 말 것. git push, 워크플로 끄기, `argocd app set`은 학습자의 요청(단계 1, 3, 5, 8, 11)이 있을 때만 한다. `argocd app set` 전에 argocd context가 EKS의 Argo CD인지 확인한다
- ⛔ AI가 하지 말 것: Part A에서 매니페스트를 git push하지 말 것
- ⛔ AI가 하지 말 것: Part B에서 `paths-ignore: deploy_manifest/**`를 빼지 말 것. 자기가 올린 커밋으로 다시 돈다
- ⛔ AI가 하지 말 것: `argocd login`에 `--insecure`를 쓰지 말 것. 10.5의 Argo CD는 TLS 없이 동작해 `--plaintext`가 맞다
- ⛔ AI가 하지 말 것: 이미지를 arm64로만 빌드하지 말 것. EKS 노드는 amd64다
- ✅ AI가 해도 됨: 워크플로 yaml 작성, Actions 로그 해석, 방식 2개의 비교 설명
- ⚠️ 워크플로 이름은 AI가 지은 것이라 정답 파일과 다를 수 있다. Actions 탭에서는 방금 push한 커밋으로 찾는다
- ⚠️ EKS를 다시 만들면 Argo CD의 주소와 비밀번호가 바뀐다. `ARGOCD_ADMIN_PASSWORD` Secret도 다시 넣는다
- ⚠️ EKS는 지우지 말고 10.7~10.10으로 이어 간다(정리는 10.10)
