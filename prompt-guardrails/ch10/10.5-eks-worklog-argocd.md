# 10.5 EKS에 Worklog App + Argo CD 배포 (공통)

> **학습자 진입 방식**:
> - `[학습자 직접]`: 이미지 태그 정하기, ALB 확인, Argo CD 주소와 비밀번호, CLI 로그인, 배포 확인
> - `[학습자 직접 · 웹]`: 브라우저로 앱과 Argo CD 접속
> - `[AI 프롬프트]`: 로컬 자동 sync 끄기, AWS Load Balancer Controller 설치, 7장 매니페스트 수정과 적용, Argo CD 설치와 노출, `deploy_manifest`를 ALB Ingress로 바꾸기와 push, Application 적용(프롬프트는 학습자가 처음부터 작성)

> 외부 노출(HTTPRoute → ALB Ingress)만 바꾼다.

### 단계 2: 컨트롤러 설치 `[AI 프롬프트]`

로컬 클러스터의 NGINX Gateway Fabric과 HTTPRoute는 EKS에 없다. EKS에서 앱을 밖으로 내보내려면 AWS Load Balancer Controller(ALB Ingress)를 먼저 설치한다.
컨트롤러가 AWS API를 부를 권한은 EKS Pod Identity로 준다. 10.4에서 `eks-pod-identity-agent` 애드온을 이미 설치했다.
IRSA(OIDC provider 방식)는 쓰지 않는다. AWS 새 가입 방식 계정은 OIDC provider 생성을 거부한다. Pod Identity는 기존 방식 계정에서도 똑같이 동작한다.
이 IAM 정책과 역할은 Terraform 밖에서 만들었으므로 10.10 단계 13에서 따로 지운다.

참고로 AI가 실행할 순서는 이렇다(run-41에서 41초).

```bash
cd /root/ch10
curl -sSfo iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v3.6.0/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam_policy.json
# trust.json: {"Effect":"Allow","Principal":{"Service":"pods.eks.amazonaws.com"},"Action":["sts:AssumeRole","sts:TagSession"]}
aws iam create-role --role-name AmazonEKSLoadBalancerControllerRole --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name AmazonEKSLoadBalancerControllerRole --policy-arn <policy_arn>
aws eks create-pod-identity-association --cluster-name cicd-learning-eks \
  --namespace kube-system --service-account aws-load-balancer-controller --role-arn <role_arn>
helm repo add eks https://aws.github.io/eks-charts && helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system --version 3.6.0 \
  --set clusterName=cicd-learning-eks --set serviceAccount.create=true \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=$(aws configure get region) --set vpcId=$(terraform -chdir=/root/ch10/terraform-eks output -raw vpc_id)
```

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
EKS에 AWS Load Balancer Controller v3.6.0을 설치해줘. Ingress로 ALB를 만들려는 거야. 설치하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- kubectl context가 eks인지 먼저 확인해.
- IAM 정책 AWSLoadBalancerControllerIAMPolicy: 컨트롤러 v3.6.0의 docs/install/iam_policy.json
- IAM 역할 AmazonEKSLoadBalancerControllerRole: 신뢰 대상 pods.eks.amazonaws.com, 위 정책 연결
- Pod Identity로 kube-system의 aws-load-balancer-controller 서비스 계정과 연결
- Helm 차트 3.6.0, vpcId는 /root/ch10/terraform-eks의 terraform output vpc_id
- IRSA(OIDC provider)는 사용하지 마.
- 끝나면: aws-load-balancer-controller Deployment 결과를 보여줘.

### 단계 3: 이미지 태그 정하기 `[학습자 직접]`

EKS 노드는 amd64다. 로컬 노드가 arm64(Apple Silicon)라면 Jenkins가 노드에서 빌드한 frontend 이미지는 arm64뿐이라 EKS에서 뜨지 않는다.
GitHub Actions가 만든 이미지는 아키텍처 2개가 모두 들어 있다. 그 태그를 쓴다. frontend 태그도 같은 명령으로 `linux/amd64`가 있는지 본다.

```bash
grep "image:" /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml
git -C /root/workspace/worklog-frontend log origin/main --author=github-actions --format=%s -1
docker buildx imagetools inspect <dockerhub_username>/worklog-backend:<backend_tag> | grep Platform     # linux/amd64가 보여야 한다
docker buildx imagetools inspect <dockerhub_username>/worklog-frontend:<frontend_tag> | grep Platform
```

### 단계 12: deploy_manifest 수정 `[AI 프롬프트]`

단계 14의 Application은 fork의 `deploy_manifest/worklog-backend.yaml`을 본다. 그 파일에는 로컬 클러스터용 HTTPRoute가 있어 EKS에서는 동기화가 실패한다.

`group.name`이 같은 Ingress는 ALB 1개를 나눠 쓴다. 단계 4의 `worklog`(경로 `/`)와 이 `worklog-backend`(경로 `/health`)가 같은 ALB의 규칙 2개가 된다. 그룹을 지정하지 않으면 Ingress마다 ALB가 1개씩 생겨 비용이 는다.
`group.order`는 규칙을 보는 순서다. 숫자가 작은 쪽을 먼저 본다. `/health`(1)를 `/`(10)보다 먼저 봐야 한다. 순서를 정하지 않으면 이름순이라 `/`가 먼저 걸려 `/health`도 frontend로 간다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
deploy_manifest의 HTTPRoute를 ALB Ingress로 바꿔줘. EKS에는 Gateway API가 없어서야. 수정하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- 파일: /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml
- Ingress 이름 worklog-backend, ingressClassName alb
- annotation scheme, target-type, group.name은 참고 파일과 같게, group.order만 "1"
- 경로 /health(Prefix)를 worklog-backend Service의 80으로
- Deployment, Service, Secret과 image 줄, # IMAGE_TAG 주석은 그대로 둬.
- 참고: /root/ch10/4.worklog-ingress.yaml
- 끝나면: 바뀐 부분을 보여줘. 커밋 전에 멈춰줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| group.name worklog, group.order 1 | ALB가 1개 더 생겨 비용 증가 |
| Secret 유지 | Argo CD가 MongoDB Secret을 지움 |
| image 줄과 # IMAGE_TAG 주석 유지 | 파이프라인이 태그를 바꾸지 못함 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 13: push `[AI 프롬프트]`

GitHub 워크플로는 `deploy_manifest/**` 변경을 무시하므로 파이프라인은 돌지 않는다.

짧은 요청이라 계획 없이 바로 맡긴다. 학습자 요청 예:

```text
deploy_manifest 변경을 커밋하고 push해줘. 커밋 메시지는 deploy: use ALB ingress on EKS, push 전에 git pull --rebase 해줘.
```

**AI가 따를 조건**

- 커밋 메시지는 deploy: use ALB ingress on EKS
- push 전에 git pull --rebase
- 끝나면: push 결과를 보여줘.

### 단계 14: Application 적용 `[AI 프롬프트]`

6.5에서 만든 Application 파일을 고치지 않고 그대로 쓴다. 저장소, 경로, 대상(`https://kubernetes.default.svc`)이 같기 때문이다. Argo CD가 설치된 클러스터가 EKS로 바뀌었을 뿐이다.

짧게 요청하고 AI가 보여 주는 계획을 검토한다. 학습자 요청 예:

```text
6.5의 Application 파일을 EKS에 적용하고 Synced와 Healthy가 될 때까지 기다려줘. 적용하기 전에 계획부터 보여줘.
```

**AI가 따를 조건** (학습자 요청에 적혀 있지 않아도 이 가드레일에서 읽어 따른다. 파일을 만들거나 실행하기 전에 계획을 먼저 보여 준다)

- kubectl context가 eks이고 argocd CLI가 EKS의 Argo CD를 보는지 먼저 확인해.
- /root/workspace/argocd-application.yaml은 고치지 말고 그대로 적용
- 끝나면: argocd app wait worklog-backend --sync --health --timeout 300 결과를 보여줘.

**계획에서 확인할 것**

| 확인 항목 | 누락 시 결과 |
|---|---|
| kubectl과 argocd context가 EKS | 로컬 Argo CD에 적용 |
| 파일은 수정하지 않음 | 대상 클러스터 주소가 바뀜 |

계획이 맞으면 학습자가 "계획대로 진행해줘"(파일이면 "계획대로 만들어줘")라고 한다. 빠진 항목이 있으면 학습자가 그 항목만 1줄로 요청한다.

### 단계 15: 배포 확인 `[학습자 직접]`

## 트러블슈팅

### Pod가 `exec format error`로 재시작한다

arm64만 있는 이미지를 amd64 노드에 올린 것이다. 단계 3의 `imagetools inspect`로 `linux/amd64`가 있는 태그를 선택해 다시 적용한다.

### 브라우저에 `Blocked request. This host is not allowed`

frontend 이미지가 오래된 것이다. frontend `main`의 `vite.config.ts`가 `.elb.amazonaws.com`을 허용해야 ALB 주소로 열린다. 7.7 트러블슈팅처럼 fork를 기준 저장소와 맞추고(Sync fork) 7.8 파이프라인으로 이미지를 다시 만든다.

### ALB 주소의 `/health`가 frontend 화면(HTML)을 돌려준다

Ingress 2개의 `group.order`가 같거나 없다. `kubectl get ingress -o yaml | grep group.order`로 `worklog`가 10, `worklog-backend`가 1인지 본다.

### Ingress의 ADDRESS가 비어 있다

`kubectl -n kube-system logs deploy/aws-load-balancer-controller --tail=20`을 본다. 권한 오류면 단계 2의 Pod Identity 연결을, 서브넷을 못 찾는다면 10.4의 서브넷 태그를 확인한다.

## 주의사항

- ✅ 학습자의 요청이 짧아도 이 가드레일의 "AI가 따를 조건"을 따른다. 요청과 조건이 다르면 요청을 따르되 다른 점을 계획에 적는다
- ⛔ AI가 하지 말 것: 계획 검토 단계에서 계획을 보여 주기 전에 파일을 만들거나 명령을 실행하지 말 것. 학습자가 "계획대로"라고 한 뒤에 진행한다. 정답 파일을 읽어 그대로 쓰지 않는다
- ⛔ AI가 하지 말 것: `kubectl apply`, `helm install`, `aws` 명령, git push를 학습자의 요청(단계 1, 2, 5, 8, 13, 14) 없이 하지 말 것. 적용 전에 kubectl context가 `eks`인지 확인한다
- ⛔ AI가 하지 말 것: Argo CD 초기 비밀번호를 읽어 화면에 보여 주거나 대신 로그인하지 말 것(단계 9~11은 학습자가 한다)
- ⛔ AI가 하지 말 것: 7장의 매니페스트를 처음부터 다시 만들지 말 것. 복사해서 필요한 곳만 고친다
- ⛔ AI가 하지 말 것: Argo CD를 Helm 차트나 공식 `stable` 매니페스트로 설치하라고 안내하지 말 것. 6.3과 같은 파일을 쓴다
- ⛔ AI가 하지 말 것: Service를 ClusterIP로 두고 `port-forward`로만 접근하게 하지 말 것
- ✅ AI가 해도 됨: 매니페스트 수정, Ingress annotation 설명, 컨트롤러 로그 해석
- ⚠️ 로드밸런서가 둘 생긴다. Ingress의 ALB 하나와 Argo CD Service의 로드밸런서 하나다. 둘 다 시간당 과금된다
- ⚠️ EKS는 10.10까지 켠 채로 이어 간다. 10.5부터 10.10까지 한 번에 진행하도록 일정을 잡는다
- ⚠️ 롤아웃 직후 ALB가 잠깐 502를 줄 수 있다. backend는 replicas가 1이고 ALB의 대상 등록이 Pod 교체보다 조금 늦다. 몇 초 뒤 다시 본다
- ⛔ 정리 순서: Ingress와 LoadBalancer Service를 `kubectl delete`로 먼저 지운 뒤 `terraform destroy`를 한다(10.10 단계 11). AWS 콘솔에서 로드밸런서만 직접 지우면 보안 그룹이 남아 VPC 삭제가 실패한다
