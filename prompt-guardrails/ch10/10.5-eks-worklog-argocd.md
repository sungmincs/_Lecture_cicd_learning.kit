> - `[학습자 직접 · 웹]`: 브라우저로 앱과 Argo CD 접속
> - `[AI 프롬프트]`: 7장의 매니페스트를 EKS용으로 고치기, fork의 `deploy_manifest`에서 HTTPRoute를 ALB Ingress로 바꾸기

## 실행 지침

### 단계 0: 로컬 클러스터의 Application 자동 sync 끄기 `[학습자 직접]`

단계 9에서 fork의 `deploy_manifest`를 EKS용으로 바꾼다. 로컬 클러스터의 `worklog-backend` Application도 같은 main을 보고 있어 그대로 따라온다.
로컬에는 ALB가 없으므로 따라오지 않게 자동 sync를 꺼 둔다. 이 명령은 argocd CLI가 아직 로컬 Argo CD를 보고 있을 때 한다.

```bash
argocd context                                           # 현재 서버가 로컬(argocd-server의 ClusterIP)인지 확인
argocd app set worklog-backend --sync-policy none
kubectl config current-context                           # eks
```

### 단계 1: AWS Load Balancer Controller 설치 (Pod Identity) `[학습자 직접]`

로컬 클러스터의 NGINX Gateway Fabric과 HTTPRoute는 EKS에 없다. EKS에서 앱을 밖으로 내보내려면 AWS Load Balancer Controller(ALB Ingress)를 먼저 설치한다.
컨트롤러가 AWS API를 부를 권한은 EKS Pod Identity로 준다. 10.4에서 `eks-pod-identity-agent` 애드온을 이미 설치했다.

```bash
cd /root/ch10

# 1. IAM 정책 (컨트롤러 버전에 맞는 공식 정책 문서)
LBC_VERSION=v3.6.0
curl -sSfo iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/${LBC_VERSION}/docs/install/iam_policy.json
POLICY_ARN=$(aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json --query Policy.Arn --output text)

# 2. Pod Identity용 IAM 역할 (신뢰 대상이 pods.eks.amazonaws.com)
cat > trust.json <<'JSON'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"pods.eks.amazonaws.com"},"Action":["sts:AssumeRole","sts:TagSession"]}]}
JSON
ROLE_ARN=$(aws iam create-role --role-name AmazonEKSLoadBalancerControllerRole \
  --assume-role-policy-document file://trust.json --query Role.Arn --output text)
aws iam attach-role-policy --role-name AmazonEKSLoadBalancerControllerRole --policy-arn $POLICY_ARN

# 3. 서비스 계정과 역할 연결
aws eks create-pod-identity-association --cluster-name cicd-learning-eks \
  --namespace kube-system --service-account aws-load-balancer-controller --role-arn $ROLE_ARN

# 4. Helm 설치 (서비스 계정은 차트가 만든다)
VPC_ID=$(terraform -chdir=/root/ch10/terraform-eks output -raw vpc_id)
helm repo add eks https://aws.github.io/eks-charts && helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system --version 3.6.0 \
  --set clusterName=cicd-learning-eks --set serviceAccount.create=true \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=$(aws configure get region) --set vpcId=$VPC_ID
kubectl -n kube-system rollout status deploy/aws-load-balancer-controller
```

IRSA(OIDC provider 방식)는 쓰지 않는다. AWS 새 가입 방식 계정은 OIDC provider 생성을 거부한다. Pod Identity는 기존 방식 계정에서도 똑같이 동작한다.
이 IAM 정책과 역할은 Terraform 밖에서 만들었으므로 10.10 단계 10에서 따로 지운다.

### 단계 2: EKS에 올릴 이미지 태그 정하기 `[학습자 직접]`

EKS 노드는 amd64다. 로컬 노드가 arm64(Apple Silicon)라면 Jenkins가 노드에서 빌드한 frontend 이미지는 arm64뿐이라 EKS에서 뜨지 않는다.
GitHub Actions가 만든 이미지는 두 아키텍처가 모두 들어 있다. 그 태그를 쓴다.

```bash
grep "image:" /root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml                      # backend: 지금 main의 태그
git -C /root/workspace/worklog-frontend log origin/main --author=github-actions --format=%s -1          # frontend: 7.8이 올린 태그
docker buildx imagetools inspect <dockerhub_username>/worklog-backend:<backend_tag> | grep Platform     # linux/amd64가 보여야 한다
docker buildx imagetools inspect <dockerhub_username>/worklog-frontend:<frontend_tag> | grep Platform
```

### 단계 3: 7장의 매니페스트를 EKS용으로 고치기 `[AI 프롬프트]`

> "컨트롤 플레인 노드의 `/root/ch7/`에 있는 `1.mongodb-manifest.yaml`, `2.worklog-backend-with-db.yaml`, `3.worklog-frontend-manifest.yaml`을 `/root/ch10/`으로 복사해서 EKS용으로 고쳐줘. 적용은 내가 할게.
> - 세 파일에서 HTTPRoute 리소스는 지워줘. EKS에는 Gateway API가 없다. Deployment, Service, Secret은 그대로
> - backend 이미지와 IMAGE_TAG 값: `<dockerhub_username>/worklog-backend:<backend_tag>`
> - frontend 이미지: `<dockerhub_username>/worklog-frontend:<frontend_tag>`
> - `/root/ch10/4.worklog-ingress.yaml`을 새로 만들어줘. 이름 `worklog`, `ingressClassName: alb`, annotation은 `alb.ingress.kubernetes.io/scheme: internet-facing`, `alb.ingress.kubernetes.io/target-type: ip`, `alb.ingress.kubernetes.io/group.name: worklog`, `alb.ingress.kubernetes.io/group.order: "10"`. 경로 `/`(Prefix)를 worklog-frontend Service의 8080으로"

frontend만 ALB에 건다. 브라우저는 frontend만 부르고, `/api` 요청은 frontend Pod 안의 개발 서버가 backend Service로 넘긴다(7.7에서 본 프록시). 클러스터가 바뀌어도 이 구조는 같다.

### 단계 4: Worklog App 배포 `[학습자 직접]`

```bash
cd /root/ch10
grep -n "image:\|kind:" 1.mongodb-manifest.yaml 2.worklog-backend-with-db.yaml 3.worklog-frontend-manifest.yaml 4.worklog-ingress.yaml
kubectl apply -f 1.mongodb-manifest.yaml -f 2.worklog-backend-with-db.yaml -f 3.worklog-frontend-manifest.yaml -f 4.worklog-ingress.yaml
kubectl rollout status deploy/worklog-backend
kubectl rollout status deploy/worklog-frontend
kubectl get ingress worklog          # ADDRESS에 *.elb.amazonaws.com 이 나올 때까지 1~2분
```

ALB가 준비되면(2~3분) frontend를 거쳐 backend까지 닿는지 본다.

```bash
ALB=$(kubectl get ingress worklog -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'); echo $ALB
curl -s -o /dev/null -w "%{http_code}\n" http://$ALB/                    # 200
curl -s http://$ALB/api/v1/todos; echo                                   # [] (EKS의 MongoDB는 비어 있다)
```

호스트 브라우저에서 `http://<ALB 주소>`를 연다. hosts 파일을 고칠 필요가 없다. 할 일을 하나 넣어 본다.

### 단계 5: Argo CD 설치와 노출 `[학습자 직접]`

6.3과 같은 매니페스트를 쓴다(버전 고정, TLS 없이 동작).

```bash
kubectl create namespace argocd
kubectl apply -n argocd --server-side -f /root/_Lecture_cicd_learning.kit/ch6/6.3/argocd-manifest.yaml
kubectl -n argocd rollout status deploy/argocd-server
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "LoadBalancer"}}'
kubectl get svc argocd-server -n argocd          # EXTERNAL-IP에 *.elb.amazonaws.com 이 나올 때까지 1~3분
```

로컬에서는 HTTPRoute로 내보냈지만 EKS에서는 Service를 LoadBalancer로 바꾸면 AWS가 로드밸런서를 만들어 준다.

### 단계 6: Argo CD 주소와 초기 비밀번호 `[학습자 직접]`

```bash
ARGOCD_URL=$(kubectl get svc argocd-server -n argocd -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "http://${ARGOCD_URL}"
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d && echo
```

이 비밀번호는 10.6과 10.7에서 파이프라인의 Secret과 Credential로 다시 쓴다. 로컬 Argo CD의 비밀번호와 다른 값이다.

### 단계 6-1: Argo CD UI 접속 `[학습자 직접 · 웹]`

브라우저에서 위 `http://` 주소를 열고 `admin`과 단계 6의 비밀번호로 로그인한다. `https://`는 연결되지 않는다(이 매니페스트는 TLS를 쓰지 않는다).

### 단계 7: argocd CLI를 EKS의 Argo CD로 로그인 `[학습자 직접]`

```bash
argocd login ${ARGOCD_URL} --username admin --plaintext      # 비밀번호는 프롬프트에 입력한다
argocd context                                                # EKS 주소에 * 표시
argocd app list                                               # 아직 비어 있다
```

`--plaintext`를 쓴다. `--insecure`로는 `server is not configured with TLS` 뒤 연결이 끊긴다. 이제부터 `argocd` 명령은 EKS의 Argo CD를 본다.

### 단계 8: fork의 `deploy_manifest`에서 HTTPRoute를 ALB Ingress로 바꾸기 `[AI 프롬프트]`

단계 10의 Application은 fork의 `deploy_manifest/worklog-backend.yaml`을 본다. 그 파일에는 로컬 클러스터용 HTTPRoute가 있어 EKS에서는 동기화가 실패한다.

> "컨트롤 플레인 노드의 `/root/workspace/worklog-backend/deploy_manifest/worklog-backend.yaml`에서 HTTPRoute 리소스를 지우고 ALB Ingress로 바꿔줘. 커밋과 push는 내가 할게.
> - Ingress 이름 `worklog-backend`, `ingressClassName: alb`
> - annotation은 `/root/ch10/4.worklog-ingress.yaml`과 같게 (scheme, target-type, `group.name: worklog`). `group.order`만 `"1"`로 달리해줘
> - 경로 `/health`(Prefix)를 worklog-backend Service의 80으로
> - Deployment, Service, Secret은 그대로 둬. image 줄과 `# IMAGE_TAG` 주석도 건드리지 마"

`group.name`이 같은 Ingress는 ALB 하나를 나눠 쓴다. 단계 3의 `worklog`(경로 `/`)와 이 `worklog-backend`(경로 `/health`)가 같은 ALB의 규칙 두 개가 된다. 그룹을 지정하지 않으면 Ingress마다 ALB가 하나씩 생겨 비용이 는다.
`group.order`는 규칙을 보는 순서다. 숫자가 작은 쪽을 먼저 본다. `/health`(1)를 `/`(10)보다 먼저 봐야 한다. 순서를 정하지 않으면 이름순이라 `/`가 먼저 걸려 `/health`도 frontend로 간다.

### 단계 9: 바꾼 매니페스트 push `[학습자 직접]`

```bash

git checkout main && git pull --rebase
git diff --stat
git add deploy_manifest/worklog-backend.yaml
```

### 단계 10: Argo CD Application 적용 `[학습자 직접]`

6.5에서 만든 Application 파일을 고치지 않고 그대로 쓴다. 저장소, 경로, 대상(`https://kubernetes.default.svc`)이 같기 때문이다. Argo CD가 설치된 클러스터가 EKS로 바뀌었을 뿐이다.

```bash
kubectl apply -f /root/workspace/argocd-application.yaml
argocd app wait worklog-backend --sync --health --timeout 300
argocd app get worklog-backend | grep -E "Sync Status|Health Status"
kubectl get ingress                      # worklog와 worklog-backend의 ADDRESS가 같다
curl -s http://$ALB/health; echo         # {"health":"OK","imageTag":"<backend_tag>"}
```

단계 4에서 kubectl로 올린 backend Deployment와 Service를 Argo CD가 이어받아 관리한다. 이름이 같아서 새로 만들지 않는다.

## 트러블슈팅

### Pod가 `exec format error`로 재시작한다

arm64만 있는 이미지를 amd64 노드에 올린 것이다. 단계 2의 `imagetools inspect`로 `linux/amd64`가 있는 태그를 골라 다시 적용한다.

### 브라우저에 `Blocked request. This host is not allowed`

frontend 이미지가 오래된 것이다. frontend `main`의 `vite.config.ts`가 `.elb.amazonaws.com`을 허용해야 ALB 주소로 열린다. 7.7 트러블슈팅처럼 fork를 기준 저장소와 맞추고(Sync fork) 7.8 파이프라인으로 이미지를 다시 만든다.

### ALB 주소의 `/health`가 frontend 화면(HTML)을 돌려준다

두 Ingress의 `group.order`가 같거나 없다. `kubectl get ingress -o yaml | grep group.order`로 `worklog`가 10, `worklog-backend`가 1인지 본다.

### Ingress의 ADDRESS가 비어 있다

`kubectl -n kube-system logs deploy/aws-load-balancer-controller --tail=20`을 본다. 권한 오류면 단계 1의 Pod Identity 연결을, 서브넷을 못 찾는다면 10.4의 서브넷 태그를 확인한다.

## 주의사항

- ⛔ AI가 하지 말 것: `kubectl apply`, `helm install`, `aws` 명령, git push를 대신 실행하지 말 것
- ⛔ AI가 하지 말 것: 7장의 매니페스트를 처음부터 다시 만들지 말 것. 복사해서 필요한 곳만 고친다
- ⛔ AI가 하지 말 것: Argo CD를 Helm 차트나 공식 `stable` 매니페스트로 설치하라고 안내하지 말 것. 6.3과 같은 파일을 쓴다
- ⛔ AI가 하지 말 것: Service를 ClusterIP로 두고 `port-forward`로만 접근하게 하지 말 것
- ✅ AI가 해도 됨: 매니페스트 수정, Ingress annotation 설명, 컨트롤러 로그 해석
- ⚠️ 로드밸런서가 둘 생긴다. Ingress의 ALB 하나와 Argo CD Service의 로드밸런서 하나다. 둘 다 시간당 과금된다
- ⚠️ EKS는 10.10까지 켠 채로 이어 간다. 10.5부터 10.10까지 한 번에 진행하도록 일정을 잡는다
- ⚠️ 롤아웃 직후 ALB가 잠깐 502를 줄 수 있다. backend는 replicas가 1이고 ALB의 대상 등록이 Pod 교체보다 조금 늦다. 몇 초 뒤 다시 본다
- ⛔ 정리 순서: Ingress와 LoadBalancer Service를 `kubectl delete`로 먼저 지운 뒤 `terraform destroy`를 한다(10.10 단계 8). AWS 콘솔에서 로드밸런서만 직접 지우면 보안 그룹이 남아 VPC 삭제가 실패한다
