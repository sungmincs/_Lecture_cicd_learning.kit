## 실행 지침

### 단계 1: kubectl 컨텍스트 확인 `[학습자 직접]`

```bash
kubectl config current-context
kubectl get nodes
```

컨텍스트가 EKS 클러스터를 가리키는지 확인. 로컬 클러스터와 혼동하지 않도록 주의.

### 단계 2: AWS Load Balancer Controller 설치 `[학습자 직접]`

로컬 클러스터의 **NGINX Gateway Fabric + HTTPRoute는 EKS에 없다.** EKS에서 앱을 외부 노출하려면 AWS Load Balancer Controller(ALB Ingress)를 먼저 설치한다.

1. IAM 정책 생성: 공식 `iam_policy.json` 다운로드 → `aws iam create-policy`
2. IRSA 구성: 클러스터 OIDC provider(10.4 terraform이 생성)로 IAM 역할 + trust policy → 정책 attach → `kube-system/aws-load-balancer-controller` ServiceAccount에 role-arn annotation
3. Helm 설치:

```bash
helm repo add eks https://aws.github.io/eks-charts && helm repo update
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system \
  --set clusterName=<eks_cluster_name> --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=<aws_region> --set vpcId=<vpc_id>
```

Helm 설치 전에 IAM 정책과 IRSA를 먼저 만든다.

1. IAM 정책 생성
   ```bash
   curl -o iam_policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/<버전>/docs/install/iam_policy.json
   aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam_policy.json
   ```
2. IRSA: 클러스터 OIDC provider(10.4 terraform이 생성)로 IAM 역할과 trust policy를 만들고
   정책을 attach한 뒤, `kube-system/aws-load-balancer-controller` 서비스 계정에
   role-arn annotation을 단다.
3. 위 helm 명령으로 설치한다.

### 단계 3: Worklog App 배포 (매니페스트 재사용 + 노출만 ALB로 교체) `[학습자 직접]`

```bash
kubectl apply -f ~/_Lecture_cicd_learning.kit/ch7/7.7/1.mongodb-manifest.yaml
kubectl apply -f ~/_Lecture_cicd_learning.kit/ch7/7.7/2.worklog-backend-with-db.yaml
kubectl apply -f ~/_Lecture_cicd_learning.kit/ch7/7.7/3.worklog-frontend-manifest.yaml

kubectl get pods
kubectl get svc
```

> ⛔ **매니페스트 안의 HTTPRoute/Gateway 리소스는 EKS에서 apply가 실패한다** (Gateway API CRD·NGF 없음). Deployment/Service/Secret은 그대로 쓰고, **노출부만 ALB Ingress(`ingressClassName: alb`)로 교체**한다:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: worklog
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - { path: /health, pathType: Prefix, backend: { service: { name: worklog-backend, port: { number: 80 } } } }
          - { path: /, pathType: Prefix, backend: { service: { name: worklog-frontend, port: { number: 8080 } } } }
```

`kubectl get ingress worklog`로 ALB 주소 확인 → `curl http://<alb>/`(프론트 200), `curl http://<alb>/health`(백엔드 200).

### 단계 4: Argo CD 설치 `[학습자 직접]`

```bash
kubectl create namespace argocd
kubectl apply -n argocd -f ~/_Lecture_cicd_learning.kit/ch6/6.3/argocd-manifest.yaml
```

또는 공식 install:

```bash
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
```

### 단계 5: Argo CD LoadBalancer 노출 `[학습자 직접]`

```bash
kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "LoadBalancer"}}'
kubectl get svc argocd-server -n argocd -w
```

`EXTERNAL-IP` 컬럼에 `*.elb.amazonaws.com` 형태 호스트네임이 표시되면 성공 (1~3분 소요).

> ⚠️ 로컬 클러스터(ch6)에서는 NodePort를 사용했지만, EKS에서는 LoadBalancer로 변경. AWS가 자동으로 NLB를 프로비저닝한다.

### 단계 6: Argo CD 초기 비밀번호 추출 `[학습자 직접]`

```bash
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d && echo
```

이 비밀번호는 ch10.6/10.7/10.8 파이프라인의 `ARGOCD_ADMIN_PASSWORD` Secret/Variable 값으로 사용한다.

### 단계 7: Argo CD UI 접속 확인 `[학습자 직접]`

```bash
ARGOCD_URL=$(kubectl get svc argocd-server -n argocd -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "https://${ARGOCD_URL}"
```

브라우저에서 위 URL 접속 → 자체 서명 인증서 경고 무시 → `admin` / 단계 6 비밀번호로 로그인.

### 단계 8: Argo CD Application 등록 (ch6.5 참고) `[AI 프롬프트]`

### 단계 9: Argo CD CLI 로그인 (선택, 파이프라인 사전 검증용) `[학습자 직접]`

## 주의사항

- ⛔ AI가 하지 말 것: ch3/ch8 매니페스트를 임의로 EKS 전용으로 다시 만들지 말 것 — 재사용이 본 절의 핵심
- ⛔ AI가 하지 말 것: Argo CD를 helm chart로 설치하면서 추가 values 적용 (ch6와 동일한 단순 install 유지)
- ⛔ AI가 하지 말 것: Service type을 ClusterIP로 두고 `port-forward`로만 접근 — EKS는 LoadBalancer 외부 노출 가능하므로 활용
- ✅ AI가 해도 됨: LoadBalancer 노출 패치 명령 설명
- ✅ AI가 해도 됨: 초기 비밀번호 추출 bash 스니펫
- ✅ AI가 해도 됨: ch6.5 Application yaml의 EKS 적용 시 조정 포인트 안내
- ⚠️ Argo CD LoadBalancer Service는 추가 NLB를 프로비저닝 → 시간당 약 $0.025 추가 비용
- ⚠️ 본 절 종료 후에도 `terraform destroy`하지 않고 ch10.6/10.7/10.8 진행 시 비용 계속 발생 — 한 번에 끝낼 수 있도록 일정 조정 권장
- ⚠️ `argocd-initial-admin-secret`은 최초 로그인 후 비밀번호 변경하면 삭제되므로, 변경 전에 백업
- ⛔ **teardown 순서 필수**: LoadBalancer Service와 ALB Ingress를 **`kubectl delete`로 먼저** 지워 컨트롤러/CCM이 ELB·ALB와 보안그룹을 회수하게 한 뒤 `terraform destroy`. AWS CLI/콘솔에서 LB만 직접 지우면 `k8s-elb-*` 보안그룹이 orphan으로 남아 VPC 삭제가 DependencyViolation으로 실패한다(실검증에서 발생).
- ⛔ ALB Controller의 IAM 정책·역할은 terraform 밖에서 만든다면 실습 후 별도 삭제
