# 10.2 클라우드 전환 개요 (로컬 K8s → AWS EKS)

> **학습자 진입 방식**: 개념 섹션 — 실습 없음. 로컬과 클라우드 K8s의 차이, 전환의 목적과 진행 방법을 이해한 뒤 10.3으로 진행.

## 이 장의 목적

ch2~ch9까지는 Vagrant + VirtualBox로 만든 **로컬 K8s**에서 worklog 앱의 CI/CD 전체 흐름을 구축했다. ch10은 그 결과물을 **실제 클라우드(AWS EKS)** 로 옮긴다. 핵심은 "처음부터 다시 만드는 것"이 아니라, **앞서 만든 매니페스트·파이프라인·GitOps 구성을 거의 그대로 클라우드에서 재현**하는 것이다 — 이것이 쿠버네티스를 쓰는 가장 큰 실익(이식성)이다.

전환은 **Terraform(IaC)** 으로 EKS 클러스터를 코드로 프로비저닝하고, 기존 CI/CD 파이프라인의 배포 대상만 EKS로 바꾸는 방식으로 진행한다.

## 로컬 K8s vs AWS EKS — 무엇이 달라지나

코드(앱·매니페스트)는 거의 그대로지만, **클러스터를 둘러싼 인프라 4개 영역**이 클라우드 관리형으로 바뀐다.

| 영역 | 로컬 (ch2~ch9) | AWS EKS (ch10) |
|---|---|---|
| **네트워킹** | MetalLB + NGINX Gateway Fabric | AWS Load Balancer Controller(ALB/NLB) |
| **스토리지** | NFS(`managed-nfs-storage`) | EBS / EFS CSI Driver |
| **보안/인증** | 로컬 admin kubeconfig | IAM + IRSA(IAM Role for Service Account) |
| **스케일링** | 수동 노드 추가(vagrant) | Managed Node Group + Cluster Autoscaler |

> 클러스터 생성 방식도 다르다 — 로컬은 `kubeadm`(수동), EKS는 **Terraform이 control plane·노드그룹·네트워킹을 코드로 생성**한다. 클러스터가 둘이 되므로, 이 시점부터 `kubectl config use-context`로 대상 클러스터(로컬/EKS)를 반드시 명시한다.

## 진행 방법 (이 장의 흐름)

1. **AWS 준비**: IAM 사용자·CLI·자격증명 구성 → AWS를 다룰 권한 확보
2. **EKS 프로비저닝**: Terraform으로 클러스터를 코드로 생성(+삭제) → IaC 체험
3. **앱·GitOps 이식**: worklog 앱과 Argo CD를 EKS에 배포 → 로컬 구성 재현
4. **파이프라인 전환**: 기존 GitHub/Jenkins/GitLab CI의 배포 대상을 EKS로 교체

> ⚠️ EKS는 **유료**다(클러스터 시간당 요금 + 노드 EC2 요금). 실습 후 반드시 `terraform destroy`로 정리해 비용이 누적되지 않게 한다 — 10.3에서 생성과 삭제를 함께 다룬다.
