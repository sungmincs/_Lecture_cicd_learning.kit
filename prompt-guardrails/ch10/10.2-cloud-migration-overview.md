# 10.2 클라우드 전환 개요 (로컬 K8s → AWS EKS)

> **학습자 진입 방식**: 개념 절이다. 실습 없음. 로컬과 클라우드 K8s의 차이, 전환의 목적과 진행 방법을 이해한 뒤 10.3으로 진행.

## 이 장의 목적

ch2~ch9까지는 Vagrant + VirtualBox로 만든 **로컬 K8s**에서 worklog 앱의 CI/CD 전체 흐름을 구축했다. ch10은 그 결과물을 **실제 클라우드(AWS EKS)** 로 옮긴다. 핵심은 "처음부터 다시 만드는 것"이 아니라, **앞서 만든 매니페스트, 파이프라인, GitOps 구성을 거의 그대로 클라우드에서 다시 쓰는 것**이다. 쿠버네티스를 쓰는 가장 큰 이점인 이식성이 여기서 보인다.

전환은 **Terraform(IaC)** 으로 EKS 클러스터를 코드로 프로비저닝하고, 기존 CI/CD 파이프라인의 배포 대상만 EKS로 바꾸는 방식으로 진행한다.

## 로컬 K8s와 AWS EKS는 무엇이 다른가

코드(앱·매니페스트)는 거의 그대로지만, **클러스터를 둘러싼 인프라 4개 영역**이 클라우드 관리형으로 바뀐다.

| 영역 | 로컬 (ch2~ch9) | AWS EKS (ch10) |
|---|---|---|
| **네트워킹** | MetalLB + NGINX Gateway Fabric | AWS Load Balancer Controller(ALB/NLB) |
| **스토리지** | NFS(`managed-nfs-storage`) | EBS / EFS CSI Driver |
| **보안/인증** | 로컬 admin kubeconfig | IAM + EKS Pod Identity (Pod에 IAM 역할을 연결) |
| **노드 사이 통신** | 막는 것이 없다 | 보안 그룹이 포트를 거른다 (10.4에서 노드끼리 여는 규칙을 하나 넣는다) |
| **스케일링** | 수동 노드 추가(vagrant) | Managed Node Group + Cluster Autoscaler |

> 클러스터 생성 방식도 다르다. 로컬은 `kubeadm`(수동), EKS는 **Terraform이 control plane·노드그룹·네트워킹을 코드로 생성**한다.

## 어디서 하나

10장도 컨트롤 플레인 노드에서 한다. aws, terraform, helm, kubectl을 모두 노드에서 실행하고, AWS 자격 증명도 노드의 `aws configure`에 둔다. 호스트에는 아무것도 설치하지 않는다.

클러스터가 둘이 된다. 10.4에서 kubectl context 이름을 `local`(지금까지 쓴 로컬 클러스터)과 `eks`로 정한다. 10장의 명령 블록은 context가 `eks`인 상태를 기준으로 쓰고, 로컬 클러스터를 볼 때는 `kubectl --context local ...`처럼 적는다. 헷갈리면 `kubectl config current-context`부터 본다.

로컬 클러스터는 끄지 않는다. Jenkins가 거기서 돌고 있고, 10.7에서 그 Jenkins가 EKS에 배포한다.

## 진행 방법 (이 장의 흐름)

1. **AWS 준비**: IAM 사용자·CLI·자격증명 구성 → AWS를 다룰 권한 확보
2. **EKS 프로비저닝**: Terraform으로 클러스터를 코드로 생성(+삭제) → IaC 체험
3. **앱·GitOps 이식**: worklog 앱과 Argo CD를 EKS에 배포 → 로컬 구성 재현
4. **파이프라인 전환**: 기존 GitHub Actions/Jenkins 파이프라인의 배포 대상을 EKS로 교체
5. **GitLab CI로 확장**: 같은 일을 GitLab CI로 해 보고, Terraform state까지 GitLab에 맡겨 인프라를 파이프라인으로 관리

> ⚠️ EKS는 **유료**다(클러스터 시간당 요금 + 노드 EC2 요금). 10.4에서 만든 EKS는 10.10까지 켠 채로 이어 가고, 10장의 마지막 단계(10.10)에서 GitLab 파이프라인으로 지운다. 10장은 한 번에 이어서 진행하기를 권한다.
