# 4.2 CI/CD 도구 3종 개요와 선택 (GitHub Actions / Jenkins / GitLab CI)

> **학습자 진입 방식**: 개념+준비 섹션 — 본격 실습 없음. 3종 도구의 특징을 이해하고 사전 준비를 마친 뒤 4.3으로 진행.

## 이 챕터에서 다루는 것

ch4에서는 현업에서 가장 많이 쓰이는 **CI/CD 도구 3종을 직접 "찍먹"** 해본다. 하나의 정답 도구를 고르는 게 아니라, 같은 빌드 파이프라인을 세 도구로 각각 만들어보며 **공통 개념(트리거 → job/stage → 빌드)** 과 **도구별 차이**를 몸으로 익히는 것이 목표다. 이후 ch5~ch10에서도 이 세 도구를 나란히 다루므로, 여기서 각 도구의 위치를 잡아두면 전체 강의가 수월해진다.

## 3종 도구 비교

| 구분 | GitHub Actions | Jenkins | GitLab CI/CD |
|---|---|---|---|
| 형태 | SaaS (GitHub 내장) | 셀프호스팅 (직접 설치·운영) | SaaS (GitLab 내장) |
| 설정 방식 | `.github/workflows/*.yaml` | `Jenkinsfile` (Groovy) | `.gitlab-ci.yml` |
| 실행 환경 | GitHub 호스팅 러너 | 직접 구성한 에이전트/노드 | GitLab 러너 (SaaS/셀프) |
| 진입 장벽 | 낮음 (저장소만 있으면 시작) | 높음 (설치·플러그인 관리) | 낮음 (저장소만 있으면 시작) |
| 강점 | 생태계·마켓플레이스 | 유연성·플러그인·온프레미스 | 통합 DevOps(이슈~배포 일원화) |

> 본 강의는 세 도구를 모두 실습하며, **GitHub Actions → Jenkins → GitLab CI 순서**로 진행한다. 이 순서는 한국 시장 인기 순(당시 국내 인프라 사용자 그룹 설문 기준: 1위 GitHub Actions, 2위 Jenkins)을 따른 것이다. 최신 추세도 대체로 유사하다. GitLab CI는 자체 호스팅(온프레미스)으로 소스 관리부터 CI/CD까지 한 플랫폼에서 운영하는 기업이 국내에도 많아, SaaS(GitHub Actions)·셀프호스팅 빌드 서버(Jenkins)와 더불어 배포 방식의 균형을 맞추기 위해 포함한다. ch5~ch10에서도 이 순서가 일관되게 반복된다.

## 선택 기준 (실무 관점)

- **이미 GitHub/GitLab을 쓰고 있다** → 같은 플랫폼의 내장 CI(Actions/GitLab CI)가 마찰이 가장 적다.
- **온프레미스·규제 환경, 세밀한 커스터마이징이 필요하다** → Jenkins.
- **무엇을 고르든 핵심 개념은 동일** → 트리거(push/PR/tag) → 단계(job/stage) → 아티팩트(이미지) 빌드·푸시. ch4는 이 공통 골격을 세 번 반복해 체득시킨다.

## 실습 사전 준비

| 도구 | 준비물 | 비고 |
|---|---|---|
| GitHub Actions | GitHub 계정 + worklog 저장소 fork | ch3.3에서 fork·clone 완료 |
| Jenkins | (설치는 4.5에서 진행) | K8s에 Helm으로 설치 |
| GitLab CI/CD | GitLab 계정 + 저장소 | gitlab.com 무료 계정 가능 |

> Docker Hub 계정은 ch3.5에서 이미 만들어 로컬 `docker login`·`push`를 해봤다. ch4는 파이프라인 "구조"만 익히는 단계라 이미지 push까지 가지 않으므로 추가 준비가 필요 없다. ch5에서 파이프라인이 이미지를 자동 빌드·push할 때 Docker Hub **Access Token**을 시크릿으로 등록한다.
