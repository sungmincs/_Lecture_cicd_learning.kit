# 4.2 CI/CD 도구 개요와 선택 (GitHub Actions / Jenkins)

> **학습자 진입 방식**: 개념+준비 섹션 — 본격 실습 없음. 두 도구의 특징을 이해하고 사전 준비를 마친 뒤 4.3으로 진행.

## 이 챕터에서 다루는 것

ch4에서는 현업에서 가장 많이 쓰이는 **CI/CD 도구 두 가지를 직접 "찍먹"** 해본다. 하나의 정답 도구를 고르는 게 아니라, 같은 빌드 파이프라인을 두 도구로 각각 만들어보며 **공통 개념(트리거 → job/stage → 빌드)** 과 **도구별 차이**를 몸으로 익히는 것이 목표다. 이후 ch5~ch10에서도 이 두 도구를 나란히 다룬다. 세 번째 도구인 GitLab CI는 10장(10.8~10.10)에서 앞의 두 도구와 무엇이 다른지에 초점을 맞춰 다룬다.

## 도구 비교

| 구분 | GitHub Actions | Jenkins | GitLab CI/CD (10장) |
|---|---|---|---|
| 형태 | SaaS (GitHub 내장) | 셀프호스팅 (직접 설치·운영) | SaaS (GitLab 내장) |
| 설정 방식 | `.github/workflows/*.yaml` | `Jenkinsfile` (Groovy) | `.gitlab-ci.yml` |
| 실행 환경 | GitHub 호스팅 러너 | 직접 구성한 에이전트/노드 | GitLab 러너 (SaaS/셀프) |
| 진입 장벽 | 낮음 (저장소만 있으면 시작) | 높음 (설치·플러그인 관리) | 낮음 (저장소만 있으면 시작) |
| 강점 | 생태계·마켓플레이스 | 유연성·플러그인·온프레미스 | 통합 DevOps(이슈~배포 일원화) |

> 본편(ch4~ch9)은 **GitHub Actions → Jenkins 순서**로 진행한다. 이 순서는 한국 시장 인기 순(당시 국내 인프라 사용자 그룹 설문 기준: 1위 GitHub Actions, 2위 Jenkins)을 따른 것이다. 최신 추세도 대체로 유사하다. SaaS 내장 CI와 셀프호스팅 빌드 서버라는 두 방식을 함께 보는 구성이다.
>
> GitLab CI는 자체 호스팅(온프레미스)으로 소스 관리부터 CI/CD까지 한 플랫폼에서 운영하는 기업이 국내에도 많다. 이 강의는 GitLab CI를 10장에서 다룬다. 두 도구로 개념을 익힌 뒤라 차이만 보면 되고, GitLab이 Terraform state를 보관하는 기능을 써서 인프라까지 파이프라인으로 관리해 본다.

## 선택 기준 (실무 관점)

- **이미 GitHub/GitLab을 쓰고 있다** → 같은 플랫폼의 내장 CI(Actions/GitLab CI)가 마찰이 가장 적다.
- **온프레미스·규제 환경, 세밀한 커스터마이징이 필요하다** → Jenkins.
- **무엇을 고르든 핵심 개념은 동일** → 트리거(push/PR/tag) → 단계(job/stage) → 아티팩트(이미지) 빌드·푸시. ch4는 이 공통 골격을 두 번 반복해 체득시킨다.

## 실습 사전 준비

| 도구 | 준비물 | 비고 |
|---|---|---|
| GitHub Actions | GitHub 계정 + worklog-backend fork + 노드의 GitHub 로그인 | fork와 clone은 ch3.3, `gh auth login`은 ch2.13에서 완료. 4.3부터 노드에서 `git push`를 한다 |
| Jenkins | (설치는 4.5에서 진행) | K8s에 Helm으로 설치 |

> Docker Hub 계정은 ch3.5에서 이미 만들어 노드에서 `docker login`·`push`를 해봤다. ch4는 파이프라인 "구조"만 익히는 단계라 이미지 push까지 가지 않으므로 추가 준비가 필요 없다. ch5에서 파이프라인이 이미지를 자동 빌드·push할 때 Docker Hub **Access Token**을 시크릿으로 등록한다.
