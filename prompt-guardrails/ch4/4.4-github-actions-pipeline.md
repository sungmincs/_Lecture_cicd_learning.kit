# 4.4 GitHub Actions 빌드 파이프라인 구조 만들기

> **학습자 진입 방식**:
> - `[학습자 직접]`: git push
> - `[학습자 직접 · 웹]`: Actions 탭에서 결과 확인
> - `[AI 프롬프트]`: 파이프라인 yaml 작성/수정
>
> 파일은 `.github/workflows/hello-pipeline.yaml` 하나다. 단계 4, 5, 6은 이 파일을 고친다. 고칠 때마다 단계 7의 방법으로 push하고 결과를 본다.

## 사전 조건

- ch4.3 완료 (`.github/workflows/` 존재, 첫 워크플로우 실행 경험)

## 실행 지침

### 단계 1: 기본 3단계 파이프라인 `[AI 프롬프트]`

```text
test → build → deploy 3단계 GitHub Actions 파이프라인을 만들어줘. 실제 작업 대신 echo로 단계만 만들어 job이 차례로 실행되는 구조를 보려는 거야.
파일: /root/workspace/worklog-backend/.github/workflows/hello-pipeline.yaml
끝나면: 파일을 보여줘. 커밋 전에 멈춰줘.
```

✅ 정답 파일 (완성 후 비교): `ch4/4.4/1.hello-pipeline.yaml`

### 단계 2: git push `[학습자 직접]`

```bash
cd /root/workspace/worklog-backend
git add .github/workflows/hello-pipeline.yaml
git commit -m "add: hello pipeline"
git push
```

### 단계 3: 실행 순서 확인 `[학습자 직접 · 웹]`

Actions 탭에서 Job 실행 순서(test → build → deploy) 확인.

### 단계 4: 빌드 실패 시나리오 `[AI 프롬프트]`

```text
hello-pipeline.yaml에서 build job이 의도적으로 실패하도록 바꿔줘. build가 실패하면 뒤 job이 어떻게 되는지 보려는 거야.
파일: /root/workspace/worklog-backend/.github/workflows/hello-pipeline.yaml
끝나면: 바꾼 부분을 보여줘. 커밋 전에 멈춰줘.
```

기대 결과: build failure, `needs`로 묶인 deploy는 skipped. 실패 알림 job은 아직 없고 단계 6에서 붙는다.

✅ 정답 파일 (완성 후 비교): `ch4/4.4/2.hello-pipeline_build-failure.yaml`

### 단계 5: Job 간 변수 전달 `[AI 프롬프트]`

```text
hello-pipeline.yaml을 앞 job의 output을 다음 job에서 사용하는 파이프라인으로 바꿔줘. job 사이에 값을 넘기는 법을 보려는 거야.
파일: /root/workspace/worklog-backend/.github/workflows/hello-pipeline.yaml
조건:
- 단계 4에서 넣은 build 실패는 되돌려줘.
끝나면: 바꾼 부분을 보여줘. 커밋 전에 멈춰줘.
```

✅ 정답 파일 (완성 후 비교): `ch4/4.4/3.hello-pipeline_build-pass-variables.yaml`

### 단계 6: 변수 전달 + 실패 시나리오 `[AI 프롬프트]`

```text
hello-pipeline.yaml에 성공 알림 job과 실패 알림 job을 추가하고 build job이 다시 실패하게 바꿔줘. 결과에 따라 알림 job 2개가 어떻게 나뉘어 실행되는지 보려는 거야.
파일: /root/workspace/worklog-backend/.github/workflows/hello-pipeline.yaml
조건:
- job 사이에 넘기는 변수는 그대로 둬.
끝나면: 바꾼 부분을 보여줘. 커밋 전에 멈춰줘.
```

기대 결과: build failure, deploy와 notify-success-result는 skipped, notify-failure-result만 실행.

✅ 정답 파일 (완성 후 비교): `ch4/4.4/4.hello-pipeline_build-pass-variables-failure.yaml`

### 단계 7: 시나리오마다 git push `[학습자 직접]`

단계 4, 5, 6을 하나 끝낼 때마다 push한다. 3번 한다.

```bash
cd /root/workspace/worklog-backend
git add .github/workflows/hello-pipeline.yaml
git commit -m "update: <시나리오 이름>"
git push
```

### 단계 8: 시나리오 결과 비교 `[학습자 직접 · 웹]`

Actions 탭에서 push마다 생긴 실행을 열어 기대 결과와 비교한다.

| 단계 | 기대 결과 |
|---|---|
| 4 | build failure, deploy skipped |
| 5 | 모두 success, 뒤 job 로그에 앞 job이 넘긴 값이 찍힘 |
| 6 | build failure, deploy와 notify-success-result skipped, notify-failure-result만 실행 |

## 주의사항

- ⛔ AI가 하지 말 것: git push 대신 실행하지 말 것
- ✅ AI가 해도 됨: 파이프라인 yaml 작성 및 수정
- ✅ AI가 해도 됨: Job 실행 결과 및 의존성 관계 설명
- ✅ AI가 해도 됨: `needs`, `outputs`, `if` 키워드 설명
- ⛔ AI가 하지 말 것: 4단계의 변경을 한 번에 모두 적용하지 말 것 — 단계별로 하나씩 진행
- ⚠️ 이 절은 단계 6의 실패 상태로 끝난다. 그대로 두면 이후 push마다 실패가 쌓이므로 4.5 단계 1에서 끈다
- ⛔ AI가 하지 말 것: 단계 4와 단계 6의 의도적 실패(`exit 1`)를 "수정"해주지 말 것. 실패를 관찰하는 것이 학습 목표
